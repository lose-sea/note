# 多轮 RAG 查询改写实战：把对话历史塞进检索

单轮 RAG 的检索很单纯：用户问什么，就拿什么去向量库里找。但真实对话很少有「一句话把需求说清楚」的好用户——更多是这样的场景：

> 用户：帮我看看退货政策。
> 助手：好的，退货政策是……
> 用户：**这个** 7 天无理由吗？

第二句的「这个」指代什么？如果直接拿「这个 7 天无理由吗」去检索，向量库大概率检索不到，因为它根本不知道「这个」是「退货政策」。这就是**多轮检索的核心难题：指代消解 + 上下文补全**。

本文讲清楚：为什么原始 query 不能直接用于多轮检索、三种改写策略怎么选、以及怎么在工程上落地一个不翻车的改写器。

## 一、为什么多轮下不能直接用原始 query

向量检索是**无状态**的。它只看你给的那串文本，不知道你上一轮聊了什么、上一轮召回了哪些文档。

举几个典型翻车现场：

- **指代缺失**：「它支持吗」「这个方法怎么样」「上面的方案靠谱吗」——脱离上下文就是一串代词，检索必挂。
- **省略补全**：「那北京的呢」「换个更便宜的」——省略了主语（前一轮的酒店 / 方案），检索词不完整。
- **隐含约束**：「再详细点」「用通俗的话说」——这不是新检索需求，是对上一轮答案的二次加工，根本不该触发新检索。
- **主题漂移**：聊了 10 轮后，第 11 轮突然问「回到最开始那个问题」——需要把话题拉回最初。

所以多轮 RAG 的第一步，永远不是「检索」，而是「**把当前这一句，结合历史，改写成一个自包含的检索 query**」。

## 二、三种改写策略

按「改写的激进程度」从低到高，有三种主流做法。

### 策略 1：上下文拼接（最保守）

把最近 N 轮对话直接拼到当前 query 前面，整体送进 embedder。

```
检索文本 = "用户: 退货政策\n助手: ...\n用户: 这个 7 天无理由吗"
```

优点：零额外 LLM 调用，实现成本最低。缺点也很明显——拼接后的文本又长又杂，embedder 会被无关信息带偏，而且「助手上一轮的回答」往往比「用户问题」噪声大得多。只适合非常简单的场景。

### 策略 2：LLM 改写（推荐）

单独调一次便宜的小模型（甚至可以用分类/改写专用的小模型），让它根据历史输出一个干净的检索 query：

```
系统提示：你是检索 query 改写器。给定对话历史和最新提问，
输出一个自包含的检索 query，不要包含寒暄和废话，只输出检索词本身。

历史：
用户: 帮我看看退货政策
助手: 退货政策包含 7 天无理由、15 天质量问题退换……
最新提问：这个 7 天无理由吗

输出：退货政策 7 天无理由 适用条件
```

这是业界最通用的做法。关键设计点：

- **改写器用小模型**：改写不需要推理能力，gpt-4o-mini / qwen-turbo 这类就够，省钱省延迟。
- **只输出检索词**：强制「只输出 query，不要解释」，避免把改写器的废话混进 embedding。
- **限制历史窗口**：一般用最近 3~5 轮，太长的历史反而引入噪声。
- **带上上一轮召回的文档标题**：有时用户说的是「上面这个方法」，把上一轮检索到的文档标题喂给改写器，指代消解会更准。

### 策略 3：LLM 改写 + 多 query 展开

在策略 2 基础上，让模型一次输出 2~3 个不同角度的 query（比如一个偏语义、一个偏关键词），分别检索再做融合（RRF）。召回率更高，代价是多一次检索。适合「用户提问模糊、宁可多召回不可漏召」的场景。

## 三、工程落地：一个不翻车的改写器

核心代码结构（伪代码，可套任意框架）：

```python
from dataclasses import dataclass
from typing import List

@dataclass
class Turn:
    role: str          # "user" / "assistant"
    content: str

REWRITE_PROMPT = """你是检索 query 改写器。
给定对话历史和最新提问，输出一个自包含的检索 query。
规则：
1. 补全指代和省略，让 query 脱离上下文也能被理解
2. 只输出检索词本身，不要解释、不要标点堆砌
3. 如果用户只是在追问上一轮答案的细节（如"再详细点"），
   则输出上一轮的核心主题词，不要输出空洞的代词

历史：
{history}
最新提问：{query}
输出："""

def rewrite_query(history: List[Turn], query: str, llm) -> str:
    # 只取最近 5 轮，且去掉助手回复里的代码块（噪声大）
    recent = history[-5:]
    hist_text = "\n".join(f"{t.role}: {t.content}" for t in recent)
    prompt = REWRITE_PROMPT.format(history=hist_text, query=query)
    raw = llm.invoke(prompt).content.strip()
    # 兜底：如果改写器抽风返回空，降级用原始 query
    return raw if raw else query
```

几个必须加的**护栏**：

1. **改写失败兜底**：模型偶尔会返回空或者一整段废话。解析不出干净 query 时，降级用「原始 query + 上一轮用户问题」拼接，至少不比原来差。
2. **长度截断**：改写结果超过 200 字就截断——embedding 模型对超长文本会截断头部，过长反而坏事。
3. **缓存改写结果**：同一轮对话里可能多次检索，改写结果可以复用，避免重复调模型。
4. **不要对所有轮都改写**：如果当前 query 本身已经自包含（含明确实体、无代词），就跳过改写直接检索，省一次调用。

## 四、怎么判断改写器在起作用

别只看「有没有调通」，要看**检索质量有没有提升**。两个可量化指标：

- **指代类问题召回命中率**：构造一批「代词 / 省略句」测试集，对比「原始 query 检索」和「改写后检索」的 top-k 命中率，改写器至少要把命中率拉高 20 个点。
- **端到端答案准确率**：用真实多轮对话日志做回归，看改写上线前后，最终答案「答非所问」的比例有没有下降。

一个小技巧：把改写前后的 query 都打进 LangSmith / 日志里，哪一轮翻车了一眼就能定位是「改写错了」还是「检索本身不行」。

## 五、常见坑

- **把助手回复全塞进历史**：助手上一轮可能输出了一大段代码或表格，这些对改写几乎无用还占 token。建议历史里助手的回复只保留前 200 字 + 文档标题。
- **改写器用大模型**：没必要。改写是「压缩 + 补全」，小模型足够，用大模型纯属浪费。
- **忽略主题回跳**：用户说「回到第一个问题」，改写器如果只看下一个，会改写出一个莫名其妙的 query。可以在 prompt 里加一句「如果用户要求回到早前话题，请基于最早的相关轮次补全」。
- **多 query 展开忘了去重**：三个 query 召回的文档会有大量重叠，融合前先按文档 id 去重，否则 RRF 分数被重复文档刷爆。

## 小结

多轮 RAG 的检索质量，很大程度取决于查询改写这一步。最省事的做法是「小模型改写 + 最近 5 轮历史 + 失败兜底」三件套：用最小的成本，把无状态的向量库，伪装成「听得懂上下文」的有状态检索。先把这个跑通，再考虑多 query 展开这类进阶优化。
