# 代码生成 Agent：从"能写 demo"到"能改代码库"

让模型写个快排、写个爬虫，今天是个demo 就能做的事。但真正有价值的代码 Agent 是能**在你的代码库里工作**的：读懂跨文件的结构、按你的风格改代码、跑测试验证、失败了自己修。这篇文章讲代码生成 Agent 的生产形态——上下文工程、执行验证闭环、以及落地时的安全边界。

## 先分清三种代码 Agent

不同产品的架构差距比人和狗都大，混为一谈会选错技术路线：

| 类型 | 输入 | 输出 | 架构重点 |
|---|---|---|---|
| **补全型** | 光标上下文 | 几行补全 | 延迟优先，Cursor/Copilot 补全 |
| **生成型** | 自然语言需求 | 单个文件/函数 + 解释 | 提示词 + 约束编译 |
| **仓库级** | 任务描述 + 代码库访问 | 跨文件 patch + 提交/PR | 上下文检索 + 执行验证闭环 |

补全型已经被 IDE 插件形态做透了，不在本文范围。生成型解决了"从 0 到 1 写一段"，仓库级解决"在已有系统里干活"——后者才是 2025 年代码 Agent 的主战场（Cursor Agent、Claude Code、SWE-agent 一脉）。本文重点讲这个。

## 仓库级 Agent 的核心：上下文工程

模型看不到你的代码库，你能给的只有上下文窗口。**代码 Agent 80% 的工程量在决定"给模型看什么"**。三个机制：

### 1. 代码库地图（Repo Map）

不能把整个代码库塞进上下文（超过百万 token），但模型需要"知道什么文件在哪"。Aider 推广的做法：用 tree-sitter 解析代码库，抽取每个文件/类/函数的签名和调用关系，生成一份压缩的地图（通常占几千 token），附在系统提示里。模型看到地图，才知道要改 `services/user.py` 而不是 `models/user.py`。

### 2. 检索式上下文

任务进来后，模型/离线模块按语义 + 关键词检索相关文件、相关片段。和 RAG 是一个套路，但代码检索有特殊性：

- **混合检索是刚需**。代码查询里标识符（函数名、类名）权重要高——搜 `get_user_preferences`，字面匹配比语义 embedding 靠谱得多。BM25 + embedding 混合，代码场景下 BM25 的权重应该比通用 RAG 更高。
- **按"定义 + 调用点"成组召回**。改一个函数要同时给它定义和它的 3 个调用方，只召回定义模型改完 breaks 调用方。代码检索的单元应该是"符号切片"而不是"文本块"。

### 3. 按需展开（Read/Grep/Glob 工具集）

给 Agent 一组仓库工具，让它自己按需取证——这是 Claude Code/Cursor 的标准形态：

```
list_files(path)         # 看目录结构
read_file(path, range)   # 读文件（可指定行范围，省 token）
grep(pattern)            # 正则搜索符号
find_definition(symbol)  # 跳转定义
run_tests(path)          # 跑测试
apply_patch(diff)        # 提交修改
```

Agent 循环里模型决定"我现在需要看 X"，工具执行回填。这个循环和前几篇讲的工具调用 Agent 完全同构——**代码 Agent 的特殊性不在循环，在上下文供给和验证**。

## 执行验证闭环：Agent 怎么知道改对了

补全型助手可以不管对错（反正人看着），仓库级 Agent 的核心差异是**能自己验证**。闭环三件套：

### 编译/解释器检查（第一道闸）

改完马上跑 `python -m py_compile`、`tsc --noEmit`、`cargo check`——静态检查秒级返回，能抓掉一半低级错误（语法、类型、未导入）。这一层几乎没有成本，必须每次修改后都跑。

### 测试验证（核心闸）

给 Agent 明确指令：**改完代码，跑相关测试；红了，读报错，自己修**。

```python
# 简化的验证循环
for round in range(5):
    patch = model.generate(f"修复测试失败：{last_error}")
    apply(patch)
    ok, output = run_tests(affected_files)
    if ok:
        break
    last_error = output[-3000:]   # 回填完整报错，别总结
```

报错回填的原则和数据分析 Agent 一样：**原样回填**。测试输出里 `AssertionError: expected 3 got 4` 这种信息，总结成人话反而丢信息。

### 单测生成（兜底闸）

更激进的 Agent 拿到任务先写测试再写实现（TDD 模式），验证闭环天然成立。生产中不一定强推 TDD，但**"修改公共函数前先确认有个测试保护它"**是个好纪律——没有测试的函数，Agent 改坏了没人知道。

## 安全边界：危险的三个口子

代码 Agent 本质是"让模型执行任意的 shell 和文件写入"，安全模型必须显式设计：

**命令白名单**。不是所有 shell 都让跑。`rm -rf`、`curl | sh`、`git push --force`、访问生产数据库——按任务类型配允许的命令集合。Claude Code 的做法是默认全问：危险命令弹人工确认。 governed 场景下 Agent 跑在容器里，容器挂载最小权限卷，跑完即焚——沙箱思路和数据分析 Agent 完全一致。

**密钥隔离**。Agent 的 bash 环境里绝不出现生产凭证。它需要 push 代码，用短期的、只有目标仓库权限的 token，不用你的个人 PAT。日志脱敏——Agent 的 trace 里如果打印了 `env` 输出，密钥就进 LangSmith 了。

**diff 审核，永远保留人工门**。再强的 Agent 也应该把改动以 diff 形式呈现等人确认（或至少 PR review 时过一道）。**自主合并进 main 的代码 Agent，事故只是时间问题**。工程上的折中：Agent 改到测试全绿，自动开 PR，merge 永远是人点的。

## 上下文经济：token 账要算

代码 Agent 是 token 饕餮——一次仓库级任务动辄几十万输入 token。几个控制手段：

- **读文件带行范围**：默认只读相关段落，不是整个文件 read 进来。模型说"读 data.py 的 120-200 行"比读整个 800 行文件省 70%。
- **grep 优先于 read**：定位符号时 grep -n 出位置，再定点读，比全文顺序读省得多。
- **报错截断但保留关键帧**：traceback 只保留最后 50 行（前面多是 import 路径堆栈）。
- **文件写入用 patch 不用全文重写**：让模型输出 unified diff，只把改动部分算进输出 token。读入旧文件、算出新文件这个动作在执行侧完成。
- **成本归因**：按任务记 token 消耗（前文成本归因篇的架构复用到这里），识别哪些任务类型烧钱最多，针对性优化 prompt 或改走批处理。

## 评估：代码 Agent 怎么测

业界基准是 SWE-bench（真实 GitHub issue + 隐藏测试），但自建系统要自己的评测集。建议按"任务卡片"攒：

```json
{
  "id": "fix-user-serializer",
  "repo_snapshot": "branch:test/fix-serializer",
  "task": "用户查询接口返回的 role 字段有时是 null，修复并保持向后兼容",
  "verify": "pytest tests/test_user_api.py -x",
  "forbidden_paths": ["migrations/"],
  "max_wall_time_min": 15
}
```

跑分指标：**任务完成率（测试全绿且没碰禁区）**、**平均轮数**、**平均 token 成本**、**人工接管率**。这套评测接 CI，每次换模型、改提示词都跑一轮——和前几篇评测框架的思路一致，只是验证函数从"答得对不对"换成"测试过不过"。

## 结语

代码生成 Agent 的生产形态 = 上下文工程（给对信息）+ 执行闭环（改完能验证）+ 安全边界（危险操作有闸）+ 成本工程（token 花在刀刃上）。从补全 → 生成 → 仓库级，架构复杂度逐级上升，但底层的 Agent 循环、沙箱隔离、评测方法都是相通的。下一篇看客服 Agent——一个把前面所有能力（RAG、工具、护栏、评测）都用上的综合场景。
