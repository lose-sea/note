# 多语言 RAG 实战：让中英文混着搜，跨语言也能召回

全球化业务里，知识库天然是多语言的：英文技术文档、中文用户手册、日文合规条款堆在一起。用户却可能用中文问一个英文文档里才有的概念。传统单语 RAG 直接趴窝——中文 query 和英文文档在向量空间里八竿子打不着。

**多语言 RAG** 要解决的，就是「用一种语言问，召回另一种语言的文档」。本文讲清楚三种主流方案怎么选、以及工程落地的坑。

## 一、为什么单语 embedding 不行

大部分早期 embedding 模型（如早期 bge / text2vec）只在单语空间训练，中英文向量不在同一个语义空间。中文「如何配置负载均衡」和英文 "how to configure load balancer" 语义完全相同，但向量距离可能很远，检索召回不了。

解法本质是：**把不同语言映射到同一个语义空间**。

## 二、方案 A：多语言 embedding 模型（最省事）

直接用原生支持多语言的 embedding 模型，比如 `bge-m3`、`multilingual-e5`、`paraphrase-multilingual`。这些模型在几十种语言上联合训练，同一个概念的不同语言表述，向量天然接近。

```
中文 query → bge-m3 → 向量 → 和英文文档的 bge-m3 向量做余弦
→ 同语义跨语言自然命中
```

优点：零额外 pipeline，换模型即可，中英文混合检索开箱即用。缺点：极端小语种或专业术语，跨语言对齐不如「翻译后检索」精准。

## 三、方案 B：翻译后检索（最精准）

检索前先把 query 翻译成知识库的主要语言，再检索；或者把所有文档统一翻译成一种语言后建库。

```
用户中文问 → 翻成英文 → 英文检索英文库 → 取回英文文档 → 答中文时引用原文
```

甚至双向：query 翻译 + 文档统一翻译，双保险。优点：对齐最准，尤其术语密集场景。缺点：多一次翻译调用（延迟 + 成本），且翻译本身可能引入错误。

实战常把 A、B 结合：**用多语言模型做主检索，翻译做兜底或 rerank 特征**。

## 四、方案 C：跨语言 rerank（精排补刀）

召回阶段用多语言 embedding 粗排，rerank 阶段用支持多语言的 cross-encoder（如 `bge-m3` 的 rerank 模式）做精细排序。rerank 模型对跨语言语义对齐更强，能把「语义近但向量稍远」的正确文档拉到 top。

```
多语言 embedding 粗排 top-20 → 跨语言 rerank → top-5
```

这是性价比很高的组合：粗排保召回、精排保准确。

## 五、工程落地的关键设计

- **统一向量空间**：全库（无论哪种语言）必须用同一个多语言模型 embedding，不能中文用 A 模型、英文用 B 模型，否则空间不互通。
- **语言元数据**：每篇文档标 `lang` 字段，可做「优先召回用户母语文档，找不到再跨语言」的路由策略。
- **query 语言识别**：先识别用户 query 语言，决定「翻译目标语言」和「是否启用跨语言检索」。
- **答案回译**：召回的是英文文档，最终答案用中文，但要保留关键术语的原文（如 API 名、专有名词），避免翻译失真。
- **混合语料处理**：用户一句里中英文夹杂（"怎么用 Kubernetes 做 HPA"），多语言模型天然能处理，但翻译方案要先正确切分语言再翻。

## 六、评测跨语言召回

- **跨语言召回率**：用 X 语问、Y 语文档的问题集，看 top-k 能否召回正确文档（这是核心指标）。
- **答案准确率**：跨语言召回后，最终答案是否准确（翻译失真会拉低这块）。
- **语言路由正确率**：该母语优先的是否优先了，该跨语言的跨没跨。

## 小结

多语言 RAG 的核心是把不同语言拉进同一个语义空间。最省事是换多语言 embedding 模型（bge-m3 / e5-multilingual），最精准是翻译后检索，最稳是「多语言 embedding 粗排 + 跨语言 rerank 精排」组合拳。工程上记住：全库统一模型、标语言元数据、识别 query 语言做路由、答案保留关键原文。这样中英文混搜、跨语言召回就能稳稳跑起来。
