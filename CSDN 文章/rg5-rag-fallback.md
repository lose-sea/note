# RAG 降级链路实战：检索挂了，答案也不能挂

RAG 系统上线后，你迟早会遇到这些瞬间：

- 向量库半夜宕机，检索直接超时；
- embedding 服务限流，调一次报错一次；
- rerank 模型 OOM，长 query 必崩；
- 知识库当天没更新，用户问的全是库里没有的新问题。

这时候如果直接给用户弹「系统繁忙」，体验就是灾难。**RAG 必须有降级链路（fallback）：任何一环挂了，都要能兜住，退而求其次给出「还能看」的答案，而不是直接躺平。**

本文讲清楚：RAG 有哪些环节会挂、每层的降级策略、以及怎么设计一条「层层兜底」的链路。

## 一、先画清楚 RAG 的故障面

一个完整 RAG 链路，从前往后至少有这些环节，每个都可能挂：

```
用户 query
  → query 改写（LLM）   ← 模型限流 / 超时
  → embedding（模型）   ← 限流 / 服务挂
  → 向量检索（数据库）  ← 宕机 / 慢查询
  → rerank（模型）      ← OOM / 超时
  → 拼 prompt + 生成（LLM） ← 限流 / 上下文过长
```

任何一环失败，整体就失败。降级的核心思想就是：**单点失败不应导致整体失败，能跳过就跳过，跳不过就换一条更便宜的路。**

## 二、分层降级策略

按「损失最小」原则，从外到内逐层降级。

### 第 1 层：跳过 rerank

rerank 是整个链路里最贵、也最容易 OOM 的一环。它挂了，**直接退回「向量检索 top-k 不经 rerank」** 即可——召回质量会降一点，但答案还在。这是最无痛的降级。

实现上用 try/except 包住 rerank，异常就返回向量检索的原顺序：

```python
try:
    ranked = rerank(query, candidates)
except Exception:
    ranked = candidates   # 降级：用向量分排序
```

### 第 2 层：跳过 embedding，用关键词检索

embedding 服务挂了，向量检索就废了。但很多知识库同时建了 BM25 / 全文索引。**降级到纯关键词检索（BM25）**，虽然语义能力弱，但「精确匹配术语」类问题反而更准。等 embedding 恢复再切回混合检索。

### 第 3 层：跳过检索，用模型先验

如果连关键词索引都挂了（极端情况），最后的兜底是用 LLM 自身的知识直接答，但必须**明确标注「以下答案未经知识库核实」**。这对时效性内容不适用，但能挡住「系统完全不可用」的尴尬。配合一个置信度判断：如果模型对这个问题没把握，就老老实实说「暂无可靠来源，建议稍后再试」。

### 第 4 层：直接返回友好提示

所有路都堵死时，返回一个结构化提示：「当前检索服务暂时不可用，您的提问已记录，恢复后我们会优先处理」——比裸奔报错专业得多。

## 三、降级不是「静默发生」，要可观测

降级最怕的是「悄悄发生，没人知道」。必须做到：

1. **每次降级都打日志 + 埋点**：哪个环节降级了、降级到了第几层、影响了多少请求，要有仪表盘。否则你以为系统健康，其实一半流量都在跑降级路径。
2. **给用户透明提示（适度）**：如果是「跳过 rerank」这种无损降级，不用打扰用户；但如果是「模型先验答、未经核实」，必须在界面上标注，否则用户把猜测当事实，后果更严重。
3. **自动恢复**：监控到依赖恢复后，自动从降级态切回正常态，不要人工介入。可以用「连续 N 次调用成功就解除降级」的熔断器逻辑。

## 四、用熔断器管理降级

推荐引入经典的**熔断器（Circuit Breaker）**模式管理每个外部依赖：

```python
class CircuitBreaker:
    def __init__(self, fail_threshold=5, reset_timeout=30):
        self.fails = 0
        self.threshold = fail_threshold
        self.reset_after = reset_timeout
        self.opened_at = None

    def allow(self):
        if self.opened_at is None:
            return True
        if time.time() - self.opened_at > self.reset_after:
            self.opened_at = None
            self.fails = 0
            return True
        return False

    def on_fail(self):
        self.fails += 1
        if self.fails >= self.threshold:
            self.opened_at = time.time()   # 熔断，进入降级
```

逻辑：某个依赖连续失败超过阈值，就「熔断」——后续请求直接走降级路径，不再打这个依赖，避免雪崩；等冷却时间过后，放一个请求探活，成功就恢复。这比「每次都 try/except 重试」更保护下游。

## 五、降级设计的几个原则

- **降级顺序要按「质量损失从小到大」排**：先丢最不重要的 rerank，最后才丢检索。不要一上来就跳过检索。
- **降级路径也要测试**：很多团队的降级代码从没被测过，真出事时降级本身也挂。降级路径要写单测，定期演练（chaos test）。
- **不要无限重试**：主路径失败就赶紧降级，别在已经限流的依赖上疯狂重试，那只会让它更挂、自己也更慢。
- **区分「可降级」和「不可降级」**：生成 LLM 挂了基本没法降级（除非有备用模型），这类要单独做「多模型故障转移」，不属于检索降级范畴。

## 六、小结

RAG 的可用性，不在于「每个环节都不挂」（那不现实），而在于「某个环节挂了，整体还能兜住」。设计一条分层降级链路：

1. 跳过 rerank → 退回向量排序；
2. 跳过 embedding → 退回 BM25 关键词；
3. 跳过检索 → 模型先验 + 明确标注；
4. 全挂 → 友好提示 + 记录待补。

配合熔断器自动切换、降级可观测，你的 RAG 就能在半夜依赖宕机时， quietly 扛住大部分流量，而不是集体躺平。
