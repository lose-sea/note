# 客服 Agent 上线实战：把前面所有能力攒成一个产品

写到这里，我们这个系列已经攒齐了零件：RAG 检索、工具调用、记忆、评估、护栏、审计、降级链。客服 Agent 是把这些攒成一台机器的综合考题——它同时踩中 LLM 应用的全部难点：知识要准、口气要稳、成本要省、出事要能查。这篇文章以一个典型电商客服场景为例，讲这个综合体怎么从零上线。

## 需求拆解：客服 Agent 到底干什么

先定义清楚边界，别做成"什么都能聊"的四不像。一个电商客服 Agent 的职责：

| 职责 | 例子 | 不用 LLM 的部分 |
|---|---|---|
| 答政策 | "退货政策是什么""多久发货" | RAG 检索知识库 |
| 查订单 | "我的订单到哪了" | 工具：内部订单 API |
| 办业务 | "申请退货""改地址" | 工具：写操作，**必须人工确认** |
| 安抚转人工 | "我要投诉""找你们领导" | 意图识别 → 转人工技能组 |
| 闲聊应付 | "在吗" | 兜底话术，不接知识产权题 |

注意最后两行：**转人工和兜底不是模型的失败，是设计的一部分**。没有顺畅升级通道的客服 Agent，出事概率翻倍。行业经验值：成熟系统 60%~80% 会话无人工办结，剩下的 20~40% 主动升级才是正常形态——追求"全自动解决"的系统往往在投诉里翻车。

## 架构：一个编排 + 三层能力

```
                ┌─────────────────────────────┐
   用户消息 ──▶ │  对话编排层（LangGraph）      │
                │  ①输入护栏 ②意图路由          │
                └──────┬──────────────┬───────┘
              政策问答 │              │ 业务办理
                ┌──────▼──────┐  ┌────▼─────────┐
                │  RAG 检索    │  │  工具调用层   │
                │  政策知识库  │  │  查询类(自动) │
                └──────┬──────┘  │  操作类(确认) │
                ┌──────▼──────┐  └────┬─────────┘
                │ 回答生成     │       │
                │ + 输出护栏   │       │
                └──────┬──────┘       │
                   ┌───▼───────────────▼───┐
                   │  记忆：短期会话+长期用户画像 │
                   └───┬────────────────────┘
                       ▼
                  回答 + 引用来源 + 转人工选项
```

意图路由是入口：政策问答走 RAG，业务办理走工具，情感/投诉走转人工。**别让一个 prompt 干所有事**——分类 + 分发比端到端大 prompt 稳定得多，也便宜得多：路由可以用小模型甚至规则，只有叶子节点才用大模型。

## 知识库：客服 RAG 的特殊性

客服知识库和通用 RAG 不一样，三个特点决定设计：

**1. 更新频率极高**。促销规则、发货时效天天变。索引要支持近实时更新：政策文档改了，T+0（分钟级）进索引。LangChain 的增量索引管道 + 按 knowledge_id 的删除重建，做到文档级粒度更新。

**2. 知识有"版本"和"生效期"**。"七天无理由"在 A 商家和 B 商家政策不同、且活动期间可能变。检索时按商家 ID 过滤（`metadata: {merchant_id}` 是硬过滤，不是软过滤——软过滤靠模型"注意只回答 X 商家的"，它会忘），政策文档带 `effective_from/effective_until`，检索把过期政策降权或剔除。

**3. 答案要带引用**。客服场景说错话的代价是真实的赔付纠纷。每个回答必须附知识来源（"根据《售后政策 V3.2》"），链接到具体条目。用户/客服主管质疑答案时，秒级溯源。这也是审计日志里必须记 `retrieval.doc_ids` 的原因。

```python
# 客服检索管道的典型配置
retriever = vector_store.as_retriever(
    search_kwargs={
        "k": 4,
        "filter": {"merchant_id": merchant_id, "status": "active"},  # 硬过滤
    }
)
# 重排 + 新鲜度加权：政策更新时间越近越优先
```

## 工具调用：查自动、办确认

客服的工具权限必须按"读/写"分级：

- **查询类**（订单状态、物流轨迹、余额）：Agent 自主调用，结果直接组织成回答。
- **操作类**（退款、改地址、发优惠券）：Agent 只能"生成待办申请"，**弹卡片给人确认**。

```python
class RefundTool(BaseTool):
    name = "apply_refund"

    def _run(self, order_id: str, amount: float, reason: str):
        # 永远不直接执行，生成确认请求
        return action_request(
            kind="refund",
            payload={"order_id": order_id, "amount": amount, "reason": reason},
            confirm_text=f"确认给订单 {order_id} 退款 ¥{amount}？原因：{reason}",
            ttl_minutes=10,
        )
```

产品形态上，这个"确认请求"渲染成聊天窗口里的确认卡片，用户点同意才真正调退款 API。这个设计同时解决两个问题：**合规**（资金操作有人确认）和**体验**（模型理解错了用户能拦住，比事后申诉便宜一百倍）。金额超过阈值的退款，甚至要求二次客服人工复核——分级授权。

## 记忆：会话内 + 用户级

两层记忆，对应两个 TTL：

- **短期**：当前会话最近 20 轮，滑动窗口。多轮指代消解靠它——用户先说"查一下订单 123"，再说"那改地址到……"，"那"指什么靠窗口。
- **长期**：用户画像 + 历史会话摘要。用户 ID 维度：常用收货地址、历史订单类型、过去的投诉记录、偏好（"别打电话发短信"）。进上下文的方式是**摘要注入**而不是全量——"该用户上月有一次物流投诉，敏感词：暴力分拣" 三十个字，比五条完整历史省 token 且信息密度高。

注意合规：客服对话里有大量个人信息（地址、电话），记忆存储要脱敏或加密，留存周期按隐私政策走。上一篇审计日志的设计在这里直接复用。

## 兜底与转人工：体验的生死线

三张网必须织好：

**兜底话术**。模型没把握时明确说"这个我需要转接专员"，而不是硬编一个答案。提示词里授权模型说"我不知道"——很多系统把客服 prompt 写成"你必须给出有帮助的回答"，逼得模型不懂装懂，答错一个政策就是一起纠纷。

**转人工通道**。用户说"转人工"要**立即**转，不要让模型再挽留三轮。情感识别（生气、辱骂高频）自动升级。转人工时把会话摘要 + 已识别的订单上下文一并交给人工客服——用户最烦的莫过于"转人工后从第一句重新讲"。

**感觉要出事的熔断**。同一用户连续三次对回答点"没用"、识别到投诉升级关键词、模型连续拒答——触发规则直接转人工。这是属于客服系统特有的守卫：宁可错转，不可漏转。

## 评估：客服 Agent 的指标体系

上线不是终点，是运营的起点。指标分三层：

**质量层（抽检 + 评测集）**：每周抽 100 条会话人工打分（准确性、礼貌度、解决率）；评测集持续回流 badcase。**解决率**是北极星指标——问题真的解决了吗，而不是"回答得像解决了"。判断方式：用户后续又发起同类提问 = 没解决。

**体验层（实时看板）**：转人工率、平均响应时长、点踩率、平均轮次。转人工率短期涨了不一定是坏事（可能是兜底变准了），要配合解决率一起看。

**成本层**：单会话 token 成本、RAG 检索命中率（命中低 = 知识库有问题，不是模型问题）、缓存命中率（政策类问题高度重复，**语义缓存对客服场景 ROI 极高**，前面缓存篇的架构直接用）。

## 灰度上线路线

别周一全量。一个稳妥的五步走：

1. **影子模式**：Agent 后台回答但不展示，人工客服正常接待。收集 Agent 答案 vs 人工答案的差异，只看不动。
2. **建议模式**：回答作为建议展示给人工客服，人改完再发。人机差异继续收敛。
3. **小流量自动**：5% 流量全自动，配随时可点的转人工。看解决率、投诉率、兜底触发频率。
4. **扩量**：解决率和兜底质量稳定后，30% → 60% → 100%，每档观察至少三天——周末单独看，客服流量的周末形态完全不同。
5. **持续运营**：评测集周更、政策文档实时更新、每周 badcase 复盘会。**客服 Agent 是运营出来的，不是发布出来的**。

## 结语

客服 Agent 是本系列能力的集大成：RAG 保知识准确、工具分级保安全、记忆保连贯、护栏和兜底保体验、审计保可追责、评估集和灰度保迭代。所有这些单独拿出来都不难，难的是把它们拧成一个在投诉和纠纷压力下依然稳的系统。把客服这个综合体啃下来，你就有了把 Agent 落地到任何垂直行业的完整方法论。下一篇讲评测驱动开发（EDD）——把上线后的迭代也变成工程。
