# RAG 里上下文窗口该塞多少：不是越大越好

现在的模型动不动就 128K、200K 甚至 1M 上下文，很多人自然而然地想：既然窗口这么大，那我干脆把 top_k 拉到 50，甚至整个知识库都塞进去得了，反正装得下。

别这么做。实测下来，往上下文里塞更多文档，收益很快就会变成负数。这一篇就把"到底塞多少"这件事讲清楚：为什么塞多了会变差、不同位置的信息利用率差多少、怎么在窗口限制下做取舍、以及长上下文模型出现后这个结论有没有变。

---

## 一、"塞满"的四个问题

### 1.1 Lost in the Middle（中间丢失）

这是最核心的一条。斯坦福 2023 年的研究发现：模型对长上下文里信息的利用呈 **U 型曲线**——开头和结尾的内容容易被注意到，中间的内容大量被忽略。

具体数据（GPT-3.5，20 篇文档）：

| 答案文档位置 | 准确率 |
|-------------|--------|
| 第 1 位 | 0.73 |
| 第 5 位 | 0.61 |
| 第 10 位（中间） | 0.52 |
| 第 15 位 | 0.63 |
| 第 20 位（末尾） | 0.70 |

中间位置的利用率比两端低了 20 个百分点。你把 top_k 从 5 拉到 20，等于把大量正确答案放进了"容易被忽略区"。

（关于 Lost in the Middle 的完整机制和对策，我单独写了一篇，这里不展开。）

### 1.2 噪声稀释

每多塞一篇文档，就多一份"看起来相关但实际没用"的内容。这些内容会：

- 分散模型的注意力，让它在多个似是而非的说法之间摇摆；
- 提供相互冲突的信息，模型不知道该信哪个（尤其知识库里有版本更新、旧文档没清理时）；
- 诱导模型去"综合"而不是"引用"，产生编造。

我做过一个对比：同样的问题，给 3 篇精心筛选的材料 vs 给 15 篇粗糙召回的材料，前者准确率高 18 个百分点。**材料少而精，远胜多而杂**。

### 1.3 成本和延迟

token 是线性计费的。上下文从 2k 涨到 20k，单次成本涨 10 倍。延迟也涨——prefill 阶段的计算量随上下文长度增长（虽然不是严格线性，但绝对不便宜）。

对生产系统来说，这笔账必须算。**同样的准确率，用 1/5 的 token 达成，就是实打实的竞争力**。

### 1.4 长上下文不等于长注意力

这是最容易产生的误解。模型"能接受 128K 输入"和"能充分用好 128K 输入"是两回事。前者是架构能力，后者是训练出来的实际表现。

多个长上下文基准测试（如 Needle In A Haystack）显示：即使是宣称支持长上下文的模型，在上下文超过某个长度后，检索能力也会明显下降，而且**下降往往从中间区域开始**。

## 二、那到底塞多少

### 2.1 一条经验基线

在我做过的几个中等规模技术文档库（1~3 万 chunk）上，反复测试得到的甜点区：

| 场景 | 重排后送入的文档数 | 说明 |
|------|------------------|------|
| 简单事实查询 | 2~3 篇 | 答案集中，多了就是噪声 |
| 常规问答 | 3~5 篇 | 默认配置 |
| 需要对比/综合 | 5~8 篇 | 多子问题场景，每子问题 1~2 篇 |
| 长文生成（报告/综述） | 8~15 篇 | 生成目标本身就需要广度 |

**默认从 4 篇开始。** 拿评测集往上试 6、8，看指标是否还涨；不涨就退回来。

### 2.2 按 token 而不是按篇数控制

"4 篇"这个说法有个问题：篇的长度差异很大。chunk_size 800 的 4 篇是 3200 token，chunk_size 2000 的 4 篇就是 8000 token。

更稳的做法是**按 token 预算控制**：

```python
import tiktoken

def build_context(docs, max_tokens=3000, enc=None):
    enc = enc or tiktoken.get_encoding("cl100k_base")
    parts, used = [], 0
    for d in docs:
        n = len(enc.encode(d.page_content))
        if used + n > max_tokens:
            # 剩余空间还够塞一个截断版本就塞，否则停
            if max_tokens - used > 200:
                truncated = enc.decode(enc.encode(d.page_content)[:max_tokens - used])
                parts.append(truncated)
            break
        parts.append(d.page_content)
        used += n
    return "\n\n".join(parts), used
```

**3000 token 是我常用的默认预算**。理由：

- 加上系统提示、Few-shot、用户问题，总计 4000~5000 token，多数场景够用；
- 不超过大多数模型"注意力稳定区"的边界；
- 成本可控。

### 2.3 预留多少给生成

别忘了上下文是双向的：输入 + 输出共用窗口。如果你的模型窗口是 8K，输入占了 7K，那输出最多 1K——长答案会被截断。

一个安全的分配比例：

```
输入（提示+上下文） ≤ 窗口的 60%
预留输出 ≥ 窗口的 25%
余量 15%（应对提示词膨胀、Few-shot 变长）
```

窗口 8K：输入 ≤ 4800，输出预留 2000。
窗口 128K：理论上输入可以到 76K，但实际上——见下一节。

## 三、长上下文模型出现后，结论变了吗

部分变了，但没变那么多。

### 3.1 变了的部分

新一代模型（GPT-4o、Claude 3.5、Gemini 1.5 等）在长上下文上的表现确实比 GPT-3.5 时代好得多：

- U 型曲线变浅了，中间位置的衰减没那么陡；
- 能可靠处理的上下文长度上限提高了（从 4K 级别到 32K 级别）；
- 对"跨文档综合"类任务的支持更好。

所以**绝对上限确实提高了**。原来塞 20 篇会崩，现在塞 10 篇可能还行。

### 3.2 没变的部分

1. **U 型仍然存在**，只是变浅。中间位置的劣势依然可以被测出来。
2. **噪声稀释没有消失**。不相关的文档进去，还是会干扰。
3. **成本随长度线性增长**，这点没有任何变化。
4. **"答案在其中"和"模型能找到答案"依然是两件事**。

一个实测对比（同一评测集，同一知识库）：

| 上下文配置 | GPT-3.5 准确率 | GPT-4o 准确率 |
|-----------|--------------|--------------|
| top3 重排后 | 0.71 | 0.83 |
| top10 重排后 | 0.66 | 0.81 |
| top20 重排后 | 0.58 | 0.76 |

GPT-4o 的抗噪声能力强很多（top20 还有 0.76），但**依然是 top3 最高**。趋势没变，只是斜率变了。

**结论**：长上下文模型让你"可以塞更多而不崩"，但不代表"应该塞更多"。少而精依然是更优解，只是容错空间大了。

## 四、排序：把最重要的放对位置

既然位置影响利用率，那排序就是个可以主动优化的变量。

### 4.1 利用 U 型曲线的排法

相关性最高的放**开头和结尾**，次要的放中间：

```python
def reorder_for_attention(docs):
    """按重要性重排：最重要的两端，次要的中间"""
    ranked = sorted(docs, key=lambda d: d.metadata.get("score", 0), reverse=True)
    n = len(ranked)
    result = [None] * n
    left, right = 0, n - 1
    toggle = True
    for doc in ranked:
        if toggle:
            result[left] = doc
            left += 1
        else:
            result[right] = doc
            right -= 1
        toggle = not toggle
    return result
```

这个"从两端往中间填"的排法，实测能挽回 3~6 个百分点的准确率（相比按分数降序直接排）。

**注意**：结尾位置尤其重要。很多模型对靠近生成起点的上下文（也就是输入的末尾）注意力最强。所以**最高分的那篇应该放最后**，而不是最前。

### 4.2 一个更简单的做法

如果上面的重排让你觉得麻烦，至少做一件事：**把最相关的那篇单独放到末尾，并显式标注**：

```python
best = ranked[0]
others = ranked[1:]

context = "## 参考材料\n" + "\n\n".join(d.page_content for d in others)
context += "\n\n## 最相关的材料（重点参考）\n" + best.page_content
```

这个简单的调整就能拿到大部分收益。

### 4.3 加位置标签

给每篇材料编号，让模型在引用时能指回来源：

```
[1] 内容...
[2] 内容...
[3] 内容...
```

并要求模型回答时标注 `[1]`。好处有两个：一是可溯源，用户能核对；二是**编号让模型更容易区分不同的材料**，减少张冠李戴。

## 五、压缩：塞不下或不想塞太多时的办法

有时候确实需要覆盖更多内容，但不想让上下文膨胀。几条路：

### 5.1 抽取式压缩

从每篇里只抽取和问题相关的句子：

```python
COMPRESS_PROMPT = """从下面的材料中，抽取与问题相关的句子。
要求：
1. 原样复制，不要改写、不要总结；
2. 只保留与问题直接相关的句子；
3. 若整篇都无关，输出 NONE。

问题：{question}
材料：{doc}

输出抽取结果："""
```

保留原文（不改写）是关键——改写会引入模型自己的理解，可能失真。抽取式压缩通常能把长度减到 30~50%，同时保住绝大部分有效信息。

### 5.2 摘要式压缩

适合长文档、需要保留整体结构时。但要注意：摘要是有损的，具体数字、代码片段、专有名词容易在摘要中丢失。**事实型问答不要用摘要压缩**。

### 5.3 结构化：把重复的格式去掉

工程上最容易被忽略的一条。如果你的文档里有大量重复的页眉页脚、导航栏、版权声明，在入库前就清洗掉；上下文里的 Markdown 表格如果列头重复，可以合并。

这类"格式噪声"有时能占到上下文的 20%，清掉是纯赚。

### 5.4 多路检索时的分块汇总

如果是多子问题/多查询的场景，先对每个子问题的结果做局部压缩，再汇总：

```
子问题1 → 检索5篇 → 压缩成200字
子问题2 → 检索5篇 → 压缩成200字
子问题3 → 检索5篇 → 压缩成200字
                    ↓
              汇总 600 字 + 原始 top3 全文
```

这样既保留了覆盖面，又控制了长度。

## 六、一个完整的上下文构建流程

把上面说的串起来，我实际在用的流程：

```python
def build_rag_context(question, retriever, reranker,
                      max_tokens=3000, keep_full=3):
    # 1. 粗召回（数量多一些，保证覆盖）
    candidates = retriever.invoke(question)          # top 20

    # 2. 重排（提精度）
    ranked = reranker.rank(question, candidates)     # 按相关度排序

    # 3. 前 keep_full 篇保留全文，其余压缩
    full_docs = ranked[:keep_full]
    rest_docs = ranked[keep_full:keep_full + 7]

    compressed = [compress(question, d) for d in rest_docs]
    compressed = [c for c in compressed if c != "NONE"]

    # 4. 组装：压缩内容在前，最相关的全文在末尾
    parts = []
    if compressed:
        parts.append("## 背景材料（已压缩）\n" + "\n\n".join(compressed))
    parts.append("## 核心材料\n" + "\n\n---\n\n".join(
        f"[{i+1}] {d.page_content}" for i, d in enumerate(full_docs)))

    context = "\n\n".join(parts)

    # 5. token 预算兜底
    return truncate_to_budget(context, max_tokens)
```

这个流程的几个设计点：

- 粗召回 20 → 重排 → 取前 10，保证覆盖和精度；
- 前 3 篇保留全文（最可靠的证据），后 7 篇压缩（补充背景）；
- **最相关的放末尾**，利用注意力分布；
- 最后一道 token 截断兜底，防止意外膨胀。

## 七、怎么验证你的配置

别凭感觉调。建一个最小的评测：

```python
# 1. 准备 50~100 条问答对（人工标注或 LLM 辅助生成后人工校验）
test_set = [{"q": "...", "a": "...", "doc_ids": [...]}, ...]

# 2. 跑几组配置
configs = [
    {"top_k": 3, "max_tokens": 1500},
    {"top_k": 5, "max_tokens": 3000},
    {"top_k": 10, "max_tokens": 6000},
    {"top_k": 20, "max_tokens": 12000},
]

# 3. 看三个指标：准确率、平均 token、平均延迟
```

**一定要同时看准确率和成本**。只看准确率，你可能会选 top_k=20；同时看成本，你会发现 top_k=5 用 1/4 的钱拿到了 98% 的效果。

另外建议分开统计：

- **答案在 top1 的题**：这类题应该看 top_k 小的时候的表现；
- **答案在 top5~10 的题**：这类题决定了 top_k 的下限；
- **答案完全没召回的题**：这类不是上下文的问题，是索引/检索的问题，别指望调 top_k 解决。

## 小结

- **上下文不是越大越好。** 塞多了会触发 Lost in the Middle、噪声稀释、成本线性上涨三个问题。
- 默认 **3~5 篇 / 3000 token** 起步，用评测集往上试，指标不涨就停。
- 长上下文模型让"塞多了不崩"，但**没有让"塞多了更好"**。少而精依然是更优解。
- **排序是可优化的变量**：最相关的放末尾（靠近生成的输入端），次要的放中间。
- 需要覆盖更多内容时，用**抽取式压缩**（保留原句）而不是塞全文；摘要压缩有损，事实型问答别用。
- 调参必须同时看**准确率和成本**，只看一个会做出错误决策。

一个判断做对了没有的简单标准：如果把某篇文档从上下文里去掉，答案质量不变，那这篇就不该在里面。用这个标准逐个筛，你会惊讶地发现能去掉的比想象中多。
