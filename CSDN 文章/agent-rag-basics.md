# RAG 入门：为什么大模型需要外挂一个知识库

你肯定遇到过这种情况：问模型一个你们公司内部的问题，它一本正经地编了一个答案。不是它笨，是它**真的不知道**——训练数据里没有。

**RAG（Retrieval-Augmented Generation，检索增强生成）** 就是解决这个问题的主流方案。思路朴素得让人意外：**先去你的资料里搜出相关内容，把内容一起塞给模型，让它基于这些材料回答。**

这篇讲：**它为什么有效、完整流程分几步、最小实现长什么样、以及新手最容易做砸的三个地方**。

---

## 一、为什么需要 RAG

先看看不用 RAG 的三条路，各自的问题：

| 方案 | 做法 | 问题 |
|---|---|---|
| 直接问 | 什么都靠模型记忆 | 不知道私有知识，还会编造 |
| 微调 | 把知识训进模型参数 | 贵、慢、知识更新要重训、容易遗忘旧知识 |
| **RAG** | 用时检索，把材料塞进上下文 | 需要搭检索链路，但**知识随时可更新** |

RAG 的核心优势就一个：**知识存在模型外面**。改文档就生效，不用重训，而且**能给出处**——这点对企业场景几乎是刚需。

---

## 二、完整流程：离线 + 在线

RAG 分两条线，别搞混：

```
【离线·建索引】                  【在线·问答】
文档 ─► 切分 ─► 向量化 ─► 存库      问题 ─► 向量化 ─► 检索 ─► 组装 ─► 生成 ─► 答案
```

### 离线阶段（做一次）

1. **加载**：读 PDF / Word / Markdown / 网页；
2. **切分（Chunking）**：把长文档切成一小段一小段；
3. **向量化（Embedding）**：每段转成一个向量；
4. **入库**：向量 + 原文 + 元数据存进向量库。

### 在线阶段（每次问答）

1. **问题向量化**：用同一个 embedding 模型；
2. **检索**：在库里找最相似的 K 个片段；
3. **组装提示词**：把片段和问题拼成提示词；
4. **生成**：模型基于材料作答。

## 三、最小实现（不到 50 行）

不依赖任何框架，把流程跑通：

```python
# ---- 离线：切分 + 向量化 + 入库 ----
import numpy as np

docs = [
    "公司报销流程：提交发票后 5 个工作日内到账。",
    "年假规则：入职满一年享 10 天年假，逐年递增 1 天，上限 15 天。",
    "加班规定：工作日加班按 1.5 倍时薪计算，需主管审批。",
]

def embed(text: str) -> np.ndarray:
    """真实场景调 embedding 模型；这里用字符频率做个玩具向量"""
    v = np.zeros(26)
    for ch in text.lower():
        if 'a' <= ch <= 'z':
            v[ord(ch) - 97] += 1
    return v / (np.linalg.norm(v) + 1e-9)

index = [(d, embed(d)) for d in docs]

# ---- 在线：检索 + 生成 ----
def retrieve(query: str, k: int = 2):
    q = embed(query)
    scored = [(float(np.dot(q, e)), d) for d, e in index]
    scored.sort(reverse=True)
    return [d for _, d in scored[:k]]

def answer(query: str):
    ctx = "\n".join(f"[{i+1}] {c}" for i, c in enumerate(retrieve(query)))
    prompt = f"""只根据下面的资料回答问题，资料里没有就说"资料未提及"。
回答时标注引用的编号。

资料：
{ctx}

问题：{query}"""
    return call_llm(prompt)      # 换成你的模型调用

print(answer("工作几年能休 15 天年假？"))
```

真实项目里把 `embed` 换成 embedding 模型、把内存列表换成向量库即可，**流程完全一致**。

## 四、三个最容易做砸的地方

### 坑 1：切分切错了

这是 RAG 效果的头号杀手。常见错误：

- **按固定字数硬切**：一句话被劈成两半，两段都不完整；
- **切太大**（几千字）：塞进上下文后稀释了关键信息，还费钱；
- **切太小**（几十字）：语义不完整，检索匹配不准。

**实用做法**：

```python
def chunk(text, size=500, overlap=50):
    """按段落优先切，超长再按句切，段间保留重叠防止语义断裂"""
    paras, chunks, buf = text.split("\n\n"), [], ""
    for p in paras:
        if len(buf) + len(p) <= size:
            buf += p + "\n\n"
        else:
            if buf: chunks.append(buf.strip())
            buf = p + "\n\n"
    if buf: chunks.append(buf.strip())
    return chunks
```

要点：**优先按语义边界（段落/句子）切**，块之间留 50~100 字重叠，单块控制在 300~800 字。

### 坑 2：检索回来的东西不相关

表现是答案驴唇不对马嘴。原因通常有三个：

1. **embedding 模型不适合中文**。很多开源模型中文语义表征弱，务必用中文优化过的（如 bge 系列）；
2. **问题和文档的表述差异大**。用户问「报销多久到账」，文档写「款项将在五个工作日内汇入」——纯向量可能匹配不上。解法是**混合检索**（向量 + 关键词 BM25 一起用）；
3. **K 值不合适**。太小漏掉关键片段，太大引入噪声。一般先试 3~5。

### 坑 3：模型无视材料自说自话

明明给了资料，模型还是按自己的记忆答。对策写在提示词里：

```
只使用【资料】中的信息回答。
如果资料中没有答案，直接说"资料未提及"，不要猜测。
每个结论后用 [编号] 标注来源。
```

**「没有就说不知道」这句一定要写**，否则模型会忍不住编。

## 五、效果怎么评估

别凭感觉。搭一个最小的评测集：

```python
test_cases = [
    {"q": "年假上限是多少天？", "expect": "15"},
    {"q": "加班费怎么算？",     "expect": "1.5 倍"},
]

hit = 0
for c in test_cases:
    ctx = retrieve(c["q"])
    hit += any(c["expect"] in t for t in ctx)      # 召回是否命中
print(f"召回命中率: {hit}/{len(test_cases)}")
```

**先测召回率，再测答案质量**。如果检索都没把正确片段找回来，换什么大模型都救不了——RAG 的瓶颈八成在检索，不在生成。

---

## 六、小结

1. RAG = **用时检索 + 塞进上下文**，知识存在模型外面，随时可更新、可溯源。
2. 两条线：**离线（切分→向量化→入库）** 和 **在线（问题向量化→检索→组装→生成）**。
3. 三个高频坑：**切分不当、检索不相关、模型无视材料**，分别对应语义切分 + 重叠、混合检索 + 中文 embedding、提示词里写死「不知道就说不知道」。
4. 评估要**先测召回率**——RAG 的瓶颈通常在检索端。
5. 最小实现不到 50 行就能跑通，先跑通再优化。
