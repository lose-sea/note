# RAG 检索缓存实战：省钱省延迟，但别缓存成过期答案

RAG 线上跑起来之后，第一道成本墙往往是**检索 + 重排**。每一次用户提问，都要先 embedding 一次、再向量库查一次、可能还要 rerank 一次。流量一大，这几步的 API 账单和延迟都吃不消。

检索缓存（Retrieval Cache）是性价比最高的一招：把「query → 召回的文档列表」缓存起来，命中就直接复用，跳过 embedding 和向量查询。但它也是个双刃剑——缓存的是「检索结果」，而文档库是会变的，**缓存错了比不缓存更糟**。

本文讲清楚：什么该缓存、缓存键怎么设计、失效策略怎么选、以及怎么避免缓存出 stale 答案。

## 一、缓存能省什么

先算笔账。一个典型的 RAG 检索链路：

- embedding 调用：一次，约 10~50ms，按 token 计费
- 向量库查询：一次，约 5~30ms
- rerank（如果用 cross-encoder）：一次，约 100~500ms，最贵

一个热门问题如果被问 1000 次，不做缓存就要重复 1000 次 rerank，这是纯浪费。缓存命中后，第 2 次到第 1000 次几乎零成本、零延迟。

经验值：在客服、FAQ、内部知识库这类「问题高度重复」的场景，检索缓存命中率轻松到 40%~70%，直接砍掉一半检索成本。

## 二、缓存键怎么设计

缓存键（cache key）决定了「什么算同一个问题」。设计不对，要么命中率极低（键太细），要么缓存错答案（键太粗）。

### 错误做法：用原始 query 做键

用户问「Python 怎么读文件」和「python 读取文件」语义完全一样，但字符串不同，原始 query 做键就缓存不到。更糟的是「怎么用 pandas 读 csv」和「怎么用 pandas 读 excel」字符串像但语义不同，直接做键又会错配。

### 推荐做法：用 embedding 向量做近似键

把 query embedding 后，用向量本身（或量化后的哈希）做键，在向量空间里做「近似最近邻查找」：

```
命中条件：存在一个已缓存 query，其 embedding 与当前 query 的余弦相似度 > 0.95
```

相似度阈值一般取 0.92~0.97。太低会错配，太高命中率上不去。这个阈值建议用历史日志调：取一批真实问题，看阈值变化对「错配率」和「命中率」的影响。

### 折中做法：改写后 query + 主题哈希

如果前面用了查询改写器，可以直接用「改写后的干净 query」做精确键——因为改写器已经把同义问题归一化了。再叠加一个「知识库版本哈希」，保证文档库更新后缓存自动失效（见第三节）。

## 三、失效策略：缓存最难的不是写入，是失效

RAG 缓存的是「召回的文档列表」，而文档库是活的。三种失效策略：

### 1. TTL 过期（最简单）

给每个缓存项设一个过期时间，比如 10 分钟 / 1 小时 / 1 天。适合「文档更新不频繁」的场景。缺点：TTL 内文档变了，缓存还是旧的；TTL 外文档没变，缓存也失效了（浪费）。

### 2. 知识库版本号（最稳）

每次文档库有增删改，就 bump 一个全局版本号（或文档集合的哈希）。缓存键里带上版本号，版本一变，旧缓存全部自然失效。这是生产环境最推荐的做法——**缓存的是结果，失效靠版本，二者解耦**。

```
cache_key = f"{query_embedding_hash}#{kb_version}"
```

### 3. 文档级失效（最精细）

如果缓存项里记录了它命中了哪几篇文档，当其中任意一篇被更新时，精准作废依赖它的缓存项。实现复杂（要维护 doc → cache_key 的倒排），但能做到「只失效受影响的缓存，其余照常命中」。适合文档更新极频繁、又想最大化命中率的场景。

## 四、不能缓存的东西

有几类 query 绝对不能进缓存，否则会出事故：

- **带时间敏感的 query**：「今天汇率多少」「最新的政策」——缓存一天就是错答案。这类要么不缓存，要么 TTL 设到秒级。
- **带用户私有上下文的 query**：「我的订单」——不同用户问的「我的」指向完全不同，缓存会串号。键里必须带 user_id 隔离，或者直接不缓存。
- **个性化 / 权限相关的 query**：多租户场景，A 租户召回的文档不能给 B 用。缓存键必须包含租户 id。

一句话：**缓存键里凡是会决定「召回哪些文档」的变量（用户、租户、时间、知识库版本），都必须进键；否则就是 bug。**

## 五、工程实现骨架

```python
import hashlib, time

class RetrievalCache:
    def __init__(self, ttl=3600, sim_threshold=0.95):
        self.ttl = ttl
        self.sim = sim_threshold
        self.store = {}   # key: (query_vec, docs, ts)

    def _key(self, vec, kb_version):
        h = hashlib.md5(vec.tobytes()).hexdigest()[:16]
        return f"{h}#{kb_version}"

    def get(self, vec, kb_version):
        k = self._key(vec, kb_version)
        item = self.store.get(k)
        if not item:
            return None
        if time.time() - item["ts"] > self.ttl:
            del self.store[k]
            return None
        return item["docs"]

    def put(self, vec, docs, kb_version):
        self.store[self._key(vec, kb_version)] = {
            "docs": docs, "ts": time.time()
        }
```

真实项目里会用 Redis 替代内存 dict（支持 TTL、分布式、持久化），但核心逻辑一样：**键 = 向量哈希 + 版本号，写入带 TTL，读取先查过期**。

## 六、小结

检索缓存是 RAG 上线后最该做的第一道优化：成本低、收益大、实现简单。记住三条军规——

1. 缓存键必须包含一切「决定召回结果」的变量（租户、用户、知识库版本）；
2. 失效优先用「知识库版本号」，TTL 只是兜底；
3. 时间敏感 / 私有的 query 直接不缓存。

把这三件事做对，缓存就是纯增益；做错任何一条，缓存就会变成「安静地给所有用户喂旧答案」的隐形炸弹。
