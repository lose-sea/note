# Supervisor、Team、Swarm 怎么选：多智能体编排的三条路

多智能体框架一上手，第一个问题就是「用哪种编排」。LangGraph 生态里有 Supervisor（主管）、Team/Skills（团队）和 Swarm（蜂群，源自 OpenAI 的 Swarm 项目），名字听着都像，用起来差别很大。

选错了的代价很实际：用 Supervisor 做需要高频切换的任务，每个决策都要绕一圈主管；用 Swarm 做有严格权限区分的任务，智能体之间互相乱调；想让多个 Agent 共享一份状态，却发现框架天然隔离。

这篇把三种模式的边界划清楚，并给一个不需要看框架文档就能做的判断。

---

## 一、三者的核心差异

先看一张表，这是全文的骨架：

| | **Supervisor** | **Team / Skills** | **Swarm** |
|---|---|---|---|
| **控制流** | 中心化，主管决定下一步 | 分散，每个成员主动接手 | 平等，Agent 之间直接 handoff |
| **状态共享** | 全局共享黑板 | 共享消息列表 | 各自上下文，交接时传递 |
| **决策者** | Supervisor（LLM） | 成员自己决定要不要干 | 当前 Agent 决定交给谁 |
| **适用** | 需要统一管控、有依赖关系 | 同构任务、能力互补 | 对话式交接、客服路由 |
| **典型场景** | 研究任务（搜索 + 分析 + 写作） | 并行处理一批文档 | 售前咨询 → 技术支持 → 售后 |
| **主要风险** | 主管成为瓶颈和单点 | 成员可能都不动手或抢着干 | 交接循环、责任不清 |

### 1.1 Supervisor：一个主管带着一群专员

```
        ┌──────────────┐
        │  Supervisor  │  ← 唯一的决策者
        └──┬────┬────┬─┘
           ▼    ▼    ▼
        [搜索][分析][写作]     ← 专员只执行，不决策
```

**工作方式**：用户请求进来，Supervisor 判断「这一步该让谁干」，把任务派给专员，拿回结果，再判断下一步。专员之间不直接通信。

**核心优势**：
- **流程可控**。每一步的走向由一个中心节点决定，天然适合有依赖、需要串行的任务
- **容易加人工审批**。在主管那一层插入 HITL 很自然
- **日志清晰**。一条主线 trace，排障容易

**代价**：
- **主管是瓶颈**。如果每一步都要主管决策，一个 10 步任务就是 10 次主管 LLM 调用 + 10 次专员调用
- **上下文压力**。主管要持有全部子任务的摘要才能决策，任务一多它的上下文就紧张
- **延迟**。每一步都是「主管想 → 专员干 → 回到主管」，串行链路长

### 1.2 Team：一群平等待人，谁有空谁上

```
   消息进入
      │
      ▼
  [成员A] ── 能处理？→ 是 → 处理
      │ 否
      ▼
  [成员B] ── 能处理？→ 是 → 处理
      │ 否
      ▼
   (都不处理 → 兜底)
```

**工作方式**：一批成员共享同一个消息池，每个成员看一遍，**声明自己能不能处理**。有一个接手就跑，没有就降级。

**核心优势**：
- **无单点瓶颈**。多个成员可以并行评估，不存在中心节点
- **扩展简单**。加一个能力就是加一个成员，不用改主管的逻辑
- **适合同构任务**。N 份文档 N 个处理 Agent，谁空闲谁处理

**代价**：
- **可能都不动手**。每个成员都觉得「这不是我的活」，任务被踢皮球
- **可能抢着干**。两个成员同时声明能处理
- **决策质量不可控**。成员自己判断「我能不能处理」，判断错了任务就悬空

### 1.3 Swarm：智能体之间直接交接

```
   [Agent A] ──handoff→ [Agent B] ──handoff→ [Agent C]
       ▲                                        │
       └────────────────────────────────────────┘
```

**工作方式**：当前 Agent 判断「这事不该我管，该交给 B」，直接把控制权（连同上下文）交给 B。**没有中心节点**。

**核心优势**：
- **延迟低**。没有主管那一绕，交接只是一次工具调用
- **擅长对话式场景**。客服对话里「这个问题涉及退款，转售后 Bot」非常自然
- **上下文连续**。交接时携带历史，用户感受不到换人

**代价**：
- **容易循环**。A 交给 B，B 又交给 A，没有终止判断就死循环
- **责任不清**。出问题时不知道是哪一环的决策
- **不适合有严格依赖的任务**。没有全局视角，容易漏步骤

## 二、一个不依赖框架文档的判断方法

忘掉框架名，问四个问题：

### 问题一：任务步骤之间有没有依赖？

- **有依赖**（必须先 A 再 B 再 C）→ **Supervisor**。只有中心节点能可靠地编排顺序
- **无依赖**（N 个同构子任务）→ **Team**。并行处理，谁空谁上
- **不是步骤而是路由**（不同问题走不同专家）→ **Swarm**

### 问题二：谁来决策「下一步干什么」？

- **必须由全局视角决定**（要考虑整体进度、预算、优先级）→ Supervisor
- **每个子任务自己说了算** → Team
- **当前处理者判断该转给谁** → Swarm

### 问题三：对可控性的要求多高？

- **要审计、要审批、要中断**（金融、法务、运维）→ Supervisor。中心节点插入这些能力最方便
- **无所谓，跑通就行** → 都可以
- **要快速响应、低延迟** → Swarm

### 问题四：上下文要不要跨 Agent 共享？

- **要共享**（分析结论要给写作 Agent 用）→ Supervisor（全局黑板）
- **部分传递**（交接时带历史，但不共享全部）→ Swarm
- **不共享**（各干各的）→ Team

**四个问题的答案会明确指向一种模式。** 如果读完还在纠结，用 Supervisor——它是兜底选择，出问题最少（虽然最慢）。

## 三、组合用法（生产里的常态）

真实系统很少纯用一种。三种常见组合：

### 3.1 外层 Supervisor，内层 Team

```
Supervisor
 ├─► Team(并行处理 10 份文档)     ← 同构，Team 更快
 ├─► 专员(写报告)
 └─► 专员(人工审批点)
```

主管负责「什么时候该并行处理、什么时候收尾」，团队负责把同构任务摊开跑。这是**最常见也最实用的结构**。

### 3.2 Swarm 前置路由 + Supervisor 后置编排

```
用户问题
   │
   ▼
[Swarm 层: 售前→技术→售后 路由]     ← 低延迟，快速定位域
   │
   ▼
[Supervisor 层: 该域内的多步任务]   ← 域内流程可控
```

**客服类系统的标准形态**：先用 Swarm 快速路由到正确的域（用户不想等），域内再用 Supervisor 严格编排（任务不能乱）。

### 3.3 Team 做评估 + Supervisor 做决策

```
[Team: 3 个评审 Agent 并行看方案]  →  各自打分
                    │
                    ▼
           [Supervisor: 汇总择优]
```

并行评估提覆盖，中心决策保一致。

## 四、落地时的通用坑

不管选哪种，这几个坑都会遇到。

### 4.1 没有终止条件

多智能体最容易出的 bug 是**跑不停**。

- Swarm：A↔B 无限交接
- Team：没人认领，也不退出
- Supervisor：一直派任务不结束

**每种模式都要有硬性终止**：

```python
MAX_HANDOFFS = 10          # Swarm 交接上限
MAX_MESSAGES = 50          # Team 消息轮数上限
MAX_STEPS = 30             # Supervisor 派发上限
```

到上限必须强制结束或转人工，不能指望模型「自己知道该停了」。

### 4.2 上下文爆炸

多 Agent 里上下文会以两种方式暴涨：

- Supervisor 持有所有子任务摘要，N 个子任务就是 N 段摘要
- Swarm 每次交接都带历史，交接 5 次历史叠 5 份

**对策**：
- 子任务结果**只回摘要不回全文**（详见 DeepAgents 那篇的文件系统方案）
- Swarm 交接时**压缩历史**，只保留与目标 Agent 相关的部分

### 4.3 排障困难

多 Agent 的 trace 是树形或图形的，比单 Agent 难读。**必须做三件事**：

1. 每一步记录 `trace_id / span_id / parent_span_id`
2. 记录**决策依据**：Supervisor 为什么派给 A 不派给 B（把它的推理输出存下来）
3. 记录**上下文内容**：Agent 收到什么（不只是它返回什么）

没有这三样，出问题时你只能看到「最终答案错了」，看不到错在哪一环。

### 4.4 成员职责重叠

Team/Swarm 模式下，两个 Agent 都能处理同一类任务，就会互相抢或者互相推。**定义成员时职责必须互斥**——每个 Agent 的 system prompt 里明确写「你负责 X，不负责 Y（这是 Z 的职责）」。

## 五、一份快速的选型清单

按这个顺序过一遍：

```
1. 任务是一批同构子任务吗？
   是 → Team
   否 ↓

2. 步骤之间有依赖、需要全局编排吗？
   是 → Supervisor
   否 ↓

3. 主要是按问题类型路由到不同专家吗？
   是 → Swarm
   否 ↓

4. 都不确定 → Supervisor（最稳的兜底）
```

然后检查三个必选项：

- [ ] 有硬性终止上限（handoff 数 / 消息轮数 / 步数）
- [ ] 子任务结果按摘要回传，不全量回传
- [ ] trace 覆盖到每个 Agent 的每次决策

**最后提醒**：如果你的多智能体系统只有两个 Agent，或者任务其实一条链就能走完——**别上多智能体**。一个带清晰步骤划分的 Plan-and-Execute 通常比三个 Agent 协作更简单、更快、更可控。多智能体解决的是「职责真的需要分离」的问题，不是「听起来更高级」的问题。

## 小结

- **Supervisor = 中心化编排**。全局视角、流程可控、易加审批，代价是主管瓶颈和延迟。适合有依赖、要管控的长任务。
- **Team = 分散并行**。同构任务谁空谁上，无单点，但可能踢皮球。适合同构批量处理。
- **Swarm = 对等交接**。低延迟、对话路由自然，但易循环、责任不清。适合客服式路由。
- 选型四问：**有没有依赖？谁决策？要多少可控性？上下文要不要共享？** 纠结就用 Supervisor 兜底。
- 生产常态是**组合**：外层 Supervisor + 内层 Team（最常用）、Swarm 前置路由 + Supervisor 后置编排。
- 四个通用坑：**必须有硬性终止上限、上下文要按摘要回传、trace 要记决策依据、成员职责必须互斥**。
- 最后一条：任务一条链能走通、Agent 少于三个，就别上多智能体。

多智能体不是「更先进的单 Agent」，它是另一种组织方式。选哪种，取决于你的任务是「一条流水线」「一堆同构活」还是「一个分诊台」——先想清楚这个，再选框架。
