# Step-back Prompting：让问题退一步，反而检索得更准

这是个反直觉的操作：用户明明问了一个很具体的问题，你却先把它"变笼统"，拿那个笼统的问题去检索，结果反而更好。

Step-back Prompting（退一步提示）来自 Google 2023 年的一篇论文，思路是让大模型从具体问题中抽象出更高层的概念或原理，用抽象后的查询去检索背景知识，再结合原始问题作答。

它解决的是一类很特定的失败：问题太具体，以至于知识库里**根本没有直接讲这个具体场景的段落**，只有讲通用原理的段落。

---

## 一、问题太具体会怎样

看一个真实例子。用户问：

> "我们的 Milvus 集群，3 个 QueryNode 里挂了 1 个，正在进行的查询会失败吗？"

这句话里有大量具体信息：Milvus、3 个节点、QueryNode、挂 1 个、进行中的查询。用这句原文去检索会发生什么？

向量模型会把整句编码成一个向量，这个向量被"3 个节点""挂了 1 个"这些具体细节主导。而知识库里大概率没有一段话恰好讨论"3 个 QueryNode 挂 1 个"——更可能存在的段落是：

- "QueryNode 负责执行查询，多个节点间通过负载均衡分配请求"
- "Milvus 的节点故障恢复机制：协调节点会检测心跳超时并重新分配 segment"
- "查询执行期间若节点不可用，请求会被路由到其他副本"

这些段落讨论的是**通用机制**，和"3 个节点挂 1 个"这个具体场景在向量空间里并不近。结果就是：直接检索召回不到，或者召回到一堆讲 Milvus 安装的无关内容。

### 1.1 退一步之后

让 LLM 对原问题做抽象，得到的 step-back 问题可能是：

> "Milvus 查询节点的故障容错机制是什么？"

拿这个问题去检索，上面那三段通用机制的内容全部能被召回。有了这些原理性材料，再回到原始的具体问题，模型就能做推理：3 个节点挂 1 个 → 请求会路由到其他副本 → 正在进行的查询可能重试但不一定失败。

**核心洞察**：具体问题的答案常常不在"讲这个具体问题"的文档里，而在"讲它背后的原理"的文档里。你要先把问题提升到原理层，才能找到那些文档。

## 二、抽象的方向有哪些

"退一步"不是随便泛化，有几种明确的抽象路径，不同问题适合不同的。

### 2.1 提概念：具体实例 → 通用类别

| 原始问题 | Step-back 问题 |
|---------|---------------|
| Redis 的 HNSW 索引 ef_search 设多少合适？ | 向量索引的查询参数如何影响召回率与延迟？ |
| bge-small-zh 的 512 维够用吗？ | embedding 维度与语义表达能力的关系？ |
| 我们 K8s 上部署的 Qdrant 内存一直涨怎么办？ | 向量数据库的内存占用构成与常见增长原因？ |

适用于：问题涉及某个具体产品/型号/版本的细节，但知识库只有通用原理类内容。

### 2.2 去约束：去掉时间/规模/场景限定

| 原始问题 | Step-back 问题 |
|---------|---------------|
| 2024 年一线城市差旅住宿标准是多少？ | 差旅住宿标准是如何按城市分级制定的？ |
| 200 人规模的公司该怎么配向量库集群？ | 向量数据库集群规模如何根据数据量和 QPS 规划？ |

适用于：问题带着一堆限定词，限定词稀释了核心语义。**注意**：去掉的约束不是丢弃，要在最后作答时加回去。

### 2.3 提原理：现象 → 成因/机制

| 原始问题 | Step-back 问题 |
|---------|---------------|
| 为什么我加了 chunk overlap 之后答案反而变差了？ | chunk overlap 的作用机制与副作用是什么？ |
| 召回的文档都对，但模型还是答错，为什么？ | LLM 在长上下文中定位信息的注意力分布特点？ |

适用于：问题是在问"为什么"，需要因果链条而非事实片段。

### 2.4 补前提：具体问题 → 前置概念

| 原始问题 | Step-back 问题 |
|---------|---------------|
| 我们的 IVF_PQ 为什么 nlist 调大之后召回降了？ | IVF_PQ 的聚类划分与倒排列表检索原理？ |

适用于：问题使用了专业术语，需要先建立术语理解才能找到材料。

## 三、代码怎么写

### 3.1 生成 step-back 问题

```python
STEPBACK_PROMPT = """你是检索优化助手。请对用户问题做"退一步"抽象。

规则：
1. 提取问题中涉及的通用概念、原理或机制，形成一个更抽象的问题；
2. 抽象问题应当是原问题的上位概念，而不是同义改写；
3. 保留领域关键词（产品名、技术名），只去掉具体场景细节；
4. 只输出一个抽象后的问题，不要编号、不要解释、不要回答。

示例：
原问题：Redis 的 HNSW ef_search 设多少合适？
输出：向量索引的查询参数如何影响召回率和延迟？

原问题：{question}
输出："""

def generate_stepback(question: str, llm) -> str:
    resp = llm.invoke(STEPBACK_PROMPT.format(question=question))
    return resp.content.strip().split("\n")[0]
```

给 few-shot 示例很重要。没有示例时，模型经常把 step-back 做成同义改写（那就是普通的 query rewrite 了），达不到抽象效果。

### 3.2 双路检索 + 合并

step-back 的标准用法是**两路都检索**，不是只检索抽象问题：

```python
def stepback_retrieve(question: str, k: int = 4):
    sb_question = generate_stepback(question, llm)

    # 路 1：原始问题（找具体事实）
    docs_specific = retriever.invoke(question)

    # 路 2：抽象问题（找原理背景）
    docs_general = retriever.invoke(sb_question)

    # 合并去重
    seen, merged = set(), []
    for d in docs_specific + docs_general:
        key = hash(d.page_content[:200])
        if key not in seen:
            seen.add(key)
            merged.append(d)

    return sb_question, merged
```

为什么两路都要？因为具体问题和抽象问题找到的材料是**互补**的：

- 具体路可能命中恰好讲这个场景的段落（如果有，质量最高）
- 抽象路命中的是原理性段落（覆盖面广，是主要保障）

只走抽象路会丢掉精确命中的机会；只走具体路就回到原来的问题。

### 3.3 组织上下文时分层

合并后的材料不要打乱顺序直接拼。分层组织，让模型知道哪部分是什么：

```python
def build_context(question, sb_question, docs_specific, docs_general):
    parts = []

    if docs_specific:
        parts.append("## 直接相关的材料\n" +
                     "\n\n".join(d.page_content for d in docs_specific))

    if docs_general:
        parts.append(f"## 背景原理材料（针对「{sb_question}」）\n" +
                     "\n\n".join(d.page_content for d in docs_general))

    parts.append(f"## 需要回答的问题\n{question}")
    return "\n\n---\n\n".join(parts)
```

把抽象问题也写进上下文，等于告诉模型"这些背景材料是为了回答什么层面找来的"，它更容易把原理和具体场景对接起来。

### 3.4 生成提示词里加一步推理

```python
ANSWER_PROMPT = """基于下面的材料回答用户问题。

答题步骤：
1. 先从背景原理材料中，找出与问题相关的机制或原理；
2. 再结合直接材料中的具体信息；
3. 把原理应用到用户的具体场景，得出结论；
4. 若材料不足以支撑，明确说明缺什么。

材料：
{context}

用户问题：{question}"""
```

要求模型"先讲原理、再套场景"，比直接让它答，正确率明显更高。这本质上是在诱导它做 CoT。

## 四、什么时候该用，什么时候别用

### 4.1 适合用的三类问题

1. **问"为什么"/"怎么办"的排查类问题** —— 需要因果链，原理性材料是关键。
2. **带着一堆具体参数的工程问题** —— 具体参数稀释语义，抽象后命中率提升明显。
3. **知识库以概念/原理类内容为主时** —— 比如技术文档、教材、规范，这类语料天然在"原理层"。

### 4.2 不该用的三类问题

1. **纯事实查找**："错误码 E1024 是什么？"——答案就是一条具体记录，抽象成"错误码体系设计原理"完全是南辕北辙。
2. **知识库以具体条目为主时**：比如 FAQ、工单记录、产品手册，语料本身就是具体场景，抽象反而找不到。
3. **问题本身已经很通用**：再退一步就变成教科书第一章了，毫无信息量。

### 4.3 用一个分类器做开关

不要对所有查询无脑启用。加一个轻量判断：

```python
STEPBACK_TRIGGERS = ["为什么", "怎么办", "如何排查", "是什么原因", "会不会",
                     "影响因素", "原理", "机制"]

def need_stepback(q: str) -> bool:
    # 触发词命中
    if any(t in q for t in STEPBACK_TRIGGERS):
        return True
    # 问题较长且含数字参数（具体场景特征）
    return len(q) > 30 and any(c.isdigit() for c in q)
```

规则判断比再调一次 LLM 便宜得多。命中率要求不高——漏掉一些没关系，误伤（对不该抽象的做了抽象）才是要避免的。

## 五、效果与代价

### 5.1 实测数据

技术文档库，200 条评测，其中 60 条是"为什么/怎么办"类：

| 方案 | 整体准确率 | 排查类准确率 | 平均延迟 | 候选文档数 |
|------|-----------|------------|---------|-----------|
| 单条检索 | 0.68 | 0.44 | 0.6s | 5 |
| + step-back 双路 | 0.72 | **0.67** | 1.5s | 9 |
| + step-back + 重排 | **0.75** | **0.70** | 2.2s | 9→4 |

重点看排查类：0.44 → 0.67，涨了 23 个百分点。整体只涨 4 个点，因为简单事实题没变化——这再次说明**条件启用**的必要性。

### 5.2 代价清单

- **一次额外 LLM 调用**：生成 step-back 问题，约 0.5~1s，100~200 token
- **一次额外检索**：可并行，延迟不叠加多少，但候选集翻倍
- **上下文变长**：9 条 vs 5 条，必须配重排压回去
- **抽象跑偏的风险**：模型抽象错了方向，会召回到完全不相关的领域

最后一条要重点防。我的做法是**要求抽象问题保留领域关键词**（提示词第 3 条），并且在检索后检查：如果抽象路的召回结果和具体路的召回结果**完全没有交集**，说明抽象可能跑偏了，这时候降低抽象路结果的权重或者丢弃。

## 六、和其他查询优化技术的区别

这张表值得存下来：

| 技术 | 输入 → 检索什么 | 适用 | 是否需要额外生成 |
|------|---------------|------|----------------|
| 查询改写 | 口语 → 书面规范表达 | 表述不规范、有指代 | 是（1 次） |
| 多查询 | 1 个问题 → N 个同层问法 | 表述差异、多角度 | 是（1 次生成 N 条） |
| 查询分解 | 1 个复合问题 → N 个子问题 | 多跳、比较类 | 是（1 次）+ N 次检索 |
| **Step-back** | 具体问题 → 1 个上位问题 | 需要原理支撑 | 是（1 次） |
| HyDE | 问题 → 假答案文档 | 查询与文档长度不对称 | 是（1 次） |

**最关键的区别**：多查询和查询分解是在**同一抽象层级**上做扩展（横向），step-back 是在**抽象层级**上做移动（纵向）。它们解决的是不同的问题，也可以组合。

一个实用的组合顺序：

```
查询改写（去指代、纠错）
    ↓
判断是否需要 step-back（排查类问题）
    ↓
双路检索（具体 + 抽象）
    ↓
判断是否需要分解（比较类/多跳）
    ↓
合并 → 重排 → 生成
```

但别一上来就全串起来。我建议的落地顺序是：改写 → 重排 → 多查询 → step-back → 分解。每加一层都拿评测集验证收益，没有收益就停在上一层。

## 小结

- Step-back 解决的是"答案在原理层，问题在实例层"的错配。做法是**把问题上提一个抽象层级**再检索。
- 四种抽象路径：提概念、去约束、提原理、补前提。核心是**保留领域关键词，剥离场景细节**。
- 标准用法是**双路检索**（具体 + 抽象）再合并，单走抽象路会丢掉精确命中机会。
- 上下文要分层组织，生成时要求模型"先讲原理、再套场景"。
- **条件启用**：排查类、带具体参数的问题才用；纯事实查找、FAQ 型知识库别用。实测排查类准确率 0.44 → 0.67，整体只 +0.04，说明收益高度集中在特定题型。

它不是一个通用增强，而是一把针对特定锁的钥匙。先确认你的问题分布里有没有那把锁，再决定要不要配这把钥匙。
