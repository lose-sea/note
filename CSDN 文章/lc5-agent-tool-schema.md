# 工具描述的写法：几个字符的差别，调用成功率差一倍

同一个工具，只改描述，模型的调用成功率可能从 60% 涨到 90%。这不是玄学——**工具描述就是 Agent 的 API 文档，而 API 文档的质量直接决定使用者的出错率。**

我见过太多团队把精力花在模型选型、提示词调优上，却给工具写一句 `"""查询数据"""` 就完事。模型只能猜，猜错就调用失败，然后在错误参数上反复重试——**你以为的「模型不行」，其实是文档不行。**

这篇把工具描述和参数设计的可操作规则讲清楚，附一份可以直接套用的检查清单。

---

## 一、工具描述的三个作用

模型看到工具定义时，它在回答三个问题：

```
【这个工具是干什么的？】      → 功能定位
【我该用它还是用别的？】      → 边界与适用场景
【参数怎么填？】             → 参数语义与约束
```

三个都答清楚，模型选得对、传得对。任何一个含糊，就会选错工具或者参数填错。

**多数团队的描述只答了第一个问题，甚至第一个都答得含糊。**

---

## 二、规则一：第一句话就写清边界

工具描述的开头，必须是「**这个工具是什么，且只做什么**」。

```python
# ❌ 差：只说做什么，没说边界
@tool
def query_alarm(time_range: str) -> str:
    """查询告警信息。"""
```

模型看到这个，会把它用在任何和「告警」沾边的问题上——包括要查告警统计、查已归档告警的。选错了工具，参数再怎么对也是白费。

```python
# ✅ 好：功能 + 边界 + 交叉引用
@tool
def query_alarm(time_range: str) -> str:
    """实时告警查询。只覆盖最近 7 天、未归档的活跃告警。

    查告警的历史统计聚合用 query_alarm_stats；
    查 7 天前已归档的告警用 query_archived_alarm。
    如果用户问的是「告警多不多」这类统计问题，不要用本工具。
    """
```

三行字，把「是什么、不是什么、该用什么」全说清了。**这类交叉引用是性价比最高的写法**——它主动把模型往正确的工具上推。

### 2.1 一个实用的判断法

写完描述后，找两个同事看，问：「用户问 X，你会用这个工具吗？」如果两人答案不一致，描述还没写好。

## 三、规则二：显式写「什么时候不要用我」

这违反直觉——用户一般会把文档写成「我的优点」，但工具描述里**写清「别用我」的场合，能显著降低误选率**。

原因：模型选错工具的典型场景不是「完全不相关」，而是「看起来相关」。当两个工具的语义接近时，一句「如果你的需求是 A，请用 B」能直接打破平局。

```python
@tool
def search_docs(query: str, top_k: int = 5) -> list[str]:
    """在公司制度文档库中检索条款原文。

    适用：公司政策、流程规范、制度条款类问题。
    不适用（请改用其他工具）：
    - 查具体工单/故障记录 → search_tickets
    - 查产品技术文档 → search_tech_docs
    - 实时数据（监控指标、订单状态）→ 走 data_api
    """
```

**这段「不适用」清单，是在替模型做消歧。** 没有它，模型只能凭对四个 `search_*` 工具的模糊理解去猜。

### 2.1 什么时候写「不适用」最有效

当你系统里有**语义相近的多个工具**时，这是必写的。如果工具之间界限分明（`read_file` / `write_file` / `delete_file`），写不写差别不大。

## 四、规则三：参数说明要带约束和示例

### 4.1 每个参数都要说清「能填什么、不能填什么」

```python
# ❌ 差
@tool
def query_order(status: str, days: int) -> list:
    """查订单。

    Args:
        status: 订单状态
        days: 天数
    """
```

模型会填出 `status="已完成"`（该用英文枚举）、`days="7"`（该用 int）、`days=30`（系统只支持 7/30/90）。

```python
# ✅ 好
@tool
def query_order(status: str, days: int) -> list:
    """按状态和时间范围查询订单列表。

    Args:
        status: 订单状态，只能是以下三个值之一：
            "shipped"（已发货）, "pending"（待处理）, "cancelled"（已取消）。
            不接受中文或其他值，查所有状态传 "all"。
        days: 查询最近多少天，只能是 7、30 或 90 三个整数，
            其他值会被拒绝。用户说「最近一周」→ 7，「最近三个月」→ 90。
    """
```

**关键要素**：
1. **枚举值穷举**，不要写「订单状态」这种让模型自己想的
2. **中文映射**。用户说「最近一周」要映射到 7，写出来比让它猜强
3. **非法值的处理方式**。说清「不接受 X」「会被拒绝」，模型会主动避开

### 4.2 参数名和说明要让模型「能对应上用户的话」

用户说「帮我看看上个月的订单」，模型要把「上个月」映射到参数。如果你的参数叫 `lookback_period_seconds`，模型要做两次转换（上个月 → 天数 → 秒）。

**参数名和单位尽量贴近用户语言**：

```python
# ❌ 模型要猜
def query(range_start_ms: int, range_end_ms: int): ...

# ✅ 模型能直接填
def query(start_date: str = "2026-10-01",
          end_date: str = "2026-10-31",
          _docs="日期格式 YYYY-MM-DD"): ...
```

如果必须用机器友好的类型（时间戳、毫秒），就在说明里给清楚换算规则，并**给一个示例值**。

### 4.3 给出完整示例（对复杂工具特别有效）

```python
@tool
def create_ticket(summary: str, priority: str, tags: list[str],
                  assignee: str | None = None) -> dict:
    """创建一张运维工单。

    完整示例：
    用户说「数据库挂了，很紧急，转给 DBA」
    → create_ticket(
        summary="生产数据库不可用",
        priority="P1",
        tags=["database", "outage"],
        assignee="dba-team"
      )

    Args:
        summary: 工单标题，一行，不超过 60 字，不要带句号
        priority: P1(线上故障)/P2(功能受损)/P3(一般问题)，默认 P3
        tags: 标签列表，可多选：database/network/application/security/
              deployment/other。不确定就填 ["other"]
        assignee: 处理组名称，可选。用户没指定就填 null，不要自己编
    """
```

**示例是概率最高的成功引导**——模型会直接模仿示例的格式。对参数多的工具，一段示例胜过十行说明。

## 五、规则四：给「空值」和「缺省」明确出路

模型遇到「用户没提供这个参数」时，最常见的两种错误行为：

1. **瞎编一个**（`assignee="admin"`）
2. **不调用工具，去问用户**（明明有合理默认值）

在描述里把出路写清楚：

```python
Args:
    assignee: 处理组名称。用户明确指定了才填；没指定填 null，
              由系统按规则自动分配。不要猜测或填默认值。
    limit: 返回条数，默认 20。用户说「全部」时填 100（系统上限）。
    keyword: 关键字。用户的问题里没有明确关键字时填 null，
             并告知用户这是全量查询。
```

**核心原则：任何参数都要么有明确默认规则，要么明确「不确定就填 null」。** 不要留模糊地带让模型自己裁量。

## 六、规则五：把安全约束写进 docstring

危险操作必须让模型知道要谨慎。但**光靠 docstring 不够**——它是提示，不是防线。真正的防线是代码层的二次确认：

```python
@tool
def delete_records(table: str, where_clause: str, dry_run: bool = True) -> dict:
    """删除表中的记录。高危操作。

    Args:
        table: 表名，必须是白名单内的表（见 /docs/allowed_tables）
        where_clause: WHERE 条件，不允许为空（禁止全表删除）
        dry_run: 默认 True。为 True 时只返回将删除的行数，不实际删除。
                 只有用户明确确认「确定要删」之后，才能传 False。

    调用历史：本工具若 24 小时内对同一条件调用超过 3 次，
    会自动要求人工审批。
    """
    # 代码层强制校验，不依赖模型自觉
    if where_clause.strip() in ("", "1=1", "TRUE"):
        raise ToolException("禁止无条件删除")
    if dry_run is False and not confirmed_recently(table, where_clause):
        raise ToolException("危险操作需先 dry_run 再确认")
    ...
```

**「dry_run 默认为 True」是一个很强的设计**：模型调用一次先看影响范围，用户确认后再真正执行。两道保险。

## 七、参数设计的常见错误

| 错误 | 后果 | 修正 |
|------|------|------|
| 枚举值不穷举 | 模型填中文/近义词 | 列出所有合法值 + 中文映射 |
| 布尔参数语义不清 | 模型填反 | 说明里给正反例子 |
| 单位不明确 | 秒/毫秒混用 | 参数名带单位，或说明里给换算示例 |
| 可选参数不给默认规则 | 模型瞎编 | 写「不确定填 null」或给默认值 |
| 参数太多（>5 个） | 模型漏填、错填 | 合并或拆成多个工具 |
| 参数名离用户语言太远 | 模型要做多次转换 | 用贴近用户表述的命名 |
| 必填/可选不分 | 模型该传的不传 | 类型标注 + 说明里强调 |
| 危险操作无确认机制 | 误删误改 | dry_run + 代码层白名单校验 |

## 八、一份可以直接用的检查清单

写完一个新工具，对着过一遍：

**描述**
- [ ] 第一句说清「是什么 + 只做什么」
- [ ] 有语义相近的工具时，写了交叉引用（「查 X 用 Y 工具」）
- [ ] 写了「不适用」清单（列出该用其他工具的场景）
- [ ] 高危操作标注了「需确认 / 需 dry_run」

**参数**
- [ ] 每个参数都有说明（没有说明的参数 = 让模型猜）
- [ ] 枚举值全部穷举，附中文映射
- [ ] 单位、格式、范围写清，附示例值
- [ ] 可选参数有默认规则或「不确定填 null」
- [ ] 参数数量 ≤ 5，多了考虑拆
- [ ] 参数名贴近用户语言

**安全**
- [ ] 危险操作在代码层校验（不依赖模型自觉）
- [ ] 删除/修改类默认 dry_run
- [ ] 输出做过长度截断（防模型 `print("x"*10**9)`）

**文档**
- [ ] 复杂工具附一个完整调用示例
- [ ] 团队有统一的动词前缀约定（`query_` / `create_` / `search_`）

## 九、怎么验证描述写得好不好

不用等到线上才发现问题。两个便宜办法：

### 9.1 抽样对拍

取 20 个真实用户问题，让 Agent 跑一遍，人工看：

- 选对工具了吗？
- 参数填对了吗？
- 如果错了，是「描述没说清」还是「模型能力不够」？

**多数参数错误是描述问题，不是模型问题。**

### 9.2 让模型给自己挑错

```python
AUDIT_PROMPT = """评审下面这个工具的定义，指出会让 LLM 用错的地方。

工具定义：
{tool_definition}

检查点：
1. 功能边界是否清晰？
2. 有没有语义相近工具会让模型混淆？
3. 参数约束是否穷举（枚举、单位、范围）？
4. 可选参数的默认行为是否明确？
5. 有没有遗漏的「不适用」场景？

输出：问题列表 + 修改建议"""
```

用另一个模型（或同一个模型换一个「审稿人」身份）审，比自查有效——这和自我批评那篇是同一个道理：**换视角才能发现自己的盲区。**

## 小结

- 工具描述不是注释，是 **API 文档**，直接决定模型的调用成功率。同样是那个工具，改描述能把成功率从 60% 拉到 90%。
- 模型看工具定义时在问三个问题：**这是什么、该不该用我、参数怎么填**。多数描述只含糊答了第一个。
- 五条核心规则：**第一句写清边界、显式写「不适用我」的场合、参数约束必须穷举（枚举+中文映射+示例）、空值和默认值给出路、安全约束进 docstring 并在代码层兜底**。
- 危险操作的设计范式：**`dry_run` 默认 True + 代码层白名单校验**。docstring 是提示，代码才是防线。
- 验收靠两件事：**抽样对拍（20 个真实问题人工看）** + **让模型审自己的定义**。
- 写完对着检查清单过一遍，十分钟的事，能省几周返工。

「模型老是调错工具」这个锅，一半在模型，另一半在文档。而文档这一半，是你今天下午就能修好的。
