# LLM Agent 是什么：从 ChatBot 到自主智能体的演进

「Agent」大概是最近两年被滥用得最狠的词之一。有人说它就是一个会调 API 的 ChatGPT，有人说它是下一代操作系统，还有人把任何带 if-else 的脚本都包装成 Agent。

这篇文章把概念压实：**先用一个具体场景说明 Agent 到底解决了什么问题，再拆开它的四个组成部分，最后手写一个能跑起来的最小 Agent 循环**。看完你应该能判断——某个东西到底是不是 Agent，以及你的场景需不需要它。

---

## 一、先看一个场景：为什么光靠对话不够

假设你要让大模型帮你做这件事：

> 「帮我看看公司上周的销售数据，找出下滑最厉害的品类，写一份分析发到我邮箱。」

如果你直接把这句话丢给一个 ChatBot，它会怎么做？它大概率会**编造**一份看起来很像那么回事的分析——因为它根本看不到你的销售数据，也发不了邮件。这就是大模型最本质的缺陷：**它只有参数里记住的知识，没有感知外部世界和影响外部世界的能力**。

要让这件事真正跑通，模型需要三样本事：

1. **能看到数据** —— 连数据库、读文件、调接口；
2. **能做动作** —— 发邮件、写文件、下订单；
3. **能自己决定下一步** —— 先查哪个表、查完发现不够再补一次、最后整理成报告。

第 3 条是关键，也是「Agent」和「普通应用」的分界线。

---

## 二、三个层次：ChatBot、工作流、Agent

| 形态 | 谁决定下一步 | 典型实现 | 灵活度 | 可控性 |
|---|---|---|---|---|
| ChatBot | 不需要下一步，一问一答 | 直接调 LLM API | 低 | 高 |
| 工作流（Workflow） | **开发者**预先写死流程 | 代码 / DSL 编排 LLM 调用 | 中 | 高 |
| Agent | **模型自己**决定流程 | 循环调用 LLM + 工具 | 高 | 低 |

**工作流和 Agent 的区别值得多说一句**，因为很多人混淆。

工作流是你画好流程图：先调 A，再调 B，B 失败就走 C。LLM 只负责流程里某几个节点的「翻译」「总结」「分类」。流程是**确定的**，输入输出都是你可预期的。

Agent 是你只给它一个目标和一堆工具，让它自己想：我先调 A 吧，拿到结果一看不对，那我再调 D 试试。流程是**运行时才产生的**，你事前不知道它要走几步。

一句话：**工作流是你指挥模型，Agent 是模型指挥自己。**

---

## 三、Agent 的四件套

不管什么框架，一个 Agent 拆到底就是四样东西：

```
┌─────────────────────────────────────┐
│               Agent                 │
│                                     │
│   ① 大脑：LLM（负责推理与决策）      │
│   ② 规划：把目标拆成步骤             │
│   ③ 工具：感知和影响外部世界的手     │
│   ④ 记忆：短期上下文 + 长期存储      │
└─────────────────────────────────────┘
```

### ① 大脑（Model）

就是大模型本身。它在这里的角色不是「写文章」，而是**当决策器**：看一眼当前状态和历史，输出「下一步做什么」。

### ② 规划（Planning）

复杂任务需要拆。常见的两种思路：

- **一次性拆解**：先让模型输出一个步骤清单，然后按清单执行（简单但僵化）；
- **逐步推进**：每轮只决定下一步，做完看结果再决定再下一步（灵活但容易迷路）。

后者就是 ReAct 范式，后面单独一篇讲。

### ③ 工具（Tools）

这是 Agent 和普通对话最本质的区别。工具本质上是**一段带描述的函数**：

```python
def query_sales(db, start_date, end_date):
    """查询指定时间段的销售数据，返回按品类聚合的 DataFrame"""
    ...
```

关键在于那句文档字符串——**模型是通过读你的描述来决定要不要用这个工具的**。描述写得含糊，工具就会被误用或视而不见。这是实践中最高频的踩坑点。

### ④ 记忆（Memory）

- **短期记忆**：本轮对话的消息列表。受限于上下文窗口，长任务会被撑爆。
- **长期记忆**：向量库存历史、数据库存结构化状态、摘要压缩旧对话。

没有记忆的 Agent 做不了长任务——它会忘记自己十步之前查到了什么。

## 四、手写一个最小可用的 Agent

不依赖任何框架，用纯 Python 就能跑通核心循环。下面这个例子只有几十行，但包含了 Agent 的全部骨架：

```python
import json

# ---- ③ 工具：普通函数 + 描述 ----
TOOLS = {
    "query_sales": {
        "desc": "查询销售额。参数：{\"days\": 天数}。返回各品类的销售额字典。",
        "fn": lambda args: {"数码": 120000, "服饰": 78000, "食品": 31000},
    },
    "send_email": {
        "desc": "发送邮件。参数：{\"to\": 收件人, \"body\": 正文}。",
        "fn": lambda args: print(f"[已发送邮件给 {args['to']}]") or "ok",
    },
}

def call_llm(messages):
    """① 大脑：真实场景下替换成你的模型调用"""
    # 这里用一个假的"模型"演示：第一轮决定查数据，第二轮决定发邮件
    if len(messages) < 3:
        return {"tool": "query_sales", "args": {"days": 7}}
    return {"tool": "send_email", "args": {"to": "boss@corp.com", "body": "分析已完成"}}

def run_agent(goal: str, max_steps: int = 8):
    """② 规划 + 循环：模型自己决定走几步"""
    history = [f"目标：{goal}",
               "可用工具：" + json.dumps({k: v["desc"] for k, v in TOOLS.items()},
                                         ensure_ascii=False)]
    for step in range(max_steps):              # 必须有步数上限，否则可能死循环
        decision = call_llm(history)           # ① 模型决定下一步
        tool, args = decision["tool"], decision["args"]
        if tool == "finish":                   # 模型认为可以收工了
            break
        result = TOOLS[tool]["fn"](args)       # ③ 执行工具
        history.append(f"第{step+1}步：调用 {tool}({args}) -> {result}")   # ④ 记忆
        if tool == "send_email":
            break
    return history

for line in run_agent("分析上周销售数据并邮件汇报"):
    print(line)
```

这段代码里有几个**必须注意的点**：

1. **`max_steps` 一定要有**。模型可能陷入「查数据 → 不满意 → 再查」的死循环，没有上限就是无底洞（也是无底账单）。
2. **工具描述决定了工具能不能被正确调用**。`desc` 写得越清楚，误用越少。
3. **每轮把工具结果拼回历史**，这就是短期记忆——模型靠它知道前面发生了什么。
4. **终止条件要显式设计**。不能指望模型自己说「我完了」，通常要给它一个 `finish` 工具。

## 五、Agent 的能力边界：它最容易栽在哪

写 Agent 之前先知道它的失败模式，能省掉大量调试时间。

| 失败模式 | 现象 | 常见原因 |
|---|---|---|
| **死循环** | 反复调同一个工具，结果都一样 | 工具返回没变化，模型看不出进展 |
| **工具误用** | 该查数据库却去搜网页 | 工具描述含糊或功能重叠 |
| **上下文撑爆** | 跑到十几步后开始胡言乱语 | 历史没压缩，超出窗口 |
| **幻觉成功** | 工具报错了，它却说任务完成 | 没把错误信息回传给模型 |
| **偏离目标** | 中途被某个中间结果带跑偏 | 缺少目标复述 / 检查点 |

其中**「幻觉成功」最危险**——工具调用明明失败了，Agent 却在最终汇报里说「已完成」。对策很简单：**把工具的真实返回（包括报错原文）原样塞回历史**，让模型自己判断成败，不要帮它美化。

## 六、什么时候该用 Agent，什么时候不该

**该用：**

- 步骤数量无法事前确定（要查几次取决于查到了什么）；
- 需要根据中间结果动态调整策略；
- 任务空间大、分支多，穷举流程不现实。

**不该用：**

- **流程固定、步骤明确** —— 老老实实写工作流，可控且便宜得多；
- **对可靠性要求极高**（转账、删数据）—— Agent 的不确定性是致命的；
- **延迟敏感** —— 多轮调用叠加起来很慢。

一个实用的判断标准：**如果你能用流程图把任务画出来，就别用 Agent。** Agent 是为「画不出流程图」的场景准备的，代价是成本和可控性。

---

## 七、小结

1. Agent 解决的是大模型「**看不见、动不了**」的问题——给它工具，让它自己决定怎么用。
2. 它和普通应用的分界线是：**下一步由模型决定，而不是由代码写死**。
3. 四件套：**大脑（LLM）+ 规划 + 工具 + 记忆**，任何框架都逃不出这个结构。
4. 核心循环只有四步：模型决策 → 执行工具 → 结果写回历史 → 重复，**必须设步数上限**。
5. 最大的坑是**幻觉成功**和**死循环**；工具描述、错误回传是两个最值得投入的优化点。

下一步建议：把上面那段代码里的 `call_llm` 换成你自己的模型调用，加两个真实工具（比如读本地文件、调一个公开 API），亲手跑一遍——理解 Agent 最快的方式，就是看它在第 3 步开始跑偏，然后想办法把它拽回来。
