# RAG 时效性问答实战：别让用户读到一年前的「最新」答案

「现在最新的利率是多少？」「这个政策目前还有效吗？」——这类**时效性问答**是 RAG 的一个隐蔽雷区。知识库里的文档是某个时间点抓的，三个月后政策改了、价格变了、接口弃用了，但 RAG 还会一脸真诚地把旧文档当成「最新事实」喂给用户。

更糟的是，模型自己也有「知识截止日期」，两者叠加，用户拿到的可能是双重过期的答案。本文讲清楚：时效性问答的坑在哪、怎么在检索和生成两侧同时设防。

## 一、时效性问题的两种形态

- **强时效**：答案本身随时间变（利率、股价、政策、库存、天气）。这类问题，**任何没有时间戳的答案都不可信**。
- **弱时效**：文档里的方法论、概念、代码范式长期有效，但举例用的版本号 / API 可能过时。这类要标注「示例基于某版本」，避免用户照搬旧写法。

RAG 对强时效问题尤其危险，因为向量检索只看语义相似，完全不关心「这篇文档是不是半年前的」。

## 二、检索侧：给文档打时间标签

第一道防线在**数据入桶时**就做：每篇文档必须带结构化的时间元数据——

```json
{
  "doc_id": "policy_123",
  "content": "...",
  "published_at": "2026-03-01",
  "effective_until": "2026-12-31",
  "source": "官网公告"
}
```

检索时，时间元数据参与过滤和排序：

- **过期过滤**：`effective_until` 已过且未被新文档取代的，直接降权或排除。
- **新鲜度加权**：同主题多篇，优先召回最近发布的（recency boost）。
- **时间感知重排**：rerank 阶段把「文档时间 vs 问题时间意图」作为特征，问「现在」就推新文档。

## 三、生成侧：让模型会「拒答旧答案」

即使检索召回了旧文档，生成模型也必须被明确告知「注意时效」：

```
规则补充：
- 如果参考文档的发布时间早于问题所问的时间范围，或文档标注已过期，
  请在答案中注明"以下信息截至 {文档日期}，建议核实最新情况"
- 如果用户问"最新/当前/现在"，而参考文档不是近期发布的，
  明确提示信息可能已过期，不要假装是实时数据
```

这一句能大幅降低「把旧数据当实时」的事故。关键是把**文档时间戳显式塞进 prompt**，模型才知道该不该提醒。

## 四、强时效场景：RAG 之外接实时源

对于「当前股价 / 实时汇率 / 库存」这种秒级变化的强时效问题，RAG 知识库根本不该是真相源——应该**接实时 API / 数据库**，用 Agentic RAG 的思路把检索换成「工具调用」：

```
用户问当前汇率 → 模型识别为实时需求 → 调用汇率 API → 返回精确实时值
```

RAG 知识库只负责「解释汇率是什么、怎么看」，实时数值交给确定性接口。两者分工，互不越界。

## 五、增量更新与版本治理

时效性的根子在「知识库多久更新一次」：

- **增量索引**：新文档进来增量建向量，别每次全量重建（前面有专篇讲）。
- **失效标记**：旧政策被新政策取代时，显式标记旧文档 `superseded_by: 新文档id`，检索时旧文档自动降权。
- **定期巡检**：跑一个定时任务，扫描 `effective_until` 临近 / 已过的文档，提醒运营更新或下线。

## 六、评测时效性问答

- **过期答案率**：抽样强时效问题，看答案是否在「用过期文档答当前问题」而不提示。
- **时间戳标注率**：该提醒过期的，有没有标注（人工 / 规则检查）。
- **实时源命中率**：强时效问题有没有正确路由到实时工具而非知识库。

## 小结

时效性问答的核心认知：**向量检索不关心时间，所以你必须替它关心**。三道防线——入桶打时间标签 + 检索新鲜度加权、生成侧强制过期提示、强时效接实时源。再配合增量更新和失效标记，才能避免用户在某天突然发现，系统给的「最新政策」其实是去年的。
