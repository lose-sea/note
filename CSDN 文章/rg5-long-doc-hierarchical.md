# 长文档分层检索实战：父子索引、摘要索引与章节树

三百页的产品手册、几百页的标书、动辄几十万字的小说——当单篇文档的长度超过 embedding 模型的处理窗口、超过 LLM 的上下文上限，"一把切成 512 字块"的策略就开始崩：检索命中的是碎片，答案要的大局在碎片里拼不出来。这篇文章讲三种长文档处理范式：**父子索引**（大块拆小块）、**摘要索引**（自底向上建摘要树）、**章节结构索引**（顺着文档天然层级走），以及它们各自的适用场景和组合用法。

## 一、长文档为什么是 RAG 的特大困难

先量化困难。一篇 20 万字的技术手册：

- **切分即碎**：按 512 字切 ≈ 400 个 chunk，一个"故障排查"主题可能散在 15 个 chunk 里，语义查询召回其中 1~2 个，答案缺胳膊少腿；
- **上下文放不下**：20 万字 ≈ 20 万 token，主流模型上下文 128K 顶天，"全文塞进去"不现实，而且塞了也贵；
- **结构信息全丢**：原文档的"第 5 章 → 5.3 节 → 图 5-7"层级，硬切之后 metadata 只剩页码。

三种范式就是对着这三个痛点来的：父子索引解决"检索粒度"，摘要索引解决"宏观视角"，章节树解决"结构丢失"。

## 二、范式一：父子索引（Parent-Child）

**核心思想：用小块检索，用大块生成。**

小 chunk（child，256 字）负责被向量检索——粒度细、语义聚焦、命中准；命中后把它所属的大块（parent，2000 字）取出来喂给 LLM——上下文完整、不用拼碎片。

```
文档
 └─ 切大块（parent，2000 字，按语义边界切）
     └─ 每块再切小块（child，256 字）
         ├─ child-1 → embedding → 入库（带 parent_id）
         ├─ child-2 → embedding → 入库（带 parent_id）
         └─ ...

检索："索引优化怎么做？"
 → 命中 child-3（parent=P7）
 → 返回 P7 全文给 LLM
```

代码骨架：

```python
parents, children = [], []
for p_idx, parent_text in enumerate(semantic_split(doc, size=2000)):
    pid = f"{doc_id}_p{p_idx}"
    parents.append({"id": pid, "text": parent_text})
    for c_idx, child_text in enumerate(split(parent_text, size=256)):
        children.append({
            "id": f"{pid}_c{c_idx}",
            "text": child_text,
            "parent_id": pid,
        })

# 只给 child 建向量索引，parent 走 KV 存储
vs.add([embed(c["text"]) for c in children], metadatas=children)
kv.put_bulk(parents)

# 检索
hit = vs.search(embed(query), top_k=5)
parent_ids = unique([h["parent_id"] for h in hit])
context = [kv.get(pid)["text"] for pid in parent_ids]
```

**关键细节**：

1. **去重**：5 个 child 命中可能同属一个 parent，取 parent 前先去重，上下文别重复塞；
2. **parent 大小平衡**：太大超过上下文、太小不完整。1500~2500 字是甜点区；
3. **child 之间重叠**：按语义边界切的话重叠会制造重复命中，按固定 256 字切建议 10%~20% 重叠防断句；
4. **parent 也建索引（粗粒度）**：还可选给 parent 建"摘要级"向量索引，让"章节主题"类查询先命中 parent 再定位 child——这是父子 + 摘要的混合，后面讲。

## 三、范式二：摘要索引树（RAPTOR 式）

**核心思想：自底向上递归摘要，建一棵"文档语义树"。**

RAPTOR（Recursive Abstractive Processing for Tree-Organized Retrieval）的流程：

```
Level 0: 原始 chunks（叶子）
   按相似度聚类，每组过 LLM 生成摘要 → Level 1 节点
Level 1: 摘要节点
   再聚类再摘要 → Level 2 节点
   ...
根节点 = 整篇文档的一句话/一段话摘要

检索：所有层级的节点全部向量化入库
查询 → 命中哪层算哪层
   "索引优化怎么做" → 命中 Level 0 具体 chunk
   "这本手册讲了什么" → 命中 Level 2/根摘要
```

**摘要树的检索哲学**：查询不再只面对碎片，而是面对一棵从细节到全局的语义树——**细节问题命中叶子，宏观问题命中根**，一个索引同时服务两种查询。

```python
def build_summary_tree(chunks, llm, sim_threshold=0.7, max_group=10):
    level = [{"id": f"L0_{i}", "text": c, "level": 0} 
             for i, c in enumerate(chunks)]
    tree = list(level)
    while len(level) > 1:
        groups = cluster_by_similarity(level, sim_threshold, max_group)
        next_level = []
        for g_idx, group in enumerate(groups):
            if len(group) == 1:       # 聚不起来的单节点上升到上层
                next_level.append(group[0]); continue
            summary = llm(f"用 200 字概括以下文本的共同主题和关键信息：\n"
                         + "\n---\n".join(n["text"] for n in group))
            node = {"id": f"L{level[0]['level']+1}_{g_idx}",
                    "text": summary, "level": level[0]["level"]+1,
                    "children": [n["id"] for n in group]}
            next_level.append(node)
            tree.append(node)
        level = next_level
    return tree
```

**成本账必须算**：每个非叶子节点一次 LLM 摘要调用。400 个 chunk 的文档，树高 2~3 层，大约 200~400 次摘要——**建库成本比父子索引高一个量级**（纯 embedding vs 纯 LLM）。只对"高频查询的长文档"建，别全库开。

**检索时的层级加权**：宏观问题的答案在高层，细节问题在低层。默认全层级混排，可按查询类型先探测（短查询偏细节、长查询偏宏观）再选层——或者干脆全层级检索后靠 rerank 自然排序，多数场景够用。

## 四、范式三：章节结构索引（顺着文档天然层级）

**核心思想：文档本身就有层级，别重新发明切分。**

技术手册的"第 3 章 → 3.2 节 → 3.2.1 小节"是作者写好的大纲，比任何算法聚类都准。做法：

```python
# 1. 解析阶段保留标题层级（Docling/Unstructured 天然支持）
tree = parse_with_headings("manual.pdf")   
# → [("第3章 索引优化", 1), ("3.2 B+树结构", 2), 
#    ("3.2.1 节点分裂", 3), ("正文...", 3), ...]

# 2. 按"叶子标题下的内容"为单元切块，块带完整标题路径
chunks = []
for section in extract_leaf_sections(tree):
    chunks.append({
        "text": section.content,
        "title_path": " > ".join(section.heading_ancestors),  # 第3章 > 3.2 B+树结构 > 3.2.1 节点分裂
        "heading": section.heading,
    })
```

**标题路径进 chunk 文本**（不仅是 metadata）：`embed("第3章 索引优化 > 3.2 B+树结构 > 3.2.1 节点分裂：<正文>"`），查询"节点分裂"或"3.2.1 讲了什么"都能命中，而且命中后上下文自带完整结构。

**"目录页"特判**：长篇文档开头常有目录（3 章 47 节一页全列），单独成块入库，查询"这本手册有哪些章节"直接命中目录页——这是最容易被漏掉的高价值 chunk。

## 五、三种范式的组合拳

生产上不是三选一，是按文档类型组合：

| 文档类型 | 推荐组合 |
|---|---|
| 结构化手册/标书（标题清晰） | **章节树为主 + 父子索引**（叶子节内再切） |
| 长篇纯文本（小说、连续叙事） | **父子索引**（语义切分 + parent 上下文） |
| 超长研究报告（查询偏宏观） | **摘要索引树 + 父子索引**（宏观走摘要，细节走父子） |
| 法规条文（按条组织） | **章节树**（按"条"切，条号就是 ID） |

一个组合实现：章节树切大块 → 大块内切小块父子 → 对大块生成一级摘要（只一层，不建全树）——三层结构，覆盖从"这条怎么规定的"到"整体框架是什么"的全部查询。成本的增量只有一级摘要，可控。

## 六、评估：长文档 RAG 的测试集怎么建

长文档场景的评估必须专门建测试集，通用问题集测不出问题：

```python
# 三类探针
probes = {
    # 细节型：答案在某一小节里
    "detail": ["节点分裂的具体条件是什么？", "3.2.1 提到的触发阈值是多少？"],
    # 跨节型：答案要综合两节
    "cross": ["索引分裂和页合并的关系？", "第 3 章和第 5 章的配置参数怎么联动？"],
    # 宏观型：答案在摘要层
    "global": ["这本手册的核心主题是什么？", "手册推荐的整体优化思路？"],
}
```

三类问题的召回率分开统计——**只测细节型是自欺欺人**（那正是传统切分擅长的），跨节和宏观的命中才是长文档方案的增量价值。

## 七、常见坑

1. **父子索引的 child 切得太碎**（128 字以下）：embedding 语义不足，命中率反而降。256 起步；
2. **摘要失真累积**：RAPTOR 高层摘要的错误会向上传染（L1 摘要错了，L2 基于错误的 L1 再摘要），摘要节点要标注"由 LLM 生成"——答案引用时优先引原文层；
3. **章节树的标题层级识别失败**：扫描件、非规范排版文档没有干净标题，Docling 的版面识别也不是 100% 准——复杂文档先跑标题识别准确率抽样，不够就退化为父子索引；
4. **parent 上下文超限**：LLM 上下文 32K 时塞 10 个 2000 字 parent 就危险了——**按模型上下文动态调 top_k × parent_size**，别硬编码；
5. **忘了给"图表"留位置**：长文档里的图（哪怕已有 VLM 描述），在章节树里应该挂在所属节下，而不是漂浮在文档级。

## 八、落地检查清单

- [ ] 文档分类：结构化手册 / 长篇连续文本 / 研究报告，各走对应组合；
- [ ] 父子索引：child 256±、parent 2000±、命中 parent 去重；
- [ ] 章节树：标题路径进文本、目录页单独入库、图表挂到所属节；
- [ ] 摘要树只在"高频查询的长文档"上建，成本评估先于建设；
- [ ] 三类探针评估集（细节/跨节/宏观）分开统计；
- [ ] top_k 与 parent size 按模型上下文联动调整，不硬编码；
- [ ] 摘要节点标注生成方式，引用优先原文层。

## 九、小结

长文档检索的四句话：

- **父子索引是基座**：小块检索、大块生成，解决"检索粒度 vs 上下文完整"的根本矛盾，通用性最强；
- **摘要索引树服务宏观查询**：细节命中叶子、全局命中根，一份索引两种服务，但 LLM 摘要成本高，只给高频长文档建；
- **章节结构索引最被低估**：文档自带的大纲比算法聚类准，标题路径进 chunk、目录页单独入库，两行改动大幅提升结构化文档表现；
- **组合 + 分类评估**：按文档类型组合三种范式，评估必须分细节/跨节/宏观三类探针——跨节和宏观的命中率才是长文档方案的真实价值。
