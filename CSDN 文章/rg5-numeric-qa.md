# RAG 数字问答实战：让模型算得准，而不是编得圆

「我们公司去年 Q3 的营收是多少？」「这表里 A 产品和 B 产品的差额多大？」——这类**数字问答**是 RAG 落地最容易被打脸的场景。模型很会写通顺的中文，但让它做精确数值计算，翻车率奇高：张冠李戴、算错加减、单位混淆、把「亿元」读成「万元」。

原因很简单：RAG 把文档喂给 LLM 让它「读后回答」，而 LLM 本职是语言模型不是计算器。本文讲清楚数字问答为什么难、以及工程上怎么让 RAG「算得准」。

## 一、数字问答的三类翻车

- **检索漏数**：表格里 20 行数据，召回只取了 top-3 片段，关键那行没召回，模型只能蒙。
- **计算错误**：召回对了，但「求和 / 占比 / 同比」要算，模型心算能力飘忽，10 个数加起来能错。
- **单位 / 口径错**：文档写「营收 12.3 亿元」，模型答「12.3 万」，或把「累计」当「单季」。

核心矛盾：**精确数值需要精确处理，而 LLM 是概率生成**。把计算和事实提取完全押在模型身上，等于把算账交给一个会写诗但不太会算账的实习生。

## 二、解法一：把表格抽出来，交给程序算

最稳的思路——**别让 LLM 算，让代码算**。RAG 检索到含表格的文档后，把表格结构化抽取成 DataFrame / 二维数组，数值计算用 Python / SQL 做，LLM 只负责「理解问题 + 描述结果」。

```
流程：
1. 检索召回含目标表格的文档
2. 用表格解析（camelot / tabula / 多模态模型）把表格转成结构化数据
3. LLM 把用户问题翻译成计算指令（如 "SUM(col=营收, row=Q3)")
4. 程序执行计算，返回精确结果
5. LLM 用自然语言组织答案，并附原始数据
```

这一步的关键是**第 3 步的「问题→计算指令」映射**：可以用 function calling / 工具调用，让模型输出结构化查询（选哪些列、什么聚合、什么过滤），再由确定性代码执行。模型只做它擅长的「语义理解」，计算交给确定性引擎。

## 三、解法二：程序化断言校验

即使让 LLM 直接答，也要加一道**数值校验**：答案里的每个关键数字，回文档里核一遍，或者让模型「先列算式再给结果」，然后用代码验证算式结果是否和模型给的一致。

```python
# 模型输出: "Q3 营收 = 12.3 亿元"
# 校验: 从文档抽取 Q3 营收原始值，比对是否一致
extracted = extract_number(doc, "Q3 营收")   # 12.3 亿
assert abs(extracted - model_said) < epsilon
```

不一致就触发重生成或标红提醒。这类「生成 + 验证」闭环，能把数值错误率压下一个数量级。

## 四、解法三：Text-to-SQL 做结构化问答

如果数据本来就在数据库 / 数仓里（而不是散落在文档），最优解是**Text-to-SQL**：用户问自然语言，模型生成 SQL，执行后返回精确结果。这比从文档里抠数字靠谱得多——数据库是确定性的真相源。

适用边界：数据结构化程度高、能建表建字段的场景。如果数据只在 PDF 里，得先 ETL 进库，成本更高，这时用解法一。

## 五、检索侧也要为数字优化

数字问答对检索有特殊要求：

- **表格片段整段召回**：别把表格拆成碎片，一行行召回会丢上下文。表格作为整体单元召回，或至少保证「表头 + 完整行」一起回来。
- **保留单位与口径**：召回片段里必须带单位（亿元 / 万台）、时间维度（Q3 / 累计），否则模型算对也答错。
- **数值型元数据索引**：对文档里的关键指标建结构化索引（指标名 → 值 → 单位 → 时间），检索时直接命中，不必依赖模型从文本里抠。

## 六、怎么评测数字问答

数字问答的评测必须**精确匹配**，不能靠「语义相似」：

- **数值精确率**：答案里的数字，和真值偏差在容差内算对（考虑单位统一后的比对）。
- **单位正确率**：单位 / 口径错了，数值再对也判错。
- **计算正确率**：多步计算题，分步验证中间结果。

构造评测集时，故意混入口径陷阱（「累计 vs 单季」「万元 vs 亿元」），看系统能不能稳住。

## 小结

数字问答的本质矛盾是「LLM 概率生成 vs 数值确定计算」。解法就一句话：**让 LLM 理解语义、让确定性程序做计算**。要么表格抽出来用代码算 + 断言校验，要么数据进库走 Text-to-SQL。检索侧保证表格整段召回、单位不丢。把计算和事实提取从模型肩上卸下来，RAG 才算真正「算得准」。
