# 评测驱动开发（EDD）：把"感觉变好了"变成"分数涨了"

TDD 改变了传统软件的写法：先写测试，再写实现，红灯绿灯间保持系统永远可交付。LLM 应用能不能照方抓药？能，但要变形——**评测驱动开发（Eval-Driven Development）**。这篇文章讲 EDD 的完整工作流：评测先行怎么落地、红绿灯怎么定义、日常迭代里评测集怎么维护。这是我们这个系列工程篇章的收官方法。

## 为什么 EDD 对 LLM 应用更重要

传统代码的失败是显式的：跑不过测试就是错的，黑白分明。LLM 应用的失败是渐进的、隐蔽的：

- 你改了系统提示词想提升回答简洁度，三天后发现工具调用成功率悄悄掉了 5%。
- 升级了 embedding 模型，主打场景好了，一个小语种场景烂了，而它根本不在你的 demo 清单里。
- 换了个检索策略，demo 上效果拔群，线上一个老知识点的召回没了。

没有评测的 LLM 迭代，本质上是"用新 bug 换旧 bug"的轮盘赌。EDD 做的事：**给每次改动一个客观的、可量化的裁决**。传统 TDD 防"功能被改坏"，EDD 防"质量被改坏"——在 LLM 系统里，后者才是主要风险。

## EDD 工作流：五个环节

```
  ①定义指标      ②收集/扩充评测集       ③写基线
  (本次改动要提升什么) (真实 case 驱动)   (当前系统得分)
       │                │                   │
       ▼                ▼                   ▼
  ┌─────────────────────────────────────────────────┐
  │  ④ 迭代循环：改 → 跑评测 → 对比基线 → 留下/回滚  │
  └─────────────────────────────────────────────────┘
                        │
                        ▼
        ⑤ CI 门禁 + 线上回流（闭环回到 ②）
```

### ① 定义指标：改动前先说清楚赌什么

每次改动前（prompt 改动、模型升级、检索参数调整），写一句话：**"我希望 X 指标上升，且其他指标不降"**。没有这句话的改动不许进分支。这句话同时是验收标准——两周后复盘，你至少知道自己赌赢了没有。

常见指标对：准确率 vs 延迟；tool_call 成功率 vs token 成本；引用忠实度 vs 回答长度。**明确这次赌哪头**，是 EDD 和"瞎调"的第一道分水岭。

### ② 评测集：EDD 的"测试用例"

前文 LangSmith 篇讲过怎么攒，这里讲 EDD 视角的维护纪律：

- **真实 case 驱动**。每一个线上 badcase 都是一个高价值测试用例——它天然带"当前系统会失败"的属性。测试集的意义一半在防止未来的你破坏它。
- **分层**：冒烟集（20 条，秒级跑完，每次提交都跑）、标准集（100~200 条，PR 跑）、深度集（500+，夜间跑）。跟传统测试金字塔同理——LLM 评测贵，分层是刚需。
- **标注与版本化**。每条 case 的参考答案/要点清单定期复核，防止"标准过期"。case 集本身走 git 版本管理，PR 里 case 的变更也要 review——**往评测集里加一条掩盖 bug 的 case 是最隐蔽的作弊**。

### ③ 基线：没有基线就没有对比

改动前，在当前系统上跑一遍评测集，记录分数作为基线。没有基线的"跑分"毫无意义——0.85 是好是坏，只有和上一次比才知道。基线记录三要素：分数、评测集版本、系统配置（prompt hash、模型版本、检索参数）。这三样对不上号的对比都是自欺欺人。

### ④ 迭代循环：红绿灯纪律

```
┌─────────┐     ┌─────────┐     ┌──────────┐
│ 红：指标下降 │ ──▶ │ 分析失败 case │ ──▶ │ 修 or 回滚 │
└─────────┘     └─────────┘     └──────────┘
     ▲                                  │
     │            ┌─────────┐           │
     └────────────│ 绿：指标上升 │ ◀───────┘
                  └─────────┘
```

红灯时不许"整体方向是好的，先合了"。LLM 系统的改动没有"整体方向"——每个 case 背后是一个真实用户。红灯时期只有两条路：接着修，或者回滚。允许"已知退化"合入的团队，退化会以复利方式累积，半年后系统烂到没人知道从哪坏的。

分析失败 case 有个高效路径：把失败 case 按**失败环节**聚类（检索没召回 / 理解错意图 / 工具参数错 / 生成跑题），聚类比逐个看快得多。四类失败对应四类修法，别用提示词硬修检索问题——那是用创可贴治骨折。

### ⑤ CI 门禁与回流

CI 里三关：冒烟集必须全绿（有 case 挂了大概率是系统坏了）；标准集主指标不降（相比 main 分支基线）；新代码覆盖率——**新增功能必须先带 case**，没有对应 case 的功能不许合。第三个门是 EDD 从"可选实践"变成"团队纪律"的关键。

线上 badcase 回流管道上一篇客服篇讲过：点踩 → 待标注队列 → 人工标注 → 进评测集。**这套管道是评测集的造血干细胞**，断了它，评测集三个月就变成化石。

## 一个完整循环的实例

把流程跑一遍更有体感。场景：RAG 问答系统，本轮改动是把检索 top_k 从 4 提到 6，赌"召回提升 → 答案准确率提升"。

**① 定义指标**："事实准确率上升 ≥3%，token 成本涨幅 ≤20%"。为什么赌这次：线上抽样发现 15% 的失败 case 是正确答案没进 top4。

**③ 基线**：当前系统跑标准集——准确率 0.72，平均 token 9800，检索命中率 0.81。

**④ 第一轮**：top_k=6 重跑——准确率 0.74（+2），token 涨到 12400（+27%，超预算）。红灯。分析失败 case：没提升的 case 里 60% 是"召回了但排后面被截断"，说明单纯加数量没解决排序问题。

**④ 第二轮**：加 cross-encoder 重排，重排后取 top5——准确率 0.79（+7），token 11800（+21%，还是略超）。继续分析：多余的 token 花在哪？长文档块占了 60%。

**④ 第三轮**：把重排后的文档块摘要化再进上下文——准确率 0.78（+6），token 10200（+4%）。主指标达标、成本接近预算。和第一轮方案对比（准确率 0.74、token 12400），第三轮全面占优——**这就是评测环境下的演化，demo 环境里根本看不出这两条路的差别**。

**⑤ 收尾**：case 集加五条本轮发现的 badcase，CI 门禁更新基线，PR 描述写清"top_k 4→6 + 重排 + 摘要化，准确率 +6%，成本 +4%"。

## EDD 落地的三个阻力及化解

**"写评测集太慢"**。慢在标注参考答案。化解：开放题不写参考答案，写要点清单（rubric）；标准答案能用脚本从系统真实输出里"冻结"的从简；冷启动只写 20 条冒烟，边跑边攒。**先跑起来，再求完美**——空谈质量的团队评测集永远是 0 条。

**"评测跑一次又慢又贵"**。LLM 裁判是主要成本。化解：分层（上面说的）、缓存（同一输入同一系统配置的结果直接复用）、采样（深度集跑 20% 抽样 + 每周全量一次）。

**"分数不动了"**。长期平台期，指标都在 0.85 附近磨。这不是 EDD 失效，是**评测集饱和**——它测不出你的系统现在的问题了。解法：主动构造对抗性 case、按线上分布重新采样、给老 case 加噪声变体。评测集要跟着系统一起成长，停滞的评测集迟早变成一件皇帝的新衣。

## 与传统 TDD 的对照

| 维度 | TDD | EDD |
|---|---|---|
| 测试编写时机 | 实现之前，先红 | 指标与冒烟集先行，case 持续补充 |
| 断言 | 精确相等 | 分数阈值 + 分布不退化 |
| 红灯处理 | 修实现 | 修 or 回滚，不许带病合入 |
| 测试维护 | 需求变了改测试 | 分布漂移了扩测试，防饱和 |
| 核心目标 | 功能正确 | 质量不退化 + 改动可量化 |

## 结语

EDD 不是给 LLM 应用锦上添花的方法论，是把"玄学调优"变成"工程迭代"的唯一通路。指标先行、基线对照、红绿灯纪律、CI 门禁、线上回流，五件事形成闭环，你的每次改动就都站在上一次的肩膀上，而不是在雷区里赌运气。下一篇收个尾，讲 LangGraph Studio——把图和执行变成看得见、点得着的调试体验。
