# 审计日志：出事的时候，你得能回答"它做了什么"

前面几篇我们给系统装了输入护栏、输出护栏，但别忘了：**护栏拦不住所有事，事后追责和复盘全靠日志**。一个 Agent 每天替用户调几十次工具、读几十篇文档、生成几百条回答，出事时老板问"它对那个用户干了什么"——你拿不出记录，比出事本身更被动。这篇文章讲审计日志记什么、怎么记、怎么用。

## 审计日志 vs 应用日志

先厘清概念，两者服务不同对象：

| | 应用日志 | 审计日志 |
|---|---|---|
| 读者 | 开发者 | 安全/合规/事后调查者 |
| 内容 | 调试细节、堆栈、性能指标 | **谁、在什么时间、通过哪个 Agent、做了什么、结果如何** |
| 生命周期 | 天~周级滚动 | 月~年级留存 |
| 修改 | 随便改 | **只追加，不可改、不可删** |
| 触发 | 系统事件 | 安全敏感事件 + 关键业务操作 |

用同一套日志系统并发两者也行，但字段标准不同，别把审计记录混在 `print("debug")` 里。核心区别一句话：应用日志回答"系统好不好"，审计日志回答"系统干了什么、能不能证明"。

## 一次 Agent 交互要记什么

以一次 RAG/Agent 请求为例，一份合格的审计记录长这样：

```json
{
  "trace_id": "req-20261016-a3f9c",
  "ts": "2026-10-16T14:32:11+08:00",
  "actor": {
    "user_id": "u_88213",
    "tenant_id": "t_corp_a",
    "role": "analyst",
    "source_ip": "10.x.x.x",
    "client": "web"
  },
  "agent": {
    "id": "rag-agent-v3",
    "prompt_version": "p-20261012",
    "model": "gpt-4o-mini"
  },
  "action": {
    "type": "tool_call",
    "tool": "send_email",
    "input_digest": "sha256:9f2c...",
    "input_summary": "给 1 位收件人：ops@corp-a.com",
    "confirmed_by_user": true
  },
  "retrieval": {
    "query_summary": "Q3 报销政策",
    "doc_ids": ["doc-118", "doc-233"],
    "top_scores": [0.87, 0.81]
  },
  "result": "success",
  "latency_ms": 4210,
  "cost_tokens": {"prompt": 3120, "completion": 480}
}
```

字段设计的门道在四个地方：

**1. actor 必须带租户和角色**。多租户系统里"是哪个租户的谁干的"是调查起点，缺了租户 ID 的审计日志在出事时基本残废。有外部用户时按合规要求处理 IP、设备指纹。

**2. 输入存摘要而不是全文**。审计日志要长留存，用户问的可能含身份证号、商业数据，原文全存既撑爆存储又制造二次泄露风险。存 SHA256 摘要 + 人工摘要：需要比对时能验一致性，调查时人能看懂。

**3. 每次工具调用单独成条，且带确认状态**。Agent 的核心风险面就是工具——读了什么敏感库、给谁发了邮件、改了什么配置。每次调用一条记录，`confirmed_by_user` 字段区分"Agent 自主发起"和"人工确认后执行"，这是追责时的关键分界。

**4. prompt/model 版本入库**。同一条输入换个模型、换条 prompt，输出可能天差地别。出问题复盘"它为什么这么答"，版本没记下来，复盘只能靠猜。

## 不可篡改性：只追加，外加防拆

审计日志最大的价值在于"上了法庭算数"。所以：

- **只追加存储（append-only）**。用只支持 insert 的库或 WORM（一次写多次读）存储。S3 的 object lock、云厂商的归档桶都提供这个能力。本地最简易方案：按天切分文件 + 内容哈希链——每条记录带上一条的哈希，改中间任何一条都会断链。
- **和业务库物理隔离**。审计日志放独立的库/桶，业务库管理员删不掉它。SQL 注入打穿了业务系统，也摸不到审计侧。
- **时钟同步**。所有节点 NTP 对齐，时间戳是调查的时间轴基础，別自己机器上跑的容器各慢五分钟。

```python
# 哈希链式审计：当日第一条 prev_hash 用日期种子
import hashlib, json, datetime

class AuditChain:
    def __init__(self, day: str):
        self.day = day
        self.prev = hashlib.sha256(day.encode()).hexdigest()

    def append(self, record: dict, sink) -> None:
        record["prev_hash"] = self.prev
        self.prev = hashlib.sha256(
            json.dumps(record, sort_keys=True, ensure_ascii=False).encode()
        ).hexdigest()
        record["hash"] = self.prev
        sink.insert(record)   # 只 insert，不 update/delete
```

## 什么事件必须记

不是所有日志都配叫审计。这几类是底线：

- **所有工具调用**（读了什么、写了什么、发了什么，尤其是高危工具）
- **所有权限相关操作**：用户切换角色、token 刷新失败、越权访问尝试
- **所有护栏命中**：输入侧拦截、输出侧拦截、重生成
- **数据访问**：检索命中了哪些文档、访问了哪些客户的记录
- **管理操作**：prompt 上线、工具增删、限流规则修改
- **异常**：认证失败、限流触发、外部 API 大面积报错

原则：**任何"事后可能需要向人解释"的动作都记**。记多了最多费存储，记漏了没法补。

## 拿日志做什么

审计日志不是写完就吃灰的，三个用法：

**故障复盘**。一次答非所问的客诉，顺着 trace_id 把检索、工具调用、prompt 版本全串起来，十分钟定位是文档过期还是 prompt 跑偏。比"我看看日志"翻半天高效。

**滥用检测**。单用户调用量异常峰值、某租户的检索关键词集中在敏感库、凌晨三点的高频外发动作——审计日志按月跑一次聚合分析，是发现内部滥用的主路径。

**合规交差**。等保、数据安全法、行业合规，问就是"你能说明这个 AI 系统处理了哪些数据、做了什么操作吗"——审计日志就是答案本身。真到被审计那天，有它和没它是两种体验。

## 成本与取舍

审计日志最大争议是"记太细费钱"。实际取舍按三个杠杆调：

- **全文 vs 摘要**：默认摘要，窗口期（近 7 天）可查全文明细，过期只留摘要。
- **采样**：普通工具调用可采样，高危操作（写操作、外发、鉴权）必全记。
- **压缩**：JSON 行 + zstd，通常能吃下 5~10 倍体积。

千万别省的：工具调用记录、actor 身份、时间戳、结果状态。这四样缺一，审计日志就退化成"系统曾经运行过"的证明，而不是"系统做了什么"的证据。

## 结语

输入输出护栏是主动防御，审计日志是被动防御——前者拦在你的系统前面，后者在出事时给你一个说清楚的机会。记什么、怎么存、怎么用，核心就一句话：**让每一个"Agent 替人做过的动作"在事后可追溯、可解释、不可抵赖**。做到这一条，你的 Agent 才真正能进入有治理要求的组织。
