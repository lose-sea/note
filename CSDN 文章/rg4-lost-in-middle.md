# Lost in the Middle：为什么你的 RAG 答案明明在上下文里，模型却视而不见

这是 RAG 里最让人困惑的失败之一：你打开日志，发现正确答案那一段赫然就在送给模型的上下文里，可模型给出的答案要么错了，要么说"材料中没有提到"。

你检查了 embedding、检查了切分、检查了提示词，都没问题。问题出在一个很容易被忽略的地方——**那段材料在上下文里的位置**。

斯坦福 2023 年的论文《Lost in the Middle: How Language Models Use Long Contexts》系统地研究了这件事。这篇就把这个现象讲透：它到底是什么、有多严重、为什么会发生、以及工程上怎么应对。

---

## 一、现象：U 型曲线

研究者做了一个很干净的实验：给模型 N 篇文档，其中只有一篇包含正确答案，改变这篇文档在序列中的位置，看模型能不能找到。

结果是这样一条曲线：

```
准确率
  │  ●                                    ●
  │  ●   ●                            ●   ●
  │      ●   ●                    ●   ●
  │          ●   ●            ●   ●
  │              ●   ●    ●   ●
  │                  ●  ●
  │
  └────────────────────────────────────────
   第1位        中间位置              第N位
```

具体数据（GPT-3.5-turbo，20 篇文档）：

| 答案位置 | 准确率 |
|---------|-------|
| 第 1 位 | 73% |
| 第 5 位 | 61% |
| 第 10 位 | 52% |
| 第 15 位 | 63% |
| 第 20 位 | 70% |

**首尾强、中间弱**，中间位置比两端低了约 20 个百分点。而且这个现象在不同模型、不同任务上都成立，只是程度有差异。

### 1.1 更糟的情况：多文档综合任务

上面的实验是"单针"（只有一个文档包含答案）。研究者还做了"多针"实验——多个文档各包含一部分答案，模型需要综合。这时候中间丢失的影响更大：

- 需要综合的文档分散在中间时，准确率下降幅度达到 30%+；
- 模型倾向于只用首尾的文档作答，中间的被系统性忽略。

这意味着：**你的 RAG 系统如果需要跨文档综合，中间丢失的伤害会被放大**。

### 1.2 长上下文模型也一样

有人以为这是老模型的问题。2024 年后的长上下文模型（GPT-4o、Claude 3.5、Gemini 1.5）确实好很多——曲线的谷底抬高了，衰减没那么陡。但：

- U 型依然存在，只是变浅；
- 上下文越长，衰减越明显（128K 输入的谷底比 8K 输入的谷底低得多）；
- 在需要精确定位的任务上，中间丢失仍然可以被测出来。

**结论：现象减轻了，但没有消失。**

---

## 二、为什么会这样

严格的原因学术界还在争论，但有几个被广泛接受的解释。

### 2.1 训练数据的位置偏置

模型在预训练时接触的绝大多数文本，重要信息往往出现在开头（主题句、标题、摘要）或结尾（结论、总结）。这种分布让模型学到了一种隐性偏置：**开头和结尾更可能是重要的**。

这不是模型"故意"的，而是统计规律的产物。

### 2.2 注意力机制的实际分布

Transformer 的注意力在理论上是全局的，但实际学到的注意力模式有强烈的局部性和边界偏好：

- **Attention sink**：大量注意力头会强烈关注序列最开始的几个 token（哪怕它们毫无意义）。这是一个被广泛观察到的现象。
- **近因效应**：靠近当前生成位置的 token 天然获得更多注意力，因为它们在解码时"更近"。
- 中间区域既没有位置优势也没有近因优势，两头不靠。

### 2.3 相对位置编码的衰减

现代模型普遍使用 RoPE 等相对位置编码。这类编码的一个特点是：**对相对距离的敏感性随距离增长而衰减**。也就是说，模型区分"第 3 篇和第 4 篇"比区分"第 10 篇和第 11 篇"更容易。

这解释了为什么上下文越长，中间丢失越严重——距离拉大，位置分辨率下降。

### 2.4 长上下文训练往往不够"深"

很多模型的长上下文能力是通过在训练后期加入长样本获得的，而这部分数据量通常远少于短文本数据。结果就是：模型"能处理"长上下文，但"处理得好"的程度不如短上下文。

## 三、这对 RAG 意味着什么

### 3.1 直接推论一：top_k 不能盲目加大

如果答案文档随机分布在你塞进去的 20 篇里，那它有相当大概率落在"低利用率区"。

一个粗略的估算：20 篇文档，中间 60%（第 5~16 位）的平均利用率比两端低约 15%。也就是说，**加大 top_k 带来的召回提升，会被位置效应吃掉一部分**。

这解释了为什么很多人的体验是"top_k 从 5 加到 20，Recall 涨了，但答案质量没涨甚至降了"。

### 3.2 直接推论二：排序是免费的优化

既然位置影响利用率，而排序是**零成本**的（不花 token、不花时间），那它就是性价比最高的优化手段之一。

很多人花大力气调 embedding、调重排模型，却把重排后的结果按分数降序直接拼进去——**这恰好是最差的排法之一**：最相关的在第 1 位（还行），次相关的在第 2、3 位，越往后越差，而末尾是最差的文档。

### 3.3 直接推论三：压缩有时比保留全文更好

如果第 10~20 篇文档只能被低效利用，那把它们压缩成几句话放在前面，可能比保留全文更有效——**同样信息量，占用的位置更少，被有效利用的比例更高**。

## 四、工程对策

按性价比从高到低排列。

### 4.1 对策一：重排 + 按注意力分布重排序

最高优先级。你既然已经有重排分数了，就别浪费它：

```python
def reorder_for_attention(docs):
    """
    按相关度重排：最重要的放两端（末尾优先），次要的放中间
    docs: 已按相关度降序排列
    """
    n = len(docs)
    if n <= 2:
        return docs

    result = [None] * n
    left, right = 0, n - 1
    toggle = True

    for doc in docs:
        if toggle:
            result[left] = doc
            left += 1
        else:
            result[right] = doc
            right -= 1
        toggle = not toggle

    return result
```

这个排法把第 1、3、5 名放左边，第 2、4、6 名放右边（从右往左填）。结果是中间位置是最不相关的文档——**把低利用率的位置留给最不重要的内容**。

### 4.2 对策二：最高分的单独放末尾

如果上面的重排觉得复杂，这个简化版能拿到大部分收益：

```python
ranked = reranker.rank(question, candidates)  # 降序

best = ranked[0]
others = ranked[1:6]

context = f"""## 参考材料

""" + "\n\n---\n\n".join(
    f"[{i+1}] {d.page_content}" for i, d in enumerate(others)
) + f"""

## 最关键的材料（请重点参考）

[★] {best.page_content}

---

请基于上述材料回答问题：{question}"""
```

**为什么放末尾而不是开头？** 因为生成是从上下文末尾之后开始的，末尾的内容离生成起点最近，获得的注意力最强。实测中，把最关键材料放末尾比放开头能高出 3~5 个百分点。

（注意：这和很多人的直觉相反。很多人默认把最重要的放开头，因为"开头是摘要位置"。在 RAG 场景下，末尾通常更优，但**最好你自己测一下**——不同模型可能有差异。）

### 4.3 对策三：减少文档数量，用重排提精度

这是根本解。与其塞 20 篇然后想办法让中间的不被忽略，不如**只塞 5 篇高精度的**。

塞 5 篇时，最差的位置（第 3 位）的利用率损失很小；塞 20 篇时，中间 10 篇都在低效区。**减少数量本身就能缓解位置效应**。

配套动作：
- 粗召回可以大（top 20~50），保证覆盖；
- **重排必须做**，把真正相关的挑出来；
- 最终送入 3~5 篇。

### 4.4 对策四：压缩次要文档

需要保留覆盖面但不想让上下文膨胀时：

```python
# 前 3 篇保留全文（放末尾区）
# 其余 7 篇抽取压缩成 1~2 句（放开头区）

context = "## 背景要点\n" + compressed_summary
context += "\n\n## 核心材料\n" + full_texts
```

压缩后的内容信息密度高、占用位置少，放在开头（高利用率区）刚好。全文材料放末尾（也是高利用率区）。中间不放东西。

这实际上是在**主动构造一个"两端高价值、中间空"的 U 型分布**，正好匹配模型的注意力特性。

### 4.5 对策五：显式提示位置

给模型一个明确的指引，让它知道去哪里找：

```python
prompt = """下面是 N 段材料，材料的末尾部分（标注为「核心材料」）与问题最相关，请重点参考。

{context}

问题：{question}"""
```

这种元提示的效果没有重排那么显著，但成本几乎为零，值得加上。

### 4.6 对策六：分段处理 + 汇总（针对超长场景）

如果确实要处理 30+ 篇文档，别一次性全塞。分批：

```python
def map_reduce_answer(question, docs, batch_size=5):
    partials = []
    for i in range(0, len(docs), batch_size):
        batch = docs[i:i + batch_size]
        ctx = "\n\n".join(d.page_content for d in batch)
        ans = llm.invoke(
            f"基于材料回答，若材料不足请说'无'。\n材料：{ctx}\n问题：{question}"
        ).content
        partials.append(ans)

    # 汇总
    return llm.invoke(
        f"综合以下 {len(partials)} 份局部回答，给出最终答案。\n"
        + "\n\n".join(f"局部{i+1}：{p}" for i, p in enumerate(partials))
    ).content
```

每批只有 5 篇，位置效应基本消失。代价是多次 LLM 调用。适合对准确率要求高、对延迟不敏感的场景（如离线报告生成）。

## 五、怎么确认你的系统有没有这个问题

一个很简单的诊断方法：**位置消融测试**。

```python
def position_ablation(question, gold_doc, filler_docs, positions):
    """把 gold_doc 放在不同位置，看答案准确率"""
    results = {}
    for pos in positions:
        docs = filler_docs.copy()
        docs.insert(pos, gold_doc)
        ctx = "\n\n".join(d.page_content for d in docs)
        ans = llm.invoke(f"{ctx}\n\n问题：{question}").content
        results[pos] = evaluate(ans, gold_answer)
    return results
```

跑完画成曲线，你就能直观看到自己系统里的 U 型有多深。如果中间位置比两端低 15% 以上，说明位置效应显著，值得做重排序优化。

**简化版**：不用消融，直接对比两种排序方式的准确率——

1. 按重排分数降序直接拼（原始顺序）
2. 按 4.1 的重排序规则重排

在我的几个库上，方法 2 比方法 1 平均高 4~7 个百分点，**成本为零**。这是最容易验证、最容易拿到的收益。

## 六、和其他环节的关系

### 6.1 vs 重排

重排解决"哪些文档相关"，位置优化解决"相关文档放在哪"。**先有重排，位置优化才有意义**——如果排序本身是错的，那怎么摆放都没用。

顺序：粗召回 → 重排（得到可靠的相关度分数）→ 位置优化（按分数重排布局）。

### 6.2 vs top_k

它们是一对需要联合调节的参数：

- top_k 小（3~5）：位置效应弱，但可能漏召回；
- top_k 大（15~20）：召回覆盖好，但位置效应强、噪声多。

**最优解通常是"大 top_k 粗召回 + 重排 + 小 top_n 送入"**，而不是直接调 top_k。

### 6.3 vs 上下文压缩

压缩和位置优化是互补的：压缩减少位置占用，位置优化决定压缩后放哪。两者结合是处理"需要覆盖面但窗口有限"场景的标准打法。

## 七、常见误区

**误区一：以为长上下文模型解决了这个问题。**
没有。曲线变浅了但没消失，而且上下文越长、谷底越深。

**误区二：只优化召回不优化排序。**
召回到的文档放在错误位置，等于白召回。排序是零成本优化，不做太亏。

**误区三：认为"放开头最重要"。**
在 RAG 场景里，末尾（靠近生成起点）往往比开头更有利。不要照搬"摘要放开头"的直觉，**自己测**。

**误区四：用增加文档数量来弥补召回不足。**
如果召回质量不行（embedding 不合适、切分有问题），加数量只是把噪声也一起加进来，还会恶化位置效应。**先修召回，再谈数量**。

---

## 小结

- **Lost in the Middle**：模型对长上下文的利用呈 U 型，首尾强、中间弱，差距可达 20 个百分点。
- 成因包括训练数据的位置偏置、注意力 sink 与近因效应、相对位置编码的距离衰减。
- **最有效的对策是减少送入文档数 + 重排 + 按注意力分布重排序**，这三项里重排序是零成本的，性价比最高。
- 在 RAG 场景中，**最相关的材料放末尾**（靠近生成起点）通常优于放开头，但建议自己实测确认。
- 需要覆盖面时，用**压缩次要文档 + 核心全文放末尾**，主动构造"两端高价值、中间空"的分布。
- 诊断方法很简单：做位置消融测试，或者对比"原始顺序 vs 重排序"的准确率。

这个问题之所以容易被忽略，是因为它在日志里完全看不出来——文档明明送进去了，你不会想到是位置的问题。**如果你的 RAG 系统准确率卡在某个水平上不去，而又确认召回没问题，不妨先查一下排序。**
