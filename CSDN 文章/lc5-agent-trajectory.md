# 轨迹分析：用 Trace 复盘 Agent 到底错在哪一步

Agent 答错了，你打开 trace，看到 20 个 span，每个 span 里有 LLM 响应、工具调用、参数 JSON。**然后呢？**

大部分人的复盘停在「哦，它调用了 query_order，参数好像不对」。但真正有价值的问题要多问三层：它是从哪一步开始偏的？为什么选了那个工具？上下文里到底有什么导致它这么选？

**轨迹分析（Trajectory Analysis）就是把「看一眼 trace」变成「定位到根因」的方法。** 这篇讲一套可操作的复盘流程。

---

## 一、为什么 trace 要有专门的分析方法

### 1.1 Agent trace 的特殊性

普通后端的 trace 是线性的：请求 → 中间调用 → 响应。出问题通常是某个节点失败，一看就知道。

Agent 的 trace 是**带决策的分支结构**：

```
用户输入
 ├─ LLM 响应1: "我需要查订单" → tool_call(query_order, {...})
 ├─ 工具返回: {...}
 ├─ LLM 响应2: "没找到，换个关键词" → tool_call(search_orders, {...})
 ├─ 工具返回: {...}
 ├─ LLM 响应3: "还是不对，试试直接查数据库" → tool_call(query_db, {SQL})
 └─ ...最终答案
```

每一轮都是「模型看了上下文 → 做了个决定」。**错误可能发生在任何一个决定点，而且会向后传播。** 第 3 步选错工具，第 8 步看起来的「幻觉」其实是第 3 步的果。

### 1.2 只看最终输出的盲区

同一个错误答案，可能有完全不同的根因：

| 现象 | 根因 A | 根因 B |
|------|-------|-------|
| 答非所问 | 第 2 步就没理解任务 | 前面都对了，最后生成跑偏 |
| 参数错误 | 工具描述没写清约束 | 上下文里有矛盾的示例 |
| 工具循环 | 参数一直不对，不知道该改 | 没有终止判断 |

**不 trace 就无法区分。** 而修复方式完全不同：A 要改提示词，B 要改工具描述或参数校验。

## 二、复盘四问法

拿到一条失败轨迹，按顺序问四个问题。这套流程是我复盘几百条轨迹浓缩出来的。

### 2.1 第一问：任务在哪一步开始偏的？

**从后往前找「第一个错误决策」。**

```python
def find_first_error(trajectory, expected_plan) -> dict:
    """对比实际轨迹和期望路径，找最早的分歧点。"""
    for i, step in enumerate(trajectory):
        expected = expected_plan[i] if i < len(expected_plan) else None
        if expected and step.deviates_from(expected):
            return {
                "step": i,
                "actual": step.action,
                "expected": expected.action,
                "divergence_type": classify_deviation(step, expected),
            }
    return {"step": None, "note": "轨迹与预期一致，问题可能在最终生成"}
```

**为什么要从后往前、找「第一个」**：因为错误会传播。第 6 步的胡言乱语，可能是第 2 步就种下的。修最后一个错误点是治标。

**实操**：拿日志里同一批成功案例的轨迹做对比。成功案例在第 2 步做了什么，失败案例做了什么？**差异就是分歧点。**

### 2.2 第二问：这一步的决策依据是什么？

定位到分歧的那一步后，**必须看它当时的完整上下文**——不是现在的上下文，是**做出那个决定时模型看到的内容**。

```python
def decision_context(trajectory, step_index) -> dict:
    """还原某个 step 决策时模型的输入。"""
    step = trajectory[step_index]
    return {
        "system_prompt": step.system_prompt,
        "messages": trajectory[:step_index],       # 它之前看到的所有内容
        "tools_available": step.tools,
        "llm_raw_output": step.raw_response,       # 完整原文，含 reasoning
        "model_config": step.model_config,
    }
```

**必须存 raw_response**。只存「调用了 query_order」不足以复盘——模型可能有一段内心独白解释它为什么这么选，那段话往往就是根因所在。

### 2.3 第三问：上下文里有什么误导了它？

这是最花时间但最有价值的一问。在决策上下文里找四类「嫌疑物」：

**嫌疑一：矛盾信息**

```
前面工具返回: "订单 ORD-123 状态：已取消"
后面用户补充: "这个订单我已经重新激活了"
模型上下文里两者并存，没有明确谁更新 → 模型可能用旧的
```

**对策**：时间戳 + 「以上一条为准」的显式标记。

**嫌疑二：过长的无关内容**

上下文里 3000 token 的工具输出，模型只用到其中两行。剩下的都在稀释注意力。

**对策**：压缩工具输出，只留相关部分（见我的「上下文窗口」那篇）。

**嫌疑三：工具的相似描述**

```
search_orders(keyword)     - 搜索订单
query_order(order_id)      - 按 ID 查订单
get_order_info(...)        - 查订单详情
```

模型在这三个之间犹豫，描述没写清边界，它就会选错。

**对策**：改写工具描述，加交叉引用（见「工具描述的写法」那篇）。

**嫌疑四：历史错误的残留**

```
第 3 步工具报错: "参数 order_id 格式不正确"
第 5 步模型: 还是用错了格式（没从上一条错误里学到）
```

**对策**：错误消息要写成模型能理解的（「应该是 ORD- 开头 + 8 位数字，你传了 xxx」），而不是只返回「格式错误」。

### 2.4 第四问：这个根因能推广吗？

单个案例修完不算完，要问：**同类问题还会在哪里出现？**

```python
def generalize(trajectory_failure) -> list[str]:
    """从单条失败提炼出可回归的测试点。"""
    root_cause = trajectory_failure["root_cause"]
    if root_cause["type"] == "tool_ambiguity":
        return [f"测试所有涉及 {root_cause['tools']} 的查询"]
    if root_cause["type"] == "context_conflict":
        return ["测试所有涉及该实体被多次更新的任务"]
    ...
```

**把每个根因变成一条回归测试**，加进评测集。否则这个 bug 会在下一个版本悄悄回来。

## 三、可视化的轨迹视图

人眼看 20 个 span 的 JSON 很痛苦。做三个简化视图能大幅提升复盘效率。

### 3.1 决策点视图

只显示「模型做了什么决定」，隐藏工具返回细节：

```
步骤   决策                              输入(压缩)          结果
1      tool_call query_order(order_id)  "查订单状态"         ✓ 成功
2      tool_call search_orders(kw)      "订单没找到，搜搜"   ✓ 空结果
3      tool_call query_db(SQL)          "直接查库"           ✗ SQL 语法错
4      (放弃) answer                     "算了直接说找不到"    ✗ 幻觉
```

**一眼能看到：第 3 步是分水岭。** 前两步合理，第 3 步开始瞎搞，第 4 步基于错误状态给了答案。

### 3.2 时间线视图

```
t=0.0s    用户输入
t=0.2s    LLM #1  (1.9k tokens, 2.1s)
t=2.3s    tool query_order  ✓ (0.4s)
t=2.7s    LLM #2  (3.4k tokens, 3.8s)     ← 上下文在涨
t=6.5s    tool search_orders ✓ (0.3s)
t=6.8s    LLM #3  (6.1k tokens, 7.2s)     ← 更慢了
...
```

**上下文单调上涨 + 延迟上升**，说明任务在「重复付上下文的钱」。这种任务要么压缩，要么拆子任务。

### 3.3 上下文增长视图

```
步骤   上下文token   新增内容                    利用率
1      2000         系统提示+用户问题              高
2      2900         工具返回(订单JSON)             低(用了2行)
3      4200         工具返回(搜索结果30条)          极低
...
15     18000        累计                           —
```

**利用率低 + 持续增长 = 上下文污染的典型形态。** 这是「为什么这个 Agent 又慢又贵」的直接答案。

## 四、常见失败模式与对应根因

复盘多了，会发现失败高度集中在几类。这张表是我的速查表：

| 现象 | 常见根因 | 验证方法 | 修复 |
|------|---------|---------|------|
| 选错工具 | 工具描述相似、无交叉引用 | 看决策时的 tools 列表 | 重写描述，加「该用X」 |
| 参数错 | schema 没写约束/示例 | 看 raw_response 里它怎么理解的 | 补枚举值、单位、示例 |
| 工具死循环 | 同样的调用反复出现 | 数重复 step | 加步数上限 + 错误反馈 |
| 幻觉 | 上下文缺关键信息 | 看生成时的完整 messages | 补检索 or 改拒答机制 |
| 步骤爆炸 | 无效步数多 | 看时间线的无效步 | 拆子任务 / 压缩上下文 |
| 答案对但绕路 | 早期走了弯路 | 对比成功案例轨迹 | 优化提示词的任务分解 |
| 前半对后半错 | 上下文污染 | 看上下文增长视图 | 压缩 / 分段处理 |

**先用这张表定位到根因类别，再针对性深挖。** 比每条 trace 从零分析快得多。

## 五、把复盘变成流程

### 5.1 失败案例的收集

```python
# 自动收集：每次任务失败/评分低，落库
def persist_failure(task, trajectory, score):
    failures.insert({
        "task": task,
        "trajectory": compress(trajectory),   # 压缩存储
        "score": score,
        "root_cause": None,                  # 人工分析后填
        "analyzed": False,
        "created_at": now(),
    })
```

### 5.2 每周复盘会

固定节奏：每周抽 10 条最差的失败案例，人工过一遍，填 root_cause。**这一步不能省**——自动化只能发现「失败了」，定位「为什么」目前还得靠人。

### 5.3 根因的归类统计

```python
# 每周看一次根因分布
causes = Counter(f["root_cause"] for f in unanalyzed_now_analyzed)
# {'tool_ambiguity': 4, 'context_conflict': 3, 'missing_retrieval': 2, ...}
```

**连续两周同一个根因占大头，就该立项修它**，而不是继续加新功能。

### 5.4 回归

每个根因 → 一条测试用例 → 进评测集。这样「轨迹分析」的价值才能沉淀下来，而不是每次复盘完就忘。

## 六、常见误区

**误区一：只看最终输出，不看过程。** 同一个错误答案根因不同，修复方向完全不同。

**误区二：修最后一个错误点。** 错误会传播，要找**第一个**分歧点。拿成功案例的轨迹做对比是最快的定位方法。

**误区三：复盘不看当时的上下文。** 「它为什么这么做」的答案全在决策时的输入里。而且**必须存 raw_response**——模型的内心独言往往是根因。

**误区四：一次只分析一条 trace。** 批量对比成功/失败轨迹的差异，比单条深挖更能看出系统性问题。

**误区五：没有上下文增长视图。** 「又慢又贵」的 Agent，看一眼这个图就知道了——通常是工具输出没压缩。

**误区六：复盘完就结束。** 每个根因都要变成回归测试，否则一定会复发。

---

## 小结

- Agent 的错误会**传播**，所以定位要找**第一个分歧点**，不是最后一个错误表现。最快的方法是拿成功案例的轨迹对比。
- **四问法**：①第一步什么时候偏的 ②那一步的决策依据是什么（必须是决策当时的完整上下文）③上下文里有什么误导了它（矛盾信息/过长无关内容/相似工具描述/历史错误残留）④根因能否推广成回归测试。
- 三个视图大幅提效：**决策点视图**（一眼看分水岭）、**时间线视图**（看上下文是否在涨、延迟是否在升）、**上下文增长视图**（看利用率，回答「为什么又慢又贵」）。
- 失败模式高度集中，用速查表先归类再深挖：选错工具→描述问题，参数错→schema 问题，幻觉→上下文缺信息，步骤爆炸→流程问题。
- **必须存 raw_response**——模型解释自己为什么这么选的那段话，往往是根因所在。
- 复盘要成流程：自动收集失败 → 每周人工定位 10 条 → 根因归类统计 → **每个根因变一条回归测试**。

Trace 不是为了「出事之后有据可查」，它是 Agent 迭代的主要信息来源。**会读 trace 的团队，Agent 每週都在变好；不会读的，每次改动都是碰运气。**
