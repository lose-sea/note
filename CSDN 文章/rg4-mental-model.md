# 建立 RAG 的正确心智模型：它不是"把文档喂给模型"

> 很多人的第一印象是：
> "RAG 就是把我的一堆文档丢给大模型，然后它就能回答关于这些文档的问题了。"
>
> 这个印象**在结果上是对的，在机制上完全错了**。
> 机制理解错了，后面所有的调优都会走偏。

## 一、常见但错误的三个心智模型

**❌ 模型一：RAG 是"把知识装进模型"**

以为文档会"变成模型的记忆"。**不是。**模型本身没有任何改变——它只是在生成时看到了相关片段。

**❌ 模型二：RAG 是"先检索再生成"的两步流程**

技术上没错，但过于简化。真正的流程是：

```
切分 → 向量化 → 存储 → （查询改写）→ 检索 → （重排）→ 组装上下文 → 生成 → （校验）
```

**每一步都可能成为瓶颈。**

**❌ 模型三：RAG 的瓶颈是模型不够强**

换更强的模型确实能提升，但**RAG 的瓶颈通常不在生成端，而在检索端**——检索错了，再强的模型也只能基于错内容回答。

## 二、正确的心智模型：开卷考试

把 RAG 想成**开卷考试**：

| 考试环节 | RAG 对应 | 谁负责 |
|---|---|---|
| 教材怎么编 | 文档切分 | 你 |
| 教材怎么索引 | 向量化 + 存储 | 你 |
| 看到题目，去哪找 | 检索策略 | 你 |
| 找出来的那几页对不对 | 召回质量 | 你 |
| 拿到资料后怎么写答案 | 生成 | 模型 |

**关键洞察：除了最后一步，其余全是你的活。**

## 三、用这个模型解释四个真实故障

**故障一：检索到的完全不对**

```
现象：问"退款流程"，检索到"会员积分规则"
原因：教材索引有问题（embedding 不适合该领域，或分块太碎）
责任：你的检索层
```

**故障二：检索对了，但答案不完整**

```
现象：检索到了退款流程的前两步，第三、四步没检索到
原因：一个完整的流程被切成了 4 块，只召回了 2 块
责任：你的分块策略
```

**故障三：答案里出现了文档中没有的信息**

```
现象：文档只说"7 个工作日内"，模型说"3-5 个工作日"
原因：模型的先验知识盖过了检索内容
责任：提示词约束（要明确"只依据资料回答"）
```

**故障四：文档里有，但模型说"没找到"**

```
现象：文档第 3 页明确写了，模型却说"资料中没有相关信息"
原因：那条信息被切碎了，或者排在了上下文中间（Lost in the Middle）
责任：分块 + 上下文排序
```

**四个故障里，三个在检索侧。** 这就是为什么"优化 RAG"的功夫主要在检索。

## 四、RAG 的三个本质权衡

**权衡一：召回 vs 精度**

```
多召回几篇 → 答案完整，但引入噪声、成本高
少召回几篇 → 上下文干净，但可能漏掉关键信息
```

**没有最优解，只有适合场景的解。**

**权衡二：块大 vs 块小**

```
块大 → 上下文完整，但检索粒度粗（一篇里只有一句相关，也要整块塞进去）
块小 → 检索精准，但容易丢上下文（"他"指代的是谁？）
```

**权衡三：延迟 vs 质量**

```
快 → 直接向量检索，返回即用
慢 → 加查询改写、多路召回、重排、校验
```

**这三个权衡贯穿 RAG 的所有调优决策。**

```
                    └──────┬──────┘
                           ▼
                    ┌─────────────┐

                    └──────┬──────┘

                    └──────┬──────┘

                    │  向量库     │ ← 索引类型、距离度量
                    └─────────────┘

                    └──────┬──────┘

                    └──────┬──────┘
                           ▼
                    ┌─────────────┐

                    └──────┬──────┘
                           ▼
                    ┌─────────────┐
                    │   重排      │ ← 交叉编码器
                    └──────┬──────┘

                    ┌─────────────┐

                    └──────┬──────┘

```

**离线 3 步，在线 6 步，共 9 个环节。** 每个环节都有优化空间，也都有踩坑可能。

## 六、排错应该从哪开始

**从后往前排，从最简单的开始。**

```
① 先看检索到的内容对不对        ← 80% 的问题在这
② 再看拼进上下文的顺序           ← 10% 在这
③ 最后才改提示词和换模型         ← 只有 10% 在这
```

具体做法：

**第一步：打印检索结果**

```python
docs = retriever.invoke(question)
for i, d in enumerate(docs, 1):
    print(f"[{i}] score={d.metadata.get('score', '-')}")
    print(d.page_content[:200])
    print("-" * 50)
```

**如果检索结果里有正确答案** → 问题在生成侧（提示词/模型）。
**如果检索结果里没有** → 问题在检索侧（分块/embedding/查询）。

这一步能筛掉 80% 的无效调优——**很多人一上来就换模型、改提示词，其实问题是检索根本没找到**。

**第二步：检查分块**

```python
for i, chunk in enumerate(chunks[:5]):
    print(f"--- 块 {i}（{len(chunk)} 字）---")
    print(chunk)
```

看有没有"半句话"、"孤立的标题"、"表格被切碎"。

**第三步：检查上下文拼装**

打印最终发给模型的完整 prompt（包括检索内容），看它实际长什么样。

## 七、四个最常见的认知误区

**误区一："用更好的 embedding 模型就能解决一切"**

embedding 只决定"语义相似度能不能算准"。如果分块本身有问题（一块里混了三个主题），再好的 embedding 也救不回来。

**误区二："块越小检索越准"**

块小确实让"每块只讲一件事"，但**检索到的块如果缺少上下文，模型理解不了**。比如块内容是"这个流程需要 3 个工作日"，没有上文"哪个流程"。

**正确做法是"小块检索，大块提供上下文"**（ParentDocumentRetriever 的思路）。

**误区三："RAG 能解决模型的幻觉"**

RAG 能**减轻**幻觉，但**不能消除**。模型依然可能：
- 把检索内容"合理化"成错误的表述
- 混入自己的先验知识
- 在资料不全时"补全"缺失部分

**误区四："文档越多效果越好"**

文档多不等于效果好。**质量差的文档（过时、矛盾、格式混乱）会主动降低效果**——检索到它，模型就会基于错误内容回答。

## 八、一个可操作的检查清单

每次 RAG 效果不好时，按这个顺序过一遍：

```
□ 检索结果里有没有正确答案？
   ├─ 没有 → 走检索侧排查
   │   □ 分块是否完整（有没有半句话/孤块）
   │   □ 块大小是否合适（试试调大/调小）
   │   □ embedding 是否适合该领域
   │   □ 查询是否需要改写
   │   □ 是否需要混合检索（向量 + 关键词）
   └─ 有 → 走生成侧排查
       □ 提示词有没有说"只依据资料回答"
       □ 检索内容在上下文里的位置（放开头/结尾）
       □ 检索内容是否太长（噪声）
       □ 是否需要重排（把最相关的放最前）
```

## 九、小结

**RAG 的正确心智模型：开卷考试。**

```
教材怎么编    → 你的分块策略
教材怎么索引  → 你的向量化
去哪找        → 你的检索策略
找得对不对    → 你的召回质量
怎么写答案    → 模型
```

三条核心认知：

1. **瓶颈通常在检索侧，不在生成侧**——先修检索，再改提示词；
2. **RAG 有九个环节，每个都是潜在故障点**——排错要成体系，别乱试；
3. **RAG 是三个权衡的艺术**（召回/精度、块大/块小、延迟/质量）——没有最优配置，只有适合场景的配置。

**建立正确的心智模型，比记住十个技巧更重要。** 因为模型错了，技巧用在哪里都是错的。
