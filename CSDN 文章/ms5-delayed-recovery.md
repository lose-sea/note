# 延迟从库：一个专门"慢半拍"的时光机副本

误删了数据，binlog 闪回是急救术，但如果误操作发生在 5 小时前、binlog 已轮转、或者破坏面太大（批量 UPDATE 污染了半个表，连闪回的"原始镜像"都分不清对错）——终极武器是**延迟从库（Delayed Replica）**：一个被刻意配置成"永远比主库慢 N 小时"的从库，误操作发生但还没同步到它，于是它天然保留着事故前的数据。这篇文章讲延迟从库的原理、配置、恢复流程和适用边界。

## 原理：CHANGE REPLICATION SOURCE 的 DELAY

```sql
-- MySQL 8.0.23+ 语法（旧版 CHANGE MASTER TO）
CHANGE REPLICATION SOURCE TO
    SOURCE_HOST = 'master.db',
    SOURCE_USER = 'repl',
    SOURCE_PASSWORD = 'xxx',
    SOURCE_AUTO_POSITION = 1,          -- GTID 模式
    SOURCE_DELAY = 14400;              -- 延迟 4 小时（秒）
START REPLICA;
```

一行 `SOURCE_DELAY = 14400`，MySQL 复制线程内部对每个 event 的执行时间做延迟调度：IO 线程照常实时拉 relay log，SQL 线程按"事件时间 + 4 小时"的节奏应用。**效果：这个从库的数据状态永远停在 4 小时前的主库**。

延迟从库长得和普通从库一样，能读能查（只读），只是数据"旧"。

## 配置要点与代价

**延迟设多久？** 业务发现误操作的平均时间 + 你响应处理的时间，再加安全余量。

| 场景 | 平均发现时间 | 建议延迟 |
|---|---|---|
| 核心交易库，实时监控完善 | 10~30 分钟 | 2~4 小时 |
| 普通业务库 | 数小时 | 6 小时 |
| 后台批处理库 | 隔天 | 24 小时 |

延迟不是越长越好：**延迟从库不能参与 failover（数据旧，提升即丢数据），也不能服务实时查询**。延迟越长，你保留的"时光机"越多，可用副本越少。经验值 4~6 小时覆盖绝大部分误操作窗口。

**拓扑注意**：

- 延迟从库是普通从库的一员，但要在 HA 工具里明确排除。MHA 配 `no_master=1`，Orchestrator 里标记为延迟实例不参与恢复。
- 复制过滤规则要跟其他从库一致（否则它也不是"完整时光机"）。
- **必须开 `super_read_only`**——被误写的延迟从库恢复出来也是脏数据。

**代价清单**：一台机器的成本（可以矮配置，只做应急）、relay log 占用的磁盘（4 小时的事件量通常不大）、以及"它平时完全没用"的运维心理成本——**直到出事那天它是全公司最重要的表**。

## 恢复流程：从时光机捞数据

误操作发生后的标准动作：

```sql
-- 1. 确认延迟从库还没同步到误操作
--    主库 gtid_executed vs 延迟从库 gtid_executed，后者落后 N 小时
SHOW REPLICA STATUS\G   -- 在延迟从库上
-- Relay_Source_Log_File / Exec_Source_Log_Pos 确认位置

-- 2. 快速确认：误操作的痕迹在延迟从库上还没有
SELECT COUNT(*) FROM biz_db.orders;   -- 数量正常 = 时光机可用

-- 3. 导出需要的数据（从延迟从库）
mysqldump --single-transaction --no-tablespaces \
    --where="id IN (受影响范围)" \
    biz_db orders > /tmp/rescue.sql

-- 4. 阻断误操作影响：主库对应表加保护/停写

-- 5. 把时光机数据导回主库（或先导测试库核对）
mysql biz_db < /tmp/rescue.sql

-- 6. 校验 + 恢复业务
```

**和 binlog 闪回的选择逻辑**：闪回是"逆运算"（DELETE 的逆是 INSERT，要求 binlog 完整 + ROW 格式 + 操作明确）；延迟从库是"原始数据照抄"（不要求 binlog、不怕复杂混合操作，只需要它还没同步）。**破坏面模糊、binlog 不全、操作时间久远的场景，延迟从库是最后的底线**。

一个高级用法：**延迟从库 + 表级对比恢复**。误操作污染了一张大表但不知道具体哪些行，用 pt-table-sync 以延迟从库为"正确源"，反向同步回主库——比闪回的行级逆运算更适合"大面积脏数据"场景。

## 什么时候不要指望延迟从库

**场景一：需要 RPO=0 的表**。延迟从库天然落后 N 小时，如果误操作后业务又产生了新数据，恢复时新旧数据怎么合并是业务问题（订单恢复旧数据、支付已是新状态——这类账务不一致不是技术能兜的）。**延迟从库恢复的是"数据切片"，不是"业务一致性"**。

**场景二：发现时间超过延迟窗口**。发现时误操作已同步进延迟从库，时光机失效。所以**发现时间的监控投入比延迟时长本身更重要**——4 小时的延迟配一套"误操作 10 分钟内发现"的监控才是完整方案。

**场景三：大 DDL 误操作**（DROP TABLE、TRUNCATE）。DDL 也走 binlog 复制，延迟从库同样会在 4 小时后同步这个 DROP。窗口内恢复没问题，比 DML 还简单（表还在）；但 DDL binlog 不像 DML 有"行镜像"能闪回，**DDL 事故只有延迟从库 + 备份两条路**。

**场景四：从库本身不可靠**。延迟从库要是挂了三天没人修，出事时它滞后三天但同步链路已断——它的数据停在某个随机位置而不是"整齐的 4 小时前"。**延迟从库的健康监控必须独立告警**：复制状态、延迟水位（应该接近但不等于配置值）、磁盘空间。

## 维护动作

```bash
# 每周巡检
# 1. 复制状态（和普通从库一样）
SHOW REPLICA STATUS\G

# 2. 实际延迟时间（应该 ≈ 配置的 SOURCE_DELAY）
-- 主库 NOW() vs 从库最新一条数据的 created_at

# 3. relay log 清理（大延迟场景下积累）
PURGE RELAY LOGS 不会自动激进清理保持在延迟窗口需要的部分——通常不用管

# 4. 每季度做一次恢复演练
-- 在测试环境用延迟从库的数据验证"恢复出来的数据是完整的"
```

**恢复演练容易被忽略**：延迟从库躺了半年，谁也不知道导出来的数据是不是真的完整、mysqldump 命令在那张大数据表上跑不跑得动、恢复流程里的 where 条件对不对。**没演练过的时光机，和纸糊的差不多**。

## 成本优化：一库多延迟 slave

预算有限时的常见做法：不搞一主一延迟，而是**延迟从库自身级联**——主库 → 实时从库 A（供读）→ 延迟从库 B（SOURCE_DELAY 挂在 A 下）。B 不直连主库，A 的 relay log 就是 B 的原料，A 挂了 B 也能续（配 A 的 `log_slave_updates`）。这避免延迟从库拖垮主库的复制连接，也让拓扑更灵活。代价是多了一跳，故障点多一个。

## 小结

延迟从库 = `CHANGE REPLICATION SOURCE TO SOURCE_DELAY = N` 配出来的时光机副本，核心价值是"误操作的原始数据还没同步到它"。配置三要点：延迟时长覆盖发现时间、HA 工具里排除、super_read_only 锁死。恢复走"停写 → 导出受影响数据 → 导回核对"流程；DDL 和大范围脏数据场景它比闪回更可靠。它是最后一道防线不意味着可以躺平——监控、演练、和 binlog 闪回/备份的配合，才让这道防线真出事时顶得住。下一篇讲 MySQL 账号权限体系与最小权限实践。
