# 多轮 RAG 上下文实战：历史压缩、指代消解与防腐烂

单轮问答的 RAG 是理想状态，真实产品里用户是在对话：先问"合同怎么签"，接着问"那电子签有法律效力吗"，再问"它和纸质的效果有什么不一样"——第三句里的"它"、以及整个话题的隐含背景，都是单轮检索的死穴。多轮 RAG 要处理三件事：**对话历史怎么进检索、指代怎么消解、上下文怎么防止腐烂**。这篇文章按实战顺序展开。

## 一、多轮 RAG 的第一个错误：把历史直接塞检索

天真做法：

```python
# 每轮都把对话历史拼起来当 query
query = "\n".join(history + [current_question])
hits = vs.search(embed(query))
```

三个后果：embedding 模型对长文本的编码质量下降（问题被历史稀释）、相似度被无关历史拉偏（第一轮问 A 第三轮问 B，历史里的 A 污染了 B 的检索）、token 浪费。

**正确思路：历史不直接进检索，先进"查询改写"**——用 LLM 把当前问题结合历史改写成"独立完整的问题"，用改写后的句子去检索。

## 二、核心机制：查询改写（Query Rewriting）

### 2.1 标准做法

```python
def rewrite_query(history, current_question, llm):
    prompt = f"""根据对话历史，把用户的当前问题改写成一个独立完整的问题。
要求：
1. 补全指代（"它"→具体事物，"那个"→具体对象）
2. 保持原有意图，不添加新信息
3. 如果当前问题已完整可独立理解，原样返回
4. 只输出改写后的问题，不要解释

对话历史：
{format_history(history[-4:])}    # 只取最近 4 轮

当前问题：{current_question}"""
    return llm(prompt)

# 实际效果：
# 历史：[合同怎么签 → 需要双方面签] [电子签有法律效力吗 → 有，依据电子签名法]
# 当前："它和纸质的有什么区别？"
# 改写 → "电子签名和纸质签名在法律效力上有什么区别？"
```

注意"只取最近 4 轮"——历史全量进改写 prompt 既贵又慢，4 轮是覆盖绝大多数指代场景的实用值。

### 2.2 改写后干什么：三条链路

改写后的独立问题有三个用途，一次改写三处受益：

```
standalone_query
  ├─ 1. 向量检索（替代原始问题）
  ├─ 2. BM25 关键词检索（"合同""电子签"这些词都在改写结果里）
  └─ 3. 索引到日志（检索日志记的是改写后问题，后续分析准确）
```

**生成阶段的 prompt 还是用原始对话**（模型回答"它和纸质…"时要看到最近几轮才能顺承语气），但**检索必须用改写后的问题**。这个分工容易搞混：检索用改写，生成看历史。

### 2.3 直接检索 + 改写检索双路

指代消解偶尔会翻车（改写错了比不改更糟），稳妥做法是**两路并行**：

```python
hits_original = vs.search(embed(current_question), k=8)       # 原问题直检
hits_rewritten = vs.search(embed(standalone_query), k=8)      # 改写检索

# RRF 融合（改写路权重略高）
final = rrf_merge(hits_rewritten * 1.2, hits_original * 1.0, k=5)
```

改写对的时候，改写路命中好；改写错的时候（比如把"它"理解错了对象），原问题直检还能兜底。**两路 RRF 是防单点失误的低成本保险**，延迟只增加一次检索（可并行）。

## 三、上下文腐烂与滑窗

多轮对话滚到第十几轮，上下文里堆满了历史答案——token 单调上涨、注意力稀释、早期错误结论被反复引用放大。这就是"上下文腐烂"（context rot）。

### 3.1 腐烂的三个症状

1. **token 膨胀**：每轮历史 500 字，20 轮就是一万字，成本线性涨；
2. **注意力稀释**：关键信息埋在大量历史中间，模型抓重点能力下降（"lost in the middle"现象）；
3. **错误累积**：第 3 轮模型答错了一个点，第 8 轮它把第 3 轮的错答案当事实引用——**错误会被自己的历史反复确认**。

### 3.2 三层治理

**滑窗（基础）**：只保留最近 N 轮完整历史（4~6 轮），更早的压缩成摘要。给每个会话维护"运行摘要"：

```python
class ConversationState:
    def __init__(self):
        self.recent_turns = []        # 最近 6 轮完整 QA
        self.summary = ""             # 更早历史的滚动摘要
        self.slot_memory = {}         # 关键实体/结论的槽位记忆

    def add_turn(self, q, a):
        self.recent_turns.append((q, a))
        if len(self.recent_turns) > 6:
            old = self.recent_turns.pop(0)
            self.summary = llm(f"""更新对话摘要，保留关键实体、结论和用户意图：
            旧摘要：{self.summary}
            新轮次：Q: {old[0]}\nA: {old[1]}""")
```

**槽位记忆（进阶）**：把对话中的关键实体/结论结构化存着——"合同类型=采购合同、违约金比例=5%、争议地=上海"。后续查询改写和生成时注入槽位，比翻历史可靠：

```python
# 生成 prompt 里注入
"用户已知信息：合同类型=采购合同，违约金=5%，争议地=上海。"
```

**检索内容遗忘**：会话开了新话题（"不说合同了，我问考勤制度"），历史里的合同信息要主动降权——用话题切换检测（当前 query 和历史 query 的相似度骤降）触发遗忘，只注入新话题相关的槽位。

### 3.3 防错误累积：历史纠错机制

发现早期答案错了，要能纠正而不是将错就错：

- 用户显式纠正（"不对，是 3%"）→ 更新槽位 + 在历史里标注"已更正"；
- 新检索证据和旧答案矛盾 → 在回答里显式处理："此前提到 X，但根据最新资料应为 Y"——**别静默改口，用户会困惑**。

## 四、多轮 RAG 的日志与评估

多轮场景的评估比单轮难，要构造**多轮测试集**：

```python
# 评估集构造：一个会话多个递进问题
sessions = [
    {"turns": [
        {"q": "合同怎么签", "expect_docs": [...], "expect_answer_points": [...]},
        {"q": "电子签有法律效力吗", "expect_docs": [...], ...},
        {"q": "它和纸质的有什么区别", "expect_docs": [...], ...},   # 依赖指代消解
    ]}
]
```

评估指标比单轮多两个维度：

1. **指代消解准确率**：含指代的轮次，改写后的 query 是否指向正确的对象（人工或 LLM 评判改写结果）；
2. **上下文一致性**：第 N 轮的答案和第 N-2 轮已确认的事实是否矛盾（用裁判模型比对前后轮）。

**离线回放工具**：把真实会话日志跑一遍"改写 → 检索 → 生成"，输出每轮的改写 query 和命中——**看改写日志是优化多轮 RAG 最高效的手段**，指代错、话题偏，一眼就能看出来。

## 五、落地检查清单

- [ ] 检索前查询改写（最近 4 轮历史进 prompt，输出独立问题）；
- [ ] 改写路 + 原问题直检双路 RRF 融合；
- [ ] 生成 prompt 用原始对话历史（顺承语气），检索用改写问题——分工明确；
- [ ] 滑窗 4~6 轮 + 滚动摘要 + 槽位记忆三层上下文管理；
- [ ] 话题切换检测，新话题主动遗忘旧槽位；
- [ ] 用户纠正和证据矛盾的显式处理，不静默改口；
- [ ] 多轮评估集：指代消解准确率 + 上下文一致性两个专项指标；
- [ ] 改写日志可观测（每轮记录改写前后 query），作为首要调试入口。

## 六、小结

多轮 RAG 上下文处理的五句话：

- **历史不直接进检索**，先 LLM 改写成独立问题——指代消解是检索准确率的第一杠杆；
- **改写路 + 原问题直检双路融合**，改写翻车时有兜底，一次改写三处受益（向量/BM25/日志）；
- **上下文腐烂是必然的**：滑窗 + 滚动摘要 + 槽位记忆三层治理，关键是关键结论结构化，不是堆历史；
- **错误会自我强化**：早期错答案会被后续历史反复确认——用户纠正要进槽位，证据矛盾要显式处理；
- **改写日志是最高效的调试入口**：每轮记录"改写前 → 改写后"，多轮 RAG 的绝大多数问题在改写环节就现形了。
