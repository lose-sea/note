# 流式 UI：把 Agent 的中间步骤做成能看的过程

SSE 把事件推到了前端，然后呢？大多数实现是：把事件 append 到一个日志框里，像看控制台输出。

控制台式的过程展示能用，但不够好。**用户在 30 秒的等待里需要的不是日志，是「正在发生什么、还要多久、我能做什么」。** 这三件事用日志框回答不了。

这一篇讲怎么把过程事件组织成「可读的过程」：信息层级、状态反馈、中断交互，以及一套能直接用的 UI 模式。

---

## 一、日志框为什么不够

### 1.1 三个体验问题

**问题一：没有层级。** 工具的返回 JSON、模型的思考、计划的步骤，全部平铺在时间线上。用户要看懂得自己在脑子里分类。

**问题二：看不出进度。** 10 条日志可能是「进行了 10%」也可能是「进行了 90%」。用户不知道还要等多久。

**问题三：不可交互。** 用户看到「正在调用 search_docs 检索」发现检索方向错了——但没法中断、没法纠正，只能干等。

### 1.2 好的过程 UI 长什么样

回顾你用过的体验好的 AI 产品：

- ChatGPT 的「正在搜索网络...」带旋转图标，搜完显示来源
- Claude 的使用工具时显示工具名 + 参数摘要，可展开看详情
- Cursor 显示「正在读取 xx 文件」「正在编辑 xx 文件」，带文件名高亮

共同点：**分层（摘要 + 详情）、有状态（进行中/完成/失败）、可展开（要看细节才展开）。**

## 二、信息层级设计

### 2.1 三层结构

```
第 1 层  计划/步骤条      ← 用户始终可见（折叠在顶部）
第 2 层  当前步骤卡片      ← 一个步骤一张卡，进行中高亮
第 3 层  工具详情          ← 默认折叠，点击展开看参数和返回
```

```
┌─────────────────────────────────────────┐
│ 调研任务                    ⏸ 停止   ⚙ │   ← 任务头：名称 + 中断按钮
├─────────────────────────────────────────┤
│ ✓ 1.确认版本与计费  ✓ 2.自建成本          │   ← 第1层：步骤条（已完成打勾）
│ ▶ 3.托管版报价    4.计算总成本  5.写报告  │
├─────────────────────────────────────────┤
│ ▶ 正在执行：查询 B 的托管报价            │   ← 第2层：当前步骤（展开状态）
│   🔧 fetch_url("https://b.com/pricing")  │
│   ⏳ 等待响应... (已等待 3s)              │
│   [展开详情 ▾]                            │
├─────────────────────────────────────────┤
│ ✓ 上一步：查询 A 的自建成本               │   ← 第2层：已完成步骤（收起）
│   🔧 web_search(...) ✓ 返回 5 条          │
└─────────────────────────────────────────┘
```

**第 1 层步骤条是最重要的设计**：它把「还要等多久」变成了可视信息。用户看到「5 步完成 2 步」，比看 20 条日志安心得多。

### 2.2 每层该显示什么

| 层 | 内容 | 密度 |
|---|------|------|
| 步骤条 | 步骤名 + 状态图标 | 极简，一行一个 |
| 当前步骤 | 正在做什么 + 关键参数 + 等待时长 | 中等 |
| 工具详情 | 完整参数 JSON + 返回摘要 | 高，默认折叠 |
| 模型思考 | 折叠的推理片段 | 中，默认折叠 |

**「等待时长」别漏。** 一个工具卡了 15 秒，用户看到「⏳ 已等待 15s」就知道该考虑取消了——这是唯一能体现「我还能等多久」的信息。

## 三、状态反馈：三种状态怎么显示

### 3.1 进行中

```javascript
// 进行中的步骤卡片：呼吸感（pulse 动画）+ 可中断
<StepCard status="running">
  <Spinner />
  <span>{step.description}</span>
  <ElapsedTimer startTime={step.startedAt} />
  <CancelButton taskId={taskId} />
</StepCard>
```

**动画要克制。** 呼吸 + 轻微的进度条就够了，别用旋转 loading——那意味着「不知道在干嘛」。

### 3.2 完成

```
✓ 已查询 B 的托管报价（2.3s）
   🔧 fetch_url  →  返回 4,127 字
   [查看详情 ▾]
```

**显示耗时和产出量**。这两数字让用户知道「这步花了多久、拿到了多少东西」，是判断任务健康度的依据。

### 3.3 失败

```
✗ 查询 A 的自建成本失败（3.0s）
   🔧 web_search  →  TypeError: connect timeout
   [重试该步] [跳过] 
```

**失败必须显眼，且给操作选项。** Agent 的优势就是失败后可干预——重试这一步、跳过这一步、或者改参数重来。**不给选项的失败展示，等于浪费了 Agent 的可干预性。**

## 四、中断交互：过程 UI 的核心价值

这是流式 UI 和日志框最大的差别——**它让用户能在过程中干预。**

### 4.1 全局中断

```javascript
// 用户点「停止」→ 发中断请求 → 服务端优雅停止
async function cancelTask(taskId) {
    await fetch(`/agent/task/${taskId}/cancel`, { method: "POST" });
    // UI 标记为「已中断」，保留已完成的部分
}
```

**中断不是「断开 SSE」**——那样服务端还在跑。要发取消信号，让服务端把状态置为 cancelled 并停掉子任务。

### 4.2 步骤级干预

某些场景用户想跳过某一步或者事后补一个输入：

```javascript
<StepCard status="running">
  <span>正在生成报告</span>
  <button onClick={() => proposeDirection()}>补充要求</button>
</StepCard>
```

**「补充要求」的实现**：发一个事件给服务端，插到任务的消息队列里，Agent 在下一步时读到用户输入并调整。这是异步交互，Agent 不用停。

### 4.3 原地产出 vs 实时产出

一个体验细节：**最终答案应该在过程中就开始流式出现，而不是等全部步骤完成才显示。**

```
步骤条（顶部，折叠）
├─ 答案区（实时打字机输出）   ← 用户在等待时就在读内容
└─ 过程详情（可展开）
```

这样 30 秒的任务里，用户有 15 秒已经在读答案了。**相比「先转 30 秒圈再一次性显示答案」，感知等待时间大幅缩短。**

## 五、前端实现要点

### 5.1 状态管理

```javascript
// 用 reducer 把事件流转成 UI 状态
const initialState = {
  taskStatus: "idle",       // idle | running | paused | done | error
  steps: [],
  answer: "",
  toolDetails: [],
};

function taskReducer(state, event) {
  switch (event.name) {
    case "planned":
      return { ...state, taskStatus: "running",
               steps: event.data.steps.map((s, i) => ({...s, index: i, status: "pending"})) };
    case "step_start":
      return { ...state,
               steps: markStatus(state.steps, event.data.step_id, "running") };
    case "step_end":
      return { ...state,
               steps: markStatus(state.steps, event.data.step_id,
                                 event.data.ok ? "done" : "failed") };
    case "token":
      return { ...state, answer: state.answer + event.data.text };
    case "tool_result": {
      // 工具详情只保留最近 N 条，别无限增长
      const details = [...state.toolDetails, event.data].slice(-20);
      return { ...state, toolDetails: details };
    }
    default:
      return state;
  }
}
```

**工具详情要设上限（slice(-20)）**，否则长任务的详情能攒几百条，DOM 和内存都受不了。

### 5.2 渲染性能

流式更新是高频的（token 级别每秒几十次）：

```javascript
// 1. token 合并：别每个 token 都 setState
function coalesceTokens(buffer, flushInterval = 50) {
    // 攒 50ms 或攒够 8 个 token，一次性更新
}

// 2. 虚拟列表：过程条目多了要虚拟化
import { VariableSizeList } from "react-window";

// 3. 思考过程降频：不需要每个 token 都显示
setInterval(flushThinking, 200);      // 每 200ms 刷一次
```

**不优化的话，一个长任务能占满前端主线程，页面卡死。**

### 5.3 移动端适配

- 步骤条在小屏改成「3/6 步 · 正在 X」的单行摘要
- 工具详情默认折叠到底，点「详情」才展开
- 不能再像桌面端那样同时显示计划 + 当前步骤 + 历史步骤

## 六、常见误区

**误区一：把 SSE 事件直接渲染成日志。** 没有层级、没有进度、不可交互。**先设计步骤条和卡片结构。**

**误区二：完成态不显示耗时和产出量。** 这两个数字是用户判断任务健康度的依据。

**误区三：失败只显示红字。** 必须给「重试 / 跳过 / 改参数」的选项——Agent 的优势就是可干预。

**误区四：最终答案等全部完成才显示。** 流式输出应该和过程并行，让用户在等待时就开始读内容。

**误区五：中断只断 SSE 不断任务。** 服务端还在跑，白烧 token。**要发取消信号让服务端真停。**

**误区六：token 级高频更新不做合并。** 前端卡死。合并成 50ms 一批。

**误区七：工具详情无限累积。** 上限 20 条 + 虚拟列表。

---

## 小结

- SSE 推过来的事件，**不能直接渲染成日志框**——没有层级、看不出进度、不可交互。好的过程 UI 是「分层 + 有状态 + 可干预」。
- 三层结构：**步骤条（始终可见，回答「还要多久」）+ 步骤卡片（当前进行中，历史收起）+ 工具详情（默认折叠）**。
- 三种状态各有要点：进行中（显示已等待时长 + 可取消）、完成（显示耗时和产出量）、失败（给重试/跳过/改参数选项）。
- **中断交互是过程 UI 的核心价值**：Agent 的每一步都可干预，让它比一次性批任务更好用。
- 体验关键：**最终答案应该流式并行输出**，让用户在等待中就开始读内容，感知等待时间大幅缩短。
- 工程三要点：**token 合并更新（50ms 一批）、详情列表设上限 + 虚拟化、移动端简化层级**。
- 中断要「真停」：发取消信号，不是只断 SSE 连接。

过程 UI 做好了，30 秒的任务感知上只有 15 秒；做不好，15 秒的任务也像 1 分钟。**Agent 的等待体验，一半在模型速度，一半在你怎么展示。**
