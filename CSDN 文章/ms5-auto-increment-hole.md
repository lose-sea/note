# MySQL 自增 ID 空洞：为什么删了数据 ID 还是不连续

新员工问了个经典问题："表里删了几行，插入的新行 ID 怎么接不上？还有批量插入和事务回滚也会让 ID 跳？"——自增 ID 不连续几乎是 MySQL 的"默认行为"，而理解它的成因，直接决定了你能不能回答领导那句"为什么订单号中间缺了几个"。这篇文章把自增空洞的六个成因、InnoDB 的计数器机制、重置的正确与错误姿势、以及"ID 必须有业务含义"场景下的替代设计，一次讲清。

## 一、先接受一个事实：自增 ID 从来就不保证连续

MySQL 官方文档原话级结论：`AUTO_INCREMENT` 保证**唯一、递增**，但**不承诺连续**。缺失的场景每天都在发生：

```sql
CREATE TABLE t_order (id BIGINT AUTO_INCREMENT PRIMARY KEY, note VARCHAR(50));
INSERT INTO t_order (note) VALUES ('a'),('b'),('c');   -- id = 1,2,3

DELETE FROM t_order WHERE id = 2;
INSERT INTO t_order (note) VALUES ('d');              -- id = 4，不是 2

-- 事务回滚也一样
START TRANSACTION;
INSERT INTO t_order (note) VALUES ('e');   -- 占用了 id=5
ROLLBACK;                                   -- 回滚，5 永久消失
INSERT INTO t_order (note) VALUES ('f');   -- id = 6
```

删了不回填、回滚不留号，这不是 bug，是设计。下面逐个拆解成因，因为"知道为什么"才能判断"能不能接受"。

## 二、六个空洞成因，按出现频率排

### 成因 1：DELETE 不回退计数器

最常见。自增计数器在内存里（InnoDB），`DELETE` 只删数据不动计数器。MySQL 8.0 之前重启后计数器会被重建为 `MAX(id)+1`，所以**重启会"追认"空洞**——删除后再重启，新插入直接接着 MAX(id)+1。

### 成因 2：事务回滚/插入失败占用 ID

自增值在 `INSERT` 执行时就分配，不等事务提交。回滚后这些值**不会归还**。批量插入部分失败同理：一批 100 行，第 50 行违反唯一键，前 49 行的 ID 已分配，整体失败后 100 个号全废。

这对"插入重试"很致命：应用层重试一次，ID 就跳一段。高并发写入 + 重试策略的系统，ID 间隔几十上百是常态。

### 成因 3：innodb_autoinc_lock_mode 与批量插入

InnoDB 有三种自增锁模式（`innodb_autoinc_lock_mode`）：

| 模式 | 行为 | 影响 |
|---|---|---|
| 0（traditional） | 语句级锁，语句结束才释放 | 批量插入可能一次拿一大段号 |
| 1（consecutive，5.7/8.0 默认） | 简单 INSERT 用轻量互斥量；`LOAD DATA`、`INSERT...SELECT` 等 bulk 操作仍锁表 | bulk 场景预留号段，中途失败整段作废 |
| 2（interleaved） | 完全不锁，并行最高 | ③ 不保证同语句内连续，性能最好 |

模式 1 下这种语句会产生空洞：

```sql
INSERT INTO t_order (note) SELECT note FROM t_staging;  -- 假设源 1000 行
-- 若目标表有重复键冲突，插入 500 行后失败：
-- 已分配的 1000 个号中，前 500 行也没提交，整段作废 → 下一条 ID 从 1001 开始
```

`LOAD DATA INFILE` 批量导入同样按块预分配，导入失败会跳一大截。

### 成因 4：UPDATE 改主键（少见但致命）

```sql
UPDATE t_order SET id = id + 1000 WHERE ...  -- 手动改自增主键
```

把 id 改大后，计数器下次从 `MAX(id)+1` 开始，中间全部变空洞。虽然不推荐手动改自增列，但数据订正场景确实有人这么干。

### 成因 5：AUTO_INCREMENT 计数器被显式设置过

```sql
ALTER TABLE t_order AUTO_INCREMENT = 10000;
```

一锤定音跳到一万。常用于"掩盖历史数据量"，但代价就是这个值之前的所有号段永久跳空。

### 成因 6：复制架构下的天然错位

主库模式 2（interleaved）下，binlog 是 statement 格式时，主从上执行的 INSERT 顺序如果和自增分配顺序不一致，从库的 ID 分配与主库不同——虽然数据一致（因为行里带了真实 ID），但如果从库提升为主库，新插入的 ID 会从从库的 `MAX(id)+1` 开始，可能和主库未同步的号段冲突。**主从切换后 ID 回跳**是高可用架构的经典问题，MySQL 8.0 默认 `binlog_format=ROW` 已经大幅缓解（ROW 格式记录真实 ID，不依赖分配顺序）。

## 三、InnoDB 的计数器：8.0 的红利

这里有一个重要版本差异：

- **MySQL 8.0 之前**：自增计数器**只在内存**，重启后重建为 `MAX(id)+1`。所以"删除最大 id 的行 → 重启 → 插入"，新 ID 会复用刚删掉的号。
- **MySQL 8.0 起**：自增计数器**持久化到 redo log**，重启后**不回收**——删了最大行再重启，ID 也接着走，不会复用。

8.0 这个变化堵上了"ID 复用"的伦理风险（刚删的订单号被新订单复用，财务对不上账），代价是彻底放弃"连续"——所以如果项目还在 5.7，删除后重启会看到"ID 复用"，别以为是灵异事件。

查看当前实例的模式：

```sql
SHOW VARIABLES LIKE 'innodb_autoinc_lock_mode';
SHOW VARIABLES LIKE 'auto_increment%';       -- increment / offset 步进
```

`auto_increment_increment` / `auto_increment_offset` 常用于多主架构（双主双写），让两个库分配不同号段避免冲突——但这是给多主用的，单库保持默认 1。

## 四、想重置？先看清代价

有人想"修复"空洞，让 ID 重新连续。先看三种方式：

### 4.1 ALTER TABLE ... AUTO_INCREMENT = n（基本无效还想）

```sql
ALTER TABLE t_order AUTO_INCREMENT = 100;
```

只能把计数器**调大**或调到当前 MAX+1（如果 n 比 MAX(id) 小，MySQL 静默忽略或置为 MAX+1）。**永远不能把 ID 倒回去复用已删除的号**——这不是限制，是特性：复用 ID 会让 binlog 闪回、逻辑备份、审计链条全部错乱。

### 4.2 TRUNCATE TABLE（物理清零）

```sql
TRUNCATE TABLE t_order;
```

删全表 + 计数器归零，ID 从 1 重新开始。**DDL 操作、不可回滚、立即提交、触发器和外键受限**——这是"测试环境初始化"的手段，生产表慎用，有外键引用时直接报错。

### 4.3 重建表（导出导入）

`mysqldump` + 重新插入，不带自增列的值，导入后从 1 排。这是唯一能让 ID 完全连续的方法，但只适用于小表/归档场景，生产在线表等于自杀。

**结论：接受空洞。** 任何"修复 ID 连续性"的操作，风险都远大于收益。自增 ID 的唯一职责是**唯一标识**，连续性从来不是承诺。

## 五、什么时候"连续"是硬需求

确实有些场景对连续性有真实要求，此时自增 ID 从根上就不适合，应该换方案：

| 场景 | 为何自增不行 | 替代方案 |
|---|---|---|
| 订单号、票据号对外展示 | 空洞对外=可疑，且自增可预测（竞品能猜单量） | 业务号生成器：日期段 + 号段（`20261016-000123`） |
| 分布式 ID | 单库计数器是瓶颈和单点 | 雪花算法、Redis 号段、数据库号段表 |
| 审计序列 | 合规要求严格递增无缺口 | 独立序列表 + 事务，或数据库序列 |
| 对外 API 资源 ID | 可遍历 = 爬虫友好 | UUID / 哈希化 ID |

这些场景的标准做法是**双字段**：内部主键用自增 BIGINT（性能好），对外暴露的业务单号用单独字段 + 发号器。

```sql
CREATE TABLE t_order (
  id BIGINT AUTO_INCREMENT PRIMARY KEY,      -- 内部主键
  order_no VARCHAR(32) NOT NULL UNIQUE,      -- 对外单号，发号器生成
  ...
);
```

发号器可以用 Redis `INCR`（高性能但有持久化权衡）、数据库号段表（一次取一段，如 1000 个，用完再取，平衡性能与连续性），或雪花算法（无中心但有回拨风险）。选型看并发量和对"绝对连续"的要求等级。

## 六、监控与运维：怎么和空洞相处

日常运维要接受空洞，但要**监控异常大小的空洞**——空洞本身正常，空洞突增往往是系统出问题的信号：

1. **监控自增消耗速率**：`SHOW TABLE STATUS` 的 `Auto_increment` 字段，对比昨天同期，速率突增说明有批量失败重试或异常写入；
2. **监控号段余量**：`Auto_increment` 逼近列类型上限是大坑——`INT` 上限 21 亿，`BIGINT` 到 922 亿亿。表用 `INT` 自增且已过半的，规划改 `BIGINT`（这是另一个"迟早要炸"的经典问题）；
3. **失败重试要节流**：应用层对唯一键冲突的重试，加退避和上限，避免一次故障烧掉一段号；
4. **批量插入用 `INSERT IGNORE` 或预去重**，减少整批作废；
5. **归档数据别 DELETE 大量行当日常**——这才是空洞的最大来源，归档走分区表 `DROP PARTITION`（物理删除文件，不经过自增计数器混乱），或直接归档到历史库。

**关于主键类型**：新建表一律 `BIGINT`（哪怕是"不可能超过 20 亿"的小表），改造成本一次付清，省得某天凌晨从 INT 溢出中醒来。`INT` 只用于确定的小维度表。

## 七、一张速查表

| 现象 | 成因 | 正常吗 |
|---|---|---|
| 删行后 ID 不连续 | DELETE 不动计数器 | ✅ 设计如此 |
| 事务回滚后 ID 跳过 | 回滚不归还自增值 | ✅ |
| 批量插入失败跳一大截 | autoinc_lock_mode=1 预分配整段 | ✅ |
| 重启后 ID 复用（5.7） | 计数器重建为 MAX+1 | ⚠️ 8.0 已修复 |
| 重启后 ID 继续跳（8.0） | 计数器持久化 | ✅ |
| 主从切换后 ID 错乱 | interleaved 模式 + statement binlog | ⚠️ ROW 格式缓解 |
| ID 消耗速率突然翻倍 | 批量失败重试、异常写入 | ❌ 查应用 |

## 八、小结

自增 ID 的三句话总结：

- **自增只保唯一、不保连续**：删除不回退、回滚不归还、批量预分配作废，都是正常设计，不要试图"修复"；
- **8.0 的持久化计数器堵上了 ID 复用风险**，5.7 及之前版本要知道"删最大行 + 重启 = 复用"这个行为；
- **对外单号、分布式 ID 这类"必须连续/不可预测"的需求，用发号器单独生成**，主键和业务号分离，是标准解法。
