# Agent 工具挂太多会怎样：选择退化、成本失控与治理清单

给 Agent 加工具是会上瘾的。一开始三个工具（搜索、计算、发邮件）跑得挺好，慢慢的变成十个、三十个、八十个——每个业务方都说「我们这边也需要一个接口」，每个周末都有人提 PR 加工具。

然后突然有一天你发现：Agent 开始选错工具了，一次简单任务要轮十几轮，token 账单翻了三倍，而且它时不时在毫不相干的工具之间反复横跳。

这不是模型退步了，是**工具数量这个变量本身在伤害 Agent**。这篇讲清楚退化的机理、临界点在哪、以及怎么治理。

---

## 一、工具变多，Agent 怎么变笨的

### 1.1 工具描述的相似度陷阱

模型选工具靠的是「用户意图 → 匹配工具描述」。当工具少的时候，每个工具的描述都足够独特：

```
search_web(query)       - 在互联网上搜索公开信息
query_db(sql)          - 查询内部订单数据库
send_email(to, body)   - 给指定收件人发邮件
```

清晰、互斥。加到 30 个之后，描述开始**语义趋同**：

```
search_docs(query)             - 搜索内部文档
search_knowledge_base(query)    - 搜索知识库
search_faq(query)              - 搜索常见问题
search_history(query)           - 搜索历史工单
```

这四个的差异只有细微的语义区别。模型不再能稳定区分它们，退化成「凭感觉挑一个近似的」。结果是：选了 `search_docs`，返回的不是用户要的，Agent 再试 `search_faq`，再试……**步数就是这么涨上去的。**

### 1.2 上下文的稀释效应

工具定义也是上下文的一部分，这部分开销是**固定成本**：

| 工具数 | 平均每个工具描述长度 | 工具定义占用 token |
|-------|-------------------|------------------|
| 5 | 120 | 600 |
| 20 | 120 | 2,400 |
| 50 | 120 | 6,000 |
| 100 | 150 | 15,000 |

50 个工具的 Agent，光是「知道自己有什么工具」就要吃掉 6000 token。如果上下文窗口是 8K，这一步就占掉四分之三——留给实际任务的空间所剩无几。

而且这部分开销**每一轮都重复付**。一个跑 15 轮的任务，光工具定义就付了 90,000 token。这是纯浪费。

### 1.3 我第一次踩这个坑

一个内部运维 Agent，挂了 42 个工具（各个监控系统的查询、各种运维操作）。上线后用户问「帮我看下昨晚的告警」，Agent 的表现：

```
轮1: 调 query_alarm_center → 没结果（这个接口只能查最近7天，昨晚的告警已归档）
轮2: 调 query_alarm_history → 超时
轮3: 调 search_alarm_docs → 返回一串使用文档
轮4: 调 query_alarm_summary → 格式不对
轮5: 放弃，回答"暂时查不到告警信息"
```

人工定位：正确的工具是第 38 个，叫 `query_archived_alarm`。它的描述是「查询已归档的历史告警记录」，和 `query_alarm_history`（查询告警历史统计）语义极近。

**问题根本不在模型，在于我们同时给了它 4 个「查告警」的工具，其中 3 个名字还起得像同义词。**

## 二、临界点在哪里

我基于几个生产环境的观察，给一个大致的参考区间。**这不是精确的科学，但方向可靠。**

### 2.1 观测数据

| 工具数 | 任务完成率 | 平均轮数 | 平均 token/任务 | 选错率 |
|-------|----------|---------|--------------|-------|
| 1~8 | 0.89 | 3.2 | 18K | 3% |
| 9~15 | 0.86 | 4.1 | 26K | 7% |
| 16~25 | 0.81 | 5.8 | 41K | 15% |
| 26~40 | 0.74 | 8.3 | 68K | 26% |
| 40+ | 0.68 | 12.1 | 115K | 38% |

两个明显拐点：

- **15 个左右**：选错率开始明显抬头（7% → 15%），平均轮数开始失控
- **25 个左右**：完成率掉出可接受区间，token 成本翻倍

**工程上的建议红线：单个 Agent 的核心工具 ≤ 15 个，硬上限 25 个。**

### 2.2 但这个数不是固定的

临界点受两个因素影响很大：

- **工具描述的区分度**：如果每个工具描述都写得清晰互斥，能推到 20~25 个。如果描述都像同义词，8 个就开始退化。
- **任务域的宽度**：一个只做「数据查询」的 Agent，15 个工具都围绕同一类意图，容易混；一个跨域 Agent（查询 + 写文件 + 发通知 + 跑计算），域间区分明显，能扛更多个。

所以别把数字当金标准，**要建立自己的度量**（见第五节）。

## 三、治理手段

工具多起来是常态（业务总会要新接口），目标是**在不牺牲能力的前提下不让 Agent 变笨**。手段按成本从低到高排。

### 3.1 手段一：合并同类工具（最该先做）

回来看看那个例子。四个「查告警」的工具，为什么要分开？

```
query_alarm_center     → 查近 7 天告警
query_alarm_history    → 查告警统计
query_archived_alarm   → 查已归档告警
```

答案是：**这三个本来就应该是一个工具带参数。**

```python
@tool
def query_alarm(
    time_range: Literal["recent", "24h", "7d", "archived"],
    output_mode: Literal["list", "summary"] = "list",
) -> str:
    """查询告警信息。

    Args:
        time_range: recent=最新一批, 24h=近一天, 7d=近一周, archived=已归档
        output_mode: list=明细, summary=聚合统计
    """
    ...
```

一个工具替代三个。描述短了、选择面小了、参数化让能力反而更细。

**判断该不该合并的标准**：如果两个工具的差异只是「查的时间范围不同」「返回格式不同」，那就是一个工具的两个参数，不是两个工具。

### 3.2 手段二：工具描述的重写规则

合并解决不了的问题（工具确实不同），靠写好描述来提区分度。规则：

**规则 1：开头第一句就写清边界**

```python
# ❌ 差
"""查询告警相关数据"""

# ✅ 好
"""实时告警查询。只覆盖最近 7 天未归档的活跃告警；
查历史统计用 query_alarm_stats，查已归档告警用 query_archived_alarm。"""
```

第一句就要让模型知道「这个工具的适用边界」和「什么时候不该用它」。

**规则 2：明确写出「别用我」的条件**

这违反直觉但非常有效。当模型在两个工具之间犹豫时，一条「如果你的需求是 X，请用 Y」能直接把它推向正确的一边。

**规则 3：参数说明里加拒绝条件**

```python
Args:
    table_name: 要查的表名。只能是订单库的 6 张表之一
        （orders/order_items/payments/refunds/shipments/subscriptions），
        其他表不要传进来。
```

**规则 4：消灭近义词**

工具集里不能同时出现 `get_user` 和 `fetch_user_info` 和 `user_lookup`。命名要统一动词风格（全是 `query_` 或全是 `get_`），语义互斥。

### 3.3 手段三：工具路由（保留能力但不全给）

如果合并和描述都做了还是超 25 个，用两层路由：

```
用户请求 → 意图分类（轻量，便宜）→ 只挂载该类相关的 5~8 个工具
```

```python
TOOL_GROUPS = {
    "data_query":  [query_order, query_user, query_metric, export_csv],
    "devops":      [query_alarm, deploy, rollback, view_log],
    "writing":     [draft_doc, translate, summarize],
}

def select_tools(user_input: str) -> list:
    """根据用户意图挑工具组。"""
    cats = classify(user_input, allowed=list(TOOL_GROUPS))
    return [t for c in cats for t in TOOL_GROUPS[c]]
```

**关键**：分类器要轻（一个 8B 小模型甚至关键词规则），因为它每次请求都要跑。如果分类本身要花 2 秒，比 Agent 跑几轮的收益还大。

另外要处理「跨域请求」——「查一下昨天的告警，然后写个复盘文档」需要同时挂 `devops` 和 `writing`。分类器要支持多标签。

### 3.4 手段四：工具降级与灰度

新工具上线前，先在灰度用户里观察，看它是不是真的被用上、用得对：

```python
# 统计工具使用频次与成功率
tool_usage = {
    "query_alarm": {"calls": 1420, "success": 1298, "avg_result_score": 0.71},
    "query_alarm_stats": {"calls": 87, "success": 41, "avg_result_score": 0.22},
}
```

**一个多月只被调用几十次、成功率还低的工具，要么修，要么下掉。** 它占着上下文预算，贡献的只有噪声。

建议每季度跑一次工具清单审查：调用量、成功率、选错率，三个指标都差的就该退役。

## 四、什么时候「多」反而是对的

有几种情况，工具多不是问题，或者不是主要矛盾。

### 4.1 工具之间高度互斥且描述边界清晰

比如一组严格区分的文件操作（读/写/删/移动/重命名/搜索）——语义完全独立，描述也容易写清楚。这种加到 20 个也运行良好。

判据：**任意两个工具之间，能否用一句话说清「什么时候用 A 不用 B」？** 能，就没问题；说不清，就是退化的苗头。

### 4.2 任务域切换由 Agent 自己决定

多智能体架构里，每个子 Agent 只管自己那一摊，各自只挂 10 个左右工具。主 Agent 只负责分派，工具极少。

这种情况下「总工具数 200 个」不是问题，问题只在「单个 Agent 挂了多少」。

### 4.3 模型代际优势

更强的新模型（尤其是长上下文和指令遵循做得好的）在工具选择的鲁棒性上明显更好。同样是 30 个工具，GPT-4o 的表现比 GPT-3.5 好一大截。

但这不改变治理原则——只是让红线往后挪一点，不是让红线消失。

## 五、建立你自己的度量

别信任何通用数字（包括我这篇给的）。建三张表，每周看一次：

### 5.1 工具选错率

需要标注或抽样人工判：

```
选了工具但调用参数明显不对      → 选错
选了一个和后继步骤逻辑矛盾的工具 → 选错
调对了但结果为空、又换了工具    → 部分选错
```

### 5.2 无效轮次占比

```
无效轮次 = 调用了工具但没推进任务状态（同样参数重试、参数明显不合法的调用）
无效轮次占比 = 无效轮次 / 总轮次
```

**这个指标最容易自动化，也最灵敏。** 它超过 20% 就该警惕工具是不是太多了。

### 5.3 单任务 token 成本

按任务类型分桶统计。某个类型突然从 20K 涨到 40K，先去查是不是新加的工具把定义撑大了。

### 5.4 每期工具清单

```
工具名 | 调用次数 | 成功率 | 参数错误率 | 平均耗时 | 引入时间
```

这份表同时回答三个问题：哪些该退役、哪些该修、新增工具到底有没有人用。

## 六、一套可落地的治理流程

如果现在工具已经很多了，按这个顺序做：

**第一周：盘账**
- 拉出当前所有工具，按调用频次和成功率排序
- 找出近 30 天调用 < 10 次的，先标记为「候选退役」
- 按语义聚类，找出所有近义词工具

**第二周：合并**
- 把「参数不同」的工具合并成一个带参数的
- 按规则重写所有工具描述（边界、拒绝条件、参数约束）
- 消灭所有近义词命名

**第三周：度量**
- 上一版对比下一版：无效轮次占比、平均轮数、完成率
- 如果没改善，说明核心问题不是工具数，去查任务本身的难度或提示词

**之后：设卡**
- PR 加工具需要有度量数据的支撑（「这个工具预计被什么任务高频使用」）
- 硬规则：单 Agent 工具超过 25 个必须先过评审
- 每季度做一次清单清理

## 七、常见误区

**误区一：把工具数量当能力。** 「我们有 200 个工具」听起来厉害，实际是把选择负担转嫁给模型，而模型的出错率随负担上升。

**误区二：觉得模型够强就能扛。** 新模型确实更稳，但上下文成本是实打实的，50 个工具的定义开销不会因为模型变强而消失。

**误区三：合并工具时把不相关的合成一个。** 「把搜索、下单、退款合成一个 `do_business(action)`」——这种合并等于用参数替代选择，模型在参数这一层照样出错，而且更难排查。**只在差异确实只是参数时合并。**

**误区四：只加不减。** 工具是单向积累的，不清理就必然劣化。必须有退役机制。

**误区五：路由层做太重。** 为了路由先跑一个 70B 模型分好类，省下的工具 token 还不够付路由的成本。路由要便宜。

## 小结

- 工具多确实让 Agent 变笨，机理有三个：**描述语义趋同导致选择困难、工具定义占用固定上下文开销（每轮重复付）、噪音挤占任务空间**。
- 两个拐点大约在 **15 个**（选错率抬头）和 **25 个**（完成率掉出可接受区间）。建议单 Agent 核心工具 ≤ 15、硬上限 25，但务必建立自己的度量。
- 治理四招，按顺序做：**合并同类工具（参数差异≠两个工具）→ 重写描述（写清边界和「别用我」的条件）→ 工具路由（分类器要轻）→ 定期退役（按调用量/成功率/选错率）**。
- 最灵敏的指标是**无效轮次占比**，超过 20% 就该警惕。
- 例外情况：工具高度互斥、多智能体分域、新一代更强模型——这些能把红线往后推，但不改变原则。

给 Agent 加工具前，先问一句：**这个能力能不能用已有工具加参数实现？** 能的话，就别加。
