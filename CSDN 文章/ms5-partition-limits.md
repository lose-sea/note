# 分区的坑与边界：什么时候分区表反而坑你

前两篇讲了分区裁剪的红利和维护的节奏，这篇文章唱反调——专门讲分区表的坑。MySQL 社区里有句颇有市场的话："能用索引解决的别用分区，能不用分区就不用"。这话当然绝对了，但背后的逻辑值得每个准备上分区的团队认真读一遍：分区表不是免费的查询加速器，它有七类明确的坑，踩中任何一个都能吃掉红利还倒贴性能。

## 坑一：分区键选择错误 = 白分区

```sql
-- 按 created_at 月分区
PARTITION BY RANGE COLUMNS(created_at) ...

-- 但 70% 的查询是这样的
SELECT * FROM orders WHERE user_id = 12345 AND status = 'PAID';
-- 分区键 created_at 不在 WHERE 里 → 所有分区全扫 → 分区表比普通表还慢
```

分区键必须是**主要查询模式的第一过滤维度**。日志按时间查、订单按时间查——RANGE 时间分区成立；订单一半按 user_id 查、一半按时间查——分区键该是 user_id 或者考虑 LIST/HASH 组合。**键选错，裁剪率 0，还倒贴分区维护开销**。而分区键后期改不了（重表），选错 = 推倒重来。

## 坑二：唯一约束/主键的绑架

分区表的所有唯一索引和主键**必须包含分区键**。这意味着：

```sql
-- 想实现 email 全局唯一？分区键必须加进去
ALTER TABLE user PARTITION BY HASH(user_id) ...
-- 唯一索引变成 (id, email) 的话 id 是自增、全局唯一性靠什么保证？
-- 实际上：唯一性约束只能由"分区键 + 唯一列"的组合保证
-- email 全表唯一（跨分区）——做不到，除非把 email 设为分区键
```

**分区表丢掉的一部分约束能力**：跨分区的全局唯一性。业务上"手机号全库唯一""优惠券码全局唯一"，分区表设计上就困难。常用的妥协是分区键本身是唯一键的组成部分（如按 mobile 分区），或者接受唯一性由应用层检查（分布式下也不可靠）。

## 坑三：分区数失控

单表分区数上限 8192（`PARTITION BY` 的组合分区也算），但 8192 是上限不是目标。分区过多的真实问题：

- **分区元数据**：每个分区在 information_schema 里是一行，SHOW TABLE STATUS、information_schema.PARTITIONS 查询变慢。
- **文件句柄**：每个分区默认独立表空间一个 .ibd 文件，几百个分区 = 几百个文件，open_files_limit 和文件系统元数据压力。
- **DDL 累积**：每月加分区意味着五年后 60 个分区在表上，AD 新分区时元数据操作虽然快，但优化器评估分区数据的统计成本在涨。

**分区间隔不能太细**。按天分的表，没几年就撞管理天花板；按月分的表，20 年才 240 个分区，管理压力温和。**粒度选择要按生命周期倒推**：保留 2 年数据 → 按月 24 个分区，别按天 730 个。

## 坑四：JOIN 与子查询的复杂化

分区表的优化器支持有边界：

- **分区表 join 分区表**：MySQL 8.0 之前基本不裁剪（双方都全分区扫），8.0 之后对"分区键 join 分区键"的场景有改进但远不如单表成熟。
- **分区表 + 外键**：MySQL **不支持分区表的外键**。需要引用完整性的设计直接被堵死。
- **分区表上的派生表/物化**：优化器的 semi-join 策略在分区表上可用但调试复杂度上升，遇到执行计划异常时排查链路更长。

**分区表适合"单表大数据 + 简单查询"的形态**：查日志、查流水、删历史。一旦进入复杂关联域，普通表 + 好索引往往更稳。

## 坑五：全表操作的性能回退

```sql
-- 全表 COUNT
SELECT COUNT(*) FROM access_log;         -- 分区后比普通表慢
-- 全表扫描 + 跨分区结果合并
SELECT * FROM access_log WHERE endpoint LIKE '%api%';   -- 全分区扫，无裁剪
SELECT MAX(id) FROM access_log;          -- 想走索引？分区表上每个分区都要看
```

无 WHERE 或 WHERE 不带分区键的查询，**分区后比普通表慢 10%~30%**（逐分区开、逐分区扫、结果合并）。而现实里这类查询从来不缺——运营后台的统计页、巡检 COUNT、没有 WHERE 的导出任务。**上分区前，把查询清单按"带不带分区键过滤"分个类**，如果后者占比超三成，分区收益要重新算。

## 坑六：备份恢复粒度的复杂性

- **分区级备份**：xtrabackup 对分区表的支持按"分区是子表"处理，可以部分备份，但恢复逻辑要按分区组织，脚本复杂度上升。
- **mysqldump**：默认整表 dump，分区结构带在 DDL 里；但 `--single-transaction` 下大分区表导出时间随分区数线性增长。
- **主从复制**：ADD/DROP PARTITION 的 DDL 正常复制，但主从分区不一致（比如从库漏加）会以诡异方式暴露：主库查询正常、从库报 `Table has no partition for value`。

## 坑七：维护自动化缺失 = 半夜告警

前一篇讲过：分区要每月加、定期删。没有自动化的分区表是定时炸弹——**兜底分区被写满的那天，就是服务降级的那天**。而兜底分区写满不报错（数据能进），只表现为"查询莫名变慢"，发现周期以周计。

自动化的最小配置：加分区定时任务 + 兜底分区数据量告警（`pmax` 有数据就告警）+ 分区数水位告警。三件套配齐，分区才是资产；缺一件，它是负债。

## 判断矩阵：分区 or 不分区

| 维度 | 适合分区 | 不适合分区 |
|---|---|---|
| 数据量 | 亿级以上 | 千万以下（索引足够） |
| 查询模式 | 单一维度为主（时间/地域） | 多维混合，无明显主维度 |
| 清理需求 | 定期删历史（按月/季） | 少量删除，DELETE 可承受 |
| 约束需求 | 无跨分区唯一性要求 | 强全局唯一约束 |
| 关联复杂度 | 单表查询为主 | 多表复杂 JOIN |
| 运维能力 | 有自动化+监控 | 手动维护、无人值守告警缺失 |
| 团队 | DBA 或专职运维 | 无专职 DBA、开发兼职运维 |

**反面典型**：千万级订单表按 created_at 月分区，查询 60% 按 user_id，为了"性能更好"上分区——结果是维护成本上去、user_id 查询全分区扫、半年后团队吐槽"分区好慢"含恨回滚。分区不是万能药，**索引和查询优化永远是第一站，分区是大数据量 + 清理需求双满足后的加分项**。

## 分区的替代方案

犹豫分区时，这三个方案对比着看：

1. **普通表 + 完善索引**：千万级数据的默认答案，简单可靠。
2. **归档表 + 定时迁移**：`archive_2025` 每年一张，INSERT SELECT + DELETE 清历史。没有分区红利但有完整灵活性，JOIN、约束、备份都不受限。
3. **分库分表中间件**（ShardingSphere 等）：十亿以上、需要水平扩展时的方案，按 sharding key 路由，复杂度比分区高一个数量级但能力完整。

分区的定位卡在中间：**单机单表装不下、但没到分库分表的地步**，且清理需求刚性——这个窗口期用它是划算的。

## 小结

分区表的七类坑：分区键错配白分区、全局唯一约束丢失、分区数失控、JOIN 复杂化、全表操作回退、备份恢复复杂、维护自动化缺失。判断矩阵七维度过一遍再决策，千万级数据别碰分区。它是特定窗口期（亿级以上 + 时间维度查询 + 定期归档 + 有运维能力）的甜点方案，出了窗口就是负担。决策前问自己那句：**"这些查询真的只有分区能解决吗？"**——多数时候答案是索引。下一篇转向高可用主线：GTID 模式的操作实务。
