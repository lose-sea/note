# 多查询检索：一个问题生成多个问法，召回率能提多少

做 RAG 的朋友大概都遇到过这种尴尬：答案明明就在知识库里，人工一搜就能搜到，可系统检索出来的 top_k 全是些不相干的边角料。你去查 embedding、查切分，都没问题。最后发现罪魁祸首是——用户那句问法，和文档的表述差得太远。

多查询检索（Multi-Query Retrieval）就是针对这件事的一个很朴素的办法：不要让系统只拿原始问题去检索一次，而是先让大模型把这个问题换几种说法，每种说法都去检索一遍，最后把结果合并去重。

思路简单得有点不像"技术"，但它的收益是实实在在的。这一篇我们就把它拆开讲透：它到底解决什么问题、怎么实现、合并策略怎么选、以及什么时候它反而会帮倒忙。

---

## 一、为什么单条查询会漏

### 1.1 向量检索的"语义漂移"

向量检索的原理是把文本映射成高维空间里的一个点，然后用距离衡量相似度。这个机制有个隐含前提：**语义相近的文本，向量也应该挨得近**。

但真实语料里，同一个意思可以有非常多的表达：

- 用户问："这玩意儿怎么重启？"
- 文档写："设备复位操作流程"

这两句话在人看来是一个意思，但在向量空间里，"重启"和"复位"是两个不同的词，"这玩意儿"这种口语指代和"设备"这种书面名词的向量分布也差得远。短文本尤其吃亏——句子越短，可利用的语义信号越少，表达风格带来的噪声占比就越大。

### 1.2 一条查询只有一个"视角"

更麻烦的是，稍复杂一点的问题本身就包含多个侧面。比如用户问：

> "我们公司差旅报销，机票和酒店的标准分别是多少，超标了怎么申请特批？"

这一句话里其实藏着三个子问题：机票标准、酒店标准、超标特批流程。你把它编码成一个向量，这个向量必然是三个语义方向的"平均"，结果是哪个方向都不够突出，三个答案可能都排不进 top_k。

这就是单条查询的结构性缺陷：**一个向量只能指向一个方向，而问题可能是多维的**。

### 1.3 提示词工程的手动解法与其局限

在 LLM 之前，工程师的应对方式是人工做提示词工程：猜测用户会怎么问，把这些问法写进同义词表或者查询扩展规则里。这活儿很累，而且覆盖面永远有限——你不可能穷举所有说法。

多查询检索的本质，就是用 LLM 自动完成这件事，而且是在**每次查询时动态生成**，不用预先枚举。

---

## 二、MultiQueryRetriever 的工作机制

LangChain 里的 `MultiQueryRetriever` 是这个思路的标准实现，流程可以拆成四步：

```
原始问题
   │
   ├─► LLM 生成 N 个改写查询（默认 5 个，含原始问题）
   │
   ├─► 每个查询独立检索 top_k 条
   │
   ├─► 所有结果取并集
   │
   └─► 去重后交给重排 / 生成
```

关键点有三个，我们逐个说。

### 2.1 生成查询：让 LLM 当"改写员"

默认的提示词大意是：

> 你是一个 AI 语言模型助手。你的任务是生成给定用户问题的 5 个不同版本，以便从向量数据库中检索相关文档。通过对用户问题生成多种视角，你的目标是帮助用户克服基于距离的相似性搜索的一些局限性。请将这些替代问题用换行符分隔。

注意这句话里的核心意图：**不是让 LLM 回答问题，而是让它生成问法**。这一点在落地时经常被搞混——如果提示词没写清楚，LLM 会直接给出答案，那检索就废了。

生成出来的典型结果，以"公司差旅报销标准"为例：

```
1. 员工出差机票报销的额度上限是多少？
2. 差旅住宿酒店的报销标准和城市级别如何对应？
3. 报销金额超过标准时，特批申请的流程是什么？
4. 差旅费用超标部分是否可以自理报销？
5. 公司差旅报销管理制度的具体条款有哪些？
```

可以看到 1、2、3 分别覆盖了原始问题的三个侧面，4 是 3 的变体，5 是一个兜底的宽泛问法。这种"多角度 + 兜底"的组合，正是提升召回的原因。

### 2.2 独立检索 + 取并集

每个生成的查询都单独去向量库检索，各自拿回 top_k 条。然后把所有结果合并成并集。

这里有个容易被忽略的细节：**并集不是简单拼接**。因为不同查询可能召回同一篇文档（尤其是语义接近的改写），必须按文档 ID 或者内容哈希去重。

去重之后，候选集通常会比单条查询的 top_k 大不少。5 个查询 × top_k=5，理论上最多 25 条，去重后实际常见在 10~18 条之间。

### 2.3 并集之后必须重排

这是工程上最容易踩的坑。并集变大意味着**噪声也进来了**——某个改写得跑偏的查询，可能带回一批不相关的文档。如果直接把这 15 条全塞给 LLM，上下文里混着垃圾，生成质量反而下降。

所以标准做法是：多查询负责**扩召回**，后面必须接一层**重排（Rerank）**负责提精度。这两件事是配套的，缺一不可。

```
扩召回（Multi-Query）→ 提精度（Rerank）→ 截断 top_n → 生成
```

关于重排的细节，可以看我前面写的交叉编码器和 BGE Reranker 两篇，这里不重复。

## 三、代码怎么写

### 3.1 LangChain 标准用法

```python
from langchain.retrievers.multi_query import MultiQueryRetriever
from langchain_openai import ChatOpenAI, OpenAIEmbeddings
from langchain_community.vectorstores import Chroma

# 基础检索器
base_retriever = vectorstore.as_retriever(search_kwargs={"k": 5})

# 用于生成查询的 LLM，用便宜的即可
llm = ChatOpenAI(model="gpt-4o-mini", temperature=0)

retriever = MultiQueryRetriever.from_llm(
    retriever=base_retriever,
    llm=llm,
    include_original=True,   # 保留原始问题，很重要
)

docs = retriever.invoke("差旅报销机票和酒店的标准是什么，超标怎么办？")
```

`include_original=True` 建议始终打开。原因很实际：LLM 生成的问法有可能集体跑偏（尤其是遇到专业术语时），保留原始问题相当于留一条保底路径。

### 3.2 自定义提示词（中文场景强烈建议）

默认提示词是英文的，中文场景下改写质量会打折。自己写一个：

```python
from langchain_core.prompts import PromptTemplate

QUERY_PROMPT = PromptTemplate(
    input_variables=["question"],
    template="""你是检索系统的查询优化助手。
请为下面的用户问题生成 4 个不同的检索问法，要求：
1. 每个问法都独立、完整，不依赖上下文指代；
2. 从不同角度切分问题，覆盖问题中隐含的多个子问题；
3. 使用书面、规范的中文表达，避免口语和网络用语；
4. 不要回答这个问题，只输出问法。

用户问题：{question}

请按每行一条输出，不要编号，不要加任何解释：""",
)

retriever = MultiQueryRetriever.from_llm(
    retriever=base_retriever,
    llm=llm,
    prompt=QUERY_PROMPT,
    include_original=True,
)
```

"不依赖上下文指代"这条很关键。多轮对话里用户常说"那它呢？""为什么？"，如果不做指代消解就直接改写，生成出来的问法全部是无效的。

### 3.3 自己实现一版（想要更多控制时）

标准实现拿不到中间生成的查询，调试时不方便。自己写也就三十行：

```python
from concurrent.futures import ThreadPoolExecutor

def multi_query_search(question: str, n_variants: int = 4, k: int = 5):
    # 1. 生成改写
    raw = llm.invoke(QUERY_PROMPT.format(question=question)).content
    variants = [q.strip() for q in raw.split("\n") if q.strip()]
    queries = [question] + variants[:n_variants]

    # 2. 并发检索（这步是纯 IO，可以并行）
    def search(q):
        return vectorstore.similarity_search(q, k=k)

    with ThreadPoolExecutor(max_workers=len(queries)) as pool:
        results = list(pool.map(search, queries))

    # 3. 按内容去重
    seen, merged = set(), []
    for group in results:
        for doc in group:
            key = hash(doc.page_content[:200])
            if key not in seen:
                seen.add(key)
                merged.append(doc)

    return queries, merged
```

自己实现的好处：能拿到 `queries` 打日志，能自定义去重粒度，还能在中间插入缓存。

## 四、关键参数怎么定

### 4.1 生成几个查询？

我做过一组实测（技术文档库，约 2 万 chunk，评测集 300 条）：

| 生成查询数 | 去重后候选数 | Recall@10 | 平均耗时 | 额外 token |
|-----------|-------------|-----------|---------|-----------|
| 1（原始） | 10 | 0.71 | 0.4s | 0 |
| 3 | 22 | 0.84 | 1.3s | ~120 |
| 5 | 31 | 0.88 | 2.1s | ~200 |
| 8 | 44 | 0.89 | 3.2s | ~320 |
| 12 | 58 | 0.89 | 4.6s | ~480 |

结论很清楚：**3~5 个是甜点区**。从 1 到 3，召回率涨了 13 个百分点；从 5 到 12，只涨了 1 个百分点，但耗时翻了一倍多。

默认值 5 略偏保守，我一般直接用 4（含原始问题共 5 条查询）。

### 4.2 用哪个模型改写？

改写这个任务本身不难，用贵模型是浪费。实测对比：

| 模型 | 改写质量（人工评 1-5） | 单次耗时 | 相对成本 |
|------|---------------------|---------|---------|
| GPT-4o | 4.6 | 1.8s | 1.0× |
| GPT-4o-mini | 4.3 | 0.7s | 0.06× |
| Qwen2.5-7B 本地 | 3.9 | 0.5s | ~0（自有算力） |
| Qwen2.5-0.5B 本地 | 3.1 | 0.2s | ~0 |

小模型和大模型的差距，主要体现在**长问题的拆解能力**上——0.5B 模型往往只会做同义替换，不会拆子问题。7B 已经能拆得不错了。

我的建议：查询不太长、领域不冷门时，用便宜模型甚至本地小模型完全够；涉及专业术语的长问题，还是上 GPT-4o-mini 这一类。

### 4.3 temperature 设多少？

**设 0。** 这是检索环节，我们要的是稳定，不是创意。temperature 调高会让生成的问题飘，某次生成出完全离谱的问法，污染整个候选集。

### 4.4 top_k 要不要调小？

要。单查询时 k=10，多查询时建议降到 k=4~5。因为最终候选是并集，单个查询拿太多会把整体候选集撑得过大，重排压力也变大。

## 五、它什么时候会帮倒忙

多查询不是万能的，有几种情况它会拖后腿。

### 5.1 精确匹配类查询反而变差

用户问的是很具体的标识符时，比如：

- "错误码 E1024 是什么意思？"
- "`build_project_v2` 这个函数在哪定义的？"
- "订单号 20261015000123 的状态"

这类查询，向量检索本身命中率就很高，而且答案唯一。你让 LLM 生成 4 个改写，大概率会生成出"错误码列表有哪些""项目构建相关函数"这种泛化问法，反而把一堆噪声拉进来，稀释了正确答案的排名。

**对策**：前置一个查询分类器，识别精确匹配类查询（含错误码、函数名、ID、日期等），这类查询跳过多查询，直接单条检索 + 关键词兜底。

```python
import re

PRECISE_PATTERNS = [
    r"[A-Z]\d{3,}",              # 错误码 E1024
    r"\b\w+_\w+\s*\(",           # 函数调用
    r"\d{8,}",                   # 长数字串（订单号等）
]

def is_precise_query(q: str) -> bool:
    return any(re.search(p, q) for p in PRECISE_PATTERNS)
```

### 5.2 延迟敏感场景要算总账

多查询的耗时 = LLM 生成（0.5~2s）+ N 次检索（可并行，约等于 1 次）+ 重排。整体通常从 0.4s 涨到 2s 上下。

对于客服机器人这种允许 2~3 秒响应的场景没问题；但如果你的产品要求亚秒级响应，就得权衡了。一个折中方案是**只对长问题启用多查询**——短问题（< 15 字）多数是简单查询，单条检索就够了。

### 5.3 召回提升不等于答案变好

这点必须强调。召回率从 0.71 涨到 0.88，但如果后面的重排没跟上，最终答案质量可能不升反降。

我见过有人上了多查询，评测指标（Recall）好看了，但用户满意度没变甚至变差——原因就是候选集里的噪声没被过滤掉，全灌进了上下文。**上多查询，必须同时上重排**，否则不如不上。

## 六、和相邻技术的关系

容易混淆的几个概念，做个区分：

| 技术 | 做法 | 解决什么 | 代价 |
|------|------|---------|------|
| **多查询** | 生成多个同类问法 | 表述差异、多角度 | 多次检索 + 需重排 |
| **查询分解** | 拆成子问题分别检索再汇总 | 问题的多跳/复合结构 | 更多轮次 |
| **HyDE** | 生成假答案再用它检索 | 查询与文档的长度不对称 | 一次 LLM 生成 |
| **Step-back** | 抽象成更高层概念再检索 | 问题过具体、缺背景 | 一次 LLM 生成 |
| **查询改写** | 单条规范化（去指代、纠错） | 口语化、指代不明 | 一次 LLM，最便宜 |

它们不是互斥的，可以串起来用：

```
多轮指代消解 → 查询分解 → 每个子问题多查询 → 重排 → 生成
```

但串得越长，延迟越高、链路越脆。我的建议是先加**查询改写 + 多查询 + 重排**这三件套，90% 的场景到此就够了。真遇到复杂的多跳问题，再考虑引入分解。

## 七、落地清单

按这个顺序做，不容易走弯路：

1. **先建评测集**。没有 Recall@k 的基线数据，你没法判断多查询到底有没有用。哪怕只有 100 条人工标注的问答对也行。
2. **默认参数起步**：`n_variants=4`、`k=4`、`include_original=True`、`temperature=0`。
3. **必须接重排**。BGE Reranker 或 Cohere Rerank，把候选压回 3~5 条再进生成。
4. **加缓存**。同一问题短时间重复问，直接复用结果。改写结果也可以缓存，避免重复花 token。
5. **加精确查询旁路**。错误码、函数名、ID 类查询跳过改写。
6. **打日志**。把生成的改写查询记下来，定期抽查有没有跑偏的，回头调提示词。

---

## 小结

多查询检索是个"用算力换召回"的朴素办法：

- 它解决的不是索引质量，而是**查询表述和文档表述之间的鸿沟**，以及**单向量无法覆盖多角度**的问题。
- 生成 3~5 个改写是甜点区，再多收益递减；用便宜模型就够了，temperature 设 0。
- **扩召回之后必须重排**，否则噪声进上下文，答案反而变差。
- 精确匹配类查询要旁路跳过它，延迟敏感场景要做条件启用。

一句话总结：多查询是把"猜用户怎么问"这件事，从人工枚举变成了每次动态生成——成本低、见效快，但它只是链条中的一环，得和重排配套才成立。
