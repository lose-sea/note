# LightRAG 实战：把 GraphRAG 的成本打下来的轻量图 RAG

上一篇文章的结论可能让很多人失望：GraphRAG 效果是对的多跳查询确实强，但索引贵、查询慢，个人开发者和小团队玩不起。LightRAG（香港大学数据智能实验室开源）就是冲着这个痛点来的——同样的图谱思路，用"双索引 + 双层检索"把构建和查询成本都压了一个量级。这篇文章讲透它的设计差异、怎么用、和 GraphRAG 怎么选，以及它自己的短板。

## 一、LightRAG 解决的两个贵

GraphRAG 的两笔账：索引期每个文本块一次 LLM 抽取、查询期 Global 一次 Map-Reduce 几百次调用。LightRAG 针对两笔账各开了一副药：

### 1.1 索引期：图 + 向量双索引，增量便宜

GraphRAG 建图后查询主要靠图谱，LightRAG 同时建两套索引：

- **知识图谱**：实体、关系、关键词（抽取时一并产出）；
- **向量索引**：实体描述、关系描述、原文 chunk 各embedding。

**双索引的价值在增量更新**：新文档进来，只抽取新文档的实体关系合并进图，新 chunk 进向量库——**不动旧索引，不用全量重建社区**。GraphRAG 加文档后社区结构要重算，LightRAG 的图谱是"长出来"的，随时追加。

### 1.2 查询期：只检索不摘要

GraphRAG 的 Global 查询要 Map-Reduce 全跑一遍社区摘要；LightRAG 的查询是**纯检索**：从图谱和向量库取出相关实体、关系、原文，直接拼上下文给生成模型——**查询期零 LLM 调用（除了最后生成）**。一次查询从"几美元"变成"几分钱"。

## 二、核心概念拆解

### 2.1 图谱里的节点不止实体

LightRAG 的图谱节点有三类：**实体**、**关系**、**关键词**。抽取提示词同时产出这三类，这是它检索灵活的根源——查询可以按实体召回，也可以按关键词召回，还能顺关系边扩展。

### 2.2 双层检索（low-level / high-level）

LightRAG 的查询分两个粒度：

| 模式 | 检索起点 | 适合的问题 |
|---|---|---|
| **low-level** | 具体实体 → 出边邻居 + 关联原文 | "张伟的校友创办了什么公司"（实体级多跳） |
| **high-level** | 主题/关键词 → 社区相关的多个实体 | "知识库里讲了哪些行业"（主题级） |
| **hybrid** | 两者都跑，RRF 融合 | 默认模式，大多数场景 |

三个模式都由 `query_param.mode` 控制，像查数据库选索引一样选检索粒度。**hybrid 是默认且最稳的**，只有明确知道问题类型时才切单模式。

### 2.3 增量是设计目标不是补丁

```python
# 第一次建索引
rag = LightRAG(working_dir="./kg_store")
rag.insert("第一批文档...")

# 后续随时增量（旧数据不动，新数据并进图谱）
rag.insert("新文档...")
```

这个特性对生产太重要了：知识库每天有新合同、新工单进来，**增量入库是日常操作**。GraphRAG 时不时全量重建的痛，LightRAG 从机制上避免了。

## 三、上手：一个可跑的闭环

```bash
pip install lightrag-hku
```

```python
from lightrag import LightRAG, QueryParam
from lightrag.llm import openai_complete_if_cache, openai_embedding

async def main():
    rag = LightRAG(
        working_dir="./kg_store",
        llm_model_func=lambda p, s=None, k=None: openai_complete_if_cache(
            "gpt-4o-mini", p, system_prompt=s),
        embedding_func=openai_embedding,
    )

    # 1. 入库
    await rag.ainsert("""
    张伟于 2015 年创立蓝海科技，任 CEO。
    李娜毕业于清华计算机系，是张伟的大学校友。
    李娜 2020 年创办清风数据，专注企业知识图谱。
    """)

    # 2. 三种模式查询
    r_local  = await rag.aquery(
        "张伟的校友创办了什么公司？",
        param=QueryParam(mode="local"))
    r_global = await rag.aquery(
        "这些实体分布在哪些行业？",
        param=QueryParam(mode="global"))
    r_hybrid = await rag.aquery(
        "蓝海科技和清风数据有关系吗？",
        param=QueryParam(mode="hybrid"))

    print(r_local, r_global, r_hybrid)
```

注意 `working_dir`——图谱、向量、实体缓存全在这里面，**增量就是不停往同一个目录喂新文本**。存储可以用本地文件、Neo4j、PostgreSQL 多种后端，生产上小规模用本地文件起步，量大了迁 Neo4j。

**离线批处理模式**（省 token 的关键姿势）：

```python
# 只建索引不产出，配合定时任务
await rag.ainsert(docs, param=InsertParam(only_need_index=True))
```

## 四、和 GraphRAG 的正面对比

| 维度 | GraphRAG | LightRAG |
|---|---|---|
| 建索引成本 | 高（每块一次 LLM + 社区摘要） | 中（每块一次 LLM，无社区全量摘要） |
| 增量更新 | 社区重算，接近重建 | **并进图谱，不动旧索引** |
| 查询成本 | Global 极贵（Map-Reduce） | **纯检索，零额外 LLM** |
| 多跳能力 | 强（Local 邻居遍历） | 强（low-level 同款机制） |
| 全局总结 | 强（社区摘要专长） | 中（high-level 靠关键词扩散） |
| 存储后端 | 默认 Parquet 文件 | 文件/Neo4j/PG 可选 |
| 生态 | 微软，文档全 | HKUDS，迭代快 |

**一句话选型**：

- 语料静态、预算足、全局总结是核心场景 → GraphRAG；
- 语料每天增量、成本敏感、多跳查询为主 → **LightRAG**；
- 两个痛点都占 → 先 LightRAG 起步，扛不住再迁移（图谱抽取逻辑可复用）。

## 五、生产环境的四个注意点

### 5.1 抽取模型的成本还是大头

LightRAG 省的是查询和社区摘要，**抽取这一步省不掉**——每个 chunk 还是要过 LLM 抽实体关系关键词。省钱姿势和 GraphRAG 一样：用便宜模型（gpt-4o-mini、本地 Qwen14B）做抽取，生成阶段再用好模型。抽取质量对图谱可用度的影响大于模型强弱，本地模型完全可战。

### 5.2 实体消歧是真实痛点

"苹果"在科技文档和农业文档里是不同实体，LLM 抽取时不合并，图谱里就有两个"苹果"节点，查询时召回混乱。LightRAG 的缓解：实体描述里带上上下文，检索时靠描述消歧；根治要靠实体归一化后处理（把别名合并），这是所有图谱方案的共同难题，不是 LightRAG 独有。

### 5.3 检索深度要控制

图遍历深度是双刃剑：深度 1 只召回直接邻居（快但漏关系），深度 3 图谱一大就拖回半张图（噪音爆炸）。LightRAG 有 `top_k` 和检索范围参数，**从 top_k=20 起步，按查询质量调**，别贪多。

### 5.4 和向量 RAG 并存，不是取代

LightRAG 的高层检索对"原文细节"仍然不如向量检索直接——它是关系强、原文弱。生产架构建议：

```
查询 → 分类
  ├─ 细节型 → 向量 RAG（BM25+向量+rerank）
  └─ 关系型 → LightRAG hybrid
结果融合 → 生成
```

两路索引有重叠建设成本（都要原 chunk 的向量），换来的是两类查询各自最优。**预算紧？先纯向量 RAG，把多跳查询的失败案例攒一批，再决定要不要上图。**

## 六、评估：怎么证明图索引真的有用

上图谱前必须用数据回答"值不值"，评估集构造：

1. 从真实查询日志里挑 100 条，人工标注答案来源（单文档细节 / 多文档关系 / 全局主题）；
2. 拆成三个评估集：细节集（向量 RAG 主场）、关系集（图 RAG 主场）、混合集；
3. 同一套生成模型，分别跑"纯向量 RAG"和"向量 + LightRAG 双路"，对比答案正确率；
4. **只有关系集的提升显著（比如 +20% 以上）才值得建图**——细节集上两者差不多是预期结果。

这个评估花两三天，但能避免花三个月建完图谱发现查询日志里没有关系型问题的尴尬。

## 七、落地检查清单

- [ ] 查询日志分析：关系型/全局型查询占比；
- [ ] 评估集三分类构造，双路对比验证收益；
- [ ] 抽取用便宜/本地模型，生成用好模型；
- [ ] working_dir 纳入备份策略（图谱+向量全在里面）；
- [ ] 增量入库定时任务化（新文档 → ainsert）；
- [ ] 检索深度 top_k 按查询质量调优；
- [ ] 实体消歧后处理（别名合并）排期；
- [ ] 与向量 RAG 的融合策略定稿（并行双路 or 路由）。

## 八、小结

LightRAG 的三句话：

- **GraphRAG 的轻量替身**：双索引（图 + 向量）+ 双层检索（low/high），查询期零 LLM 调用，把 GraphRAG 的"几美元一次查询"打到几分钱；
- **增量友好是生产刚需**：新文档随时并进图谱不动旧索引，适合每天有新增的知识库；
- **仍然和向量 RAG 互补**：关系型查询上图，细节型查询走向量，先评估再建设，别为了技术先进硬上图。
