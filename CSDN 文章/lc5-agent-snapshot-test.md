# 快照测试：守住你的 prompt，改动前先看它会怎么变

每次改 prompt 都是赌博。你觉得「把这句话写得更清楚一点」不影响别的——上线后发现用户问「怎么退款」时，Agent 突然开始问「请问您的订单号是多少」（原来不会）。

问题在于：**prompt 的改动影响面是全量的，但你只能测到你想起来测的那几个 case。**

快照测试（Snapshot Testing）是解决这个的标准手段：**把「当前行为」完整录下来，改完之后对比新行为，逐条看差异。** 变了的地方一目了然，该变的不算变，不该变的立刻发现。

---

## 一、快照测试解决什么问题

### 1.1 prompt 改动的三个盲区

**盲区一：影响面看不清。** 你把「回答要简洁」改成「回答要简洁且友好」，你以为只影响语气。实际上模型可能开始加客套话，把关键信息的空间挤掉了。

**盲区二：回归不能自动化。** 你记得测了 5 个场景，但线上有 200 种问法。剩下 195 个在你改完之后变成什么样，你不知道。

**盲区三：改动理由说不清。** 老板问「这次改 prompt 有什么影响」，你只能说「测了几个 case 没问题」——没有数据。

### 1.2 快照测试的做法

```
1. 用当前 prompt 跑 30~50 个代表性问题，把【完整输出】存成基线快照
2. 改 prompt
3. 用同样的输入重跑，逐条对比新输出 vs 基线
4. 输出 diff 报告：
   - 语义相同（忽略措辞）→ OK，自动通过
   - 语义变化 → 列出具体差异，人工判断是「改进」还是「劣化」
5. 确认无误后，更新基线（新快照成为新基线）
```

**和单元测试的区别**：单元测试断言是**你写死的**（`assert "已发货" in result`）；快照的断言是**上一版本的真实行为**。所以快照能发现「你没想到要测」的变化。

## 二、快照里存什么

### 2.1 不要只存最终答案

```python
# ❌ 只存答案，信息量不够
snapshot = {"q": "怎么退款", "answer": "退款会在3个工作日到账"}

# ✅ 存完整行为
snapshot = {
    "input": {"question": "怎么退款", "user_id": "u1"},
    "prompt_version": "v2.3.1",
    "model": "gpt-4o-2024-08-06",
    "tool_calls": [
        {"name": "search_docs", "args": {"query": "退款流程"}}
    ],
    "tool_results_summary": "命中1篇：退款规则说明",
    "final_answer": "退款会在 3 个工作日内原路返回...",
    "steps": 3,
    "tokens": 1200,
    "latency_ms": 2100,
}
```

**必须存的元信息**：`prompt_version`、`model`、`temperature`。**模型升级会让快照全变**——没有版本号，你看不出是 prompt 还是模型导致的变化。

### 2.2 分级快照

全存太贵（也要花 token）。分三级：

| 级别 | 内容 | 更新频率 | 用途 |
|------|------|---------|------|
| **L1 指纹** | 调了哪些工具、参数、步数 | 每次跑 | 行为结构变化检测 |
| **L2 摘要** | L1 + 答案要点（LLM 提炼） | 每次跑 | 语义变化检测 |
| **L3 全文** | 完整答案 + 完整 trace | 每周/手动 | 深度 diff |

**日常回归用 L1 + L2（便宜），发版前用 L3。**

## 三、怎么对比：语义相同 vs 真的变了

### 3.1 直接字符串对比太严

模型有随机性，同一个 prompt 跑两次措辞也不同。逐字 diff 会把所有 case 都标成「变了」。

**要按语义对比**：把两个答案分别提炼成要点，比对要点。

```python
KEY_POINTS_PROMPT = """提取下面回答的关键信息点，每个要点一行，不要解释。

回答：{answer}

要点："""

def extract_points(answer: str) -> list[str]:
    return llm.invoke(KEY_POINTS_PROMPT.format(answer=answer)).split("\n")

def compare_answers(old: str, new: str) -> dict:
    old_pts = set(extract_points(old))
    new_pts = set(extract_points(new))

    # 语义判断：新要点是否被旧要点覆盖
    merged = old_pts & new_pts
    added = new_pts - old_pts
    removed = old_pts - new_pts

    if not added and not removed:
        return {"status": "same", "diff": None}
    return {"status": "changed",
            "diff": {"added": added, "removed": removed}}
```

**用要点集合对比，而不是字符串 diff。** 「3个工作日」和「三个工作日」在字符串层不同，在要点层是同一件事。

### 3.2 输出一份可读的 diff 报告

```
==================================================
快照对比报告  prompt v2.3.1 → v2.4.0
==================================================
共 40 个用例：
  ✅ 语义相同     28
  ⚠️ 语义变化     10
  ❌ 结构变化      2
==================================================

【语义变化】

用例 7: "怎么退款"
  旧: 退款会在3个工作日内原路返回
  新: 退款会在 3-5 个工作日内原路返回，请联系客服加急
  → 新增: [3-5个工作日, 联系客服]
  → 移除: [3个工作日]
  ⚠️ 【需要人工判断】工作日数量变了，这是 Prompt 改动的预期效果吗？

用例 15: "年假有几天"
  旧: 入职满一年有 10 天年假
  新: 根据工龄，年假为 5/10/15 天
  → 新增: [按工龄分档]
  → 移除: [固定10天]
  ⚠️ 【需要人工判断】回答结构变了，是否更准确？

【结构变化】← 高危，通常意味着出 bug 了

用例 23: "帮我查订单"
  旧: [tool_call: query_order] → [answer]
  新: [tool_call: query_order] → [tool_call: query_order] → [answer]
  ⚠️ 多了一次重复的工具调用！可能是 prompt 改动导致模型不确定

用例 31: "复杂问题"
  旧: 步数 4
  新: 步数 12
  ⚠️ 步数翻三倍，成本会涨
```

**「结构变化」要单独标红**：工具调用次数/顺序变了、步数暴涨、调用了不该调的工具——这些通常是 bug 不是改进。

### 3.3 自动放行 vs 人工把关

```python
AUTO_PASS_RULES = [
    lambda d: d["added"] and not d["removed"] and len(d["added"]) <= 1,
    # 只新增一个小要点，可以自动放行
]

REQUIRE_REVIEW = [
    lambda d: bool(d["removed"]),                  # 有移除 → 必须看
    lambda d: d.get("structure_changed"),          # 结构变 → 必须看
    lambda d: abs(len(d.get("added", [])) - len(d.get("removed", []))) > 2,
]
```

**「有内容被移除」一定要人工看**——那是能力在退化的信号。

## 四、快照的存储与基线管理

### 4.1 文件式（小团队够用）

```
snapshots/
├── v2.3.1/                    # 每个 prompt 版本一个目录
│   ├── 001-refund.json
│   ├── 002-annual-leave.json
│   └── ...
└── v2.4.0/
```

**版本目录对应 prompt 版本**，回滚 prompt 时快照基线也跟着回滚。

### 4.2 库式（要查历史）

```python
class SnapshotStore:
    def save(self, prompt_version: str, case_id: str, snapshot: dict):
        self.db.execute("""
            INSERT INTO snapshots (prompt_version, case_id, payload, created_at)
            VALUES (:pv, :cid, :payload, now())
        """, {...})

    def diff(self, old_version: str, new_version: str) -> list[DiffReport]:
        old = self.load(old_version)
        new = self.load(new_version)
        return [compare(o, n) for o, n in zip(old, new)]
```

### 4.3 基线的更新纪律

**这是最容易崩的环节。** 快照更新必须显式、可审查：

```bash
# 1. 跑对比，看报告
python snapshot.py diff --base v2.3.1 --head v2.4.0

# 2. 人工确认报告里没有「不能接受的变化」

# 3. 显式更新基线（不是自动的！）
python snapshot.py update-baseline v2.4.0 --reviewed-by zhangsan
```

**绝不自动更新基线。** 否则「模型行为悄悄变了」和「我们把新行为设为基线」没有区别——快照就白设了。

### 4.4 用例集的构成

```python
CASES = [
    # 核心场景，占 50%
    {"id": "001", "question": "怎么退款", "priority": "core"},
    # 边界场景，占 30%（多轮、长问题、指代、口语）
    {"id": "011", "history": [...], "question": "那涨价了吗", "priority": "edge"},
    # 历史 bug case，占 20%（修过的 bug 必须进快照，防复发）
    {"id": "031", "question": "帮我看看那个", "known_bug": "曾遗漏指代消解", "priority": "regression"},
]
```

**「历史 bug case」必须有**——这些是你已经付过学费的地方，最该守住。

## 五、和单元测试、eval 的分工

三个工具各有位置，别互相替代：

| | 单元测试 | 快照测试 | eval 评测集 |
|---|---------|---------|------------|
| **断言来源** | 你手写 | 上一版真实行为 | 人工标注的标准答案 |
| **能发现** | 代码逻辑 bug | prompt/模型的意外变化 | 效果好坏 |
| **速度** | 毫秒（mock） | 分钟（要跑真实模型） | 分钟~小时 |
| **成本** | 零 | 每次跑花 token | 更贵（含标注） |
| **时机** | 每次 commit | 改 prompt 后、发版前 | 每天/每周 |

**典型工作流**：

```
改代码 → 单元测试（秒级，拦逻辑 bug）
   ↓ 通过
改 prompt → 快照对比（分钟级，拦意外变化）
   ↓ 人工确认 diff
发版前 → eval 评测集（贵，看效果有没有提升）
```

**三层都过，改动才敢上。**

## 六、常见误区

**误区一：逐字 diff。** 模型有随机性，逐字 diff 全是噪声。**必须语义对比（提炼要点再比）。**

**误区二：快照只存答案。** 必须存工具调用、步数、token 和版本号，否则「结构变了」和「答案措辞变了」分不清。

**误区三：自动更新基线。** 这是最常见的自杀行为——悄悄把劣化变成基线。**必须显式 review 后才能更新。**

**误区四：快照不带版本号。** 模型升级后所有快照全变，没有 `model` 字段就定位不了原因。

**误区五：用例集全是 happy path。** 边界场景（多轮、指代、口语）和历史 bug case 才是最该守的。

**误区六：用快照替代 eval。** 快照只告诉你「变了」，不告诉你「变好还是变坏」。好坏要 eval 和人工判断。

**误区七：一上来就上完整套件。** 先用 20 个核心 case 的 L1/L2 快照跑起来，比 200 个 case 跑一次一小时实用。

---

## 小结

- 快照测试守的是**prompt 和模型的行为基线**：把当前真实行为录下来，改动后对比，看清影响面。
- 和单元测试的分工：**单元测试断言你写死，快照断言上一版的真实行为**——所以它能发现「你没想到要测」的变化。
- 快照必须存**完整行为**（工具调用、步数、token）+ **版本信息**（prompt_version、model），缺了版本号就没法定位变化原因。
- 对比要**语义级**（LLM 提炼要点再比对），逐字 diff 在随机性面前全是噪声。分级 L1 指纹 / L2 摘要 / L3 全文。
- 报告要把**「结构变化」单独标红**（工具调用次数/顺序变、步数暴涨）——那通常是 bug 不是改进。「有内容被移除」必须人工看。
- **基线更新必须显式且可审查，绝不自动**。自动更新基线 = 把悄悄劣化变成既成事实。
- 三层防护：单元测试（代码逻辑）→ 快照对比（行为回归）→ eval 评测集（效果好坏）。三者分工不重叠。
- 起步：20 个核心 case + 历史 bug case，L1/L2 级别，跑起来再说。

Prompt 是最容易被随手改坏的东西——改一行字没人 review，影响面却是全部用户。有了快照，每次改动从「赌博」变成「可对比、可审查、可回滚」。
