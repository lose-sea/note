# 提示词工程：从「会问」到「问对」的十种武器

> 很多人对提示词工程的理解停留在"找个万能模板复制粘贴"。
> 但真实情况是：模型在变、任务在变，**模板会过期，原理不会**。
>
> 本篇不讲玄学咒语，只讲十种有明确机制支撑的技巧，
> 每种都配可复现的例子和"什么时候用 / 什么时候别用"。

## 〇、先建立一个正确的心智模型

写 prompt 的本质不是"跟 AI 说话"，而是**给一个概率分布加约束**。

模型做的事是：给定前文，预测下一个 token 的概率分布。
你写的每一个字，都是在**削掉概率空间里你不想要的那部分**。

所以判断一条 prompt 好不好的标准是：
**它把输出空间收窄了多少，以及有没有把正确答案误伤掉。**

带着这个视角，下面十种技巧就不是零散的口诀，而是同一个原理的不同应用。

## 一、结构化：用分隔符划清边界

**机制**：明确区分"指令"和"数据"，防止模型把数据误当指令执行（也就是提示注入）。

```text
请总结下面这篇文章的要点。

<article>
{{ 用户输入的文章内容 }}
</article>

要求：三点以内，每点不超过 30 字。
```

用 XML 标签（`<article>`）比用引号好，因为文本里出现引号的概率远高于出现 `<article>`。
如果内容可能包含类似标签，用随机字符串做分隔更安全：

```text
内容在 ###8f3a2b### 和 ###8f3a2b### 之间：
###8f3a2b###
{{ content }}
###8f3a2b###
```

## 二、给示例：Few-shot

**机制**：不是"教它怎么做"，而是**用上下文学习把输出格式和风格锚定住**。

```text
把用户输入归类到以下标签之一：咨询、投诉、闲聊、其他

示例：
输入："我上周买的货还没到" → 投诉
输入："你们支持七天无理由吗" → 咨询
输入："今天天气不错" → 闲聊

输入："这个怎么用啊，说明书看不懂" →
```

三条示例通常够用，**顺序有讲究**：把最典型的放第一条，
最后一条放最接近当前输入的（近因效应）。

⚠️ 注意偏差：示例的分布会成为强先验。
如果你给了 5 条示例里 4 条是"投诉"，模型会倾向于把边界case也判成投诉。
**示例要均衡覆盖各类别**。

## 三、角色设定：不是cosplay，是激活领域

**机制**：角色描述会把模型拉到对应领域的语料分布上，
同时隐式设定了"什么算好答案"的标准。

```text
❌ 弱：你是一个专家。请分析这段代码。

✅ 强：你是一位有十年经验的 Python 后端工程师，
     特别关注并发安全和资源管理。
     审查以下代码，只报告会导致线上故障的问题，
     不要提代码风格偏好。
```

关键在**后半句的约束**。"专家"这种词太泛，
真正起作用的是"只报告会导致线上故障的问题"——它削掉了 90% 的无效输出。

## 四、思维链：让它把推理摊开

**机制**：每生成一个中间 token，都是下一步推理的额外条件。
**推理链本身在给模型提供更多的计算步数**。

```text
❌：这家公司 2023 年营收 100 万，2024 年 150 万，增长率是多少？

✅：请一步步计算，先写出计算公式，再代入数字，最后给出结果。
```

对数学和逻辑题，这个技巧的收益是最大的，往往能把准确率从 40% 拉到 80%+。

⚠️ 但要注意：**思维链会显著增加 token 消耗和延迟**。
简单问题用它属于浪费。而且对于创意写作这类任务，
强制"一步步想"反而会让输出变得呆板。

**最新实践**：对支持推理的模型（o1 类），不需要手写 CoT，
模型内部已经做了；强行要求"一步步思考"反而可能干扰。

## 五、输出格式约束

**机制**：用 schema 把输出空间直接钉死，省去后处理的正则地狱。

```python
from pydantic import BaseModel
from openai import OpenAI

class ReviewResult(BaseModel):
    has_bug: bool
    severity: str          # "low" | "medium" | "high"
    issues: list[str]

client = OpenAI()
r = client.chat.completions.parse(     # 注意是 .parse 不是 .create
    model="gpt-4o",
    messages=[{"role": "user", "content": "审查这段代码：\n" + code}],
    response_format=ReviewResult,
)
print(r.choices[0].message.parsed.severity)   # 直接是对象，不用 json.loads
```

用 JSON Schema / Pydantic 约束比在 prompt 里写"请输出 JSON"靠谱得多——
后者仍有概率输出 ```json 代码块包裹或前后加解释文字。

## 六、分解任务：别指望一步登天

**机制**：单次调用的能力有上限，拆开后每步的难度都落在舒适区。

```text
❌ 一步：请分析这篇 5000 字的财报，给出投资建议。

✅ 三步：
  第 1 步：提取关键财务指标（营收、利润、现金流、负债率）
  第 2 步：对比去年同期，指出变化趋势
  第 3 步：基于以上事实给出风险提示
```

**拆的依据是"中间产物是否可验证"**。
财务指标可以核对、趋势可以核对，这两步都是可验证的，
最后一步的建议才建立在可靠基础上。这也是 Chain / Pipeline 模式的由来。

## 七、让模型自己审自己

**机制**：生成和批判是两种完全不同的认知模式，
同一个上下文里让模型"生成完再自我检查"，
其实它没有真正切换视角——**必须换一次调用**。

```python
draft = call_llm(f"写一封拒绝候选人的邮件，理由：{reason}")

critique = call_llm(f"""请以收件人的角度审查这封邮件：
{draft}

指出：1) 有没有可能被误解为不尊重 2) 有没有泄露不该说的内部信息
3) 语气是否过于生硬。只列出确实存在的问题。""")

final = call_llm(f"根据以下修改意见重写邮件：\n原文：{draft}\n意见：{critique}")
```

**"只列出确实存在的问题"** 这句很关键。不加的话，
模型为了显得有用，会硬找一些问题出来（谄媚倾向）。

## 八、负面约束要说清楚

**机制**：模型的默认分布倾向于"全面地、冗长地回答"。
不说"不要什么"，它就会给你一堆你不想要的。

```text
分析这段代码。

不要：
- 不要复述代码在做什么
- 不要提命名风格和格式问题
- 不要给修改建议，只指出问题
- 不要使用"总的来说""综上所述"这类套话
```

⚠️ 有个反直觉的坑：**"不要想大象"反而会唤起大象**。
所以负面约束要用**正向替代**来表述：

```text
❌：不要写得很长。
✅：控制在 100 字以内。

❌：不要用技术黑话。
✅：用给非技术同事解释的口吻来写。
```

## 九、给不确定留退路

**机制**：模型有强烈的"必须给个答案"倾向，
不知道时会编。明确允许说不知道，能大幅降低幻觉。

```text
基于以下资料回答问题。
如果资料中没有提到，直接回答"资料中未提及"，不要推测或补充背景知识。

资料：
{{ context }}

问题：{{ question }}
```

这一条在 RAG 场景是**必加项**。不加的话，
检索没命中时模型会用参数知识编一个看起来很像真的答案——
这是 RAG 系统最危险的一类故障。

## 十、把 prompt 当代码管理

这是工程实践，不是技巧，但决定成败。

```python
# prompts/review.py —— prompt 也是源码，要版本化
SYSTEM_REVIEW = """你是一位有十年经验的 {language} 工程师。
审查以下代码，只报告会导致线上故障的问题。

输出格式：
{{"issues": [{{"line": int, "problem": str, "fix": str}}]}}

不要提及代码风格问题。
"""

def build_review_prompt(code: str, language: str = "Python") -> str:
    return SYSTEM_REVIEW.format(language=language) + f"\n\n代码：\n```\n{code}\n```"
```

配套的几条纪律：

1. **变量化**：把 `{language}`、`{context}` 抽出来，别硬编码
2. **版本化**：prompt 改动要能回滚，改坏了立刻能定位
3. **测试集**：准备 20~50 个典型 case，改 prompt 就跑一遍回归
4. **A/B 对比**：不要凭"感觉好了"，要用测试集上的准确率说话

```python
# 最朴素的 prompt 回归测试
CASES = [("这段代码有 SQL 注入吗……", True), ("……", False)]

def regression_test(prompt_fn):
    ok = sum(predict(prompt_fn(c.text)) == c.expected for c in CASES)
    print(f"准确率: {ok}/{len(CASES)}")
```

没有测试集的 prompt 优化，本质上是在掷骰子。

## 十一、一张表：什么时候用哪个

| 技巧 | 适用场景 | 不适用场景 |
|---|---|---|
| 分隔符 | 任何含外部输入的任务 | 输入可控且极短 |
| Few-shot | 格式/风格需要严格一致 | 示例会泄露或类别过多 |
| 角色设定 | 需要专业视角 | 通用闲聊 |
| 思维链 | 数学、逻辑、多步推理 | 简单问答、创意写作 |
| 格式约束 | 程序化消费输出 | 面向人阅读 |
| 任务分解 | 复杂长任务 | 一步能搞定的 |
| 自我批判 | 质量敏感内容 | 追求低延迟 |
| 负面约束 | 模型总是多说废话 | 需要发散创意 |
| 允许不知道 | RAG、事实问答 |  brainstorming |

## 十二、小结

- 写 prompt 的本质是**收窄输出分布**，不是"跟 AI 好好说话"
- 十种技巧里**性价比最高的是：输出格式约束、允许说不知道、负面约束**
- 思维链对推理题效果显著，但别滥用——它很贵
- 负面约束要用**正向替代**表述（"控制在100字" 优于 "不要写太长"）
- **prompt 要当代码管**：变量化、版本化、有测试集
- 任何"万能模板"都会过期，**原理不会**
