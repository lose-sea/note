# 从 BERT 到 GPT——预训练模型的演进

**承上**：前面我们搭好了 Transformer 骨架（5-3）、打通了分词与 Embedding（5-4）。但同样是这套骨架，BERT 和 GPT 却长成了完全不同的东西。

**本篇**：讲清预训练模型走过的三条路线——Encoder-only（BERT）、Decoder-only（GPT）、Encoder-Decoder（T5），它们的**能力边界**在哪，以及为什么今天的大模型几乎全是 Decoder-only。我们会实际跑一遍 BERT 填空和 GPT 续写，亲眼看到"双向"与"单向"的差别。

**启下**：为什么 BERT 做"填空"、GPT 做"续写"，会带来这么大的能力差异？下一篇《预训练目标——MLM 与 CLM 到底在学什么》手算这两种损失，并解释"只是预测下一个词，为什么就能学会推理"。

**学完这一节，你能动手做**：

1. 说清三条架构路线各自适合什么任务，不再选错模型
2. 用 BERT 做完形填空、用 GPT 做续写，验证双向 vs 单向的差异
3. 用 BERT 提取句向量做语义检索，并明白为什么 GPT 的原始向量不适合直接检索

---

## 一、关键分水岭：能不能"看后面"

一切的差别，源于**注意力 mask** 这一个开关：

```
                能不能看后面的词？
                        │
        ┌───────────────┴───────────────┐
        │ 能（双向）                     │ 不能（单向/因果）
        ↓                               ↓
   Encoder-only                    Decoder-only
     BERT 家族                      GPT 家族
        │                               │
   擅长"理解"                       擅长"生成"
   分类/抽取/检索                   对话/写作/代码
   需要加任务头微调                  靠 prompt 直接用
```

- **BERT**：训练时把句子里的词随机盖住，让它猜被盖住的词。要猜对，就必须**同时看左右两边**，所以是双向注意力。
- **GPT**：训练时让它预测下一个词。预测第 5 个词时，第 6 个词还没出现，自然**只能看左边**，所以是因果注意力。

**这个训练目标的差异，一路传导成了能力差异**：BERT 天生是个"完形填空高手"（理解强、生成废），GPT 天生是个"接话高手"（生成强、理解靠 few-shot 补）。

### 1.1 "看后面"这件事，为什么是生成与理解的分水岭？

语言理解任务（如情感分类、命名实体识别、语义匹配）本质上需要"通盘读懂整句话"。比如判断"这部电影虽然制作精良，但剧情实在乏味"的情感，你必须同时看到"精良"（正面）和"乏味"（负面）以及转折词"但"——**只有双向注意力能让每个词都同时感知左右上下文**，因此 BERT 类模型在理解任务上天然占优。

而语言生成任务（如写文章、写代码、对话）是"一个字一个字往外吐"的，生成第 t 个词时，第 t+1 个词根本还不存在，模型**逻辑上就不可能看到未来**。因果注意力完美匹配这种自回归结构。所以"能不能看后面"不是随便一个设计选择，而是**任务性质决定的硬约束**——理解要全看，生成只能看前面。这一条，贯穿了从 BERT 到今天所有大模型的架构选择。

### 1.2 一个反直觉的结论：生成模型也能"理解"

有人会想：GPT 只能看前面，是不是就"不懂"整段话？实际上，今天的 Decoder-only 大模型通过两种机制弥补：

1. **自回归把"全文"都喂进过上下文**：对话时，用户的问题、前面的多轮历史全在 prompt 里，模型生成每个回答词时，那些"前面的内容"已经包含了完整的对话上下文——它看得到你之前说的所有话，只是看不到"自己还没吐出来的那个词"。
2. **few-shot / 指令对齐**：通过在 prompt 里写明任务格式，GPT 能胜任大量理解类任务（分类、抽取、匹配），不一定非得用 BERT。

所以"单向=不会理解"是过时的刻板印象。准确的说法是：**BERT 在"纯理解、有标注、要句向量"的场景更高效，GPT 在"通用、靠 prompt、要生成"的场景更灵活**。这也是下一节要细说的选型逻辑。

### 1.3 "预训练 + 微调" vs "预训练 + prompt"：范式转移

在 BERT 时代（2018-2021），解决一个新任务的流程是：拿预训练 BERT → 在标注数据上微调 → 得到专用模型。每个任务一个模型，上线要维护一堆。

到了 GPT 时代（2022 至今），流程变成：一个强大的基座大模型 → 靠 prompt/指令直接做任务，必要时加 RAG 或少量 SFT。优点是一个模型服务所有任务，迭代极快，无需每任务单独训练。

这条"从微调范式转向 prompt 范式"的主线，是理解"为什么今天大模型这么火"的关键：它把 NLP 从"算法工程师调模型"变成了"产品经理写 prompt + 工程师做工程"。作为开发者，你今天 80% 的应用工作都在 prompt 和工程编排上，而不是训练模型——这也是本专栏阶段 6 以后重点要讲的能力。

有人会想：GPT 只能看前面，是不是就"不懂"整段话？实际上，今天的 Decoder-only 大模型通过两种机制弥补：

1. **自回归把"全文"都喂进过上下文**：对话时，用户的问题、前面的多轮历史全在 prompt 里，模型生成每个回答词时，那些"前面的内容"已经包含了完整的对话上下文——它看得到你之前说的所有话，只是看不到"自己还没吐出来的那个词"。
2. **few-shot / 指令对齐**：通过在 prompt 里写明任务格式，GPT 能胜任大量理解类任务（分类、抽取、匹配），不一定非得用 BERT。

所以"单向=不会理解"是过时的刻板印象。准确的说法是：**BERT 在"纯理解、有标注、要句向量"的场景更高效，GPT 在"通用、靠 prompt、要生成"的场景更灵活**。这也是下一节要细说的选型逻辑。

## 二、三条架构路线全景

| 维度 | Encoder-only | Decoder-only | Encoder-Decoder |
|---|---|---|---|
| 代表 | BERT、RoBERTa、DeBERTa | GPT 系列、LLaMA、Qwen、DeepSeek | T5、BART、GLM（部分） |
| 注意力 | 双向，无 mask | 因果，下三角 mask | Enc 双向 + Dec 因果 + 交叉注意力 |
| 预训练目标 | MLM（掩码语言模型） | CLM（因果语言模型） | Span corruption / 去噪 |
| 核心能力 | 理解、表示 | 生成（+理解） | 序列到序列变换 |
| 典型任务 | 分类、NER、语义匹配、检索 | 对话、写作、代码、推理 | 翻译、摘要、改写 |
| 怎么用 | 加任务头 + 微调 | prompt / 指令 | prompt（带前缀） |
| 上下文 | 通常 512 | 4K ~ 1M+ | 通常 512 ~ 4K |

### 时间线：从 BERT 到今天的 GPT 们

```
2018.06  GPT-1      Decoder-only 预训练 + 微调        1.1 亿参数
2018.10  BERT       Encoder-only + MLM，横扫 NLP 榜单   3.4 亿
2019.02  GPT-2      Zero-shot，能写连贯文章            15 亿
2019.10  T5         把所有任务统一成"文本到文本"        110 亿
2020.05  GPT-3      Few-shot / 涌现能力，1750 亿
2022.03  InstructGPT RLHF 对齐，开启 ChatGPT 时代
2023.02  LLaMA      开源基座，引爆开源生态              7B~65B
2023.03  GPT-4      多模态 + 强推理
2024~    Qwen2.5 / DeepSeek-V3 / Llama-3   MoE、长上下文、推理模型
```

**趋势极其清晰**：参数越来越大、**Decoder-only 一统天下**、从"微调适配任务"转向"指令 + 对齐"。

### 2.1 为什么 2018 年 BERT 风光无限，2023 年后却"失宠"了？

2018-2020 年，BERT 是 NLP 的绝对主角：它在 GLUE 等榜单上横扫，各种"BERT + 微调"的工业方案落地。但 2022 年 ChatGPT 之后，风向彻底倒向 Decoder-only，原因有三：

1. **数据利用效率**：BERT 的 MLM 只盖住 15% 的词（见下一篇），每句话只有 15% 的位置产生训练信号；GPT 的 CLM 每个位置都预测下一个词，信号密集一个数量级，能吃下更多数据、学到更多。
2. **统一范式**：GPT 一个模型既能生成又能靠 prompt 理解，省去为每类任务单独训一个 BERT + 任务头的麻烦；而 BERT 每接一个新任务就要加头 + 标注数据 + 微调，工程成本高。
3. **规模红利**：CLM 任务在 scaling law 下收益顺滑，模型越大越聪明；BERT 路线在超大参数下收益边际递减，且 Encoder-only 难以像 Decoder 那样"涌现"few-shot 和推理能力。

所以今天如果你要"新起一个 NLP 项目"，默认选 Decoder-only 大模型 + prompt/RAG，几乎总是最优解；BERT 只在"极高吞吐、超低延迟、已有海量标注"的细分场景（如实时内容审核）还保留成本优势。

### 2.2 Encoder-Decoder（T5/BART）为什么还在翻译/摘要里发光？

T5 的设计哲学很优雅：它把**所有任务都统一成"文本到文本"**（text-to-text）——翻译是"英→中"，分类是"这句话的情感是？→正面"，摘要是"长文→短文"。这种统一让一个模型用同一种训练/推理接口搞定一切，对"强序列变换"任务（翻译、摘要、改写）尤其自然，因为这类任务本就是"输入一段、输出另一段"的 Encoder-Decoder 结构。

但如前篇所说，纯文本生成/对话场景下，维护 Encoder 和 Decoder 两套缓存比纯 Decoder 复杂，且难以享受"海量单语数据"的红利，所以今天纯 Decoder-only 更主流。简言之：**做"改写/翻译/摘要"这类明确输入输出映射，T5 类依然能打；做"通用对话/推理/agent"，Decodero-only 是首选**。

### 2.3 用 Scaling Law 的视角重看这条时间线

回看时间线，2018→2024 的演进不只是"模型变多"，更是"规模遵循幂律稳定提升"的实证过程（下一篇会正式讲 Scaling Law）。关键启示：

- **GPT-1（1.1 亿）→ GPT-3（1750 亿）** 跨度三个数量级，能力从"能续写"到"能做 few-shot 算术"，不是靠换了架构，而是靠**堆数据、堆算力、堆参数**；
- **InstructGPT（2022）** 证明了"对齐"能让同样参数的模型"突然变好用"，开启了"基础能力 × 对齐"的双引擎时代；
- **2023 后开源爆发**（LLaMA、Qwen、DeepSeek），把"大模型能力"从闭源垄断变成人人可本地部署的公共资源，直接催生了今天的 AI 应用浪潮。

理解这条线，你就不会被"今天又出了个新模型"的焦虑裹挟——本质都在这条 scaling + 对齐的主轴上，只是参数、数据、训练技巧在迭代。

## 三、代码实战 1：BERT 填空 vs GPT 续写

```python
# pip install transformers torch
from transformers import pipeline

# ---------- BERT：完形填空（双向） ----------
fill = pipeline("fill-mask", model="bert-base-chinese")
text = "中国的首都是[MASK]。"
for r in fill(text)[:3]:
    print(f"{r['token_str']:6s}  score={r['score']:.4f}  → {r['sequence']}")
```

典型输出：

```
北京      score=0.9721  → 中国的首都是北京。
南京      score=0.0083  → 中国的首都是南京。
东京      score=0.0031  → 中国的首都是东京。
```

BERT 同时看到了"中国"和"首都"（左右都有），所以能高置信度填出"北京"。**它是在"理解"，不是在"创作"。**

```python
# ---------- GPT：续写（单向） ----------
gen = pipeline("text-generation", model="gpt2")
out = gen("The capital of China is", max_new_tokens=8, num_return_sequences=1)
print(out[0]["generated_text"])
```

典型输出：

```
The capital of China is Beijing, and it is the largest city in the country.
```

GPT 是在"接话"——它根据前文一个字一个字往外吐。注意它**从来没被告知答案**，只是顺着概率往下走。

**关键对照实验**：如果把 BERT 式的双向注意力用在生成上会怎样？训练时它能看到答案，推理时却看不到——**训练/推理不一致，直接生成废**。这就是为什么 BERT 不能用来聊天。

### 3.1 训练/推理不一致：一个贯穿全书的铁律

"训练时看到的东西，推理时也必须能看到"——这是所有生成模型设计的黄金法则（teacher forcing 的隐患也在这里）。BERT 的 MLM 训练时把答案盖住的词"旁边"露了出来，等于"开卷考试"；推理时做生成是"闭卷"——能力完全用不上，所以 BERT 写不出连贯文章。

反过来，GPT 训练时预测第 t 个词只用前 t-1 个词，推理时生成第 t 个词同样只用前 t-1 个词——**训练和推理的自回归条件完全一致**，所以它能"现学现卖"地往外生成。这个一致性，是 GPT 能聊天、能续写、能做 agent 的根本前提。记住它，你以后设计任何生成式模型/任务时都不会犯"开卷训练、闭卷推理"的错。

## 四、代码实战 2：为什么 BERT 适合做检索，GPT 不适合？

这是实际应用里最容易踩的坑。我们用**句向量余弦相似度**来看：

```python
import torch
import torch.nn.functional as F
from transformers import AutoTokenizer, AutoModel

def mean_pooling(last_hidden, attention_mask):
    """把 token 向量按 attention_mask 平均成句向量（忽略 padding）。"""
    mask = attention_mask.unsqueeze(-1).float()
    return (last_hidden * mask).sum(1) / mask.sum(1)

def sentence_emb(model_name, sentences):
    tok = AutoTokenizer.from_pretrained(model_name)
    m = AutoModel.from_pretrained(model_name)
    enc = tok(sentences, padding=True, truncation=True, return_tensors="pt")
    with torch.no_grad():
        out = m(**enc)
    return F.normalize(mean_pooling(out.last_hidden_state, enc["attention_mask"]), dim=-1)

sents = ["如何训练一个大模型", "大模型微调需要多少显存", "今天股市收盘上涨"]
vecs = sentence_emb("bert-base-chinese", sents)

sim = vecs @ vecs.T
print("句向量余弦相似度矩阵:")
print(sim.round(3))
print("\n(1,2) 相关话题:", round(float(sim[0][1]), 3))
print("(1,3) 无关话题:", round(float(sim[0][2]), 3))
```

典型输出：

```
句向量余弦相似度矩阵:
tensor([[1.000, 0.712, 0.318],
        [0.712, 1.000, 0.296],
        [0.318, 0.296, 1.000]])

(1,2) 相关话题: 0.712
(1,3) 无关话题: 0.318
```

相关话题 0.712，无关话题 0.318——**区分度不错**，这就是语义检索（RAG 的基础）能工作的原因。

**为什么不能直接拿 GPT 的输出向量做这个？**

1. **因果 mask 让前面的 token 看不到后面**：第 1 个词的向量里完全没有"大模型"这个后文信息，整句的表示是**残缺**的。
2. **训练目标不同**：GPT 的每个位置都在为"预测下一个词"服务，向量里编码的是"下一个词可能是什么"，而不是"这句话是什么意思"。

> 所以现在的通用做法是用**专门的 Embedding 模型**（bge、gte、text-embedding-3、Qwen3-Embedding）——它们本质是 BERT 架构 + 对比学习训练，专为"句子级语义"优化。这一点在阶段 7 RAG 会详细展开。

### 4.3 一个常见误区：用 GPT 的"最后一层最后一位"做句向量

既然 GPT 不能直接用原始向量，有人会想：那我取它"最后生成位"的向量当句向量行不行？理论上，最后一个位置的向量确实"看完了整句话"，聚合信息最全。但问题在于它的训练目标是"预测下一个词"，向量里编码的是"接下来该吐什么"而非"这句话的语义"，用于相似度检索时区分度仍然远不如专门的 Embedding 模型。

如果一定要用 GPT 类模型做检索，更靠谱的做法是：用"指令式句向量模型"（如基于 Qwen 微调的 Qwen3-Embedding），它们把生成模型改造成"编码模式"，专门输出句向量。一句话：**检索是独立任务，要用专门的模型，不要蹭生成模型的边**。

### 4.1 mean-pooling 为什么比"取 [CLS]"更常用？

BERT 原始设计用 `[CLS]` 位置的向量作句向量。但实践发现，**对所有 token 做 mean-pooling（按 attention_mask 平均）通常效果更好**：因为 `[CLS]` 只有一个位置，信息容量有限，而 mean-pooling 聚合了全句所有 token 的信息。这也是为什么上面代码用 mean_pooling 而非直接取 `last_hidden[:, 0]`。

但要注意：**mean-pooling 必须乘 attention_mask**，否则 padding 的 `<pad>` 位置的向量也会参与平均，把噪声灌进句向量（又是 mask 的功劳）。这个细节再次说明：做 NLP 工程，mask 无处不在。

### 4.2 为什么专门 Embedding 模型比 BERT-base 更强？

通用 BERT 的句向量之所以能用，是因为 MLM 训练让语义相近的句子在向量空间里靠近。但 BERT-base 毕竟是为"填空"训练的，句向量质量有限。专门的 Embedding 模型（bge、gte 等）额外做了**对比学习（contrastive learning）**：把"含义相同的句对"向量拉近、"不同的"推远，直接优化"检索区分度"这个目标。所以在向量数据库/RAG 场景，务必用专门的 Embedding 模型，而不是拿生成模型或原始 BERT 凑合——差距可能从 0.7 相似度掉到 0.3，检索召回率天差地别。

## 五、如何选模型：一图流决策

```
你的任务是要"生成新文本"吗？
    │
    ├─ 是 → Decoder-only（Qwen / DeepSeek / GPT-4o / LLaMA）
    │
    └─ 否（只要理解/分类/匹配）
            │
            ├─ 需要句向量做检索/聚类 → Embedding 模型（bge / gte / Qwen3-Embedding）
            │
            ├─ 需要判别/分类/抽取，且有标注数据 → BERT 类 + 微调（又快又省）
            │
            └─ 需要翻译/摘要这类"输入→输出"变换 → T5 / 或直接让大模型做（现在更常见）
```

**实战建议（2026 年的现状）**：

- **绝大多数场景直接用 Decoder-only 大模型 + prompt**，开发最快；
- BERT 类模型只在**高吞吐、低延迟、有标注数据**的场景（如每天的千万级内容审核）还有成本优势；
- 检索/向量化**一定用专门的 Embedding 模型**，不要拿生成模型凑合。

### 5.1 选型时的"隐藏维度"：延迟、成本、部署

选型不能只看"能力"，还要看工程现实：

- **延迟**：BERT-base（110M）推理几十毫秒，大模型动辄几百毫秒到几秒。实时场景（如搜索框联想）BERT 类仍有优势。
- **成本**：大模型 API 按 token 计费，高频调用成本不低；本地小模型（如 Qwen2.5-3B）一次部署长期零边际成本。
- **部署**：BERT 类单机 CPU 就能跑；70B 大模型需要 GPU 集群。很多公司"简单任务用本地小模型、复杂任务调云端大模型"做分层。

所以"选模型"本质是**在能力、延迟、成本、部署四角里找平衡点**，没有银弹。

### 5.2 基座 vs Instruct vs Chat：同一架构的三个"成品态"

同一个 Decoder-only 骨架，经过不同阶段训练，会变成不同"成品"（详见下一篇三阶段）：

- **base（基座）**：只做完预训练（CLM），只会续写，不会回答问题；
- **Instruct（指令）**：在 base 上做 SFT，听得懂"请做 X"；
- **Chat（对话）**：再做对齐（RLHF/DPO），会聊天、安全、有用。

你下载模型时务必看后缀：`Qwen2.5-7B` 是 base（续写），`Qwen2.5-7B-Instruct` 才是对话版。拿 base 当聊天机器人用，它会"车轱辘话"式续写，完全答非所问。

### 5.3 一个实战速查：我该从哪个模型起步？

给完全不知道怎么选的初学者一个落地建议：

1. **学原理 / 写 demo**：本地跑 `Qwen2.5-0.5B/3B` 或 `gpt2`，免费、快、能跑通全流程；
2. **做中文应用原型**：直接调 `Qwen2.5` / `DeepSeek` 的 API，中文强、便宜；
3. **做检索/RAG**：配一个 `bge-m3` 或 `Qwen3-Embedding` 做向量化；
4. **要数据不出域**：部署 `Qwen2.5-7B/14B` 到本地 GPU（阶段 10 讲部署）；
5. **极端成本敏感 / 高并发简单任务**：保留一个微调过的 `BERT` 类小模型做分类/审核。

这条清单覆盖了 90% 的应用起点。随着你深入，会自然演化出"小模型打辅助 + 大模型做核心"的分层架构。

### 5.4 别被"参数焦虑"带偏：选模型看的是"匹配度"

最后泼一盆冷水：很多人一上来就追求"最大的模型"，结果又贵又慢还容易过度生成。模型选型的核心不是"谁最大"，而是"谁最匹配你的任务 + 成本预算 + 延迟要求"。一个 7B 模型对你的任务如果已经 95% 准确，上 70B 只多 2% 却贵 10 倍、慢 5 倍，通常不值。先用小模型建立基线和成本基准，再按需升级——这是工程上最稳的节奏。

## 六、常见坑

| 坑 | 现象 | 正确做法 |
|---|---|---|
| 拿 BERT 做生成 | 输出重复、不通顺 | 生成任务必须用 Decoder-only |
| 拿 GPT 的原始向量做检索 | 召回质量差 | 用专门的 Embedding 模型 |
| 以为"参数越大越好" | 小任务又慢又贵 | 7B~14B 能搞定的别上 70B |
| 忽略上下文长度 | 长文档被静默截断 | 看 `max_position_embeddings`，做分块 |
| 混用不同模型的 tokenizer | 输出乱码 | tokenizer 必须与模型严格配套 |
| 用基座模型（base）当聊天模型 | 它只会续写，不会回答问题 | 聊天要用 **Instruct / Chat** 版本 |

> 最后一条特别重要：HuggingFace 上 `Qwen2.5-7B` 是**基座模型**（只做续写），`Qwen2.5-7B-Instruct` 才是**对话模型**（经过指令微调 + 对齐）。下载时看准后缀。

### 6.1 进阶坑：多语言与领域适配

- **多语言**：很多"中文模型"其实中英混训，对日、韩、法可能退化。跨境业务要实测目标语言效果，别想当然。
- **领域 mismatch**：通用大模型在医疗、法律、金融等专业领域常犯"一本正经胡说"。正确做法不是换更大模型，而是**RAG 注入领域知识 + 领域数据 SFT**（阶段 9）。
- **版本陷阱**：模型迭代快（Qwen2 → Qwen2.5 → Qwen3），API 默认可能不是最新版，生产环境要锁版本，避免"今天好用明天崩"。

### 6.2 开源 vs 闭源：选型时另一个维度

选型还有"是否开源"的考量：

- **闭源 API（GPT-4o、Claude、Gemini）**：能力强、省部署，但按调用计费、数据要出公网、不可离线。适合快速验证、对成本不敏感、数据合规允许上云的场景。
- **开源模型（Qwen、DeepSeek、LLaMA）**：可本地/私有云部署、数据不出域、可微调、一次部署长期零边际成本，但需自己解决算力、推理优化、运维。适合数据安全要求高、调用量大、需定制的场景。

很多公司的成熟做法是"混合"：用闭源大模型快速做原型，验证价值后用开源模型私有化部署降本。这条路径在阶段 9（微调与部署）会落地。

## 七、本篇小结

1. **一切差异源于 mask**：BERT 双向（理解），GPT 因果（生成）。训练与推理的一致性决定了各自的能力边界。
2. 三条路线：Encoder-only（BERT，理解）、Decoder-only（GPT，生成）、Encoder-Decoder（T5，变换）。
3. 演进主线：MLM 预训练 → 规模扩大涌现 few-shot → RLHF 对齐 → 开源基座 + 中文优化 + MoE。
4. **用 BERT 提句向量做相似度的实验**（0.712 vs 0.318）说明了为什么检索要用 Embedding 模型，而不能拿生成模型的向量凑合。
5. 选型口诀：**要生成用 Decoder-only，要检索用 Embedding 模型，高并发分类可留 BERT**。

## 八、实战练习（可验证小任务）

1. **填空实验**：用 `fill-mask` 跑一个英文句子（如 "Paris is the capital of [MASK]."），观察 BERT 是否高置信填出 "France"，验证双向理解。
2. **续写对比**：用 `gpt2` 对 "The capital of China is" 和 "北京是中国的" 分别续写，对比中英文下 GPT-2 的表现差异（体会上篇说的"中文压缩差、效果差"）。
3. **检索实验**：把第四节的 sents 换成你自己的 3 句话（两相关一无关），跑 cosine 相似度，验证 Embedding 模型能否把相关句区分开。
4. **选型题**：列出你手头 3 个真实需求（如"客服问答""文章分类""合同摘要"），用第五节的决策树判断各自该选哪类模型，并说明原因。
