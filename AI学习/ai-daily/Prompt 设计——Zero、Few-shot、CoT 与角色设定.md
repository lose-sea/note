## 一、Prompt 不是"问一句话"，而是"写一份需求文档"

### 1.1 什么是 Prompt，以及它为什么重要

在大模型开发的语境里，**Prompt（提示词）** 是你在一次推理调用中喂给模型的所有文本输入——它可能是 system 指令、用户问题、几个示例，也可能是工具定义和格式要求。对已经预训练好的大模型来说，你**不再改它的权重**，而是通过在输入端"下指令"来引导它的输出。这就是所谓"提示工程（Prompt Engineering）"。

很多人第一次用 ChatGPT 会觉得它"无所不能"，第二次换个说法却得到一堆废话。这并不是模型抽风，而是因为：**大模型的输出高度依赖于你给它的上下文信号**。同样的模型，一个写得好的 prompt 和一个随手敲的 prompt，质量可以差出几个数量级。在真实工程里，prompt 往往决定了产品能不能用——比如客服机器人答非所问、抽取接口把字段拼错、翻译系统丢句子，绝大多数时候都不是模型不行，而是 prompt 没把"要什么"讲清楚。

所以我们要把 prompt 当成**软件需求文档**来对待：它有明确的角色、目标、约束、输入输出样例，而且应该像代码一样被版本化管理、被测试、被复用。一个优秀的大模型应用，往往 60% 的功夫花在 prompt 与上下文设计上，剩下 40% 才是工程脚手架。

### 1.2 新手最常见的两个误区

新手最常见的错误是把 prompt 当成搜索框，随手打一句话就期待好结果：

```
❌ 帮我写个排序算法
✅ 你是一位资深 Python 工程师。请实现一个快速排序函数。
   要求：
   1. 使用原地分区，空间复杂度 O(log n)
   2. 附带类型注解和 docstring
   3. 处理空列表和单元素列表
   输出：只返回 Python 代码，不要解释。
```

第二个误区是"模型不是会聊天吗，我口述需求不就行了"。问题在于：模型没有你的业务背景，它不知道你的"排序"是指稳定的归并排序还是原地快排，不知道你用的是 Python 还是 Java，不知道输出要不要带注释。自然语言天然有歧义，**把歧义显式地消除掉，是 prompt 设计的第一要务**。

### 1.3 五段式结构：把"玄学"变成"模板"

一个好的 prompt 是一份**需求文档**。我们推荐一套五段式结构，几乎可以覆盖 90% 的业务场景：

```
┌────────────────────────────────────────┐
│ ① 角色设定   你是一位……                 │  限定知识领域与语气
│ ② 任务描述   请完成……                   │  说清要做什么
│ ③ 约束条件   要求：1. 2. 3.             │  边界、禁用项、风格
│ ④ 示例      输入… → 输出…（可选）        │  Few-shot，统一格式
│ ⑤ 输出格式   只返回 JSON / 代码 / 表格   │  让结果可被程序解析
└────────────────────────────────────────┘
```

每一段解决一个具体问题：

- **角色设定** 决定"谁来回答"。让模型以某个专家身份作答，能显著拉高术语准确性和语气一致性。
- **任务描述** 决定"回答什么"。必须是一个单一、明确、可验证的目标，而不是"帮我弄一下那个东西"。
- **约束条件** 决定"边界在哪"。包括格式、长度、禁用项、风格、必须覆盖的点。约束越具体、越可验证越好——"要专业一点"这种口号式约束基本没用，而"理由不超过 20 字，且不得出现形容词"才是可校验的。
- **示例** 是 Few-shot 的核心，后面会专讲。它用"做给你看"的方式统一格式与风格。
- **输出格式** 决定"结果怎么被程序消费"。这是工程化落地的关键——只要模型吐出的是规范 JSON，你就不需要再写一堆脆弱的正则去抠字符串。

### 1.4 为什么"角色设定"真的有用（它背后发生了什么）

这是一个常被质疑的点："模型又不是真人，我给它安个头衔有什么用？" 答案是：**有用的，因为它在重塑模型的输出分布**。

回顾阶段 5 讲过的预训练：模型在海量互联网文本上训练过，它"见过"大量"资深工程师写的代码解说"、"医生写的诊断建议"、"律师写的合同条款"。当你说"你是一位资深 Python 工程师"时，你实际上是在**把模型的采样分布往"那类文本"上引导**。它并没有真的变成工程师，但在自回归生成时，它更可能采样到工程师语境下的词（专业术语、规范风格、克制解释欲），而不是普通网友闲聊的语气。

换句话说，角色设定是一种**廉价的"领域偏置"**，几乎零 token 成本，却能把输出从"通用平均态"推向"专业态"。这也是为什么在分类、抽取、翻译、代码生成等任务里，加上一句角色设定，质量往往肉眼可见地提升。

> 补充直觉：可以把大模型想象成一个读过全图书馆书的人。你说"你是一位律师"，不是在让它变聪明，而是在告诉它"请用地契纠纷那排书架里的说话方式回答我"。它本来就会，但你得提示它从哪排书架取词。

### 1.5 Prompt 的边界：它解决不了什么，该找谁

理解 prompt 的上限，是成为合格大模型开发者的分水岭。提示工程**不能**改变模型的固有知识边界——它不知道你公司昨天的内部数据，也不会凭空学会一门从没见过的编程语言。当下面这些情况出现时，光靠 prompt 就不够了，要换武器：

- **知识过时或私有**：模型背的是训练截止日之前的公开数据。要注入"你司 2026 年的产品手册""我的私人笔记"，靠 prompt 硬塞会被上下文窗口和"迷失在中间"效应反噬——正确做法是用 **RAG（阶段 7）** 检索注入。
- **风格/能力怎么调都不到位**：比如你想让一个 7B 小模型稳定做复杂法律推理，prompt 再怎么写也顶不上大模型。这时考虑 **微调（阶段 9）**，把能力"烧"进权重。
- **需要动手做事**：模型只能"说"，查天气、调数据库得靠 **Function Calling（下一篇之后）** 把你的函数接上。

一句话记忆：**prompt 负责"怎么问"，RAG 负责"喂什么知识"，微调负责"变成什么样的人"，Function Calling 负责"能不能动手"**。四者互补，构成大模型应用工程的四块基石。把一件"该微调"的事硬用 prompt 凑，既贵又脆；反之亦然。

## 二、四种策略：什么时候用哪个

提示工程的"策略"本质上是在问：**我需要多少额外的引导信号，才能让模型把这件事做对？** 下面四种是最高频的组合拳。

| 策略 | 做法 | 适用场景 | 代价 |
|---|---|---|---|
| **Zero-shot** | 直接说任务，不给示例 | 通用任务、模型能力范围内的 | 最省 token |
| **Few-shot** | 给 2~5 个"输入→输出"示例 | 格式特殊、风格固定、分类标签明确 | 消耗 token，但最稳 |
| **CoT（思维链）** | 要求"一步步思考后再给答案" | 数学、逻辑、多步推理 | 输出变长，成本上升 |
| **角色设定** | 指定身份与专业领域 | 需要领域术语、特定语气 | 几乎零成本 |

### 2.1 经验法则：一条递进的调试路径

不要一上来就堆示例。推荐的调试顺序是"由俭入奢"——先试最省的方式，不够再叠加：

```
先试 Zero-shot
   ↓ 输出格式不稳定 → 加 Few-shot
   ↓ 结果算错了     → 加 CoT
   ↓ 语气/术语不对  → 加角色设定
   ↓ 还是不行       → 考虑微调（阶段 9）或 RAG（阶段 7）
```

这条路径的意义在于**控制成本与复杂度**。Zero-shot 最便宜，能解决就别浪费 token 写示例；只有格式真的稳定不下来才上 Few-shot；只有"推理跳步"导致结果错才上 CoT；语气不对再用角色设定收尾。绝大多数工程问题，在这四步之内都能解决，不必动辄微调。

### 2.2 Zero-shot：什么时候它已经够用

Zero-shot 指的是"不给任何示例，直接描述任务"。现代大模型（尤其是 GPT-4o、Claude、Qwen2.5、DeepSeek 这类强模型）在大量指令数据上做过对齐（RLHF / DPO），对"翻译这段话""总结这篇文档""给这段评论分类"这类常规任务，往往**零示例就能给出合格结果**。

适合 Zero-shot 的特征：
- 任务在预训练/对齐数据里大量出现（翻译、摘要、分类、常识问答）；
- 输出格式简单（一段话、一句话、一个标签）；
- 对"风格一致性"要求不高。

一旦 Zero-shot 的输出开始出现"格式飘忽""漏字段""偶尔答非所问"——这是典型信号，该上 Few-shot 了。

### 2.3 Few-shot：用"示范"统一格式与风格

Few-shot 的核心思想来自语境学习（In-Context Learning，ICL）：模型能从你给的几个示例里，**推断出你想要的格式和规律**，即使你从没显式说明规则。这就像你给一个聪明人看了两道例题，他就能照着做第三道——而不需要你写一份方法论。

写 Few-shot 示例的三条铁律：
1. **示例要覆盖边界情况**：别只给"正常输入"。要包含空输入、超长输入、异常输入。否则模型遇到边界就懵。
2. **示例标签要均衡分布**：分类任务里，如果你给的 5 个示例全是"正面"，模型会默认往"正面"偏。要按真实分布均匀采样。
3. **示例质量 > 示例数量**：2~3 个高质量、格式完美的示例，通常胜过 10 个潦草示例。一般 3~5 个足矣，再多 token 暴涨且容易被示例带偏。

### 2.4 CoT（思维链）：让模型"把过程写出来"

#### 什么是 CoT

CoT（Chain-of-Thought，思维链）是指：在问复杂问题时，明确要求模型**先一步步推理，再给最终答案**。它最早由 Google 在 2022 年的论文中提出，是提示工程史上最重要的技巧之一。

#### CoT 为什么有效（原理拆解）

因为**自回归模型不能"回头改"**。模型是一个 token 一个 token 往外吐的。如果它第一句就直奔结论、跳过了中间推理，那一旦中间某步错了，它没有任何机会回头修正——错误会顺着生成一直传递下去。

让它把中间步骤写出来，等于做了三件事：

1. **把一步到位的难题，拆成多个简单子问题**。每一步只需要解决一个小的推理环节，单步准确率远高于"一步登天"。
2. **每一步都能"看到"前面的推理**，相当于在每一步都给了模型更多的上下文信息，等于给自己更多的"计算机会"（这也是为什么推理模型效果强——它们把更多算力花在中间思考上）。
3. **出错了你能定位是哪一步错的**。这不仅是工程调试价值，更意味着你可以让模型"反思"哪一步不对——这是后续 Agent / ReAct 范式的雏形。

经典对比（同一个算术题）：

```
普通问法：
  问：一个书架有 3 层，每层放 15 本书，又买了 12 本放上去，现在一共几本？
  答：57        ← 错了（3×15+12 = 57，这次对了；但复杂题常错）

CoT 问法：
  问：……请一步步思考后再给出答案。
  答：
    第 1 步：3 层 × 每层 15 本 = 45 本
    第 2 步：45 + 新买的 12 本 = 57 本
    答案：57 本
```

> 现在的推理模型（如 DeepSeek-R1、Qwen3 的思考模式）已经把 CoT 内化了——它们会先输出一段"思考过程"再给答案，你甚至不需要在 prompt 里写"一步步思考"。但原理一致：**中间步骤 = 更多的计算机会**。对这类模型，你反而要小心"过度思考"导致输出太长、变慢、变贵，可以酌情用较短的系统提示约束它。

#### CoT 的变体

- **Zero-shot CoT**：只加一句"让我们一步步思考"（Let's think step by step），不给定具体示例，也能触发链式推理。这是最省事的 CoT 用法。
- **Self-Consistency（自洽）**：同一个问题采样多条推理路径，用不同答案投票。数学题准确率能再上一个台阶，代价是 N 倍调用成本（对应 API 里的 `n` 参数）。

### 2.5 角色设定：廉价的"领域偏置"

前面 1.4 已经讲过原理。这里补一句工程建议：**角色设定和任务类型要匹配**。让"资深 Python 工程师"去写营销文案，不如让"资深品牌文案"。角色设定本质上是在"选择模型采样时偏置的那一簇文本"，选错了簇，反而把模型往错误方向带。常见写法：

- 代码：`你是一位有 10 年经验的 Python 后端工程师，熟悉 PEP8 与类型注解。`
- 法律：`你是一位严谨的中国执业律师，回答需引用法条，且标注"仅供参考，不构成法律意见"。`
- 客服：`你是一位耐心的电商客服，语气友好，先共情再给方案。`

### 2.6 四种策略怎么组合（一个完整示例）

单独看每种策略容易，实战里往往是**叠加使用**的。把一次"让模型从用户评论里抽取结构化信息"的任务拆开看：

```
角色设定  → "你是一位严谨的电商数据分析师"        （定语气与术语）
任务描述  → "从下面评论中抽取：商品名/价格/满意度"   （定目标）
Zero-shot → 先不发示例，看模型裸答能否达标
Few-shot → 若格式飘忽，补 2~3 个"评论→JSON"示例   （定格式）
CoT      → 若抽取经常漏字段，加"先列出你识别到的实体，再生成 JSON"
输出格式  → "只返回一行 JSON，字段缺失填 null"       （定可解析性）
```

可以看到，一次真实调用里，角色设定 + 任务 + 示例 + 输出格式几乎是"标配"，CoT 视任务难度决定是否叠加。这也呼应了篇首的五段式——它本身就是四种策略的工程化落地。

一个容易踩的反向陷阱是**过度设计**：一个"把中文翻译成英文"的简单任务，你硬上 5 个示例 + CoT + 复杂角色，只会白白多花 token、拖慢响应。原则始终是：用**刚好够用**的信号把任务做对，不多不少。

## 三、代码实战 1：写一个可复用的 Prompt 构建器

把 prompt 当成代码来管理，而不是散落在业务里的字符串拼接。这样做的好处贯穿整个项目生命周期：可以版本化、可以做单元测试、可以针对不同模型切换模板，而不是在业务代码里到处拼字符串。

```python
from dataclasses import dataclass, field
from typing import Optional

@dataclass
class PromptBuilder:
    """五段式 Prompt 构建器（呼应阶段 0 的面向对象那篇）。"""
    role: str = ""
    task: str = ""
    constraints: list[str] = field(default_factory=list)
    examples: list[tuple[str, str]] = field(default_factory=list)
    output_format: str = ""

    def set_role(self, role: str) -> "PromptBuilder":
        self.role = role
        return self                      # 返回自身，支持链式调用

    def set_task(self, task: str) -> "PromptBuilder":
        self.task = task
        return self

    def add_constraint(self, c: str) -> "PromptBuilder":
        self.constraints.append(c)
        return self

    def add_example(self, inp: str, out: str) -> "PromptBuilder":
        self.examples.append((inp, out))
        return self

    def set_output_format(self, fmt: str) -> "PromptBuilder":
        self.output_format = fmt
        return self

    def build(self) -> str:
        parts = []
        if self.role:
            parts.append(f"# 角色\n{self.role}")
        if self.task:
            parts.append(f"# 任务\n{self.task}")
        if self.constraints:
            body = "\n".join(f"{i}. {c}" for i, c in enumerate(self.constraints, 1))
            parts.append(f"# 要求\n{body}")
        if self.examples:
            demo = "\n\n".join(f"输入：{i}\n输出：{o}" for i, o in self.examples)
            parts.append(f"# 示例\n{demo}")
        if self.output_format:
            parts.append(f"# 输出格式\n{self.output_format}")
        return "\n\n".join(parts)


# ---------- 用法：一个"情感分类 + 理由"的 prompt ----------
p = (PromptBuilder()
     .set_role("你是一位中文情感分析专家。")
     .set_task("判断下列评论的情感倾向，并给出一句理由。")
     .add_constraint("情感只能是：正面 / 负面 / 中性，三者之一")
     .add_constraint("理由不超过 20 个字")
     .add_example("这家餐厅的牛排太老了，服务也慢。",
                  '{"label": "负面", "reason": "抱怨食材与服务"}')
     .add_example("物流很快，包装完好，满意。",
                  '{"label": "正面", "reason": "称赞物流与包装"}')
     .set_output_format('只返回一行 JSON：{"label": "...", "reason": "..."}，不要任何额外文字。'))

print(p.build())
print("\n" + "=" * 50 + "\n")

# ---------- 同一个构建器，切到 CoT 模式 ----------
p_cot = (PromptBuilder()

**这样管理 prompt 的好处**：可以版本化、可以做单元测试、可以针对不同模型切换模板，而不是在业务代码里到处拼字符串。举一个实际例子——当模型换了供应商（比如从 OpenAI 切到 DeepSeek），你往往只需要为不同模型微调 system 措辞，而 `PromptBuilder` 的"任务 / 约束 / 示例"部分可以原样复用。更进一步，你甚至可以把每个 prompt 模板存成 YAML/JSON 文件，上线前用一批固定测试集跑回归，防止"改一个词把准确率打崩"。

## 四、代码实战 2：让模型稳定输出 JSON（含校验与重试）

大模型输出 JSON 是个高频刚需，但模型经常多说废话（"好的，这是你要的 JSON：```json ..."）。更糟的是，它有时候会输出"半个 JSON"或者夹带解释。解决方案是**三层防护**：① 宽容地把 JSON 从任意文本里抠出来；② 按 schema 做类型/枚举/长度校验；③ 校验失败就把错误信息回喂给模型，让它自我修正。

```python
import json
import re

def extract_json(text: str):
    """第 1 层：从任意文本里抠出 JSON（模型爱加 markdown 代码块和废话）。"""
    # 优先尝试直接解析
    try:
        return json.loads(text)
    except json.JSONDecodeError:
        pass
    # 去掉 ```json ... ``` 标记
    m = re.search(r"```(?:json)?\s*(.*?)```", text, re.S)
    if m:
        try:
            return json.loads(m.group(1).strip())
        except json.JSONDecodeError:
            pass
    # 找第一个 { 或 [ 到最后一个 } 或 ] 之间的内容
    for left, right in [("{", "}"), ("[", "]")]:
        s, e = text.find(left), text.rfind(right)
        if s != -1 and e != -1 and e > s:
            try:
                return json.loads(text[s:e + 1])
            except json.JSONDecodeError:
                continue
    return None


def validate(data: dict, schema: dict) -> list[str]:
    """第 2 层：按简单的类型/枚举 schema 校验。"""
    errors = []
    for key, rule in schema.items():
        if key not in data:
            errors.append(f"缺少字段 {key}")
            continue
        val = data[key]
        if "type" in rule and not isinstance(val, rule["type"]):
            errors.append(f"{key} 类型错误，期望 {rule['type'].__name__}")
        if "enum" in rule and val not in rule["enum"]:
            errors.append(f"{key} 取值 {val!r} 不在允许范围 {rule['enum']}")
        if "max_len" in rule and isinstance(val, str) and len(val) > rule["max_len"]:
            errors.append(f"{key} 超过最大长度 {rule['max_len']}")
    return errors


def call_with_retry(build_prompt, call_llm, schema, max_attempts=3):
    """第 3 层：校验失败就把错误信息回喂给模型，让它自我修正。"""
    messages = []
    for attempt in range(1, max_attempts + 1):
        raw = call_llm(build_prompt(messages))          # 伪函数：换成真实 API
        data = extract_json(raw)
        if data is None:
            messages.append("错误：你的输出不是合法 JSON，请只返回 JSON 本身。")
            continue
        errors = validate(data, schema)
        if not errors:
            return data, attempt
        messages.append("错误：" + "；".join(errors) + "。请修正后重新输出 JSON。")
    raise RuntimeError(f"{max_attempts} 次尝试后仍未得到合法输出")


# ---------- 测试第 1 层：模型常见的"脏输出" ----------
dirty_outputs = [
    '好的，这是结果：\n```json\n{"label": "正面", "reason": "物流快"}\n```',
    '{"label": "负面", "reason": "味道差"}（仅供参考）',
    '我认为应该输出：\n{"label": "中性", "reason": "没有明显情绪"}',
]
for t in dirty_outputs:
    print("脏输入 ->", repr(t[:38]), "\n  解析结果:", extract_json(t))

schema = {
    "label":  {"type": str, "enum": ["正面", "负面", "中性"]},
    "reason": {"type": str, "max_len": 20},
}
print("\n校验合法样例:", validate({"label": "正面", "reason": "物流快"}, schema))
print("校验非法样例:", validate({"label": "好评", "reason": "x" * 30}, schema))
```

运行结果：

```
脏输入 -> '好的，这是结果：\n```json\n{"label": "正面", "rea
  解析结果: {'label': '正面', 'reason': '物流快'}
脏输入 -> '{"label": "负面", "reason": "味道差"}（仅供参考）
  解析结果: {'label': '负面', 'reason': '味道差'}
脏输入 -> '我认为应该输出：\n{"label": "中性", "reason":
  解析结果: {'label': '中性', 'reason': '没有明显情绪'}

校验合法样例: []
校验非法样例: ['label 取值 '好评' 不在允许范围 ['正面', '负面', '中性'], reason 超过最大长度 20']
```

**自修正重试**是关键：把校验错误回喂给模型（"你的 label 取值『好评』不在允许范围…"），模型几乎总能在第 2 次就改对。这比自己写正则去修字符串靠谱得多。背后的原理其实是把"校验器"变成了"第二个提示"——模型看到明确错误描述后，相当于做了一次带反馈的 CoT 修正。这也是 Agent 里"工具报错回灌"这一手法的雏形（会在 Function Calling 与 Agent 篇反复用到）。

> 进阶方案：现在主流模型都支持 **JSON Schema / Structured Output 模式**（OpenAI 的 `response_format={"type": "json_object"}`、Qwen 的结构化输出、DeepSeek 的 JSON 模式），能从采样层面保证格式。**能用原生约束就别靠提示词**。但注意：原生 JSON 模式只保证"格式合法"，不保证"字段含义正确"——你仍然需要第二层的 schema 校验来兜底业务约束（比如 `label` 必须是那三个枚举值）。所以实战里往往是"原生约束 + 业务校验"双保险。

## 五、常见坑与调优清单

| 坑 | 现象 | 解法 |
|---|---|---|
| Prompt 太模糊 | 输出发散、每次都不一样 | 加约束 + 加示例 |
| 示例太多 | token 暴涨、模型被示例带偏 | 3~5 个足够，且要覆盖边界情况 |
| 示例有倾向性 | 模型只输出示例里的那几类 | 示例要**均衡分布**各标签 |
| 只说"不要做什么" | 模型反而更容易做 | 说"要做什么"，正面描述 |
| 长 prompt 塞满细节 | 中间的关键指令被忽略 | 关键约束放**开头和结尾**（首尾效应） |
| 一次问太多事 | 丢三落四 | 拆成多轮，一件事一次说清 |
| 不设 temperature | 结果不稳定或过于死板 | 分类/抽取用 0~0.3；创意写作 0.7~1.0 |

### 5.1 一个常被忽略的现象：首尾效应（Primacy & Recency）

大模型对 prompt 中**开头和结尾**的内容注意力最强，对**中间**最弱（这与"Lost in the Middle"论文结论一致）。所以编排 prompt 时：
- **最重要的指令**（比如"必须返回 JSON""不得编造事实"）放在角色段开头，以及输出格式段结尾；
- 大段背景知识、长文档放中间，且要意识到模型对它们中间部分的利用率会下降——这也再次指向后续 RAG 篇"只送相关片段"的思路。

### 5.2 正面描述优于负面描述

心理学上这叫"白熊效应"：你说"不要写代码"，模型脑子里先浮现的恰恰是"代码"，再被抑制。所以与其写"不要输出解释"，不如写"只输出 JSON，不要任何额外文字"。把约束写成**模型该做什么**，比写成它不该做什么更稳。

**调优 checklist（按顺序走一遍）**：

```
1. 任务描述是否只有一个明确目标？
2. 是否有 3 条以上可验证的约束（而不是"要专业一点"）？
3. 输出格式是否给出了具体样例（而不是"用 JSON"）？
4. 示例是否覆盖了边界情况（空输入、超长输入、异常输入）？
5. 是否用 5~10 条真实数据测过，而不是只试一句话？
6. 是否需要把 temperature 调低？
```

### 5.3 Prompt 的版本管理与 A/B 测试（工程化收尾）

prompt 一旦进入生产，它就不再是一句一次性文本，而是一个**会随业务演化的资产**。成熟的团队会像管理代码一样管理 prompt：

- **版本化**：每个 prompt 模板存快照（git 或配置中心），改一句话也要留 commit，方便回滚。一个经典的线上事故是"某次 prompt 微调让退款率识别准确率从 92% 掉到 70%"，没有版本记录根本查不出是哪次改动。
- **离线评测集**：维护一批固定的"输入→期望输出"用例，每次改 prompt 都跑一遍回归，量化对比（准确率、格式合规率、平均 token 数）。
- **A/B 测试**：两条 prompt 同时上线，按真实业务的下游指标（如客服满意度、抽取字段准确率）决定保留哪条，而不是凭感觉。
- **监控与告警**：线上记录每次 prompt 的实际消耗 token 与 `finish_reason`，对"输出被截断""JSON 解析失败率突增"设告警。

这一步看着"重"，但它是 prompt 从"玩具"走向"产品"的分水岭。当你需要同时服务多个业务线、多个模型供应商时，没有这套机制，prompt 会迅速变成谁也不敢动、动了就出事的"祖传咒语"。

## 六、本篇小结

1. **Prompt 是需求文档，不是搜索框**。五段式：角色 → 任务 → 约束 → 示例 → 输出格式。
2. **Zero-shot 打底，Few-shot 稳格式，CoT 提精度，角色设定调语气**。调试顺序由俭入奢，别一上来就堆示例。
3. **CoT 的本质**是把一步到位的难题拆成多个简单子问题，给模型更多"计算机会"，并让错误可定位。
4. 用 **PromptBuilder 把 prompt 当代码管理**，可版本化、可测试、可切换模板，还能针对不同供应商微调。
5. **结构化输出三层防护**：宽容解析 → schema 校验 → 错误回喂重试；能用模型原生的 JSON 模式就别只靠提示词，但仍需业务校验兜底。

## 七、实战练习（可验证小任务）

下面几个练习你都能在本地用任意一家模型的 API（或本专栏下一篇封装好的客户端）跑通并验证：

1. **五段式改造**：找一段你日常随手写的 prompt（比如"帮我总结这篇文章"），用五段式重写为带角色、约束、输出格式的版本，对比两次输出质量，记录差异。
2. **Few-shot 均衡实验**：做一个"判定用户问题是售前 / 售后 / 投诉"的三分类任务。先给 5 个全是"售后"的示例，观察模型是否偏向售后；再改成均衡示例，对比准确率。
3. **CoT 对照实验**：给一道含 3 步以上推理的数学应用题，分别用普通问法和 CoT 问法各问 5 次，统计普通问法出错率是否明显高于 CoT。
4. **JSON 鲁棒性测试**：故意让模型输出带 ```` ```json ```` 包裹和寒暄语的脏文本，用本篇第三、四节的 `extract_json` + `validate` 跑一遍，确认能稳定解析与校验。
5. **失败回灌**：构造一个必错的 schema（如要求 `label` 必须是"好评/差评"，但模型习惯输出"正面/负面"），调用 `call_with_retry`，观察模型第几次修正成功。
