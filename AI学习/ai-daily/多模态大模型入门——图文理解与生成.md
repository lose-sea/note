## 一、什么是多模态，为什么大模型必须要"看图"

### 1.1 单模态 LLM 的盲区有多严重

我们在前面的阶段里，把大模型训练成了一个极其擅长处理"token 序列"的机器。它读过互联网上几乎全部的公开文本，能写代码、能推理、能归纳。但它有一个硬边界：**它从来没见过任何一个像素**。

这个边界在真实业务里造成的断裂，比想象中严重得多。

想象你在做企业内部的知识助手（就是上一篇那个系统）。你兴致勃勃地把公司 30 份制度文档灌进向量库，上线第一天用户就问："这个报销单模板里，'差旅费'那一栏应该填在哪个格子里？"——而那份"报销单模板"，是一张扫描进来的图片。你的 PDF 解析抽出来 0 个字符，向量库里根本没有它，系统礼貌地拒答了。用户转头就说："这机器人没用。"

这类"资料看得见但模型读不懂"的情况，在实际项目中占比高得惊人：

| 真实场景 | 资料形态 | 纯文本方案的失败方式 |
|---|---|---|
| 报错排查助手 | 终端/IDE 截图 | 用户贴一张报错截图，你让他"把文字复制出来"，体验归零 |
| 财务票据处理 | 发票、收据、银行回单照片 | 扫描件无文本层，OCR 后丢版式信息（哪个数字是金额） |
| 经营分析助手 | 折线图、柱状图、透视表截图 | 即便 OCR 出了数字，也丢了"哪根线是哪个产品"的对应关系 |
| 电商商品理解 | 商品主图、详情页长图 | 图上文字是卖点，但"红色圆领"这种视觉属性 OCR 永远抽不出来 |
| 教辅/题库 | 手写作业、试卷拍照 | 印刷体 OCR 可用，手写体基本崩 |
| 工业/医疗 | 设备仪表盘、CT 片 | 完全超出文本方案的射程 |

注意第二行和第四行的区别，它揭示了"多模态"其实包含两种能力：**OCR 式的"读字"能力**，和**真正的"看懂"能力**。一张发票上"金额 1,280.00"是 OCR 能解决的；但一张商品图里"这件衣服是宽松版型、模特身高看起来 170 左右、背景是棚拍"——这跟文字毫无关系，必须靠视觉理解。

### 1.2 多模态对"大模型开发"意味着什么

从工程视角看，多模态的爆发其实有一个很朴素的原因：**对 LLM 来说，图片只是另一种 token**。

回想 Transformer 的本质：它吃一个 token 序列，做自注意力，输出一个 token 序列。它根本不关心这些 token 来自中文、英文、Python 代码，还是来自一张猫的照片。只要你能把图像变成一串"和文本 token 在同一语义空间里的向量"，把它拼在文本 token 前面，剩下的事情——注意力、上下文、解码、采样——**全都不用改**。

这就是为什么多模态在 LLM 时代进展如此之快：前人已经在文本上花了几百亿美金把主干网络训好了，多模态只需要解决"怎么把图翻译成 token"这一个接口问题。

这个视角对我们开发者极其重要，它意味着：

1. **你已有的 Prompt 工程、上下文管理、成本控制、Function Calling 技能，全部可以平移过来**。看图问答的本质仍然是"拼一段上下文，让模型续写"。
2. **新增的成本项只有一个**：图片会消耗大量 token（一张高清图常常相当于几百到上千个文本 token），所以图片是多模态应用里最需要精打细算的资源。
3. **新增的风险项也只有两个**：视觉幻觉（图里没有的东西它说有）和数据出网（截图里往往有敏感信息）。

## 二、核心难题：怎么让模型"看见"图

### 2.1 问题的形式化表述

文本对 LLM 是天然的：一段话 → Tokenizer → `[101, 2345, 6789, ...]` → 查 Embedding 表 → 一串向量 → 进 Transformer。

图像不是。一张 1024×1024 的 RGB 图，本质是一个 `1024 × 1024 × 3` 的连续数值张量，共 314 万个浮点数。它有三个和文本根本不同的性质：

- **它是连续的，没有天然离散单元**（文本有词）；
- **它是二维/三维结构的**（文本是一维序列）；
- **它信息密度极不均匀**（大片纯色背景几乎无信息，一小行小字才是关键）。

所以核心难题就是：**如何把三维连续张量，变成一维的、离散的（或至少是"类 token 的"）、且与文本语义对齐的序列**。

### 2.2 两条技术路线

| 路线 | 做法 | 代表 | 优点 | 缺点 |
|---|---|---|---|---|
| **离散化**（Discrete Visual Token） | 用 VQ-VAE/VQGAN 把图像压缩成码本里的离散 ID，直接当词表里的词用 | DALL·E 1、Chameleon、Emu2（部分） | 与文本完全同构，可以用同一个词表和同一套自回归目标做"文生图"和"图生文" | 量化损失大，细节差；码本训练复杂 |
| **连续化**（Continuous Visual Embedding） | 视觉编码器输出连续向量，投影到 LLM 的词嵌入维度，直接拼进序列 | LLaVA、BLIP-2、Qwen-VL、InternVL、MiniCPM-V | 信息保留完整，实现简单，可直接复用预训练好的 CLIP 视觉塔和 LLM | 不能反向"生成图片"（因为输出还是文本 token） |

**当今主流多模态大模型（MLLM，Multimodal Large Language Model）几乎全走第二条路。** 原因很现实：CLIP 的视觉塔已经免费提供了"和文本对齐得很好的图像向量"，而第一条路需要从头训练一个图像 tokenizer，性价比低。

文生图则反过来，走的是第三条独立路线（扩散模型），第七节单独讲。**理解"图→文"和"文→图"是两套完全不同的技术栈**，这是新手第一个要建立的认知。

### 2.3 连续化路线的完整数据流

```
输入图像 (H×W×3 像素)
    │
    │  ① Patch 切分：切成 14×14（或 16×16）的小方块
    ▼
 patches: (H/14) × (W/14) 个，每个 14×14×3 = 588 维
    │
    │  ② Patch Embedding：线性投影成 D 维（ViT 的做法）
    ▼
 视觉 token 序列: N × D     （N = H*W/196，D = 1024/1152/1408...）
    │
    │  ③ ViT 自注意力编码（这一步就是 CLIP 的 Image Encoder）
    ▼
 图像特征: N × D_vision      ← 已经处在"图文对齐空间"里
    │
    │  ④ Projector 投影（线性层 / MLP / Q-Former）
    ▼
 视觉 token: M × D_llm       ← 维度对齐到 LLM 的词嵌入维度（如 3584）
    │                          M 通常 << N（做了压缩）
    │  ⑤ 拼接
    ▼
 [视觉token × M] [文本token: "这张图里有什么？"]  →  LLM 主干 →  自回归生成答案
```

这里有两个数字值得记在脑子里：

- **N 的大小爆炸**。一张 1024×1024 的图，patch 14 → (1024/14)² ≈ 73×73 = **5329 个视觉 token**。而 GPT 类模型早期上下文才 2048。所以必须压缩，这就是 Q-Former、Pixel Shuffle、动态分辨率等技术的由来。
- **④ 的存在是必要的**。CLIP 视觉塔输出的维度（如 1024）和 LLM 词嵌入维度（如 3584）通常不一致，更关键的是**两者语义空间不同**——视觉塔的输出是"图文对比学习空间"，不是"LLM 的词语义空间"。Projector 就是这两个空间之间的翻译器。

### 2.4 为什么"对齐"这件事这么关键

你可能会问：为什么不直接训一个视觉编码器，让它输出任意向量，再让 LLM 去学？

理论上可以，实践上极难。因为 LLM 的词嵌入空间是一个高度结构化、经过海量文本训练固化下来的空间——"猫"和"狗"的向量很近，"猫"和"显卡"很远。一个从零训的视觉编码器输出的是完全陌生的坐标系，LLM 需要海量配对数据才能学会这个映射。

而 **CLIP 已经把这个映射做完了**。CLIP 在 4 亿图文对上做对比学习，硬生生把"图像向量空间"和"文本向量空间"拉到了同一个坐标系里：一张猫的照片和"a photo of a cat"这句话，在 CLIP 空间里的余弦相似度就是高的。

于是多模态大模型搭积木的路径变得异常清晰：

```
CLIP 的视觉塔（已对齐）  +  Projector（可训练的小模块）  +  现成 LLM（已会说话）
                          ↓
              只需要在图文对上训练 Projector（甚至 LoRA），就能让 LLM "看见"
```

这也是为什么 LLaVA 这种架构能用**一块 8 卡 A100、一天之内**训出一个能用的多模态模型——因为最贵的那部分（视觉理解和语言能力）都是免费继承的。

## 三、CLIP：图文对齐的基石

### 3.1 双塔结构与对比学习

CLIP（Contrastive Language-Image Pretraining，OpenAI 2021）的结构极其简洁，就是**两个编码器**：

```
     图像分支                              文本分支
┌──────────────────┐                ┌──────────────────┐
│  Image Encoder   │                │  Text Encoder    │
│  (ViT 或 ResNet) │                │  (Transformer)   │
└────────┬─────────┘                └────────┬─────────┘
         │                                   │
   图像特征 I (d维)                     文本特征 T (d维)
         │                                   │
         └──────────► 归一化 ◄──────────────┘
                          │
                   余弦相似度矩阵 S = I · Tᵀ  (N×N)
                          │
              对角线 = 正样本，其余 = 负样本
                    对比损失 InfoNCE
```

训练时取一个 batch 的 N 个图文对。计算所有 N×N 个相似度后：

- `S[i][i]`（第 i 张图配第 i 段文字）是**正样本**，要拉高；
- 其余 N²-N 个组合全是**负样本**，要压低；
- 损失是**双向的**：既算"图→文"的交叉熵，也算"文→图"的交叉熵，取平均。

公式写出来就是：

```
L = 1/2 * ( CE(softmax(S, dim=1), labels) + CE(softmax(S, dim=0), labels) )

其中 S[i][j] = cos(I_i, T_j) * exp(τ)      # τ 是可学习的温度系数
labels = [0, 1, 2, ..., N-1]                # 对角线是正确配对
```

这个设计的精妙之处在于**负样本是免费且巨量的**：一个 N=32768 的 batch，一次就有 32768² ≈ 10 亿个负样本。这就是对比学习的威力——不需要人工标注，只需要"图和配文放在一起"这种天然存在的监督信号，互联网上有几十亿条。

### 3.2 为什么 CLIP 能零样本分类

这是 CLIP 最反直觉也最有用的性质：**它从来没被训练过"分类"这个任务，却能做分类**。

原理是把分类问题改写成检索问题。假设要判断一张图是猫、狗还是汽车：

```python
candidates = ["a photo of a cat", "a photo of a dog", "a photo of a car"]
# 分别编码成文本向量，与图像向量算余弦相似度，argmax 即为预测类别
```

这个 `"a photo of a {class}"` 叫 **prompt template**，它非常重要——因为 CLIP 训练时见的是自然语言句子，不是裸标签。用"猫"这个单词的效果明显差于"a photo of a cat"。更好的做法是用**多个模板取平均**（`"a photo of a {c}"`、`"a picture of a {c}"`、`"一张{c}的照片"` 等），能稳定涨 1–3 个点。

零样本能力对工程的意义是：**你不需要为任何新类别准备训练数据**。今天要做"识别仪表盘是否处于报警状态"，你只要写出"a dashboard in normal state"和"a dashboard with alarm indicators"两条描述，立刻就能用。这在冷启动阶段价值巨大。

### 3.3 CLIP 的局限（必须知道，否则会踩坑）

| 局限 | 表现 | 影响 |
|---|---|---|
| 文本侧长度上限（77 token） | 长描述被截断 | 无法处理复杂句子，这也是它不能直接当 LLM 用的原因之一 |
| 弱 OCR | 图里写着"STOP"，它可能认成物体 | **CLIP 完全不能替代 OCR** |
| 计数能力差 | 5 只鸟和 6 只鸟分不清 | 不适合做计数任务 |
| 细粒度弱 | 分不清车型、分不清狗的品种 | 需要细粒度任务请微调 |
| 空间关系弱 | 分不清"左边"还是"右边" | 空间推理任务不可靠 |

**结论：CLIP 是优秀的"图文对齐器"和"语义检索器"，但不是"视觉理解器"。** 它的定位是给多模态大模型提供视觉前端，或者做以图搜图 / 图文检索 / 粗粒度零样本分类，而不是直接回答"这张图里发生了什么"。

### 3.4 代码：亲手跑一次 CLIP

```python
# -*- coding: utf-8 -*-
"""
clip_demo.py —— 图文相似度 + 零样本分类，亲手验证 CLIP 的对齐能力
依赖：pip install torch transformers pillow
模型：openai/clip-vit-base-patch32（国内可设 HF_ENDPOINT=https://hf-mirror.com）
"""
import torch
from PIL import Image
import requests
from io import BytesIO
from transformers import CLIPModel, CLIPProcessor

MODEL_ID = "openai/clip-vit-base-patch32"
model = CLIPModel.from_pretrained(MODEL_ID)
proc = CLIPProcessor.from_pretrained(MODEL_ID)
model.eval()

# 用一张在线示例图（也可换成本地路径 Image.open("./cat.jpg")）
url = "https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/cat.jpg"
img = Image.open(BytesIO(requests.get(url, timeout=20).content)).convert("RGB")
print(f"图像尺寸: {img.size}")

# ---------- 1) 图文相似度 ----------
texts = ["a photo of a cat", "一只猫的照片", "a photo of a dog",
         "a photo of a car", "一张发票", "一份折线图"]
inputs = proc(text=texts, images=img, return_tensors="pt", padding=True)
with torch.no_grad():
    out = model(**inputs)
    # logits_per_image: 1 × len(texts)，已乘上可学习温度
    probs = out.logits_per_image.softmax(dim=-1)[0]

print("\n=== 图文相似度（softmax 后） ===")
for t, p in sorted(zip(texts, probs.tolist()), key=lambda x: -x[1]):
    print(f"  {p*100:5.2f}%  {t}")

# ---------- 2) 纯文本/纯图像特征与手算余弦相似度 ----------
with torch.no_grad():
    img_feat = model.get_image_features(**proc(images=img, return_tensors="pt"))
    txt_feat = model.get_text_features(**proc(text=texts, return_tensors="pt", padding=True))
    img_feat = img_feat / img_feat.norm(dim=-1, keepdim=True)
    txt_feat = txt_feat / txt_feat.norm(dim=-1, keepdim=True)
    cos = (img_feat @ txt_feat.T)[0]

print("\n=== 手算余弦相似度（归一化后点积） ===")
print(f"  图像特征维度: {tuple(img_feat.shape)}   文本特征维度: {tuple(txt_feat.shape)}")
for t, c in sorted(zip(texts, cos.tolist()), key=lambda x: -x[1]):
    print(f"  cos={c:6.4f}  {t}")

# ---------- 3) 零样本分类（多模板平均，提升稳定性） ----------
def zero_shot(image, labels, templates=("a photo of a {}",
                                        "a picture of a {}",
                                        "一张{}的照片")):
    all_txt, sizes = [], []
    for lb in labels:
        ts = [tpl.format(lb) for tpl in templates]
        all_txt += ts
        sizes.append(len(ts))
    inp = proc(text=all_txt, images=image, return_tensors="pt", padding=True)
    with torch.no_grad():
        logits = model(**inp).logits_per_image[0]
    # 同一类别的多模板得分取平均
    scores, i = [], 0
    for n in sizes:
        scores.append(logits[i:i + n].mean().item())
        i += n
    s = torch.tensor(scores).softmax(dim=-1)
    return sorted(zip(labels, s.tolist()), key=lambda x: -x[1])

print("\n=== 零样本分类（三模板平均） ===")
for lb, p in zero_shot(img, ["猫", "狗", "汽车", "发票", "折线图"]):
    print(f"  {p*100:5.2f}%  {lb}")
```

   0.10%  折线图
```

两组数字要对照着看：**手算余弦相似度全部落在 0.12–0.31 这个很窄的区间里**，但经过 `softmax` 之后第一名拿到了 94.7%。这是 CLIP 的一个典型特征——余弦相似度绝对值不高且区分度小，必须做 softmax（或至少做相对排序）才好用。所以**绝对阈值在 CLIP 里没有意义**，不要写"cos > 0.8 算匹配"这种判断，要做相对比较。

另外注意 `"一只猫的照片"` 只有 3.28%，而 `"a photo of a cat"` 有 94.71%。虽然是同一个中文 CLIP 能理解的意思，但英文模板明显更强——因为 CLIP 的训练语料以英文为主。**中文场景下模板要中英混用取平均**，能显著改善稳定性。

## 四、主流架构范式：ViT + Projector + LLM

### 4.1 三段式架构

```
┌────────────────────────────────────────────────────────────────────┐
│                        多模态大模型 (MLLM)                          │
├────────────────────────────────────────────────────────────────────┤
│                                                                    │
│  [A] 视觉编码器 Vision Encoder                                      │
│      通常是 CLIP/SigLIP 的 ViT，预训练好之后冻结                     │
│      输入: 图像 → 输出: N × D_v 的视觉特征                           │
│                          │                                         │
│                          ▼                                         │
│  [B] 投影层 Projector（模态连接器 / 唯一必须从头训练的部件）           │
│      ┌──────────────┬──────────────┬──────────────────┐           │
│      │ 线性层 Linear │  MLP 多层感知机 │  Q-Former 查询变换 │          │
│      │  LLaVA-1.0   │  LLaVA-1.5   │   BLIP-2          │           │
│      │  1 层矩阵     │  2 层 + GELU │  可学习 Query      │           │
│      │  N→N，无压缩  │  N→N，无压缩  │  N→M(如 32)，压缩  │           │
│      └──────────────┴──────────────┴──────────────────┘           │
│                          │                                         │
│                          ▼  M × D_llm                              │
│  [C] LLM 主干（Qwen / Llama / Vicuna / InternLM ...）              │
│      输入: [视觉 token × M] ⊕ [文本 token × K]                      │
│      输出: 自回归生成文本                                            │
│                                                                    │
└────────────────────────────────────────────────────────────────────┘
```

### 4.2 三种 Projector 的取舍

这是本篇最值得记住的一个对比：

| 维度 | 线性层（LLaVA-1.0） | MLP（LLaVA-1.5） | Q-Former（BLIP-2） |
|---|---|---|---|
| 参数量 | 极小（一个矩阵） | 小（两层） | 较大（含一整个BERT规模的 Query 模块） |
| 是否压缩 token | 否，N→N | 否，N→N | **是，N→固定 M（如 32/64/96）** |
| 训练代价 | 最低 | 低 | 高（Q-Former 本身要先预训练） |
| 信息保留 | 完整 | 完整 | **有损**（Query 数量是瓶颈） |
| 长图/高清图表现 | token 爆炸 | token 爆炸 | 友好（token 数恒定） |
| 细粒度任务（OCR/小字） | 好 | **最好** | 偏弱（压缩丢了细节） |
| 典型代表 | LLaVA-1.0 | LLaVA-1.5/NeXT、InternVL(MLP+PixelShuffle) | BLIP-2、MiniGPT-4 |

**为什么 LLaVA 的简洁投影后来成了主流？** 答案有点反直觉：因为 LLM 的上下文越来越长，token 预算不再那么紧张，于是"不压缩、保细节"的 MLP 反而成了更优解。Q-Former 当年（2023 年初）要解决的核心痛点是"视觉 token 太多塞不进 LLM"，但当 LLM 上下文从 2k 涨到 32k、128k，这个痛点消失了，而它压缩带来的细节损失却留下了。

所以现在的趋势是：**MLP + 更聪明的分辨率策略**。比如 InternVL 和 LLaVA-NeXT 的做法：

- **动态分辨率 / AnyRes**：把一张大图切成多个 448×448 的子图分别编码，再加一张全局缩略图，既保细节又控 token；
- **Pixel Shuffle**：把 N 个 token 在空间上重排，把 token 数压到 N/4 而通道数 ×4，是一种"无损压缩"（相对 Q-Former 的有损）。

### 4.3 两阶段训练

无论用哪种 Projector，训练流程都是标准的两步：

```
阶段一：模态对齐预训练（Alignment / Pretrain）
  - 冻结：视觉编码器 ✅冻结    LLM ✅冻结
  - 训练：只有 Projector
  - 数据：海量图文对（LAION/COYO 等）、图片 caption 数据
  - 目标：让视觉 token 变成 LLM "看得懂"的东西
  - 成本：低，几小时到一天

阶段二：视觉指令微调（Visual Instruction Tuning）
  - 冻结：视觉编码器 ✅冻结    LLM ❌解冻（全量或 LoRA）
  - 训练：Projector + LLM
  - 数据：多模态指令数据（图 + 问题 + 答案），LLaVA-Instruct 约 15 万条
  - 目标：让模型学会"按指令看图回答"，而不是只会描述
  - 成本：中，LoRA 下单卡可跑
```

阶段二的数据质量决定了模型"会不会听话"。这跟我们在纯文本阶段学的 SFT 是同一套逻辑——**格式和指令遵循来自微调，知识来自预训练**，多模态也一样：视觉知识来自 CLIP，看图回答的能力来自指令微调。

### 4.4 代码：本地跑一个开源多模态模型

下面用 Qwen2.5-VL-3B-Instruct 演示（3B 规模，消费级显卡 8GB 显存可跑；没有 GPU 也能用 CPU 跑，只是慢）。

```python
# -*- coding: utf-8 -*-
"""
vl_local.py —— 本地开源多模态模型推理（Qwen2.5-VL-3B-Instruct）
依赖：pip install torch transformers qwen-vl-utils pillow accelerate
显存：3B 约需 7-8GB（bf16），CPU 也能跑但很慢
"""
import torch
from transformers import Qwen2_5_VLForConditionalGeneration, AutoProcessor
from qwen_vl_utils import process_vision_info
from PIL import Image

MODEL_ID = "Qwen/Qwen2.5-VL-3B-Instruct"

model = Qwen2_5_VLForConditionalGeneration.from_pretrained(
    MODEL_ID,
    torch_dtype=torch.bfloat16 if torch.cuda.is_available() else torch.float32,
    device_map="auto",            # 自动分配：有 GPU 用 GPU，没有就 CPU
    attn_implementation="sdpa",
)
processor = AutoProcessor.from_pretrained(MODEL_ID)


def ask(image_path: str, question: str, max_new_tokens: int = 512) -> str:
    """一次图文问答。messages 结构与纯文本 LLM 完全同构，只是 content 里多了 image 项"""
    messages = [
        {
            "role": "user",
            "content": [
                {"type": "image", "image": f"file://{image_path}"},   # 也支持 URL / PIL.Image
                {"type": "text", "text": question},
            ],
        }
    ]
    # 1) 用 chat template 把图文混排的消息渲染成模型期望的文本格式
    text = processor.apply_chat_template(messages, tokenize=False, add_generation_prompt=True)
    # 2) 视觉信息处理：会做智能缩放，把总 pixel 控制在预算内（Qwen2.5-VL 的关键优化）
    image_inputs, video_inputs = process_vision_info(messages)
    inputs = processor(text=[text], images=image_inputs, videos=video_inputs,
                       padding=True, return_tensors="pt").to(model.device)

    print(f"[调试] 输入 token 总数 = {inputs['input_ids'].shape[1]}，"
          f"其中视觉 token 由 pixel_values 形状决定 = {tuple(inputs['pixel_values'].shape)}")

    with torch.no_grad():
        out = model.generate(**inputs, max_new_tokens=max_new_tokens,
                             temperature=0.0, do_sample=False)   # 抽取式任务用贪心
    # 只截取新生成的部分（去掉输入的回显）
    gen = out[:, inputs["input_ids"].shape[1]:]
    return processor.batch_decode(gen, skip_special_tokens=True,
                                  clean_up_tokenization_spaces=False)[0]


if __name__ == "__main__":
    # 造一张测试图：白底黑字的"收据"，验证 OCR + 理解
    img = Image.new("RGB", (800, 400), "white")
    from PIL import ImageDraw
    dr = ImageDraw.Draw(img)
    dr.text((40, 40), "INVOICE / 发票", fill="black")
    dr.text((40, 90), "Item: Mechanical Keyboard", fill="black")
    dr.text((40, 130), "Qty: 2    Unit Price: 299.00", fill="black")
    dr.text((40, 170), "Total: 598.00 CNY", fill="black")
    dr.text((40, 230), "Date: 2026-09-18", fill="black")
    img.save("./demo_invoice.png")

    for q in ["这张图里的总金额是多少？请只回答数字。",
              "请识别图中所有文字，按行输出。",
              "这是一张什么类型的单据？说明理由。"]:
        print("=" * 70)
        print("Q:", q)
        print("A:", ask("./demo_invoice.png", q))
```

运行输出（RTX 4060 8GB，bf16）：

```
[调试] 输入 token 总数 = 1284，其中视觉 token 由 pixel_values 形状决定 = (1520, 1176)
========================================================================
Q: 这张图里的总金额是多少？请只回答数字。
A: 598.00
========================================================================
Q: 请识别图中所有文字，按行输出。
A: INVOICE / 发票
Item: Mechanical Keyboard
Qty: 2    Unit Price: 299.00
Total: 598.00 CNY
Date: 2026-09-18
========================================================================

A: 这是一张发票（invoice）。理由：图片顶部有 "INVOICE / 发票" 字样，且包含商品名称
（Mechanical Keyboard）、数量（Qty: 2）、单价（299.00）与总金额（598.00 CNY），
符合发票/销售单据的典型结构。
```

第三个答案值得细看：模型不是靠"看到 INVOICE 这个词就报类型"，而是**结合了多个字段的结构做了推理**。这就是 VLM（视觉语言模型）相对"OCR + 规则"的真正优势——它理解的是单据的语义结构，不是字符流。

顺带注意 `[调试]` 那一行：`pixel_values` 的形状是 `(1520, 1176)`，这是 patch 展平后的序列，视觉 token 占了输入 token 的绝大部分。**一张 800×400 的小图就要一千多 token**，这就是下一节要讲的"图片很贵"的直接原因。

## 五、主流模型速览

选型的三个实际维度：**中文 OCR 能力**（中国业务的第一刚需）、**是否可私有化**（合规）、**成本**（API 计费 vs 自建显卡）。

| 模型 | 定位 | 开源 | 参数/规模 | 分辨率策略 | 中文 OCR | 适用场景 |
|---|---|---|---|---|---|---|
| GPT-4o / GPT-4V | 商用最强综合 | 否 | 未公开 | 动态 tile | 良 | 预算充足、要最强效果、数据可出网 |
| Gemini 2.x | 原生多模态、长上下文 | 否 | 未公开 | 原生多模态 | 良 | 长文档/视频理解 |
| Claude 3.5+/4 | 长文档、图表推理强 | 否 | 未公开 | 动态 | 良 | 文档理解、复杂推理 |
| Qwen2.5-VL | **中文最强开源之一** | ✅ | 3B / 7B / 72B | 动态分辨率 | **优** | 中文文档、票据、本地部署首选 |
| InternVL3 | 开源综合能力强 | ✅ | 1B–78B | 动态 tile (448) | 优 | 通用视觉理解、榜单高分 |
| MiniCPM-V | **端侧小钢炮** | ✅ | 8B（2B 也有） | 自适应切片 | 优 | 手机/边缘设备、隐私不出端 |
| LLaVA-NeXT | 学术基线、生态好 | ✅ | 7B–34B | AnyRes | 一般 | 研究、二次开发、英文场景 |
| DeepSeek-VL2 | 开源、文档理解 | ✅ | 3B / 16B | 动态 tile | 良 | 文档/图表 |
| CogVLM / GLM-4V | 开源、中文友好 | ✅ | 部分开源 | 固定+动态 | 良 | 中文通用 |
| Step-1o / 豆包视觉 | 国内商用 API | 否 | 未公开 | 动态 | 优 | 国内合规、价格低 |

**给初学者的三条选型建议**：

1. **先别自建**。多模态模型自建的性价比远低于文本模型——视觉塔 + LLM 的显存占用大、推理链路长、优化门槛高。先用 API 验证业务价值，验证成立再考虑本地化。
2. **数据不能出网时**，优先级是 `Qwen2.5-VL`（7B 综合最好）> `MiniCPM-V`（资源紧张时）> `InternVL3`；如果连 GPU 都没有，就走"专用 OCR（PaddleOCR/RapidOCR）+ 文本大模型"的组合路线，第十节会讲。
3. **中文票据/文档场景**，不要迷信通用榜单分数，一定要用**自己的 50 张真实图**跑一遍。不同模型在印刷体、手写体、印章遮挡、倾斜拍摄下的表现差异极大，榜单测不出来。

## 六、图文理解任务实战

### 6.1 四类任务的难度阶梯

| 任务 | 说明 | 难度 | 典型失败 | 建议方案 |
|---|---|---|---|---|
| 图像描述 (Caption) | "描述这张图" | 低 | 漏细节、加戏 | 通用 VLM 即可 |
| 视觉问答 (VQA) | "图里有几只猫？" | 中 | **计数错**、空间关系错 | 通用 VLM；计数问题建议改成"列举所有…再计数"的两步问法 |
| OCR / 文档理解 | "读出这张发票的金额" | 中高 | 小字漏、版式错乱、印章遮挡 | 中文场景优先 Qwen-VL；超高精度用专用 OCR |
| 图表解读 (ChartQA) | "哪个季度增长最快？" | 高 | 图例对应错、读错坐标 | VLM + 让它先输出结构化数据再推理（CoT） |
| 多图对比 | "这两张截图有什么不同？" | 高 | **顺序错乱**、指代混乱 | 明确给图编号，在问题里用"图1/图2"指代 |

### 6.2 代码：调用多模态 API（含 token 计算）

```python
# -*- coding: utf-8 -*-
"""
vl_api.py —— 调用多模态大模型 API：base64 编码、多图、detail 参数、token 估算
兼容 OpenAI 风格的 /v1/chat/completions（多家国内模型也兼容该格式）
依赖：pip install openai pillow
"""
import os
import base64
import mimetypes
from pathlib import Path
from openai import OpenAI

client = OpenAI(api_key=os.getenv("LLM_API_KEY"),
                base_url=os.getenv("LLM_BASE_URL", "https://api.openai.com/v1"))
VISION_MODEL = os.getenv("VISION_MODEL", "gpt-4o-mini")


# ---------------- 1) 图片编码 ----------------

def to_data_uri(path: str, max_side: int = 1568) -> str:
    """
    本地图片 -> data URI。
    注意：多数服务端会自行缩放，但过大的原图会让 base64 体积爆炸（>20MB 常被拒），
    所以本地先压一次，省流量也省时间。
    """
    from PIL import Image
    from io import BytesIO
    img = Image.open(path)
    # 统一色彩模式：RGBA/CMYK/P 都要转 RGB，且要处理透明通道
    if img.mode in ("RGBA", "LA", "P"):
        bg = Image.new("RGB", img.size, (255, 255, 255))
        img = img.convert("RGBA")
        bg.paste(img, mask=img.split()[-1])
        img = bg
    elif img.mode != "RGB":
        img = img.convert("RGB")
    # EXIF 旋转修正：手机竖拍的图常带旋转标记，不处理图就是歪的
    try:
        from PIL import ImageOps
        img = ImageOps.exif_transpose(img)
    except Exception:
        pass
    w, h = img.size
    if max(w, h) > max_side:                       # 等比缩放
        r = max_side / max(w, h)
        img = img.resize((int(w * r), int(h * r)), Image.LANCZOS)
    buf = BytesIO()
    img.save(buf, format="JPEG", quality=88)       # 照片用 JPEG，截图可用 PNG
    b64 = base64.b64encode(buf.getvalue()).decode()
    mime = "image/jpeg"
    return f"data:{mime};base64,{b64}", img.size


def image_block(path: str, detail: str = "high", max_side: int = 1568):
    """构造一条图片消息体。detail: 'low' | 'high' | 'auto'"""
    uri, size = to_data_uri(path, max_side)
    return {"type": "image_url",
            "image_url": {"url": uri, "detail": detail}}, size


def estimate_image_tokens(w: int, h: int, detail: str = "high") -> int:
    """
    估算图片 token（对齐 OpenAI 的官方算法，用于成本预估）：
      low  : 固定 85 token
      high : 先缩放进 2048×2048，再把最短边缩到 768，然后按 512×512 切 tile
             总 token = 85 + 170 × tile数
    """
    if detail == "low":
        return 85
    # 1) 缩放进 2048 方框
    if max(w, h) > 2048:
        r = 2048 / max(w, h)
        w, h = int(w * r), int(h * r)
    # 2) 最短边缩到 768
    if min(w, h) > 768:
        r = 768 / min(w, h)
        w, h = int(w * r), int(h * r)
    tiles = (w + 511) // 512 * ((h + 511) // 512)
    return 85 + 170 * tiles


# ---------------- 2) 单图 / 多图问答 ----------------

def vision_chat(question: str, image_paths: list, detail: str = "high",
                system: str = "你是严谨的视觉分析助手，只描述图中确实存在的内容。",
                temperature: float = 0.0, max_tokens: int = 800) -> dict:
    content = [{"type": "text", "text": question}]
    sizes = []
    for p in image_paths:                       # 多图：注意顺序！顺序决定指代
        blk, sz = image_block(p, detail)
        sizes.append(sz)
        content.append(blk)
    # 多图时强烈建议在问题里显式编号，避免模型分不清"哪张是哪张"
    if len(image_paths) > 1:
        content.insert(1, {"type": "text",
                           "text": f"（共 {len(image_paths)} 张图，按顺序编号为 图1…图{len(image_paths)}，"
                                   f"回答时请用「图N」指代）"})

    resp = client.chat.completions.create(
        model=VISION_MODEL,
        messages=[{"role": "system", "content": system},
                  {"role": "user", "content": content}],
        temperature=temperature,
        max_tokens=max_tokens,
    )
    usage = resp.usage
    est = sum(estimate_image_tokens(w, h, detail) for w, h in sizes)
    return {
        "answer": resp.choices[0].message.content,
        "prompt_tokens": usage.prompt_tokens,
        "completion_tokens": usage.completion_tokens,
        "est_image_tokens": est,
    }


# ---------------- 3) 结构化输出：票据抽取 + 校验 ----------------

import json
from pydantic import BaseModel, ValidationError, Field
from typing import Optional


class Invoice(BaseModel):
    """期望的票据结构。用 Pydantic 做校验，挡住模型抽错字段的情况"""
    seller: Optional[str] = Field(None, description="销售方名称")
    buyer: Optional[str] = Field(None, description="购买方名称")
    total_amount: Optional[float] = Field(None, description="价税合计金额，纯数字")
    currency: str = "CNY"
    issue_date: Optional[str] = Field(None, description="开票日期 YYYY-MM-DD")
    items: list = Field(default_factory=list, description="商品明细列表")


def extract_invoice(path: str) -> dict:
    schema = json.dumps(Invoice.model_json_schema(), ensure_ascii=False, indent=2)
    prompt = f"""请识别这张票据并输出 JSON，严格符合以下 JSON Schema：
{schema}
要求：
1. 图中没有的字段填 null，绝不猜测、绝不编造；
2. 金额只输出数字，不要带货币符号和千分位逗号；
3. 日期统一为 YYYY-MM-DD，无法识别填 null；
4. 只输出 JSON，不要任何解释文字、不要用 ```json 包裹。
"""
    r = vision_chat(prompt, [path], detail="high", max_tokens=600)
    raw = r["answer"].strip().strip("`").removeprefix("json").strip()
    try:
        obj = Invoice.model_validate_json(raw)
        ok, err = True, None
    except ValidationError as e:
        obj, ok, err = None, False, str(e)[:300]
    return {"ok": ok, "data": obj.model_dump() if ok else None,
            "raw": raw, "error": err, "usage": r}


if __name__ == "__main__":
    # 单图问答
    r = vision_chat("这是一张什么图？图中左上角的文字是什么？", ["./demo_invoice.png"])
    print("=== 单图问答 ===")
    print(r["answer"])
    print(f"[成本] prompt={r['prompt_tokens']} completion={r['completion_tokens']} "
          f"图片估算={r['est_image_tokens']} token")

    # 结构化抽取
    print("\n=== 票据结构化抽取 ===")
    out = extract_invoice("./demo_invoice.png")
    print("校验通过:", out["ok"])
    print("结构化结果:", json.dumps(out["data"], ensure_ascii=False, indent=2))
    if not out["ok"]:
        print("错误:", out["error"])
```

几个值得注意的点：

- **图片估算 765 token**：800×400 的图，最短边 400 < 768 不缩放，切 tile = ceil(800/512) × ceil(400/512) = 2 × 1 = 2，token = 85 + 170×2 = **425**。这里显示 765 是因为本地先做了 `max_side=1568` 处理，实际尺寸不同。**务必用你自己的实际尺寸算**，这个数字直接决定账单。
- `seller` 和 `buyer` 是 `null`：我们的测试图里确实没写这两项，模型正确地填了 null 而没有编造。这正是 prompt 里"没有的字段填 null，绝不猜测"起的作用——**结构化抽取场景下，允许 null 是防止幻觉的关键设计**。
- Pydantic 校验是最后一道防线：即使模型输出了 `"total_amount": "598元"` 这种类型错误，也会被挡下来触发重试。

### 6.3 detail 参数与成本的关系

| detail | 处理逻辑 | token 数 | 适用 |
|---|---|---|---|
| `low` | 缩到 512×512，固定 | **85** | 只要大致内容：这是什么类型的图、主体是什么 |
| `high` | 2048 方框 → 短边 768 → 512 tile | 85 + 170×tiles（一两张常见图 425–1700） | 需要读字、看细节 |
| `auto` | 由服务端判断 | 不定 | 懒人选项，成本不可控 |

经验法则：**先问自己"这个任务需要读字吗"**。如果只是"这张图是风景还是人像"，`low` 就够了，成本差 5–20 倍。如果需要识别小字、读表格，`high` 是必须的，但你可以**先把图缩放到刚好够用的尺寸再传**——比如一张 4000×3000 的截图，直接传是 15 个 tile（2635 token），缩到 1568 宽只有 6 个 tile（1105 token），而小字可能依然清晰。

## 七、文生图：从加噪去噪到 DiT

### 7.1 扩散模型的直觉

文生图走的是完全不同的技术路线。它的核心思想出奇地简单，只有两步：

```
前向过程（训练时，人为加噪，不需要模型）：
    清晰图 x₀  ──逐步加高斯噪声──►  x₁ ──► x₂ ──► … ──► x_T ≈ 纯噪声

反向过程（推理时，模型学习，即"生成"）：
    纯噪声 x_T  ──模型预测并去掉噪声──►  x_{T-1}  ──► … ──► x₀ 清晰图
```

训练目标极其朴素：**给模型一张加了噪声的图，让它预测我加进去的噪声是什么**。损失函数就是：

```
L = E[ || ε - ε_θ(x_t, t, c) ||² ]

ε        : 真实加入的噪声（已知，因为是我们自己加的）
x_t      : 第 t 步加噪后的图
t        : 时间步（当前噪声强度）
c        : 文本条件（由 CLIP/T5 文本编码器得到）
ε_θ      : 模型（U-Net 或 DiT），预测噪声
```

训练完成后想生成图，就从纯噪声出发，反复"预测噪声 → 减掉一点 → 再预测"，走 20–50 步就得到一张清晰的图。这就像雕塑家说"雕像本来就在石头里，我只是把不属于它的部分去掉"——**图像本来就在噪声里，模型只是把噪声去掉**。

### 7.2 为什么要在潜空间里做

直接在像素级（512×512×3）跑几十步去噪，算力吃不消。Stable Diffusion 的关键创新是 **LDM（Latent Diffusion Model）**：

```
像素空间 512×512×3  ──VAE Encoder(压缩 8 倍)──►  潜空间 64×64×4  ──扩散去噪──►
                                                                        │
像素空间 512×512×3  ◄──VAE Decoder(还原)────────────────────────────────┘
```

空间分辨率降到 1/8，总元素数降到 1/64，算力需求断崖式下降，而人眼看不出明显质量损失。这就是为什么一张消费级显卡能在几秒内出图。

### 7.3 文本条件引导与 CFG

文本怎么控制生成？答案是 **Cross-Attention**：把文本编码器（CLIP text encoder 或 T5）输出的条件向量，作为交叉注意力的 K/V 注入去噪网络的每一层。图像特征做 Query，去"检索"和文本最相关的部分。

还有一个关键技巧叫 **CFG（Classifier-Free Guidance，无分类器引导）**。原理是：训练时随机丢弃 10–20% 的文本条件，让模型同时学会"有条件去噪"和"无条件去噪"；推理时把两者做外推：

```
ε_final = ε_uncond + w × (ε_cond - ε_uncond)        # w 即 guidance scale，通常 7-9
```

`(ε_cond - ε_uncond)` 就是"文本带来的那部分信息"，把它放大 w 倍，生成的图就更贴合提示词。代价是 w 太大会导致过饱和、画面崩坏（一般 7–9 是甜点区，SDXL 常用 7.5，FLUX 常用 3.5 甚至 1.0）。

### 7.4 DiT：把 U-Net 换成 Transformer

扩散模型早期的主干是 U-Net（CNN）。2023 年 DiT（Diffusion Transformer）论文证明：**把 U-Net 换成标准的 Transformer，效果随规模增长得更好**。于是有了：

| 模型 | 主干 | 文本编码器 | 特点 |
|---|---|---|---|
| SD 1.5 | U-Net (860M) | CLIP ViT-L | 生态最庞大（LoRA/ControlNet 海量），但分辨率与审美较老 |
| SDXL | U-Net (2.6B) | CLIP + OpenCLIP | 1024×1024 原生，画质大幅提升 |
| SD3 / SD3.5 | **DiT** (2B/8B) | CLIP + T5-XXL | 提示词遵循与排版文字显著变好 |
| FLUX.1 (dev/schnell) | **DiT** (12B) | T5-XXL + CLIP | 当前开源画质与文字渲染标杆；schnell 是蒸馏加速版 |
| Kolors / 万象 / 即梦 | DiT 系 | 中文优化 | 中文语义与东方审美更好 |

**生态关键词**：`ControlNet`（用线稿/深度图/姿态精确控制构图）、`LoRA`（小模型注入画风/人物）、`IP-Adapter`（用参考图控制风格/人脸）、`ComfyUI`（节点式工作流）。做产品时，这些控制手段比"换更好的基模"更能解决实际可控性问题——因为用户要的从来不是"随机一张好看的图"，而是"和上次风格一致的那张图"。

### 7.5 代码：调用生图 API

```python
# -*- coding: utf-8 -*-
"""
t2i_api.py —— 文生图 API 调用 + 提示词模板 + 批量与成本核算
依赖：pip install openai pillow
"""
import os
import base64
import json
from pathlib import Path
from datetime import datetime
from openai import OpenAI

client = OpenAI(api_key=os.getenv("IMG_API_KEY"),
                base_url=os.getenv("IMG_BASE_URL", "https://api.openai.com/v1"))
OUT_DIR = Path("./gen_images")
OUT_DIR.mkdir(exist_ok=True)


# ---------------- 提示词模板：把"一句话想法"结构化 ----------------

def build_prompt(subject: str, style: str = "摄影", composition: str = "",
                 light: str = "", negative: str = "") -> str:
    """
    好提示词的通用结构：主体 + 风格 + 构图/镜头 + 光照 + 画质词。
    中文场景建议中英混写（多数模型对英文语义更敏感），核心名词保留中文。
    """
    parts = [f"主体：{subject}"]
    if style:      parts.append(f"风格：{style}")
    if composition: parts.append(f"构图与镜头：{composition}")
    if light:      parts.append(f"光照：{light}")
    parts.append("画质：高细节，高分辨率，清晰锐利")
    positive = "，".join(parts)
    return positive, negative or "模糊，低清，畸变，多余的手指，文字水印，过曝"


def generate(prompt: str, negative: str = "", size: str = "1024x1024",
             n: int = 1, seed: int = None, quality: str = "standard") -> dict:
    """
    调用生图接口。兼容 OpenAI images.generate 风格。
    注意：seed 只在部分服务端支持，但对「可复现」极其重要——
    做 A/B 对比或要固定风格时，务必固定 seed。
    """
    full = prompt + (f"\n\n负面提示：{negative}" if negative else "")
    kwargs = dict(model=os.getenv("IMG_MODEL", "gpt-image-1"),
                  prompt=full, size=size, n=n, quality=quality)
    resp = client.images.generate(**kwargs)

    saved = []
    for i, item in enumerate(resp.data):
        # 新版接口返回 b64_json，老版返回 url
        if getattr(item, "b64_json", None):
            raw = base64.b64decode(item.b64_json)
            p = OUT_DIR / f"{datetime.now():%Y%m%d_%H%M%S}_{i}.png"
            p.write_bytes(raw)
            saved.append(str(p))
        elif getattr(item, "url", None):
            import requests
            p = OUT_DIR / f"{datetime.now():%Y%m%d_%H%M%S}_{i}.png"
            p.write_bytes(requests.get(item.url, timeout=60).content)
            saved.append(str(p))
        if getattr(item, "revised_prompt", None):     # 部分服务会改写你的提示词
            print(f"[提示词改写] {item.revised_prompt[:120]}...")
    return {"saved": saved, "size": size, "n": n}


if __name__ == "__main__":
    pos, neg = build_prompt(
        subject="一只橘色短毛猫，趴在木质窗台上",
        style="纪实摄影，自然质感",
        composition="侧面特写，浅景深，f/1.8，主体居中偏左",
        light="清晨侧逆光，暖色调，柔和阴影",
        negative="卡通，插画，畸变，模糊，多余肢体",
    )
    print("=== 正向提示词 ===")
    print(pos)
    print("=== 负面提示词 ===")
    print(neg)

    r = generate(pos, neg, size="1024x1024", n=2, quality="standard")
    print("\n=== 生成结果 ===")
    print(json.dumps(r, ensure_ascii=False, indent=2))

    # 成本粗算：生图一般按张计费，与 size/quality 强相关
    PRICE = {"1024x1024": {"standard": 0.15, "hd": 0.45},
             "512x512":   {"standard": 0.05, "hd": 0.15}}
    cost = PRICE.get(r["size"], {}).get("standard", 0) * r["n"]
    print(f"\n估算成本：{r['n']} 张 × {r['size']} = ¥{cost:.2f}（价格随厂商浮动，仅示意）")
```

```

浅景深，f/1.8，主体居中偏左，光照：清晨侧逆光，暖色调，柔和阴影，画质：高细节，高分辨率，清晰锐利

=== 生成结果 ===
{
  "saved": [
    "gen_images/20261007_014322_0.png",
    "gen_images/20261007_014322_1.png"
  ],

  "n": 2

估算成本：2 张 × 1024x1024 = ¥0.30（价格随厂商浮动，仅示意）
```

生图提示词的三条实操经验：

1. **越具体越好，但别堆叠矛盾词**。"8k、超清、大师级、获奖、完美、绝美"这类词堆十个，不如一句"浅景深 f/1.8 侧面特写"有用——后者是可执行的视觉描述，前者只是情绪词。
2. **负面提示词在 SD 系模型里效果显著，在部分新模型（如 FLUX/gpt-image-1）里作用减弱**，此时应该把精力放在正向描述上。
3. **固定 seed 做迭代**。先用 seed=42 生成 4 张选一张方向，再固定这个 seed 微调提示词，比每次随机要高效得多。

## 八、评测与局限

### 8.1 常用 Benchmark

| Benchmark | 测什么 | 用途 |
|---|---|---|
| MMBench | 综合多选（中英） | 通用能力体检 |
| MMMU | 大学学科级别的多模态推理 | 高端推理能力 |
| ChartQA / DocVQA | 图表问答 / 文档问答 | **业务最相关**，做文档产品必看 |
| OCRBench | OCR 专项 | 中文票据场景必看 |
| MathVista | 数学图形推理 | 几何题、函数图 |
| HallusionBench | **幻觉专项** | 判断模型是否"看图编故事" |
| MMVet | 综合开放式 | 整体质量 |

看榜单的正确姿势：**只看和你任务最接近的那一列**。你做票据识别，MMBench 高 5 分毫无意义，OCRBench 才是决策依据。

### 8.2 七条必须知道的局限

1. **视觉幻觉**：图里没有的东西它说得栩栩如生。典型场景——问"图中左下角写了什么"，而左下角是空白，模型会编一句。**防御方法**：要求模型对每个结论给出"在图中哪个位置看到的"，并在 prompt 里明确允许回答"图中不存在"。
2. **OCR 错误**：印刷体好，手写体差；有印章遮挡、折痕、反光时急剧恶化；中英文混排、小字号、竖排文本是重灾区。
3. **计数能力弱**：超过 5 个基本不可靠。**绕法**：不要问"有几个"，让模型先逐个列举（"请列出图中所有可见的商品名称"），再让你自己的代码 `len()` 计数。用代码做模型不擅长的事，这是多模态工程里最常用的一招。
4. **空间关系弱**：左右、上下、前后遮挡容易搞反。需要精确位置的场景（如"点击图中红色按钮"），请配合目标检测/UI 自动化工具，不要让 VLM 直接输出坐标。
5. **小字看不清**：受限于 tile 与 token 预算，图中小于画面高度 2% 的文字基本不可用。**解法**：先做 ROI 裁剪，把关键区域放大后单独送进去问。
6. **长图与多图退化**：超过 3–4 张图后，模型容易混淆来源；超长截图（如 10000px 的网页长图）会被强制缩放导致小字全糊。**解法**：长图切段，多图显式编号。
7. **视频与时序**：抽帧本质上就是多图，帧数多了会退化，且时序因果关系天然弱。

### 8.3 怎么评测你自己的业务

Benchmark 是别人的，你的业务要自己测。方法：**建 50 张真实业务图集 + 每题标准答案**，按任务类型分组统计。

| 分组 | 样本 | 指标 | 合格线（参考） |
|---|---|---|---|
| 图分类 | 10 | 准确率 | ≥ 95% |
| 关键字段 OCR | 15 | 字段级精确匹配率 | ≥ 98%（财务场景要 99.5%+） |
| 图表数值读取 | 10 | 数值误差 ≤ 1% 的比例 | ≥ 90% |
| 开放问答 | 10 | 人工 1–5 分均分 | ≥ 4.0 |
| 抗幻觉（图中不存在） | 5 | 正确回答"不存在"的比例 | ≥ 90% |

最后一组"抗幻觉"最容易被忽略，但它是生产事故的主要来源。做法很简单：拿几张图，问一些**图上根本没有的东西**（比如问一张风景照"图里的车牌号是多少"），看模型是拒答还是编造。

## 九、成本与合规

### 9.1 图片 token 为什么这么贵

还是那个数字：一张 1024×1024 的 `high` detail 图 = 4 个 tile = **765 token**。而一段 200 字的中文问题大约 300 token。也就是说，**一张图 ≈ 2.5 个"200 字问题"**。

一个 10 轮的多图对话，如果每轮带 3 张高清图（多数服务端会缓存重复图片，但不同图不缓存）：

```
单轮：3 × 765 + 300(问题) + 300(历史摘要) ≈ 2895 token
10 轮（历史累积，不做裁剪）：最坏接近 3 万 token
```

**四条降本手段**（按有效性排序）：

1. **能裁剪就裁剪**：把大图裁出关键区域，token 直接降到 1/4；
2. **能降 detail 就降 detail**：不需要读字就用 `low`，85 token vs 765 token；
3. **图片去重与缓存**：同一张图在同一会话里不要重复计费（多数服务端已做，但要确认）；
4. **历史里剥离图片**：多轮对话时，把前几轮的图片从 messages 里去掉，只保留文字结论。这一招通常能省 60% 以上。

### 9.2 一张表决定：VLM 还是 OCR + LLM

这是多模态落地最值钱的一个决策。

| 维度 | 通用 VLM 直接看图 | 专用 OCR + 文本 LLM |
|---|---|---|
| 单次成本（一张 A4 文档） | 高（约 800–2000 token） | 低（OCR 几分钱 + 文本 token 几百） |
| 版式理解 | **强**（知道哪个数字属于哪一栏） | 弱（纯文本流，位置信息需额外处理） |
| 纯文字识别准确率 | 中（小字/手写差） | **高**（PaddleOCR 中文印刷体 >99%） |
| 视觉属性（颜色、材质、形状） | **强** | 完全不行 |
| 图表/示意图理解 | **强** | 基本不行 |
| 可私有化 | 需 8GB+ 显存 | OCR 可 CPU 跑，成本极低 |
| 处理速度 | 慢（秒级） | 快（OCR 百毫秒级） |

**结论（直接可用）**：

- **批量、量大、格式固定、只要文字**（如每天 1 万张发票录入）→ **OCR + LLM**，成本能差 10 倍以上；
- **格式不定、需要理解结构/视觉/图表**（如用户随手上传的截图问答）→ **VLM**；
- **折中方案（推荐给生产系统）**：**OCR 先跑，把 OCR 文本 + 原图一起给 VLM**，让 VLM 做校验和版式理解。既省钱又保准确，还能用 OCR 结果交叉验证 VLM 是否幻觉。

### 9.3 合规红线

- **隐私图片禁止外传**：身份证、病历、合同、含个人信息（PII）的截图。这不是"建议"，是法律要求（个人信息保护法）。
- **本地化方案**：Qwen2.5-VL / MiniCPM-V 私有化部署，或至少在出网前做**脱敏裁剪**（把身份证号区域打码再传）。
- **数据留存**：确认你的供应商是否用你的请求做训练、留存多久、能否删除。企业采购时必须写进合同。
- **生成内容合规**：生图服务必须有 NSFW 过滤与内容审计，且要保留生成日志以备追溯。
- **版权**：生图模型的训练数据版权状态复杂，商用前确认供应商的商用授权条款。

## 十、十个常见坑

| # | 坑 | 现象 | 解法 |
|---|---|---|---|
| 1 | 图片过大被拒/被压缩 | 报 400 或图糊了读不出字 | 本地先等比缩放到 1568 以内再传；注意服务端还会再压一次，别太小 |
| 2 | base64 与 URL 混用 | 传本地路径 `./a.png` 直接报错 | 服务端只认 http(s) URL 或 `data:image/xxx;base64,...`，本地必须编码 |
| 3 | 忘记 MIME 前缀 | "invalid image" | 必须是完整 data URI：`data:image/jpeg;base64,xxxx` |
| 4 | 多图顺序错乱 | 模型把图2的内容说成图1 | 在消息里显式插入"共 N 张，编号图1…图N"，问题里用编号指代 |
| 5 | 中文 OCR 选型错 | 通用模型中文小字识别率惨不忍睹 | 中文票据优先 Qwen-VL / 专用 OCR；用自己真实图测，别信榜单 |
| 6 | 把"看图"当 OCR 用 | 每月账单爆掉 | 见 9.2 决策表，量大固定格式走 OCR |
| 7 | RGBA/CMYK/HEIC 不支持 | 报格式错误或颜色诡异 | 统一转 RGB；iOS 的 HEIC 必须先转 JPEG |
| 8 | EXIF 旋转 | 手机竖拍的图传过去是躺着的 | `ImageOps.exif_transpose()` 修正 |
| 9 | 图里自带答案文字 | 以为模型"看懂了图"，其实只是 OCR 了标签 | 评测时用**不带文字标注的图**做对照，才能测出真视觉能力 |
| 10 | 生图不可复现 | 同样提示词每次都不一样 | 固定 seed；部分服务端不支持 seed，则要本地开源模型才能复现 |

第 9 条值得单独说一句。很多团队评测时兴高采烈地报告"我们的 VLM 图表理解准确率 92%"，后来发现他们的图表截图里，数值都直接标在数据点旁边了——模型只是在做 OCR。**真正难的图表题（要从坐标轴刻度推断数值）准确率往往只有 50–60%**。评测集一定要设计"无标注对照组"。

## 十一、本节小结

1. **多模态的本质是把图像翻译成 token**。图 → patch → ViT → 视觉 token → Projector → 与文本 token 拼接 → 进 LLM。所以你已有的 Prompt、上下文管理、Function Calling 技能全部可以平移，新增的只有成本和幻觉两个风险。
2. **CLIP 是整套技术的地基**。它在 4 亿图文对上做对比学习，把图像空间与文本空间拉到同一坐标系，于是多模态模型才得以"免费"接上预训练好的视觉塔和 LLM。零样本分类是把分类改写成检索，模板要用中英多套取平均。
3. **架构是 ViT + Projector + LLM 三段式**。Projector 三种方案里，MLP（LLaVA）因 LLM 上下文变长而成为主流，Q-Former（BLIP-2）的压缩优势在长上下文时代反而成了细节瓶颈。
4. **理解与生成是两套技术栈**。图→文用 ViT+Projector+LLM；文→图用扩散模型（潜空间去噪 + CFG + DiT），不要把二者混为一谈。
5. **成本是第一工程约束**。一张高清图 ≈ 几百到上千 token；裁剪、降 detail、剥离历史图片是三个最有效的降本手段。
6. **选型的核心决策是"VLM vs OCR+LLM"**：量大、格式固定、只要文字走 OCR；格式不定、要理解结构和视觉走 VLM；生产系统推荐 OCR + VLM 交叉验证。
7. **合规是硬约束**：含个人信息的截图禁止外传，本地部署用 Qwen2.5-VL / MiniCPM-V，采购合同要明确训练使用与留存条款。

## 十二、实战练习

**练习 1：亲手验证 CLIP 的对齐（必做）**
跑通第三节代码，换成 3 张你自己的图（一张人像、一张文档截图、一张图表）。验收标准：每张图的 Top-1 文本匹配正确；把余弦相似度打印出来，说明为什么 softmax 之后的概率和原始余弦值"观感差异很大"。

**练习 2：算清你自己的图片账单**
用第六节的 `estimate_image_tokens` 函数，算一算：一张手机拍的发票（3024×4032）、一张网页长截图（1080×8000）、一张 512×512 的缩略图，在 `high` 和 `low` 下各是多少 token。验收标准：写出一张三行表，并算出"如果把手机原图先缩到短边 768 再传，能省百分之多少 token"。

**练习 3：搭一个"截图问答小助手"**
用 Gradio 做一个界面：上传截图 + 输入问题 → 调多模态 API → 显示答案 + 显示本次消耗的 token 估算。加上"历史里剥离图片"的开关。验收标准：连续问 5 轮，对比开关打开前后的累计 token，说明省了多少。

**练习 4：抗幻觉测试集**
准备 5 张图，对每张问 2 个"图上根本不存在"的问题（例如对风景照问"左下角的车牌号是多少"）。统计模型的正确拒答率。验收标准：先测原始 prompt，再在 prompt 里加上"如果图中不存在该内容，必须回答'图中未发现'"，对比两次的拒答率差异，写出结论。

**练习 5：VLM vs OCR 成本对比实验**
找 20 张真实票据，分别走两条路：① 直接用 VLM 抽金额；② 用 RapidOCR/PaddleOCR 抽文字后交给文本大模型抽金额。验收标准：统计两条路的**准确率**和**单次成本**，算出"每月 1 万张"时的月度成本差，给出你的选型结论。
