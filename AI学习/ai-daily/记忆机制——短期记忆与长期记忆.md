# 记忆机制——短期记忆与长期记忆

**承上**：8-1 手写了 ReAct 循环，8-2 用框架把工具标准化了。但有个致命问题一直没解决：那个循环里的 `history` 是**一次请求内**的临时变量，请求结束就清空。用户第二轮问"刚才算的那个华氏度，再帮我加 5 度是多少？"，Agent 已经**完全不记得**"刚才那个华氏度"是什么了。

**本篇**：系统讲清 Agent 的"记忆"分哪两类——**短期记忆**（当前对话的上下文，管"这次聊到哪了")和**长期记忆**（跨会话持久化的知识库，管"用户是谁、他喜欢什么、历史上发生了什么")。给出可运行的内存版实现，并对比"忘得快"和"记得住"两种 Agent 的体验差异。

**启下**：单 Agent 有了记忆，能应对多轮对话了。但如果任务本身很复杂——比如"调研竞品 + 写报告 + 做 PPT + 发邮件"——一个 Agent 既要搜又要写又要排，容易顾此失彼。下一篇 **8-4《多 Agent 协作——把复杂任务拆给多个角色》** 讲怎么让多个专职 Agent 分工配合，像一个小团队。

## 一、先定性：大模型本身没有记忆

这是很多人最大的误解。**你每次调用 API，模型都是"失忆"的**——它不保留上次对话的任何东西。所谓"它能记住我们聊过什么"，真相是：

> **我们把完整的历史对话，每次都重新拼进 Prompt 发给了模型。**

也就是说，"记忆"从来不是模型的能力，而是**你作为调用方，有没有把历史塞回下一次请求**。

这就天然带来两个层面的记忆需求：

| 记忆类型 | 存什么 | 存活多久 | 典型载体 |
|---|---|---|---|
| **短期记忆** | 当前这一轮对话的来回 | 一个会话内（关掉网页就没） | 内存里的 messages 列表 |
| **长期记忆** | 用户画像、历史事件、跨会话知识 | 永久（落库） | 向量库 / 数据库 / 文件 |

## 二、短期记忆：三种"怎么塞回历史"的策略

阶段 6-4 我们算过：历史越长，**每次请求 token 越多、越贵，而且逼近模型上下文上限后模型反而"记混"**。所以短期记忆的核心矛盾是：**要记住，又不能全记住**。三种常见策略：

### 策略 1：全量记忆（最省事，但有天花板）

```python
messages = [
    {"role": "system", "content": "你是个助手"},
    {"role": "user", "content": "北京多少度？"},
    {"role": "assistant", "content": "26°C"},
    {"role": "user", "content": "那加5度呢？"},   # 依赖上一轮，必须保留
]
# 每次都把整个 messages 发给模型
```

适合对话短、量小的场景；一旦对话超过几千轮，立刻撞上下文上限。

### 策略 2：滑动窗口（只留最近 N 轮）

```python
class ShortTermMemory:
    def __init__(self, system: str, keep_turns: int = 4):
        self.system = system
        self.keep_turns = keep_turns
        self.history = []          # 每项是 {"role":..., "content":...}

    def add(self, role, content):
        self.history.append({"role": role, "content": content})

    def build_messages(self):
        # 系统提示 + 最近 keep_turns*2 条（一轮=user+assistant）
        recent = self.history[-self.keep_turns * 2:]
        return [{"role": "system", "content": self.system}] + recent

mem = ShortTermMemory("你是天气助手", keep_turns=4)
for r, c in [("user","北京多少度？"), ("assistant","26°C"),
             ("user","加5度呢？"),   ("assistant","31°C")]:
    mem.add(r, c)
print(mem.build_messages())   # 永远只带最近4轮，token 可控
```

**代价**：窗口外的对话真丢了。如果用户问"我们最开始聊的那个城市是哪儿"，窗口外的信息已不在，Agent 会答不上来——这就是"记混/记丢"的典型 bug。

### 策略 3：摘要压缩（又记全、又不爆）

把窗口外的旧对话**交给模型先总结成一段**，只保留摘要 + 最近几轮。阶段 6-4 我们实测过：10 条历史 114 token，摘要压缩后降到 66 token，且关键信息不丢。这是生产级 Agent 的主流做法。

```python
def compress(mem, summarize_fn):
    if len(mem.history) <= mem.keep_turns * 2:
        return
    old = mem.history[:-mem.keep_turns * 2]
    text = "\n".join(f"{m['role']}: {m['content']}" for m in old)
    mem.summary = summarize_fn(text)          # 调 LLM 生成摘要
    mem.history = mem.history[-mem.keep_turns * 2:]
```

**选型口诀**：对话短用全量；长对话又怕贵用滑动窗口；既要全又要便宜用摘要。没有银弹。

## 三、长期记忆：让 Agent 跨会话"认识你"

短期记忆关掉就没了。但很多场景需要"Agent 记得你是谁"：

- 客服 Agent 记得"这个用户上次投诉过物流"；
- 写作 Agent 记得"这个用户偏好口语化、不要术语"；
- 你自己的助手记得"我常用 DeepSeek、不想每次都说"。

这类**跨会话、可检索**的记忆，标准做法是——没错，又是阶段 7 的向量库：

```python
# 伪代码思路（真实现用 chroma/milvus，见 7-2）
def save_long_term(memory_text: str):
    vec = embed(memory_text)
    vector_db.upsert(user_id, vec, memory_text)     # 持久化落库

def recall_long_term(query: str, top_k=3):
    vec = embed(query)
    hits = vector_db.search(vec, top_k)             # 语义检索相关记忆
    return "\n".join(h["text"] for h in hits)

# 每次对话前，先把相关长期记忆塞进 system 提示
relevant = recall_long_term("用户对写作风格的偏好")
system = f"你是助手。以下是关于该用户的历史记忆：\n{relevant}"
```

**关键点**：长期记忆**不是一次性全灌进 Prompt**（那会爆），而是**按当前问题语义检索最相关的几条**塞进去——这和 RAG 的检索逻辑完全同构。所以阶段 7 学的东西，在这里直接复用。

## 四、一个"失忆"导致的真实 bug 复盘

| 现象 | 根因 | 排查方向 |
|---|---|---|
| Agent 答非所问，像没看过前文 | 短期记忆没拼进 Prompt | 打印 `build_messages()` 看 history 是否带入 |
| 聊久了 Agent 变傻/重复 | 超上下文窗口被截断 | 检查是否上了窗口/摘要策略 |
| 换设备登录后 Agent 不认人 | 长期记忆没按 user_id 隔离 | 查 vector_db 是否带了用户维度 |
| 同一用户多条记忆冲突 | 检索召回了过时记忆 | 给记忆加时间戳，检索时优先近期 |

## 五、本篇小结

1. **大模型本身没记忆**——所谓"记住"，是调用方每次把历史重新塞回 Prompt。这是理解记忆机制的入口。
2. **短期记忆**管"这次聊到哪"，载体是内存 messages 列表；三种策略：全量（省事有天花板）、滑动窗口（控 token）、摘要压缩（又全又省，生产主流）。
3. **长期记忆**管"用户是谁、历史发生了什么"，载体是向量库/数据库；按问题语义检索相关几条塞进 system 提示——**和 RAG 同构，阶段 7 直接复用**。
4. 四大失忆 bug（答非所问、聊久变傻、换设备不认人、记忆冲突）各有固定排查方向。
5. 记忆 + 工具 + 循环，Agent 才算有了"脑、手、记忆"三件套。
