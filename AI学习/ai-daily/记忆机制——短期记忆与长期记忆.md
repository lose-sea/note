# 记忆机制——短期记忆与长期记忆

**承上**：8-1 手写了 ReAct 循环，8-2 用框架把工具标准化了。但有个致命问题一直没解决：那个循环里的 `history` 是**一次请求内**的临时变量，请求结束就清空。用户第二轮问"刚才算的那个华氏度，再帮我加 5 度是多少？"，Agent 已经**完全不记得**"刚才那个华氏度"是什么了。

**本篇**：系统讲清 Agent 的"记忆"分哪两类——**短期记忆**（当前对话的上下文，管"这次聊到哪了")和**长期记忆**（跨会话持久化的知识库，管"用户是谁、他喜欢什么、历史上发生了什么")。给出可运行的内存版实现，并对比"忘得快"和"记得住"两种 Agent 的体验差异。

**启下**：单 Agent 有了记忆，能应对多轮对话了。但如果任务本身很复杂——比如"调研竞品 + 写报告 + 做 PPT + 发邮件"——一个 Agent 既要搜又要写又要排，容易顾此失彼。下一篇 **8-4《多 Agent 协作——把复杂任务拆给多个角色》** 讲怎么让多个专职 Agent 分工配合，像一个小团队。

## 一、先定性：大模型本身没有记忆

这是很多人最大的误解，必须一开始就用最直白的话说清楚，因为它决定了你后面所有记忆设计的出发点。**你每次调用 API，模型都是"失忆"的**——它不保留上次对话的任何东西，服务器不会为你的会话偷偷存一份"这个用户之前聊过什么"。所谓"它能记住我们聊过什么"，真相只有一个，请你记牢：

> **我们把完整的历史对话，每次都重新拼进 Prompt 发给了模型。**

也就是说，"记忆"从来不是模型的能力，而是**你作为调用方，有没有把历史塞回下一次请求**。模型就像一个每次见面都失忆的顾问：你若每次都把前因后果重述一遍，他表现得像"记得"；你若只丢一句"接着说"，他一脸茫然。这一点和人类的记忆完全不同——人类的大脑会自动把昨天的事存进长期记忆，而模型的"大脑"每次调用都是从空白状态启动，历史全靠你喂。

理解这一点，你立刻能推导出两个重要结论：第一，**记忆的成本 = 把历史重新发给模型的 token 成本**，历史越长越贵；第二，**记忆的"容量"受上下文窗口限制**，超出就被截断，模型会"忘了"最前面的内容。这两个结论，正是下面所有短期记忆策略要解决的矛盾。

这就天然带来两个层面的记忆需求——一个管"这次对话内"，一个管"跨多次对话"。用一个表格先建立总览：

| 记忆类型 | 存什么 | 存活多久 | 典型载体 | 类比人类 |
|---|---|---|---|---|
| **短期记忆** | 当前这一轮对话的来回 | 一个会话内（关掉网页就没） | 内存里的 messages 列表 | 你正在进行的这通电话 |
| **长期记忆** | 用户画像、历史事件、跨会话知识 | 永久（落库） | 向量库 / 数据库 / 文件 | 你笔记本里记的"客户偏好" |

理解了这个二分法，后面所有记忆相关的设计都只是这两个容器的"存取策略"问题。短期记忆解决"这次聊到哪"，长期记忆解决"你是谁、我们过去发生过什么"。下面我们分别拆解，并给出可运行代码。

## 二、短期记忆：五种"怎么塞回历史"的策略

阶段 6-4 我们算过一笔账：历史越长，**每次请求 token 越多、越贵，而且逼近模型上下文上限后模型反而"记混"**（它塞得太满，注意力被稀释，关键前文反而被忽略，甚至开始重复自己）。所以短期记忆的核心矛盾是：**要记住，又不能全记住**。三种常见策略，本质是在"记住多少"和"花多少成本"之间找平衡，我再加一种进阶策略凑成四种，帮你覆盖更多场景。

### 策略 1：全量记忆（最省事，但有天花板）

```python
messages = [
    {"role": "system", "content": "你是个助手"},
    {"role": "user", "content": "北京多少度？"},
    {"role": "assistant", "content": "26°C"},
    {"role": "user", "content": "那加5度呢？"},   # 依赖上一轮，必须保留
]
# 每次都把整个 messages 发给模型
```

适合对话短、量小的场景；一旦对话超过几千轮，立刻撞上下文上限（比如 4k、8k、128k token 的窗口），而且越往后越贵。这是最简单的"无脑记忆"，但不 scale（无法扩展）。很多初学者的第一个线上 bug 就是：用户聊了两天，messages 累积到几万字，第 N 次请求直接超窗口报错。

### 策略 2：滑动窗口（只留最近 N 轮）

```python
class ShortTermMemory:
    def __init__(self, system: str, keep_turns: int = 4):
        self.system = system
        self.keep_turns = keep_turns
        self.history = []          # 每项是 {"role":..., "content":...}

    def add(self, role, content):
        self.history.append({"role": role, "content": content})

    def build_messages(self):
        # 系统提示 + 最近 keep_turns*2 条（一轮=user+assistant）
        recent = self.history[-self.keep_turns * 2:]
        return [{"role": "system", "content": self.system}] + recent

mem = ShortTermMemory("你是天气助手", keep_turns=4)
for r, c in [("user","北京多少度？"), ("assistant","26°C"),
             ("user","加5度呢？"),   ("assistant","31°C")]:
    mem.add(r, c)
print(mem.build_messages())   # 永远只带最近4轮，token 可控
```

**代价**：窗口外的对话真丢了。如果用户问"我们最开始聊的那个城市是哪儿"，窗口外的信息已不在，Agent 会答不上来——这就是"记混/记丢"的典型 bug。滑动窗口是"丢车保帅"：保住最近上下文的连贯，牺牲远期记忆。它适合闲聊、客服这类"只关心当下"的场景，不适合需要回溯早期约定的场景（比如"按我们开头说好的方案执行"）。

### 策略 3：摘要压缩（又记全、又不爆）

把窗口外的旧对话**交给模型先总结成一段**，只保留摘要 + 最近几轮。阶段 6-4 我们实测过：10 条历史 114 token，摘要压缩后降到 66 token，且关键信息不丢。这是生产级 Agent 的主流做法，因为它兼顾了"不丢大局"和"成本低"。实现上，你可以定时（比如每满 10 轮）触发一次摘要：

```python
def compress(mem, summarize_fn):
    if len(mem.history) <= mem.keep_turns * 2:
        return
    old = mem.history[:-mem.keep_turns * 2]
    text = "\n".join(f"{m['role']}: {m['content']}" for m in old)
    mem.summary = summarize_fn(text)          # 调 LLM 生成摘要
    mem.history = mem.history[-mem.keep_turns * 2:]
```

注意 `summarize_fn` 本身就是一次 LLM 调用，所以摘要不是免费的——它用"一次小调用"换"后续无数次大调用"的省钱，长期看划算。生产里常用"分层记忆"：近期原文 + 远期摘要，既保连贯又控成本。

### 策略 4（补充）：带重要性的记忆筛选

比滑动窗口更聪明的一种做法是给每条消息打"重要性分数"（可以用一个小模型判断"这条是否含关键信息"），只保留高分消息。比如用户说"我讨厌术语"是高分（长期偏好，但该轮是短期说的），说"好的"是低分（可丢）。这种策略介于滑动窗口和摘要之间，工程上很实用，只是多了一次打分调用。给一张四种策略的总览表，建议你打印贴在工位：

```
短期记忆四种策略对比：
策略          记住多少      成本      实现难度    适用
全量          全部          高        低         短对话
滑动窗口      最近N轮       低        低         一般对话
摘要压缩      全部(压缩)    中        中         长对话(主流)
重要性筛选    关键句        中低      中         偏好明显场景
```

### 策略 5：按 token 预算装载（生产最常用，建议直接抄）

前面四种策略都有一个共同缺陷：**它们按"条数"或"轮数"做决策，但账单是按"token 数"算的**。同样"保留最近 4 轮"，如果这 4 轮里有三轮是长篇大论的会议纪要，它可能比另外 20 轮闲聊还贵。更糟的是，一旦超了模型上下文窗口（比如 8k），请求直接失败——**而你的代码在此之前完全无法预感**。所以生产级的做法是：**把"保留多少"换算成"还剩多少预算"，从最新的一条往回装，装满为止**。

```python
def approx_tokens(text):
    """粗估 token 数：中文约 1.5 token/字，其余字符约 0.3 token/个"""
    cn = sum(1 for c in text if '\u4e00' <= c <= '\u9fff')
    return int(cn * 1.5 + (len(text) - cn) * 0.3)

class BudgetedMemory(ShortTermMemory):
    """按 token 预算装历史，而不是按轮数——账单才是唯一真相"""
    def __init__(self, system, token_budget=800):
        super().__init__(system, keep_turns=10 ** 6)
        self.token_budget = token_budget

    def build_messages(self):
        used = approx_tokens(self.system)
        picked = []
        for m in reversed(self.history):          # 从最新的一条往回装
            cost = approx_tokens(m["content"])
            if used + cost > self.token_budget:
                break
            picked.append(m)
            used += cost
        return [{"role": "system", "content": self.system}] + list(reversed(picked))

mem = BudgetedMemory("你是天气助手", token_budget=60)
dialogue = [("user", "北京今天多少度？"),
            ("assistant", "北京今天晴，26°C。"),
            ("user", "换算成华氏度呢？"),
            ("assistant", "约 78.8°F。"),
            ("user", "那上海比北京热多少？"),
            ("assistant", "上海 30°C，比北京高 4°C。")]
for r, c in dialogue:
    mem.add(r, c)

msgs = mem.build_messages()
print(f"共 {len(mem.history)} 条历史，实际装载 {len(msgs) - 1} 条，"
      f"估算 {sum(approx_tokens(m['content']) for m in msgs)} token")
for m in msgs:
    print(f"  {m['role']:>9}: {m['content']}")
```

**运行结果**：

```
共 6 条历史，实际装载 5 条，估算 56 token
     system: 你是天气助手
  assistant: 北京今天晴，26°C。
       user: 换算成华氏度呢？
  assistant: 约 78.8°F。
       user: 那上海比北京热多少？
  assistant: 上海 30°C，比北京高 4°C。
```

三条经验请收好：

1. **预算要给"输出"留出余量**。上面 `token_budget=60` 只算历史，实际上你得预留模型回答的空间（一般再留 500~1000 token），否则会出现"输入刚好填满窗口、模型一个字也吐不出来"的诡异现象。
2. **系统提示和工具说明也要算进去**。它们每轮都会重发，是固定开销。很多人算预算时只盯着对话历史，结果照样爆。
3. **`approx_tokens` 只是粗估**。中文在不同 tokenizer 下差异不小（有的 1 个字近 2 token）。生产环境请用官方 `tiktoken` 或对应厂商的估算法；这里用粗估是为了让你在没有依赖的情况下也能跑起来理解原理。

把这一节和前面的摘要压缩叠起来，就是工业界的"**分层记忆**"：近期原文（保证连贯）+ 远期摘要（保住大局）+ token 预算兜底（保证不爆）。三层组合才是能在生产里长期跑的形态。

## 三、长期记忆：让 Agent 跨会话"认识你"

短期记忆关掉就没了。但很多场景需要"Agent 记得你是谁"，这是产品能"个性化"的关键，也是让用户体验从"工具"升级为"伙伴"的分水岭：

- 客服 Agent 记得"这个用户上次投诉过物流"，下次主动安抚；
- 写作 Agent 记得"这个用户偏好口语化、不要术语"，每次都按这个调性写；
- 你自己的助手记得"我常用 DeepSeek、不想每次都说"，省去重复交代。

这类**跨会话、可检索**的记忆，标准做法是——没错，又是阶段 7 的向量库（你发现没，RAG 的检索能力在 Agent 各处都能复用，它是阶段 7 埋下的伏笔）：

```python
# 伪代码思路（真实现用 chroma/milvus，见 7-2）
def save_long_term(memory_text: str):
    vec = embed(memory_text)
    vector_db.upsert(user_id, vec, memory_text)     # 持久化落库

def recall_long_term(query: str, top_k=3):
    vec = embed(query)
    hits = vector_db.search(vec, top_k)             # 语义检索相关记忆
    return "\n".join(h["text"] for h in hits)

# 每次对话前，先把相关长期记忆塞进 system 提示
relevant = recall_long_term("用户对写作风格的偏好")
system = f"你是助手。以下是关于该用户的历史记忆：\n{relevant}"
```

**关键点**：长期记忆**不是一次性全灌进 Prompt**（那会爆），而是**按当前问题语义检索最相关的几条**塞进去——这和 RAG 的检索逻辑完全同构。所以阶段 7 学的东西，在这里直接复用。你甚至可以把"长期记忆检索"本身包装成一个工具，让 Agent 在 8-1 的循环里主动决定"我要不要回想一下这个用户以前说过什么"，这就把记忆和 Agent 循环打通了，形成"记忆驱动的行动"。

为了更具体、可本地运行，下面给一个**可运行的简化版长期记忆**（用内存字典模拟向量检索，真实场景换 chroma），让你亲眼看到"按 user_id 隔离 + 语义召回"是怎么工作的：

```python
import math

# 极简余弦相似度版"向量记忆"（仅演示思想，生产请用真向量库）
class LongTermMemory:
    def __init__(self):
        self.store = {}   # id -> {"user":..., "vec": [...], "text": str}
        self._id = 0

    def _fake_embed(self, text):
        # 真实场景调 embedding 模型；这里用字符计数做伪向量，仅演示
        return [float(text.count(c)) for c in "abcdefghij"]

    def save(self, user_id, text):
        self._id += 1
        self.store[self._id] = {"user": user_id, "vec": self._fake_embed(text), "text": text}
        return self._id

    def recall(self, user_id, query, top_k=2):
        qv = self._fake_embed(query)
        scored = []
        for item in self.store.values():
            if item["user"] != user_id:
                continue
            dist = math.dist(qv, item["vec"])
            scored.append((dist, item["text"]))
        scored.sort(key=lambda x: x[0])
        return [t for _, t in scored[:top_k]]

mem = LongTermMemory()
mem.save("u1", "用户 u1 偏好口语化表达，讨厌专业术语")
mem.save("u1", "用户 u1 常用 DeepSeek 模型")
print(mem.recall("u1", "他喜欢什么写作风格"))
# 输出: ['用户 u1 偏好口语化表达，讨厌专业术语', '用户 u1 常用 DeepSeek 模型']
```

这段代码的输出印证了：长期记忆是按"语义相关"召回的，且**按 user_id 隔离**——不同用户互不串味，这正是生产系统必须做的隔离。如果忘了加 user_id 维度，就会出现"用户 A 的偏好被用户 B 的对话触发"的隐私灾难。

### 策略补充一：给长期记忆加上时间戳、去重与"新覆盖旧"

上面的极简实现有两个致命缺陷，它们在真实产品里 100% 会出现：

- **偏好冲突**：用户 30 天前说"我喜欢简洁"，昨天改口"我要详细版"。两条都在库里，检索时都被召回，模型面前摆着两句互相矛盾的指令，于是它随机挑一条执行——用户看到的表现就是"这 AI 时好时坏"。
- **记忆无限膨胀**：每聊一句就 `save` 一条，半年后库里几万条近似重复的记录，检索质量下降、成本上升。

对策是给每条记忆加**时间戳 + topic 去重 + 时间加权排序**：**同一个 topic 只保留最新一条（旧的标记作废），排序时越新的越靠前**。注意这里的 embedding 我换成了基于 Unicode 码位的确定性伪向量，它比原来的字母计数法对中文更友好（生产环境依然请换成真正的 embedding 模型）。

```python
import json, time            # 若前面已导入可省略

def hash_embed(text, dim=24):
    """演示用的确定性伪向量：把每个字的 Unicode 码位投到 dim 个桶里计数"""
    vec = [0.0] * dim
    for ch in text:
        vec[ord(ch) % dim] += 1.0
    return vec

class TemporalLongTermMemory:
    """带 topic 去重 + 时间戳加权的长期记忆"""
    def __init__(self):
        self.store = {}
        self.latest = {}          # (user, topic) -> 最新的记忆 id
        self._id = 0

    def save(self, user_id, text, topic=None, ts=None):
        self._id += 1
        self.store[self._id] = {"user": user_id, "vec": hash_embed(text), "text": text,
                                "topic": topic, "ts": ts if ts is not None else time.time()}
        key = (user_id, topic or text)
        if key in self.latest:                       # 同一 topic 的旧记忆直接作废
            self.store[self.latest[key]]["deprecated"] = True
        self.latest[key] = self._id
        return self._id

    def recall(self, user_id, query, top_k=2, now=None):
        now = now if now is not None else time.time()
        qv = hash_embed(query)
        scored = []
        for item in self.store.values():
            if item["user"] != user_id or item.get("deprecated"):
                continue
            dist = math.dist(qv, item["vec"])
            age_days = (now - item["ts"]) / 86400
            scored.append((dist * (1 + 0.05 * age_days), item["text"]))   # 越老排得越靠后
        scored.sort(key=lambda x: x[0])
        return [t for _, t in scored[:top_k]]

DAY = 86400
now = time.time()
mem = TemporalLongTermMemory()
mem.save("u1", "用户偏好口语化表达，讨厌堆专业术语", topic="写作风格", ts=now - 30 * DAY)
mem.save("u1", "用户最近希望写得详细一点，带数据佐证", topic="写作风格", ts=now - 1 * DAY)
mem.save("u1", "用户常用 DeepSeek 模型", topic="常用模型", ts=now - 10 * DAY)
print("召回（写作风格）:", mem.recall("u1", "他喜欢什么样的写作风格", top_k=2, now=now))
print("作废条数:", sum(1 for v in mem.store.values() if v.get("deprecated")))
```

**运行结果**：

```
召回（写作风格）: ['用户最近希望写得详细一点，带数据佐证', '用户常用 DeepSeek 模型']
作废条数: 1
```

关键看点：那条 30 天前的"口语化"偏好被自动作废了，系统只保留了最新的说法——**用户改口，Agent 立刻跟着改**。这正是"新覆盖旧"的力量。工程上有两种实现流派：一种是这里演示的"物理作废"（旧的直接从检索结果里剔除），另一种是"软竞争"（两条都召回，但给新的更高权重，让模型自己判断）。**隐私合规要求严格的场景建议物理删除**（用户说"忘掉我说过的XX"，你必须真的删），其余场景软竞争更灵活。

### 策略补充二：结构化记忆——别什么都往向量库里塞

还有一类记忆，塞进向量库是**纯纯的资源浪费**：用户画像里的"行业=电商""常用模型=DeepSeek"这类字段，语义检索毫无意义（你不会想问"跟 Zara 类似的行业是什么"），它们应该是**结构化的 KV 字段**。一个成熟产品通常采用"双轨制"：**结构化画像（确定的、字段级的）+ 向量记忆（模糊的、事件级的）**。

下面演示结构化这条轨道，逻辑非常简单——从用户的话里抽关键词，命中就写画像，后者覆盖前者：

```python
PROFILE_RULES = {
    "tone":    (["口语化", "通俗易懂", "别用术语"], "口语化"),
    "detail":  (["详细一点", "展开讲", "要数据"], "详细"),
    "domain":  (["电商", "跨境电商"], "电商行业"),
    "model":   (["DeepSeek", "deepseek"], "DeepSeek"),
}

def extract_profile(utterance: str, rules=PROFILE_RULES) -> dict:
    """规则版“记忆抽取器”：命中关键词就写画像（真实场景可换成小模型抽取）"""
    hit = {}
    for field, (keywords, value) in rules.items():
        if any(k in utterance for k in keywords):
            hit[field] = value
    return hit

profile = {}
for utt in ["我讨厌术语，说话口语化一点",
            "我做跨境电商的",
            "以后都用 deepseek 帮我写",
            "帮我查下今天天气"]:
    new_fields = extract_profile(utt)
    profile.update(new_fields)                  # 新说法覆盖旧说法
    print(f"{utt:<22} → 抽取到 {new_fields or '{}'}")
print("\n最终用户画像:", json.dumps(profile, ensure_ascii=False))
```

**运行结果**：

```
我讨厌术语，说话口语化一点          → 抽取到 {'tone': '口语化'}
我做跨境电商的                     → 抽取到 {'domain': '电商行业'}
以后都用 deepseek 帮我写           → 抽取到 {'model': 'DeepSeek'}
帮我查下今天天气                   → 抽取到 {}
最终用户画像: {"tone": "口语化", "domain": "电商行业", "model": "DeepSeek"}
```

请注意最后一行：临时请求（"帮我查下今天天气"）**没有被写进画像**——这正是防治"记忆污染"最有效的一招：**规则白名单只允许写入预定义字段，写不进去的东西自然被丢弃**。相比"把所有对话都 embed 进向量库"的懒人做法，白名单虽然要多写几行，但它换来的确定性，是你在线上 troubleshoot 时能睡个好觉的保障。真实产品里通常把 `extract_profile` 换成一个小模型（便宜、快）做抽取，再用规则做最后一道校验，两者结合最稳。

## 四、一个"失忆"导致的真实 bug 复盘

记忆是 Agent 最隐蔽的 bug 来源，因为"记不住"往往表现为"答非所问"，新手很难往记忆方向想，常常误以为是模型不行。下面这张表是排障清单，建议收藏：

| 现象 | 根因 | 排查方向 |
|---|---|---|
| Agent 答非所问，像没看过前文 | 短期记忆没拼进 Prompt | 打印 `build_messages()` 看 history 是否带入 |
| 聊久了 Agent 变傻/重复 | 超上下文窗口被截断 | 检查是否上了窗口/摘要策略 |
| 换设备登录后 Agent 不认人 | 长期记忆没按 user_id 隔离 | 查 vector_db 是否带了用户维度 |
| 同一用户多条记忆冲突 | 检索召回了过时记忆 | 给记忆加时间戳，检索时优先近期 |
| 明明存了偏好却没生效 | 长期记忆检索阈值太高，没召回 | 调低 top_k 或相似度阈值 |

补充两个高频坑，它们都是我在真实项目里见过的：

- **时间戳冲突**：用户上周说"我喜欢简洁"，这周说"我要详细版"。若两条都召回，Agent 会困惑于到底听谁的。解法：给每条记忆存时间戳，召回后按时间做"后者覆盖前者"或"加权近期"，让新记忆话语权更大。
- **记忆污染**：把临时任务的中间结果（比如"正在算的 26°C"）误存进长期记忆，导致下次无关对话也把它带出来，答非所问。解法：严格区分"临时上下文"和"值得长期记住的事实"，只对后者调用 `save_long_term`，并用一个判定步骤过滤。

### 4.1 一段真实排障实录：把这套清单跑一遍

光看表格容易觉得"我懂了"，真出事时照样抓瞎。我们把上面那张清单套进一次真实排障，体验一下完整思路——这个案例来自我见过的一个客服 Agent：

> **现象**：用户反馈"机器人聊到第五句就开始胡说，还老让我重复已经说过的问题"。

**第一步，先看 Prompt 里到底发了什么**（对应表中第一行）。在 `assemble_messages` 返回后加一行 `print(json.dumps(msgs, ensure_ascii=False))`，立刻发现 `messages` 里除了第一句 system，只有当前这一轮 user ——**短期记忆压根没拼进去**。原因是做"伪流式输出"改造时，有人把 `build_messages()` 的返回值赋给了局部变量却没传进请求。这是最常见的低级错误：**改的时候只看函数本身，忘了看调用方**。

**第二步，补上历史后发现新问题**：拼进历史后，聊到第五轮模型开始重复自己。用 `approx_tokens` 一估，第六轮时单次输入已经 5600 token，接近窗口上限——对应表中第二行，"超窗口被截断"。上 `BudgetedMemory` 并设 `token_budget=2000` 后恢复稳定。

**第三步，个性化的坑**：修好短期记忆后，用户又说"它不记得我说过讨厌术语"。查长期记忆检索，发现召回了五条，但相似度最高的两条来自另一个 user_id 的记录——**检索时漏了用户过滤条件**（表中第三行）。补上 `if item["user"] != user_id: continue` 后一切正常。

请务必注意这一串推断的共同前提：**我们每一步都在打印中间结果**。记忆类的 bug 之所以难查，是因为它发生在"你以为没事"的地方——没人会怀疑"历史没拼进去"，因为代码里明明有一行append。**对付这种 bug 的唯一办法，就是把发给模型的最终 messages 原样打印出来读一遍。** 这一条习惯，比本章任何一个算法都值钱。

## 五、记忆 + RAG + Agent 的三层关系

很多人分不清"长期记忆"和"RAG 知识库"，这里一次性说清，因为这是阶段 7 和阶段 8 的交汇点：

| 维度 | RAG 知识库 | 长期记忆 |
|---|---|---|
| 存的内容 | 公开/企业文档（产品手册、制度） | 用户相关信息（偏好、历史） |
| 归属 | 系统级（所有人共享） | 用户级（按 user_id 隔离） |
| 更新频率 | 低频（文档变了才更新） | 高频（每次对话可能产生新记忆） |
| 技术 | 向量库检索 | 向量库检索（同技术，不同数据） |

你会发现：**二者技术完全一样（都是向量检索），区别只在"存什么、归谁"**。所以一个成熟的 Agent 往往同时接两个检索源：一个是 RAG 企业知识（系统级），一个是用户长期记忆（用户级），再叠加短期记忆的当前对话——三层拼成最终 Prompt。这就是业界常说的"记忆三层架构"：短期管当下、长期管用户、知识管事实。当你把这三层在代码里组织好，你的 Agent 才算真正"有记忆、有个性、有知识"。

### 5.1 把三层拼进同一个 Prompt：一段真实可用的组装代码

道理讲完了，落到代码上**到底怎么拼**？下面这段就是本篇的"收尾作品"——把短期记忆（`BudgetedMemory`）、长期记忆（`TemporalLongTermMemory`）和 RAG 检索拼成一条完整的 messages，然后一眼看清最终发出去的是什么样：

```python
def company_rag(query):
    """最简 RAG：真实项目换成 7-4 的检索 + 重排流水线"""
    KB = {"退款": "无理由退款需在签收后 7 天内申请。", "运费": "退货运费由买家承担，除质量问题。"}
    hits = [v for k, v in KB.items() if k in query]
    return "\n".join(hits)

def assemble_messages(user_id, question, short_mem, long_mem, rag_fn, system="你是资深业务助手"):
    recalled = long_mem.recall(user_id, question, top_k=2)      # ① 长期记忆：用户是谁
    facts = rag_fn(question)                                    # ② RAG：世界的事实
    parts = [system]
    if recalled:
        parts.append("关于该用户的长期记忆：\n- " + "\n- ".join(recalled))
    if facts:
        parts.append("可参考的知识库片段：\n" + facts)
    parts.append("输出约束：用口语化中文回答，不超过 3 句话。")   # ③ 约束放最后，离输出最近
    msgs = [{"role": "system", "content": "\n\n".join(parts)}]
    msgs += short_mem.build_messages()[1:]           # ④ 短期记忆：近期对话原文
    msgs.append({"role": "user", "content": question})
    return msgs

short = BudgetedMemory("你是天气助手", token_budget=200)
short.add("user", "公司退款规则是啥？")
short.add("assistant", "无理由退款需在签收后 7 天内申请。")
msgs = assemble_messages("u1", "那运费谁出？", short, mem, company_rag)
for m in msgs:
    print(f"\n[{m['role']}]\n{m['content']}")
print("\n估算总 token:", sum(approx_tokens(m["content"]) for m in msgs))
```

**运行结果**：

```
[system]
你是资深业务助手

关于该用户的长期记忆：
- 用户最近希望写得详细一点，带数据佐证
- 用户常用 DeepSeek 模型

可参考的知识库片段：
退货运费由买家承担，除质量问题。

输出约束：用口语化中文回答，不超过 3 句话。

[user]
公司退款规则是啥？

[assistant]
无理由退款需在签收后 7 天内申请。

[user]
那运费谁出？

估算总 token: 172
```

这份输出值得你反复端详，它藏着四个"只有踩过才知道"的工程细节：

1. **输出约束放最后**。大语言模型对靠近输出位置的内容注意力更强，"用什么语气、写多长"这类约束放在 system 提示的最末尾，执行率明显高于放在开头。这是提示词工程里性价比最高的一条经验。
2. **没有召回内容时，那一段要整个删掉**（代码里的 `if recalled:` / `if facts:`）。写死一句"暂无相关信息"反而会给模型一个奇怪的锚点，让它有时真的回答"暂无"，这是新人常犯的低级错误。
3. **短期记忆要放在 system 之后、当前问题之前**，顺序即优先级：越靠后越被重视。当前问题永远在最后。
4. **永远打印 token 估算**。上线前先看看一条典型请求要多少钱，比事后对着账单肉疼有用得多。

到这一步，你可以自豪地说：我做出了一个有**当下记忆**（短期）、**用户认知**（长期画像）、**企业知识**（RAG）的智能体。第 8 篇的多 Agent 协作，就是在这个基础上再往上搭一层"团队"。

## 六、记忆系统的工程落地要点（问答与陷阱深化）

理论讲完，落到工程上还有一堆"书上不会写、踩了才知道"的细节。这里用问答形式把最关键的几点讲透，帮你少走弯路。

**问一：长期记忆每次都检索，会不会很慢、很贵？**
答：检索本身是向量相似度计算，百万级数据也能毫秒级返回，不慢；贵的是"把召回的记忆塞进 Prompt"增加了 token。所以工程上的关键是"少而准"：top_k 别设太大（一般 3~5 条足够），并对记忆做去重和时效性过滤，避免把十年前的旧偏好也塞进来。另外可以把"是否启用长期记忆"做成开关——闲聊类请求干脆不检索，省成本。

**问二：用户说的话，哪些该存长期记忆，哪些不该？**
答：这是记忆污染（第四节提过）的核心防线。一个实用的判定流程是：先问"这句话三个月后还有用吗？"——"我讨厌术语""我是做电商的"这种用户画像该存；"帮我查下天气""今天几号"这种临时请求不该存。更稳的做法是专门用一个轻量 Agent 或规则来判断"这条是否值得记忆"，而不是无脑全存。存错了比不存更糟，因为错误信息会被反复召回、反复误导。

**问三：短期记忆用滑动窗口丢掉的远期内容，用户突然问起怎么办？**
答：这正是滑动窗口的软肋，也是摘要压缩策略存在的理由。如果用了滑动窗口又怕丢，可以加一个兜底：当用户的问题明显指向"早期对话"（比如含"最开始""之前说的"），临时触发一次"从原始历史里捞相关片段"的检索。或者干脆用摘要策略，把远期压成摘要保留，既不爆窗口又不丢大局。选型没有银弹，但"用户回溯早期内容"是高概率事件，生产系统一定要处理。

**问四：记忆和 RAG 知识库，能不能共用一个向量库？**
答：技术上能（都是向量检索），但强烈建议**逻辑隔离甚至物理隔离**。原因：RAG 是系统级共享知识（所有人查同一份手册），长期记忆是用户级私密数据（A 的偏好不能泄露给 B）。混在一起极易出现越权——比如检索时没过滤 user_id，把别人记忆召回。所以即便共用底层向量引擎，也要用不同的 collection 或严格的 metadata 过滤隔开，并做好权限校验。

再补一张"记忆方案选型速查表"，把全篇策略收个口：

| 你的诉求 | 推荐方案 | 注意 |
|---|---|---|
| 对话短、图省事 | 全量记忆 | 警惕上下文上限 |
| 长对话、控成本 | 滑动窗口 | 会丢远期，需兜底 |
| 长对话、要保大局 | 摘要压缩 | 摘要本身是一次调用 |
| 想抓关键句 | 重要性筛选 | 多了打分步骤 |
| 跨会话个性化 | 长期记忆(向量库) | 必须按 user_id 隔离 |

## 七、本篇小结

1. **大模型本身没记忆**——所谓"记住"，是调用方每次把历史重新塞回 Prompt。这是理解记忆机制的入口，也决定了记忆的成本与容量边界。
2. **短期记忆**管"这次聊到哪"，载体是内存 messages 列表；五种策略：全量（省事有天花板）、滑动窗口（控 token）、摘要压缩（又全又省，生产主流）、重要性筛选（抓关键句）、**token 预算装载（按账单而非条数决策，最贴近生产）**；工业界的最终形态是"近期原文 + 远期摘要 + 预算兜底"的分层记忆。
3. **长期记忆**管"用户是谁、历史发生了什么"，载体是向量库/数据库；按问题语义检索相关几条塞进 system 提示——**和 RAG 同构，阶段 7 直接复用**；必须按 user_id 隔离，还要带时间戳做"新覆盖旧"。
4. 五大失忆 bug（答非所问、聊久变傻、换设备不认人、记忆冲突、偏好不生效）各有固定排查方向。
5. 记忆 + 工具 + 循环，Agent 才算有了"脑、手、记忆"三件套；而长期记忆与 RAG 技术同源，区别只在数据与归属，二者构成记忆三层架构。
6. **双轨制记忆最实用**：结构化画像（确定的字段用 KV 白名单写入，天然防污染）+ 向量记忆（模糊的事件级内容用语义召回）；临时请求永远不写长期记忆。
7. **拼装 Prompt 的细节决定体验**：输出约束放最后、没召回就整段删掉、顺序即优先级、上线前必估 token。

一句心法收尾：**记忆系统的难点从来不是"怎么存"，而是"该不该存、什么时候忘"。** 存得多不等于记得好，会遗忘的系统才像人。

## 八、实战练习（可验证小任务）

1. **滑动窗口验证**：把 `ShortTermMemory` 的 `keep_turns` 设成 1，加 6 轮对话后打印 `build_messages()`，确认只保留最后 2 条（1 轮）。验证点：窗口外确实被丢弃。
2. **摘要触发**：写个假 `summarize_fn`（直接返回"历史已总结"），在 history 超过窗口时调用 `compress`，确认 `mem.summary` 被赋值、history 被截断。验证点：摘要机制生效。
3. **长期记忆隔离**：用第三节的 `LongTermMemory`，分别给 u1、u2 存不同偏好，然后 `recall("u2", ...)`，确认只召回 u2 的内容，绝不串到 u1。验证点：隔离正确。
4. **记忆污染实验**：故意把一条临时数据（"当前温度 26°C"）用 `save` 存进长期记忆，再问一个无关问题（"推荐本书"），观察它是否被误召回，理解隔离与筛选的重要性。
5. **组合题**：把短期记忆（滑动窗口）和长期记忆（召回偏好）拼进同一个 system 提示，模拟一次"记得用户偏好口语化"的多轮对话，感受个性化的效果。
6. **预算截断验证**：把 `BudgetedMemory` 的 `token_budget` 从 60 改成 20 再跑一次，观察装载条数从 5 条掉到 2 条，体会"按 token 而非按轮数"的差异。验证点：预算不足时系统仍能给出最近上下文。
7. **时间加权实验**：在 `TemporalLongTermMemory` 里把那条"详细一点"的记忆时间戳改成 `now - 300*DAY`，重新召回，观察它排到"常用 DeepSeek"后面。验证点：理解时间惩罚项 `1 + 0.05*age_days` 的作用。
8. **防污染检查**：往 `extract_profile` 里喂一句"我刚买的订单我想退货，别用术语讲给我听"，看它会抽出什么——如果只抽到 `tone` 而没把"退货订单"写进去，说明白名单机制生效。验证点：结构化记忆的防污染能力。
9. **端到端拼装**：在 5.1 的 `assemble_messages` 里把 `rag_fn` 换成你 7-4 写的真实检索函数，发给任意大模型，对照"有记忆"和"无记忆"两种回答的差异。验证点：把整条链路跑通。
