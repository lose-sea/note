# 上下文管理与成本控制——token 计费与缓存

**承上**：上一篇的 Function Calling 循环，每转一轮就要把**全部历史**（含冗长的工具返回结果）重新发给模型。十轮对话下来，token 可能翻十倍，账单也跟着翻十倍。

**本篇**：讲清三件事——**token 是怎么算的**、**上下文窗口的硬限制是什么**、以及**四种真正有效的省钱策略**。这是从"能跑起来"到"能上线"的分水岭。

**启下**：但有些东西再怎么压缩也塞不进去——比如你有 2000 篇产品文档、10 万条客服记录。**知识库远远大于上下文窗口，怎么办？** 这就是**阶段 7：RAG 检索增强生成**要解决的问题：不把知识塞进上下文，而是**按需检索、只送相关的那几段**。

**学完这一节，你能动手做**：

1. 精确计算 token 与成本，能预估任何功能的月度账单
2. 实现滑动窗口与摘要压缩两种上下文策略，并知道什么时候用哪个
3. 用 Prompt 缓存、模型分级、批处理把成本砍下来

## 一、钱是怎么花掉的：token 计费模型

### 1.1 先建立"token 即货币"的心智

在大模型的世界里，**token 就是钱**。你发的每一个字、模型回的每一个字，最终都折算成 token 来计价。想做"能上线的"大模型应用，第一件事就是把"这段对话要花多少 token、多少钱"刻进直觉——否则等产品跑起来，月底账单能吓你一跳。

API 计费遵循一个简单公式：

```
单次成本 = 输入token × 输入单价 + 输出token × 输出单价
```

这里有个关键点：你付的钱等于 **(你发进去的 + 模型吐出来的) 全部 token**，而且输入输出**单价不同**。

### 1.2 三个反直觉的事实

关键在于三个反直觉的事实（也是新手最容易算错账的地方）：

| 事实 | 说明 |
|---|---|
| **输入也要钱** | 而且多轮对话里，输入是**累积**的：第 10 轮要把前 9 轮全部重发 |
| **输出比输入贵** | 通常贵 3~5 倍（生成比理解更耗算力） |
| **多轮是平方级增长** | 第 n 轮的输入 ≈ n 倍单轮量，总成本 ≈ O(n²) |

展开解释：

- **输入也要钱**：很多新手以为"只有模型说话才花钱"。错。你发的 system + 所有历史 user/assistant 都算输入 token 计费。而且因为模型无记忆（见上篇），多轮对话里每轮都要把前面全部重发，输入 token 随轮数线性累加。
- **输出更贵**：生成（自回归逐个预测下一个 token）比理解（编码输入）更吃算力，所以几乎所有厂商的输出单价都是输入的 3~5 倍。这意味着"让模型少说话"比"少发点 prompt"省钱得多。
- **O(n²) 增长**：设单轮交互约 k 个 token。第 1 轮输入≈k，第 2 轮输入≈2k（带上第 1 轮历史），…第 n 轮输入≈nk。总输入 ≈ k(1+2+…+n) = k·n(n+1)/2，即 **O(n²)**。十轮对话，总成本约是单轮的十几倍，而不是十倍。

### 1.3 一个算给你看的例子

举个例子（假设输入 2 元/百万、输出 8 元/百万，单轮约 100 输入 + 200 输出）：

| 轮次 | 累计输入 token | 本轮输出 | 本轮成本 |
|---|---|---|---|
| 第 1 轮 | 100 | 200 | ¥0.0018 |
| 第 5 轮 | 900 | 200 | ¥0.0034 |
| 第 10 轮 | 1,900 | 200 | ¥0.0058 |
| **10 轮合计** | — | — | **约 ¥0.038** |

单轮看着很便宜，但如果**每天 1 万次这样的对话**：`0.038 × 10000 × 30 ≈ 每月 ¥11,400`。这就是为什么必须做上下文管理——**一旦规模上来，不做管理就是纯纯的烧钱**。

### 1.4 成本预估的正确姿势

做功能前先算账，是工程纪律。把公式写成可复用函数（本篇第四节会给出完整 `CostCalculator`），输入"预计日调用量、平均轮数、平均输入/输出 token、单价"四个数，就能算出月度预算。这条纪律能帮你：① 在选型阶段判断"用大模型还是小模型"；② 在架构阶段决定"要不要做上下文压缩"；③ 在上线后监控"实际花费是否偏离预估"。**能用一行公式提前算清的事，不要等账单来教训你**。

### 1.5 token 到底是什么：和"分词"的关系

要真正懂计费，得先懂"token 是什么"。回顾阶段 5 讲的**分词（Tokenization）**：模型不会直接处理字符，而是先把文本切成 token（一个 token 可能是半个词、一个词、或几个字）。英文里 "learning" 可能切成 "learn" + "ing" 两个 token；中文里一个字通常对应 0.6~1 个 token（取决于 tokenizer）。**计费的最小单位就是 token，不是字数**。

这带来三个实用推论：
- **同样的预算，能塞的"字数"因语言而异**：中文通常比英文"更省 token"（一个汉字信息密度高），但比代码"更费 token"——代码里大量符号、缩进会被切成很多小 token。
- **选模型要看它的 tokenizer**：同样是 1000 字中文，GPT 系和 Qwen 系的 token 数可能差出 30%，直接反映在账单上。
- **prompt 写得"紧凑"确实更省**：同一个意思用更少的 token 表达（少客套、少重复），长期累积能省可观成本。这也和第一篇"精炼 prompt"的建议一脉相承——好的 prompt 不仅效果好，还更便宜。

### 1.6 多轮成本 O(n²) 的可视化

把 1.2 节的平方增长画出来，直觉会更刺眼：

```
输入 token 随轮次（每轮新增固定 k）：
第1轮 ██            (k)
第2轮 ████          (2k)
第3轮 ██████        (3k)
第4轮 ████████      (4k)
第n轮 ████████████  (nk)
累计 = k·n(n+1)/2  → 总账随 n 平方膨胀
```

所以"对话越长越贵"不是线性，而是**加速变贵**。当你发现某个功能"聊到第 20 轮成本是第 1 轮的 20 倍不止"时，别惊讶——这正是没做上下文管理的代价，也是本篇要解决的头号问题。

## 二、上下文窗口：硬件级的硬限制

### 2.1 上下文窗口是什么

每个模型能一次处理的最大 token 数，是**架构决定的硬限制**（主要取决于位置编码的外推能力 + KV Cache 显存）。它就像模型的"工作台面"——台面就这么大，东西多了就放不下。

| 模型 | 上下文窗口 | 大约相当于 |
|---|---|---|
| GPT-3.5 / 早期模型 | 4K / 16K | 几千字 |
| GPT-4o / Qwen2.5 | 128K | 一本中篇小说 |
| Claude / Gemini | 200K ~ 2M | 整套代码仓库 |
| DeepSeek-V3 | 64K ~ 128K | 几十万字 |

### 2.2 超过窗口会发生什么

两种结果，第二种更阴险：

1. API 直接报错 `context_length_exceeded`；
2. 服务端**静默截断**（丢掉开头部分，通常是你的 system prompt！）——这更危险，表现为"模型突然不听话了"，因为你最关键的指令被悄悄扔掉了。

所以**主动管理上下文**不只是为了省钱，更是为了**保证模型真的看到了你的关键指令**。

### 2.3 长上下文 ≠ 能用满（"迷失在中间"）

> ⚠️ **长上下文 ≠ 能用满**。即使窗口是 128K，塞满之后： latency 显著上升、成本线性上升、模型对中间部分的注意力会下降（**"迷失在中间" Lost in the Middle** 现象）。**上下文里的每一段内容都应该是有用的**。

"Lost in the Middle"是 2023 年一篇论文揭示的现象：当关键信息被放在超长上下文的**中间**位置时，模型召回率明显下降；它更擅长利用开头和结尾。这再次印证了第一篇讲的"首尾效应"。工程含义很明确：**别把无关内容硬塞进上下文**，也别把所有历史无脑堆进去——那只会稀释真正重要的信息，还白白多花钱。上下文管理的目标，是让"工作台面"上只放着此刻最该被看到的东西。

### 2.4 KV Cache：为什么长上下文这么吃显存

自回归生成时，每生成一个新 token，理论上都要重新计算前面所有 token 的 K 和 V。为了避免重复计算，推理框架会把它们**缓存**下来，这就是 **KV Cache**。

显存占用可以精确估算：

```
KV Cache 显存 = 2 × 层数 × d_model × 序列长度 × batch × 每个元素字节数
               ↑ K和V两份
```

```python
def kv_cache_gb(num_layers, d_model, seq_len, batch=1, dtype_bytes=2):
    """fp16 下每个元素 2 字节。"""
    return 2 * num_layers * d_model * seq_len * batch * dtype_bytes / 1024**3

print("7B 模型（32 层, d_model=4096）:")
print("  4K 上下文 : %.2f GB" % kv_cache_gb(32, 4096, 4096))
print("  32K 上下文: %.2f GB" % kv_cache_gb(32, 4096, 32768))
```

输出：

```
7B 模型（32 层, d_model=4096）:
  4K 上下文 : 2.00 GB
  32K 上下文: 16.00 GB
```

**这就是长上下文昂贵的物理原因**——32K 上下文光缓存就要 16GB 显存，比模型权重本身（14GB）还大。也解释了为什么阶段 10 会讲 vLLM 的 **PagedAttention**（像操作系统分页一样管理 KV Cache，大幅减少碎片浪费）。对应用开发者而言，这告诉我们：能压缩上下文，就不仅省了 API 钱，也减轻了服务端显存压力、降低了延迟——一举多得。

### 2.5 上下文窗口与 Prompt 缓存的协同

这里有个微妙但重要的协同关系：上下文窗口越大，你越容易"把长内容一直留着"，但长内容每轮重发既贵又占 KV Cache；而 Prompt 缓存恰恰喜欢"稳定且靠前的前缀"。所以好的设计是：**把不变的超长内容（系统指令、知识文档）放在最前面并尽量不变 → 命中缓存、省钱；把会变的历史对话用本篇的窗口/摘要策略压缩 → 控制长度、不撑爆窗口**。两者配合，既享受长上下文的能力，又不被它的成本反噬。

### 2.6 不同业务对窗口的需求差异

选模型时别只盯着"谁的窗口大"。不同业务对窗口的渴求天差地别：短平快的客服问答、分类抽取，4K~16K 完全够用，盲目上 128K 只会增加成本；而"整本书的问答""整套代码库的重构"这类任务，才真的需要大窗口兜底。更聪明的做法是：**先用窗口管理把需求压到最小，再据此选最小够用的窗口**——这既省钱，也避免"迷失在中间"的影响。窗口大小是手段不是目的。

## 三、代码实战 1：两种上下文管理策略

### 3.1 为什么需要"管理器"

既然"每轮重发全量历史"又贵又可能超窗口，就得有个组件专门负责"决定每轮到底发哪些内容"。下面这个类把两种经典策略封装好：滑动窗口（只保留最近 N 条）和摘要压缩（把更早的内容浓缩成一段摘要）。

```python
class ConversationManager:
    """对话上下文管理器：支持滑动窗口与摘要压缩两种策略。"""

    def __init__(self, system: str, strategy="window", keep_turns=4):
        self.system = system
        self.strategy = strategy          # "window" | "summary"
        self.keep_turns = keep_turns
        self.history: list[dict] = []
        self.summary = ""

    @staticmethod
    def estimate_tokens(text: str) -> int:
        """粗估：中文按 0.7 token/字，英文按 1 token/4 字符。
           生产环境请用真实 tokenizer。"""
        cn = sum(1 for ch in text if '\u4e00' <= ch <= '\u9fff')
        return int(cn * 0.7 + (len(text) - cn) / 4) + 1

    def add(self, role: str, content: str):
        self.history.append({"role": role, "content": content})

    def tokens_if_full(self) -> int:
        """不做任何压缩时的 token 数（用于对比效果）。"""
        total = self.estimate_tokens(self.system)
        return total + sum(self.estimate_tokens(m["content"]) for m in self.history)

    def build_messages(self) -> list[dict]:
        """构造实际发送给 API 的 messages。"""
        msgs = [{"role": "system", "content": self.system}]
        if self.strategy == "summary" and self.summary:
            msgs.append({"role": "system",
                         "content": f"以下是更早对话的摘要：\n{self.summary}"})
            rest = self.history[-2:]          # 摘要模式下只保留最近 1 轮
        else:
            rest = self.history[-self.keep_turns:]
        return msgs + [{"role": m["role"], "content": m["content"]} for m in rest]

    def compress(self, summarize_fn=None):
        """把较早的对话压缩成摘要（summarize_fn 通常就是一次 LLM 调用）。"""
        if len(self.history) <= self.keep_turns:
            return
        old = self.history[:-self.keep_turns]
        text = "\n".join(f"{m['role']}: {m['content']}" for m in old)
        self.summary = summarize_fn(text) if summarize_fn else text[:80] + "……（已压缩）"
        self.history = self.history[-self.keep_turns:]
```

### 3.2 跑一场 10 轮客服对话看效果

```python
# ---------- 一场 10 轮的客服对话 ----------
sys = "你是一位技术支持助手，回答简洁专业。"
dialog = [
    ("user", "我的订单一直显示待发货怎么办"),
    ("assistant", "请提供订单号，我帮你查询物流状态。"),
    ("user", "订单号 20261005XYZ"),
    ("assistant", "该订单已于昨日打包，预计今天 18:00 前发出。"),
    ("user", "能改成次日达吗？"),
    ("assistant", "可以，已为你升级为次日达，预计明天上午送达。"),
    ("user", "好的，另外我想问下退货政策"),
    ("assistant", "支持 7 天无理由退货，商品需保持完好。"),
    ("user", "运费谁承担"),
    ("assistant", "质量问题由我们承担，无理由退货由买家承担。"),
]

def tokens_of(msgs):
    return sum(ConversationManager.estimate_tokens(m["content"]) for m in msgs)

cm = ConversationManager(sys, strategy="window", keep_turns=4)
for r, c in dialog:
    cm.add(r, c)

print("不做管理（全量历史）:", cm.tokens_if_full(), "tokens")
print("滑动窗口(最近4条)  :", tokens_of(cm.build_messages()), "tokens")

cm.compress(lambda t: "用户咨询订单 20261005XYZ 的发货情况，已升级次日达；"
                      "随后询问退货政策与运费承担方，已解答。")
cm.strategy = "summary"
print("摘要压缩           :", tokens_of(cm.build_messages()), "tokens")
print("摘要内容:", cm.summary)
```

运行结果：

```
不做管理（全量历史）: 114 tokens
滑动窗口(最近4条)  : 51 tokens
摘要压缩           : 66 tokens
滑动窗口省了 55%，摘要压缩省了 42%——但摘要保留了完整语义。
```

> 说明：这里的 `estimate_tokens` 是粗略估算（中文 0.7 token/字），生产环境请用模型对应的真实 tokenizer（如 `tiktoken`、各家的 tokenizer 工具）得到精确值。粗略估算足以做对比和趋势判断，但做精确成本账必须用真 tokenizer。

### 3.3 两种策略怎么选

**两种策略怎么选？**

| 策略 | 优点 | 缺点 | 适用 |
|---|---|---|---|
| **滑动窗口** | 零成本、零延迟 | 会**丢掉早期信息** | 任务型对话（客服、问答），前文不太重要 |
| **摘要压缩** | 保留关键信息 | 多一次 LLM 调用（花钱+耗时） | 长对话、需要"记住"之前结论的场景 |
| **混合**（推荐） | 兼顾 | 实现稍复杂 | **窗口保最近 N 轮 + 摘要兜住更早内容** |

选择的核心判据是：**早期对话信息还重不重要？** 客服问答里"用户三年前买过什么"基本无关，滑动窗口够用；心理咨询或长文协作里"前面定下的基调"很关键，就得摘要压缩。实战里**混合策略最稳**：最近几轮原样保留（保证即时上下文连贯），更早的压成摘要（保证长期记忆不丢）。

> 还有第三种：**向量检索式记忆**——把历史消息存进向量库，每次只召回与当前问题相关的几条。这是阶段 8 讲 Agent 记忆时会展开的做法。它特别适合"历史极长、但单轮只关心其中一小部分"的场景。

### 3.4 把上下文策略接回对话循环（串联前三篇）

本篇的 `ConversationManager` 不是孤立的，它要接回前两篇的成果。一个完整的"带上下文管理的工具调用助手"，数据流是这样串起来的：

```
用户输入
  ↓
ConversationManager.add("user", 输入)        ← 本篇：先把用户话存进历史
  ↓
messages = cm.build_messages()               ← 本篇：按窗口/摘要压缩后取出
  ↓
LLMClient.chat(messages)  ← 调用第二篇封装的客户端（含重试/超时/计费）
  ↓
若模型返回 tool_calls → 执行工具（第三篇的 run_agent 循环）
  ↓
ConversationManager.add("assistant", 回答)   ← 本篇：把回答存回历史
  ↓
进入下一轮（历史已自动被管理，不会无限膨胀）
```

注意关键点：**模型无记忆（第二篇）、工具调用多轮膨胀（第三篇）、上下文必须主动压缩（本篇）** 这三件事是连动的。只有把 `ConversationManager` 放进循环，你才能既享受 Function Calling 的能力，又不让 token 随轮数失控。建议在本地用一个"假模型 + FakeLLM（第三篇）"把这个循环完整跑通一遍，亲眼看到第 10 轮时 `build_messages` 返回的 token 数被稳稳压住——那一刻你才算真正掌握了"能上线的"大模型应用骨架。

## 四、代码实战 2：成本计算器与降本策略

### 4.1 把账算清楚：CostCalculator

```python
class CostCalculator:
    """按 元/百万token 计价的简单成本模型。"""

    def __init__(self, price_in: float, price_out: float):
        self.price_in, self.price_out = price_in, price_out
        self.total_in = self.total_out = 0

    def add_call(self, tin: int, tout: int):
        self.total_in += tin
        self.total_out += tout

    @property
    def cost(self) -> float:
        return (self.total_in / 1e6 * self.price_in
                + self.total_out / 1e6 * self.price_out)

    def monthly(self, calls_per_day: int) -> float:
        per_call = self.cost / max(1, self._calls)
        return per_call * calls_per_day * 30

    _calls = 0


def compare_strategies():
    """同一个 10 轮对话，三种策略的成本对比。"""
    price_in, price_out = 2.0, 8.0          # 元/百万 token（按你的模型报价填）
    daily_calls = 10000

    strategies = {
        "全量历史":      (1900, 200),        # 平均输入/输出 token
        "滑动窗口":      (600,  200),
        "摘要压缩":      (450,  210),        # 多花 10 token 生成摘要（摊销）
    }
    print(f"假设：每日 {daily_calls} 次对话，输入 ¥{price_in}/M，输出 ¥{price_out}/M\n")
    for name, (tin, tout) in strategies.items():
        per = tin / 1e6 * price_in + tout / 1e6 * price_out
        print(f"{name:10s} 单次 ¥{per:.5f}   月度 ¥{per * daily_calls * 30:,.0f}")

compare_strategies()
```

### 4.2 六招降本组合拳

| 降本策略 | 效果 | 做法 |
|---|---|---|
| **Prompt 缓存** | 命中缓存的输入通常**便宜 50%~90%** | 把稳定的 system prompt / 长文档放**开头**，让前缀可被缓存（DeepSeek、Claude、OpenAI 均支持） |
| **模型分级** | 省 70%+ | 简单任务（分类、抽取）用小模型，复杂任务才上大模型——**用路由模型先判断难度** |
| **批处理** | 通常省 50% | 离线任务走 Batch API（24 小时内返回即可的场景） |
| **缩短输出** | 立竿见影 | 明确要求"控制在 100 字内"、设 `max_tokens`；输出比输入贵 3-5 倍 |
| **缓存结果** | 省 100% | 完全相同的问题直接查本地缓存（Redis / SQLite） |
| **精简 system** | 每次调用都省 | system prompt 会**随每轮重复计费**，写太长等于给每次调用加税 |

逐条解读：

- **Prompt 缓存**：这是"免费的性能优化"。服务商把你请求中**相同前缀**的 KV Cache 保留几分钟，第二次请求命中时不用重算前文——成本和时间都大幅下降。因此**把固定内容（system prompt、工具定义、长文档）放在 messages 最前面且保持稳定**是关键。
- **模型分级 + 路由**：别拿 GPT-4o 去做"这句话是正面还是负面"这种 7B 小模型就能搞定的事。用一个小路由模型先判断难度，简单任务分流给便宜模型，能省下大头费用。
- **批处理**：大量离线任务（如批量审核、批量摘要）走 Batch API，价格通常腰斩，代价是 24 小时内返回——对不要求实时的场景非常划算。
- **缩短输出**：因为输出更贵，"让模型少说"收益最高。明确要求长度上限 + 设 `max_tokens`，既省钱又加快响应。
- **结果缓存**：完全相同的提问（如"公司地址是什么"）直接命中本地缓存返回，连 API 都不用调，省 100%。
- **精简 system**：system 会随每轮重发，写 500 字和写 50 字，长期累积的差价惊人。

### 4.3 Prompt 缓存的原理（值得展开）

> **Prompt 缓存的原理**：模型服务商把你请求中**相同前缀**的 KV Cache 保留一段时间（通常几分钟）。你第二次请求命中时，就不用重算——成本和时间都大幅下降。所以**把固定内容（system prompt、工具定义、长文档）放在 messages 最前面且保持稳定**，是免费的性能优化。

更深一层理解：KV Cache 在上一段讲过了——它是前面所有 token 的 K/V 矩阵。如果两个请求的前缀（比如相同的 system + 相同的长文档）完全一致，那这部分前缀的 KV Cache 就可以**复用**，推理框架不必重新算一遍。于是这一次请求的有效计算量骤减，计费也按"缓存命中"的折扣价走。这给我们一个设计原则：**把"会变的内容"（用户问题）放在最后，把"不变的内容"（系统指令、知识文档）放在最前**，最大化缓存命中率。RAG（下一篇）里"把检索到的文档放前面、用户问题放后面"也部分出于这个考量。

### 4.4 真实世界的成本监控（别等账单才发现问题）

`CostCalculator` 只是"预估"。真上线后，成本会因为它和预估的偏差（流量突增、某类长输入、缓存未命中）而失控。生产级成本管理至少要三件事：

- **每次调用记录 usage**：把 `prompt_tokens` / `completion_tokens` / `cached_tokens` / `model` / `cost` 写进日志或时序数据库（如 Prometheus），形成可观测的成本曲线。
- **按维度聚合看板**：按"模型、业务线、接口、用户"分别统计成本，快速定位"哪块在烧钱"。常常会发现 80% 的成本来自 20% 的请求（比如某些超长对话）。
- **设告警阈值**：当日成本或单请求 token 超过阈值就报警。比如"单次对话超过 50K token"或"日成本同比涨 50%"立刻通知——在账单爆掉前拦住。

一句话：**成本是可观测性的一部分，不是月底才看的数字**。把 usage 当成和延迟、错误率同等重要的指标来监控，你的应用才真正"能上线、能运营"。

## 五、常见坑

| 坑 | 现象 | 解法 |
|---|---|---|
| 以为模型有记忆 | 重复发送全部历史 | 自己做上下文管理 |
| 上下文塞满 | 静默截断、模型"失忆" | 主动压缩 + 监控 token 数 |
| system prompt 写几千字 | 每轮都在交税 | 精炼，把长内容放到可缓存前缀 |
| 超长上下文却不降本 | 账单失控 | 长上下文是**能力**不是**默认选项**，按需用 |
| 把整本手册塞进 prompt | 慢、贵、效果还差 | 用 RAG 只送相关片段（阶段 7） |
| 不做结果缓存 | 重复问题反复付费 | 加一层结果缓存 |
| 所有任务都用最强模型 | 成本虚高 | 模型分级 + 路由 |

### 5.1 一个隐蔽但高频的坑：token 估算偏差

很多人用"字数 × 系数"粗略估算 token，结果预算和实际差出几倍。原因是：不同模型 tokenizer 不同（中文在 GPT 系约 1 字 0.6~1 token，在有些模型上更碎），代码/数字/符号的折算也与纯中文不同。后果是"以为很便宜实际很贵"或反过来。解法：**生产环境接入真实 tokenizer**，并在 `CostCalculator` 里用真实值而非估算值。本篇 `estimate_tokens` 仅用于演示对比，上生产请替换。

### 5.2 别把"上下文窗口大"当成"可以乱塞"

128K 甚至 1M 的窗口很容易让人产生"全塞进去就行"的错觉。但结合 2.3 的"Lost in the Middle"和 2.4 的显存/成本代价，乱塞的代价是：更贵、更慢、模型反而更可能忽略中间信息。克制地使用上下文，是成熟工程者和初学者的分水岭。**能压缩的压缩，能检索的检索，能缓存的缓存，别用堆长度掩盖设计问题**。

### 5.3 降本优先级清单（从性价比最高做起）

如果预算有限、想先动最划算的那一下，按这个顺序做，通常能最快见到效果：

1. **结果缓存**：完全相同的提问直接返回，省 100%，几乎零成本，先做。
2. **精简 system / 缩短输出**：每次调用都省，改动极小，见效快。
3. **Prompt 缓存**：把稳定前缀放最前，命中后省 50%~90%，且免费提速。
4. **上下文管理（窗口/摘要）**：本篇核心，把多轮膨胀压下来，常能砍半。
5. **模型分级 + 路由**：用便宜模型分流简单任务，省 70%+，但改动较大，放后面做。
6. **批处理**：仅对离线任务有效，单独评估。

这条清单的底层逻辑是"**先赚确定性的钱，再碰复杂的架构改造**"。前三项几乎不改业务逻辑、风险极低；后三项涉及模型选型与调用结构，需要更谨慎地灰度。

## 六、本篇小结

1. **成本 = 输入×单价 + 输出×单价**，且多轮对话是 **O(n²) 增长**；输出通常比输入贵 3~5 倍。
2. **上下文窗口**受位置编码与 KV Cache 限制；塞满会静默截断，**"迷失在中间"** 让超长上下文的效果打折。
3. **KV Cache 显存 = 2 × 层数 × d_model × 序列长度 × 字节数**——7B 模型 32K 上下文就要 16GB，这是长上下文昂贵的物理原因。
4. **滑动窗口**零成本但会丢信息，**摘要压缩**保留语义但要额外调用，**混合策略最实用**。实测：114 → 51 / 66 token。
5. 降本六招：**Prompt 缓存、模型分级、批处理、缩短输出、结果缓存、精简 system**。

## 七、实战练习（可验证小任务）

1. **算月度账单**：用本篇 `CostCalculator`，设"日调用 5 万次、平均输入 1500 / 输出 300 token、输入 ¥2/M、输出 ¥8/M"，算出月度成本，并对比"若输出压到 150 token"能省多少。
2. **跑通两种策略**：用 `ConversationManager` 构造一段 20 轮对话，分别用 `window`(keep_turns=4) 与 `summary` 统计 token，验证窗口/摘要各省了多少。
3. **验证缓存命中**：把同一段超长 system prompt 在两次请求里保持完全一致，理解"相同前缀可缓存"——可对照服务商文档的 `prompt_tokens_details.cached_tokens` 字段观察命中。
4. **模型分级设计**：列出你产品里 5 类任务，判断哪些可用 7B 小模型（分类/抽取/改写），哪些必须大模型（复杂推理/长文理解），估算分级后整体成本降幅。
