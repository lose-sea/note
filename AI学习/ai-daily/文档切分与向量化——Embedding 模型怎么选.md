# 文档切分与向量化——Embedding 模型怎么选

**承上**：上一篇我们算清楚了账——知识库塞不进上下文，塞进去又慢又贵还会"迷失在中间"。RAG（Retrieval-Augmented Generation，检索增强生成）给出的答案是：**不把知识塞进去，而是按需检索，只把最相关的几段送进上下文**。

**本篇**：RAG 的第一步，也是最容易被低估、却对最终效果影响最大的一步——**文档怎么切**。切得好，检索一击命中；切得烂，后面再强的模型也救不回来。我们会手写三种切分器并对比它们切出来的实际结果，然后讲清 Embedding 模型该怎么选。

**启下**：切完的 chunks 转成向量之后放哪？几千条可以放内存，几百万条怎么办？下一篇《向量数据库——Milvus、Chroma、FAISS 对比与实战》讲清索引原理（HNSW / IVF / PQ）与工程选型。

**学完这一节，你能动手做**：

1. 实现固定大小、递归字符、结构化三种切分器，并说清各自适用场景
2. 选对 chunk size 与 overlap，而不是拍脑袋填 500
3. 按"对称/非对称、语言、维度、文本长度"四要素选对 Embedding 模型

## 一、RAG 全景：先看清这一步在哪

在动手写代码之前，我们必须先把 RAG 在大模型开发中的位置彻底讲清楚，因为这决定了你后面每一个决策的方向。很多初学者把 RAG 当成一个"装知识的黑盒"，结果在切分、选模型这些环节反复踩坑，根本原因就是没理解它到底在解决什么。

先看一张完整的链路图：

```
离线阶段（建库，做一次）
    原始文档（PDF/Word/Markdown/网页）
        ↓ ① 解析（提取纯文本，处理表格与图片）
        ↓ ② 切分（本篇重点）
        ↓ ③ 向量化（Embedding 模型）
        ↓ ④ 存入向量库
    知识库 ✅

在线阶段（每次提问）
    用户问题
        ↓ ⑤ 向量化（同一个 Embedding 模型！）
        ↓ ⑥ 检索 Top-K 相似片段
        ↓ ⑦ 拼进 Prompt
        ↓ ⑧ 大模型生成答案
    回答 ✅
```

这张图要分两层去看。第一层是时间维度：建库是一次性的重活（解析、切分、向量化、入库），但只需做一次；在线问答是高频的轻活（把问题向量化、检索、拼 Prompt、生成），每一次用户提问都要跑一遍。第二层是数据维度：离线阶段处理的是"知识"，在线阶段处理的是"问题"，而连接两者的桥梁，正是 Embedding 模型——它必须保证两边用同一个模型、同一套语义空间，否则离线建出来的向量和在线问出来的向量根本不在同一个坐标系里，检索等于瞎找。

**一句话理解 RAG**：给大模型发一张"开卷考试的小抄"——不是让它背下所有知识，而是让它能翻到正确的那一页。这个比喻特别贴切，因为大模型本身就像个聪明但记性不好、又爱"自由发挥"的考生：你不让它看书（不注入知识），它考私有数据时只能瞎编；你把所有书全摊桌上（全塞进上下文），它又会在几十页里"迷失"，找不到该题对应的那一行。RAG 的精髓是"只把那一页递到它手上"。

为什么不直接把知识塞进上下文？上篇我们已经从 token 计费和"迷失在中间（Lost in the Middle）"两个角度算过账，这里再补一个工程视角的解释：**上下文窗口是稀缺的、昂贵的、且会稀释注意力的资源**。一个典型的客服知识库可能有几百万字，全塞进去既不现实（超窗口上限），也不经济（每次问答都付全文的钱），更不高效（模型在海量无关信息里反而答不准）。RAG 把"全量知识"和"单次问答"解耦开——知识静静躺在向量库里，每次只取最相关的几百字喂给模型，这就是它既省钱又准的核心逻辑。

**RAG 解决的三个真实问题**：

| 问题 | 微调能解决吗 | RAG 能解决吗 |
|---|---|---|
| 模型不知道你的私有数据（公司内部文档） | 勉强（且会遗忘） | ✅ 天生适合 |
| 知识会更新（价格、政策、库存） | ❌ 要重新训练 | ✅ 更新文档即可 |
| 答案要可溯源、要给引用 | ❌ | ✅ 天然带出处 |
| 幻觉（编造事实） | 部分 | ✅ 大幅降低 |

这张表里的每一行，都是真实业务里反复验证过的结论。举个具体例子：一家电商把"退款政策"写进模型做微调，结果三个月后政策改了，调整运费规则，微调模型还是按旧政策回答，只能重新训练——又是一笔成本和一遍等待。换成 RAG，运营改一下 Markdown 文档、重新跑一遍建库（几分钟的事），回答立刻更新。**知识的时效性，RAG 用"改文档"就解决了，微调要用"重训练"才解决。**

记住一条经验：**知识靠 RAG，格式和风格靠微调**。花几万块微调去注入知识，是最常见的浪费。微调真正擅长的是让模型学会"某种说话方式"或"某种输出格式"（比如永远用 JSON 返回、永远用客服口吻），而不是记忆事实。事实交给 RAG，风格交给微调，这是业界公认的分工。

最后强调一个全局认知：**切分（本篇）和向量化（本篇）是离线阶段的第②、③步，它们直接决定了在线阶段检索的天花板**。检索召回不到，后面所有环节（重排、生成）都无力回天。所以这一篇看着"基础"，实则最值得你花时间抠细节。

## 二、为什么切分这么关键？

上一节我们说了 RAG 为什么要检索，这一节说检索的最小单位为什么是 chunk（块）而不是整篇文档。这一点看似显然，但很多人真正动手时才恍然大悟。

因为**检索的最小单位是 chunk，不是文档**。当你问"退款时限是多久"，系统是在几万个 chunk 里找"最像这个问题"的几个，而不是把整本手册翻一遍。chunk 怎么切，直接决定了：

1. **语义完整性**：一个 chunk 是否讲完了一件事；
2. **噪声多少**：chunk 越大，塞进去的无关内容越多，Embedding 越"稀释"；
3. **能不能回答**：答案正好被切在两块的边界上，就谁也答不全。

我们逐个展开。

**先说语义完整性**。Embedding 模型把一个 chunk 变成一条向量，这条向量"代表"了这个 chunk 的核心意思。如果 chunk 里一半在讲退款、一半在讲物流，那这条向量就成了"退款和物流的混合物"，用户问纯退款问题时它不够像，问纯物流问题时也不够像——两头不讨好。理想情况是每个 chunk 只讲一件事，向量才"纯粹"，检索才精准。

**再说噪声**。想象一个 chunk 有 2000 字，其中只有 10 字在讲"退款时限是 7 天",其余都在讲无关的发货、会员、发票。Embedding 把这 2000 字的整体语义压成一个向量，那 10 字的关键信息被 1990 字的噪声稀释得几乎看不见。结果就是：这条例子被问到时，向量和"退款时限"的相似度不高，反而可能输给一个整段都在讲退款但措辞不同的 chunk。

**最后说"答案被切在边界"**——这是最隐蔽、最气人的坑。下面三个真实翻车例子请务必记住：

```
❌ 边界切断
   chunk1: "...退款需在签收后 7 天内申请，"
   chunk2: "超时不予受理。"
   → 用户问"退款时限是多久"，两块都只答了一半

❌ 语义稀释
   chunk: 一整章 5000 字塞进一个向量
   → 向量是"所有内容的平均"，什么问题都"有点像"，但都不够像

❌ 上下文缺失
   chunk: "运费为 12 元。"
   → 用户问"无理由退款的运费谁承担"，这块没有主语，检索不到也答不对
```

第一个例子里，正确答案被一刀劈成两半，分属两个 chunk，任何一个单看都不完整。第二个例子是"太大"的代价——chunk 成了大杂烩。第三个例子更微妙：单独一句"运费为 12 元"没有主语，用户问"无理由退款的运费谁承担"时，这句因为缺少"无理由退款"这个上下文，向量相似度低，检索不到；即使检索到了，大模型看到孤零零的"运费为 12 元"也不知道这 12 元是谁的。

**一个核心原则**：**每个 chunk 应该能脱离原文独立看懂**。你随便抽出一个 chunk 给一个没读过原文的人，他应该能明白它在讲什么、针对什么场景。这也是为什么结构化切分（后面会讲）往往比按字数硬切效果好得多——因为结构化切分会把"标题"一起带进 chunk，天然补上了上下文。

把这一节收个尾：切分不是"把文章切碎"这么简单，它是把"人读得懂的长文"转换成"机器检索得准的小知识单元"的关键工序。切得好，后面事半功倍；切得烂，后面再强的重排和模型也救不回来。

## 三、五种切分策略

讲完"为什么",这一节讲"怎么做"。切分策略有很多种，我们按"从简单到复杂、从通用到进阶"的顺序列一张总表，然后逐一拆解：

| 策略 | 做法 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| **固定大小** | 按字符数硬切 + overlap | 极简单、块大小均匀 | **会切断句子** | 快速验证、纯文本 |
| **递归字符** | 按 `\n\n` → `\n` → `。` → `，` 依次降级切 | 尽量保住段落与句子 | 长段落仍会被切 | **通用默认选这个** |
| **结构化** | 按 Markdown/HTML 标题层级切 | **语义最完整**，天然带标题 | 依赖文档有结构 | 技术文档、手册 |
| **语义切分** | 相邻句子向量相似度低处断开 | 按"话题"切 | 慢、要额外调模型 | 长文、无结构文本 |
| **父子块** | 小块检索、大块送入上下文 | 检索准 + 上下文完整 | 实现复杂 | 对效果要求高的场景 |

**① 固定大小（Fixed-size）**。最朴素：每 N 个字符切一刀，为了不让切断处的信息丢失，前后块之间留一段 overlap（重叠）。它最大的优点是"可预测"——每个块大小一致，方便后续批量处理。但它最大的硬伤是**完全不懂语义**，切在句子中间是家常便饭（后面代码实战会现场演示"签收后"被切成"收后"）。所以它只适合"快速验证链路能不能跑通",真正上线前几乎一定要换掉。

**② 递归字符（Recursive Character Splitting）**。这是 LangChain 等框架的默认切法，思路很聪明：先按空行 `\n\n` 切，如果某段还是太长，就降级按 `\n` 切；还太长，再降级按句号 `。`、逗号 `，`、空格切。它本质上是"尽量在自然的语义边界（段落、句子）处断开"。代价是：如果有一段特别长的段落（没有句号），它最终还是会硬切。但综合来看，它是对"没有清晰结构"的通用文本最稳的默认选择。

**③ 结构化（Markdown/HTML 层级）**。如果你的文档本身就有标题层级（技术手册、API 文档、带 `#` 标题的 Markdown），那就应该按标题切。这样做的好处是：每个 chunk 天然带着"它是哪一节下的内容"这个上下文（标题被拼进 chunk），语义最完整。代价是依赖"文档有结构"这个前提——扫描件 PDF 可没有。

**④ 语义切分（Semantic Splitting）**。这是更"高级"的思路：用 Embedding 模型把每个句子向量化，计算相邻句子的相似度，在"相似度突然降低"的地方断开——也就是话题转场的地方。它能切出语义上自洽的块，但代价是要先调一次模型（慢、费钱），且对短文档收益不明显。一般用在长文、没有结构、又对切分质量要求高的场景。

**⑤ 父子块（Small-to-Big / 小块检索大块送）**。这是进阶但非常实用的技巧，强烈建议生产环境考虑：

> **父子块（Small-to-Big）**是进阶但非常实用的技巧：用 200 字的小块做检索（向量精准），命中后把它的"父块"（800 字）送给大模型（上下文完整）。生产环境强烈推荐。

它的道理是：检索时块越小，向量越"纯粹"、越精准；但送给大模型时块太小又缺上下文。父子块用"小块检索、大块生成"同时拿住了两边的好处——检索准、上下文又完整。实现上就是给每个小块记录它属于哪个大块，检索命中小块后，回查它的大块送进 Prompt。

**策略选择口诀**：有结构优先结构化，无结构用递归字符兜底，要求极致效果上父子块，别用固定大小上生产。

## 四、代码实战 1：手写三种切分器并对比

光讲道理不够，我们直接写代码把三种策略跑出来看差异。用同一份退款政策文档，看三种策略切出什么——这比任何理论都直观。

```python
text = """# 退款政策

## 适用范围
本政策适用于所有自营商品。第三方商家商品以商家页面说明为准。

## 退款时限
1. 签收后 7 天内可申请无理由退款。
2. 质量问题可在 30 天内申请退款。
3. 生鲜类商品不支持无理由退款。

## 运费说明
质量问题导致的退款，运费由平台承担。
无理由退款的运费由买家承担，运费为 12 元。
"""

# ---------- 策略 1：固定大小 ----------
def fixed_size_split(text, size=80, overlap=20):
    chunks, i = [], 0
    while i < len(text):
        chunks.append(text[i:i + size])
        i += size - overlap          # 重叠部分保证边界信息不丢
    return chunks

# ---------- 策略 2：递归字符（LangChain 的默认做法） ----------
def recursive_split(text, size=80, overlap=20,
                    seps=("\n\n", "\n", "。", "，", " ")):
    def _split(t, seps):
        for sep in seps:                       # 按分隔符优先级依次尝试
            if sep in t:
                return [p + sep for p in t.split(sep) if p.strip()]
        return [t]                             # 都不行就原样返回

    chunks = []
    for part in _split(text, seps):
        if len(part) <= size:
            chunks.append(part)
        else:                                  # 太长则降级用更细的分隔符再切
            buf = ""
            for s in _split(part, seps[1:]):
                if len(buf) + len(s) <= size:
                    buf += s
                else:
                    if buf:
                        chunks.append(buf)
                    buf = s
            if buf:
                chunks.append(buf)
    return chunks

# ---------- 策略 3：Markdown 结构化（每个块带上标题路径） ----------
def markdown_split(text, max_size=300):
    chunks, header, buf = [], "", ""
    for line in text.split("\n"):
        if line.startswith("#"):               # 遇到标题就开新块
            if buf.strip():
                chunks.append((header + "\n" + buf).strip())
            header, buf = line, ""
        else:
            buf += line + "\n"
            if len(buf) > max_size:            # 单节太长才再切
                chunks.append((header + "\n" + buf).strip())
                buf = ""
    if buf.strip():
        chunks.append((header + "\n" + buf).strip())
    return chunks

# ---------- 对比 ----------
for name, chunks in [("固定大小(80/20)", fixed_size_split(text)),
                     ("递归字符(80)",    recursive_split(text)),
                     ("Markdown结构化",  markdown_split(text))]:
    lens = [len(c) for c in chunks]
    print(f"\n=== {name} === 块数={len(chunks)} 平均={sum(lens)//len(lens)} 最大={max(lens)}")
    for c in chunks[:3]:
        print("  ---", c.replace("\n", "\\n")[:88])
```

  --- ## 退款时限\n1. 签收后 7 天内可申请无理由退款。\n2. 质量问题可在 30 天内申请退款。\n3. 生鲜类商品不支持无理由退款。
  --- ## 运费说明\n质量问题导致的退款，运费由平台承担。\n无理由退款的运费由买家承担，运费为 12 元。

**逐条解读**：

- **固定大小**最致命的问题是 `签|收后` ——"7 天"和"签收后"被劈成两半。用户问"签收后多久能退"，第一块说"签收后 7 天"但被截断了，第二块从"收后 7 天"开始，主语丢失。**overlap 能缓解但不能根治**。
- **递归字符**把三个小节完整保住了，代价是第一块只有个孤零零的标题（可以在后处理里把它合并到下一块）。
- **结构化切分**效果最好：每块自带 `## 退款时限` 这样的**标题上下文**，块与文档结构一一对应，检索命中后大模型一眼就知道这段在讲什么。**而且实现只要 15 行。**

**结论**：文档有结构（Markdown/HTML/带标题）就**一定要用结构化切分**；没有结构再用递归字符切分兜底。

> 补充一个工程细节：递归字符切分里那个 `seps` 元组的顺序非常关键。它必须"从粗到细"——先按最大粒度的分隔符（空行）尝试，不行再依次降级。如果你把空格放到最前面，等于退化成固定大小切分，就失去了"保住句子"的意义。另外 `size` 和 `overlap` 的设定要配合文档的实际段落长度：技术文档段落短，size 设小一点（300~500）即可；小说、论文段落长，size 可能要放到 800 以上。

## 五、chunk size 与 overlap 怎么选

这是被问最多的问题。先给结论，再给理由：

| 场景 | 建议 chunk size | overlap | 理由 |
|---|---|---|---|
| FAQ / 短问答对 | 一条问答一块（不切） | 0 | 本身就完整 |
| 技术文档 / 手册 | 300 ~ 500 字 | 50 ~ 100 | 一节讲完一件事 |
| 长文章 / 报告 | 500 ~ 800 字 | 100 | 保留论证链 |
| 法律合同 / 论文 | 按条款 / 段落 | 0 | 结构优先 |
| 代码 | 按函数 / 类 | 0 | 语法单元 |

**chunk size 的两难**：

```
太小（100 字）→ 语义不完整，答案残缺，但向量精准
太大（2000 字）→ 语义完整，但向量是"大杂烩"，什么都像什么都不像
```

这个两难的本质是"检索精度"和"上下文完整"的拉扯。块太小，一个完整知识点被拆成几块，检索命中其中一块时信息不全；块太大，向量被稀释（前面讲过），检索区分度下降。**中间值（300~800 字）通常是最稳的甜点区**，但具体到你的数据，一定要用测试集去定，而不是抄别人的经验值。

**为什么大块会导致向量"稀释"？** 因为 Embedding 把一个 chunk 压缩成一个**固定维度的向量**。信息越多，压缩损失越大，向量就越"中庸"——跟任何 query 的相似度都差不多，检索失去区分度。打个比方：你让一个人用一句话概括一篇 5000 字文章，他只能说出"大概讲了个事"；让他概括 200 字，他能说出"具体讲退款 7 天"。向量也是一样，内容越聚焦，语义越"锐利"。

**overlap 的作用与代价**：

- 作用：缓解边界切断（答案跨块时，重叠区能补上另一半）；
- 代价：**存储膨胀**。chunk 500 / overlap 100 意味着每条内容被存了 1.25 次；overlap 250 就是 2 倍。
- 通常取 **chunk size 的 10%~20%**，超过 30% 收益递减且浪费严重。

> **实测建议**：拿 20 个真实问题做测试集，分别用 256 / 512 / 1024 跑一遍，看 Recall@5（前 5 条里有没有正确答案）。**这比任何经验值都靠谱**，我们会在 7-4 讲怎么自动化做这个评估。

再补一个容易被忽略的点：**overlap 不能当万能药**。它确实能让"被切断的答案"在重叠区补上另一半，但它解决不了"chunk 本身语义不纯"的问题。如果你的块切得乱七八糟，加 overlap 只是让乱的东西多存几遍。所以优先级永远是：先把切分策略选对（结构化优先），再调 chunk size，最后用 overlap 收尾。

## 六、Embedding 模型怎么选

切好的 chunk 要转成向量，靠的是 Embedding 模型。这一步选错，前面切得再好也白费——因为向量空间不对，检索就无从谈起。选模型看四个要素，我们一个一个讲透。

### 要素 1：对称检索 vs 非对称检索（最重要！）

这是选 Embedding 模型时最容易理解错、也最致命的一点。先看清两类检索长什么样：

```
对称（Symmetric）  ：query 和 doc 是同一种东西（都是句子）
                     例：找相似问题、去重、聚类
非对称（Asymmetric）：query 短（问题），doc 长（段落）
                     例：RAG 问答 ← 我们 99% 的场景
```

所谓"对称",是指你拿一个句子去库里找"意思最相近的句子",两边都是句子,长度相近、语义角色相同。比如社区里"找重复提问""把相似评论聚成一堆",这就是对称检索。所谓"非对称",是指你用一个短问题(query),去一堆长段落(doc)里找答案——这正是 RAG 的核心场景。两边长度不同、角色不同:query 是"问",doc 是"答的依据"。

**RAG 必须用针对非对称检索优化的模型**。很多通用 Embedding 模型在对称任务上很强（MTEB 榜单刷得高），拿来检索却很差——因为它的训练目标就是"句对相似度",而不是"问题找段落"。选模型时不能只看榜单总分,要看它有没有在 MS MARCO 这类"问题-段落"数据集上专门训过。

有些模型支持**指令前缀**（instruction prefix），能显著提升非对称检索效果：

```python
# bge 系列官方推荐：给 query 加前缀，doc 不加
query_vec = model.encode("Represent this sentence for searching relevant passages: " + query)
doc_vec   = model.encode(chunk)          # 文档侧不加前缀
```

这个前缀的作用，是"提醒"模型：接下来这句是要拿去搜段落的查询,请把它编码成"查询视角"的向量。文档侧不加前缀,保持"被检索"的视角。两边视角对齐,相似度才准。注意:前缀只对特定系列(bge 等)有效,不是所有模型都吃这套,用之前一定看官方文档。

### 要素 2：语言

这是中文场景最容易踩的坑。**用英文模型处理中文，效果会断崖式下降**。原因是英文模型（哪怕它说"支持多语言"）的训练语料里中文占比极低，中文 Embedding 的质量远不如英文。你在英文上测出来 0.95 的召回，换成中文可能直接掉到 0.6。

| 模型 | 中文 | 英文 | 维度 | 特点 |
|---|---|---|---|---|
| **bge-m3**（智源） | ✅ 强 | ✅ 强 | 1024 | 支持**多语言 + 多粒度**，还能输出稀疏向量（自带混合检索） |
| **gte-Qwen2** / conan-embedding | ✅ 很强 | ✅ | 1024~1792 | 中文榜单常客 |
| **Qwen3-Embedding** | ✅ 很强 | ✅ | 1024/2048 | 支持指令、长文本 |
| **text-embedding-3-small/large** | 一般 | ✅ 很强 | 1536/3072 | OpenAI，英文首选 |
| **m3e** | ✅ | 一般 | 768 | 轻量中文 |
| **bce-embedding-base** | ✅ | ✅ | 768 | 中英双语均衡，网易有道 |

这张表里，面向中文业务我首推 **bge-m3** 或 **Qwen3-Embedding**：前者还能顺便输出稀疏向量（为后面的混合检索打基础），后者支持长文本和指令。如果你的语料是纯英文，再考虑 OpenAI 的 text-embedding-3 系列。

> 选型的**唯一可靠方法**：在你的真实数据上跑一个 20~50 条的测试集，比 Recall@5。榜单（MTEB、C-MTEB）只能帮你筛出候选。原因很简单——榜单数据是别人的数据，你的业务文档有独特的术语和分布，榜单一哥在你这未必是第一。测试集构建的成本远低于选错模型后返工的成本。

### 要素 3：向量维度

维度决定"向量占多大空间"和"检索有多快"。先看经验表：

| 维度 | 存储（每条） | 检索速度 | 效果 |
|---|---|---|---|
| 384 | 1.5 KB | 快 | 一般 |
| 768 | 3 KB | 中 | 好 |
| 1024 | 4 KB | 中 | 更好 |
| 3072 | 12 KB | 慢 | 边际收益递减 |

**100 万条 chunk 的存储对比**（float32）：768 维约 3GB，1024 维约 4GB，3072 维约 12GB。维度直接决定内存和索引成本，够用就好。

这里有个关键判断：**维度不是越高越好**。从 768 升到 1024，效果通常有明显提升；但从 1024 升到 3072，效果提升往往很小（几个百分点），存储和检索开销却翻三倍。所以除非你的数据极其复杂、对精度有极致要求，否则 1024 维基本是性价比天花板。另外注意：有些模型支持"降维"（matryoshka 表征），训练时就把信息塞进前 N 维，你可以在不重训的情况下把 1024 维截断成 512 维用，进一步省空间——选模型时也可以关注这个特性。

### 要素 4：最大文本长度

Embedding 模型有输入长度上限（通常 512 或 8192 token）。**如果你的 chunk 超过上限，会被静默截断**——这是极其隐蔽的坑：

```
模型上限 512 token（约 350~400 汉字），你的 chunk 设了 1000 字
→ 后面 600 字直接被丢掉，向量里根本没有它们的任何信息
```

"静默"是最可怕的——模型不会报错,它只是悄悄把超出的部分扔掉,然后生成一个"只基于前半段"的向量。你检索时完全不知道后半段丢了,直到发现"明明文档里有答案却检索不到"才意识到。

**务必确认**：`chunk字长 < 模型max_length`，两者要匹配。如果 chunk 经常超长（比如法律条款、论文），要么选长文本模型（如 Qwen3-Embedding 支持 32k），要么在切分时就用 tokenizer 校验长度（而不是按字符数估算），确保每块都在模型上限内。

## 七、代码实战 2：向量化与检索的最小实现

前面把切分和选型讲透了，这一节用代码把"向量化 → 检索"的原理跑通。先用手造的向量演示数学本质，再给真实调用代码。

```python
import numpy as np

# ---------- 用手工设计的"伪语义向量"演示原理 ----------
# 4 个维度可以理解为：[退款相关, 物流相关, 费用相关, 时间相关]
docs = [
    "无理由退款需要买家承担 12 元运费",        # 退款 + 费用
    "质量问题退款由平台承担运费",               # 退款 + 费用
    "商品一般在 48 小时内发货",                 # 物流 + 时间
    "快递延误可申请补偿",                       # 物流
]
# 手工赋值的向量（真实场景由模型生成）
V = np.array([
    [0.9, 0.1, 0.8, 0.2],
    [0.9, 0.1, 0.7, 0.1],
    [0.1, 0.9, 0.2, 0.8],
    [0.2, 0.8, 0.3, 0.4],
], dtype=float)

def l2_normalize(M):
    return M / np.linalg.norm(M, axis=-1, keepdims=True)

V_norm = l2_normalize(V)
query = np.array([[0.9, 0.0, 0.6, 0.1]])          # 用户在问"退款运费谁出"
q_norm = l2_normalize(query)

# 归一化之后，余弦相似度 == 点积（这是向量库加速的关键）
scores = (q_norm @ V_norm.T)[0]
for i, (s, d) in enumerate(sorted(zip(scores, docs), reverse=True)):
    print(f"{s:.4f}  {d}")
```

运行结果：

```
0.9837  无理由退款需要买家承担 12 元运费
0.9718  质量问题退款由平台承担运费
0.3000  快递延误可申请补偿
0.2741  商品一般在 48 小时内发货
```

**关键知识点**：向量**归一化之后，余弦相似度就等于点积**。所以向量库（FAISS、HNSW）内部只需要做矩阵乘法，速度极快——这是工程上的核心优化。

> 为什么"归一化后余弦=点积"这么重要？因为向量库的核心操作就是"拿 query 向量和 N 条 doc 向量算相似度"。如果用余弦，每条都要先算模长再除，N 很大时开销可观；如果提前把所有 doc 向量归一化（模长=1），余弦就退化成纯点积，而点积可以一次性用矩阵乘法 `q @ V.T` 算完，GPU/CPU 都能高度并行。这就是百万、十亿级向量检索能做到毫秒级的数学基础。记住：embedding 阶段就把向量 normalize 好，是性能第一原则。

### 真实调用代码

```python
# pip install sentence-transformers
from sentence_transformers import SentenceTransformer
import numpy as np

model = SentenceTransformer("BAAI/bge-m3")     # 中英多语言，1024 维

docs = ["无理由退款需要买家承担 12 元运费", "商品一般在 48 小时内发货", ...]
doc_vecs = model.encode(docs, normalize_embeddings=True, batch_size=32)

# bge 系列：query 要加指令前缀
q = "退款的运费谁承担？"
q_vec = model.encode(["Represent this sentence for searching relevant passages: " + q],
                     normalize_embeddings=True)

scores = (q_vec @ doc_vecs.T)[0]
top_k = np.argsort(-scores)[:3]
for i in top_k:
    print(f"{scores[i]:.4f}  {docs[i]}")
```

**生产环境的三个注意点**：

1. **建库和检索必须用同一个模型**（换模型 = 全部重新向量化）；
2. **批量 encode**（`batch_size=32`），比一条条 encode 快一个数量级；
3. **长文档先切再编码**，别把 5000 字直接丢给模型。

再补三条实战经验，都是血泪教训：**第一**,把模型名和版本写进配置甚至写进向量库的 metadata——将来你升级模型时,必须全量重建索引,版本信息能帮你判断是否该重建。**第二**,`batch_size` 不是越大越好,太大可能爆显存;32 是通用起点,按你机器调。**第三**,向量化是 CPU/GPU 密集操作,建库时可以多进程并行切分+编码,把几小时的建库压到几分钟。

## 八、常见坑

这一节把从切分到向量化的高频坑集中列出来，方便你对照排查：

| 坑 | 现象 | 解法 |
|---|---|---|
| chunk 超过模型 max_length | 后半段被静默截断，怎么都检索不到 | 切分时用 **tokenizer** 校验长度，不是按字符数 |
| 建库与检索用了不同模型 | 检索结果完全不相关 | 模型名与版本写进配置，统一管理 |
| 用英文模型处理中文 | 召回率极低 | 换 bge-m3 / gte-Qwen2 / Qwen3-Embedding |
| 忘了 normalize | 相似度不可比 | `normalize_embeddings=True` |
| 把整篇 PDF 当一个 chunk | 什么都检索不准 | 必须切分 |
| PDF 解析丢表格 | 表格内容查不到 | 用专用解析器（如 MinerU、PyMuPDF + 表格提取） |
| 切分时丢了标题 | 块脱离上下文看不懂 | 用结构化切分，或给每块**补上标题前缀** |
| 图片/扫描件没 OCR | 内容完全丢失 | 先做 OCR，或上多模态模型 |

这张表之外的两个坑我想单独拎出来说，因为它们不属于"技术错"，而属于"流程错"：**一是没有测试集就定参数**。很多人凭感觉设 chunk=500、overlap=50，上线才发现召回差。请务必先攒 20~50 条真实问答做测试集，用 Recall@5 说话。**二是忽视 PDF/扫描件的解析质量**。再好的切分也救不了"解析出来一堆乱码"的源文档。文档解析（尤其是带表格、图片、多栏排版的 PDF）是 RAG 效果的上游瓶颈，必要时上 MinerU、PyMuPDF 这类专用解析器，甚至先做 OCR。

## 九、本篇小结

1. **RAG 的本质**是"开卷考试"：知识靠检索注入，不靠微调。**知识用 RAG，格式/风格用微调**。
2. **切分决定了检索的天花板**。原则：**每个 chunk 要能脱离原文独立看懂**。
3. 实测对比三种策略：**固定大小会切断句子**（"签收后"→"收后"），**递归字符**保住了段落，**结构化切分**效果最好（自带标题上下文，实现只要 15 行）。
4. **chunk size** 通常 300~800 字，**overlap** 取 10%~20%；最终要用 20 条真实问题测 Recall@5 来定。
5. **Embedding 选型四要素**：非对称检索能力、语言（中文必须选中英优化模型）、维度（够用就好）、最大长度（**必须 ≥ 你的 chunk 长度**）。
6. **归一化后余弦相似度 = 点积**，这是向量库能高速检索的数学基础。
