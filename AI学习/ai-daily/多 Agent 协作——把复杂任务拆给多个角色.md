# 多 Agent 协作——把复杂任务拆给多个角色

**承上**：8-1~8-3 我们给单个 Agent 装上了"循环（脑）、工具（手）、记忆（脑存储）"三件套。但真实复杂任务——比如"调研三个竞品、各写一段分析、汇成一份报告、再生成 PPT 大纲"——让**一个** Agent 又搜又写又汇总又排版，它容易顾此失彼、上下文被多种任务污染、还容易中途跑偏。

**本篇**：讲清"为什么一个大 Agent 不够"以及多 Agent 协作的两种主流模式——**主管-下属（Supervisor-Worker）** 与 **流水线（Pipeline）**。我用手写代码演示一个简单的"主管调度三个专职 Agent"的例子，并聊清楚"什么时候该拆、什么时候别拆"。

**启下**：阶段 8（Agent）到此讲完——单 Agent 循环、框架、记忆、协作都齐了。但你可能会问：这些 Agent 用的"基础模型"能不能变得更懂我的业务？比如让客服 Agent 真正熟读我家产品手册？这就进入 **阶段 9：微调与训练**——下一篇 **9-1《指令微调 SFT——数据与训练流程》** 讲怎么用自有数据"教"模型，而不是只会靠 Prompt 临时告诉它。

**学完这一节，你能动手做**：

1. 说清单 Agent 的瓶颈，以及多 Agent 在哪类任务上明显更优
2. 区分"主管-下属"与"流水线"两种协作模式的适用场景
3. 手写一个主管 Agent，按任务类型把活派给不同的专职 Agent
4. 判断"我的任务到底要不要上多 Agent"（避免过度设计）

## 一、为什么一个大 Agent 不够用？

把任务全压给一个 Agent，会撞上三个天花板。先建立直觉——想象让一个员工同时当"调研员、文案、校对、排版"，他桌上堆满资料、草稿、终稿，乱成一团，出错率必然飙升。这三个天花板，是单 Agent 架构的物理极限：

```
① 上下文污染：搜来的资料、写的草稿、排版的指令全挤在一个上下文里，
   模型分不清"这是要给客户的"和"这是中间草稿"。一旦资料太长，
   关键指令反而被稀释，模型开始"幻觉"或跑题。这是最隐蔽也最常见的坑。
② 角色冲突：让它同时当"研究员"和"文案"，风格会拧巴——
   研究报告要严谨客观，营销文案要煽情有感染力，同一张嘴说不出两种调性。
   你会在输出里看到"既想严谨又想煽动"的尴尬混合体。
③ 容错差：一步跑偏，整条链子全废，没法"这个环节换人重来"。
   比如校对发现数字错，但前面所有环节都基于这个错数，推倒重来成本极高。
```

解决思路很朴素，朴素到像常识——**像公司一样分工**：一个主管负责拆解和汇总，几个专职员工各管一摊。这就是多 Agent 系统。每个专职 Agent 有自己独立的上下文、独立的角色设定（system prompt）、独立的工具，互不干扰。主管只做"分派 + 汇总"，不做具体脏活。这样一来，研究员在自己的上下文里只看到资料，文案在自己的上下文里只看到"要写得煽情"，排版在自己的上下文里只看到格式要求——污染被天然隔离。

多 Agent 还有两个单 Agent 给不了的好处，值得单独强调：

- **可并行**：调研员 A、B、C 可以同时开工查三个竞品，总时间≈最慢那个，而不是串行累加。对于"同时调研 10 个产品"这种任务，并行能把几小时的串行缩短到几分钟。
- **可组合**：每个专职 Agent 可以复用我们 8-1~8-3 学到的循环、工具、记忆能力，相当于"用 Agent 搭 Agent"——上层主管是个 Agent，下层每个worker也是个 Agent，天然递归。这种组合性，是复杂 AI 系统能"长大"的关键。

但请记住本节最后一句警告，它贯穿全篇：**多 Agent 是止痛药，不是维生素**——只在单 Agent 真痛时才吃，乱吃伤身。第六节的"别过度设计"会展开。

## 二、模式一：主管-下属（Supervisor-Worker）

结构像一个小团队：**主管** 听老板（用户）的需求，把任务拆成子任务，派给对应的**专职 Agent**，最后汇总各自产出。主管可以是轻量的规则调度器（像我们代码里那样，不一定需要大模型），也可以是另一个更聪明的 Agent（用 LLM 决定怎么拆、派给谁）。

```
            ┌─────────────┐
   用户 ───▶ │   主管 Agent │ ◀── 汇总
            └──────┬──────┘
       ┌──────────┼──────────┐
       ▼          ▼          ▼
  研究员 Agent  写手 Agent  校验 Agent
  (搜资料)     (写文案)     (查事实)
```

**适合**：任务能拆成几个相对独立的子任务、且需要不同"专长/角色"的场景。比如"竞品分析"——研究员搜数据、写手写稿、校验员核对数字。每个下属是 8-1 学的完整 ReAct Agent（自带循环+工具），拥有独立 system prompt 定义角色，独立工具集。

主管-下属的关键设计点，请你在动手前先想清楚，否则很容易设计出"假多 Agent"（名义上多个，实际还是一团浆糊）：

- **职责边界要清晰**：每个下属只干一类事，system prompt 写死角色，避免角色冲突（对应第一节的坑 ②）。比如写手 Agent 的 prompt 开头就是"你只负责把给定资料改写成营销文案，不要做调研"。
- **汇总策略**：主管拿到各下属产出后，怎么拼？可以简单拼接，也可以再调一个"汇总 Agent"做二次加工，甚至让汇总 Agent 发现缺口后回派任务（这就接近反思机制了）。
- **失败重试**：某个下属失败，主管可以换一个下属重派，或把错误 Observation 回喂让它重试（呼应 8-1 的坑 2 对策）。

## 三、模式二：流水线（Pipeline）

结构像工厂流水线：**上一个 Agent 的输出，是下一个 Agent 的输入**，顺序固定、首尾相接。没有人"统筹全局"，大家只是接力。

```
采集 Agent ──▶ 清洗 Agent ──▶ 分析 Agent ──▶ 撰写 Agent ──▶ 排版 Agent
   输出          输出           输出            输出           最终报告
```

**适合**：步骤强有序、前一步必为后一步铺垫的场景。比如"抓网页 → 抽正文 → 摘要 → 翻译 → 排版"，环环相扣，顺序不能乱。流水线的好处是**每一步上下文极干净**（只看到上一步给它的输入），没有污染，质量稳定；坏处是**不灵活**，一旦某步要回头改，整条重跑，且难以并行。

**口诀**：要"分头干活再汇总"用主管-下属；要"一环扣一环"用流水线。现实中二者常混合：先用主管-下属并行调研，再把调研结果送进一条撰写流水线。我见过最优雅的设计，是一个"主管"先 fan-out 派三个研究员，再把他们的报告喂给一条"分析→撰写→排版"流水线——两种模式各取所长。

## 三·补充：模式三——辩论 / 投票（多数表决）

前两种模式解决的是"怎么分工"，还有一种场景它们都管不了：**同一个产物好不好，标准本身是主观的**。比如"这段文案能不能发""这个方案合不合规"，你没法写成一个函数调用的结果。这时最有效的办法是——**请多个不同立场的评审 Agent 各看一遍，然后投票**。这不是学术界的花架子，而是当下所有高质量生成系统都在用的手段（对应概念叫 self-consistency / LLM-as-judge / multi-agent debate）。

```python
def critic_strict(text):  return ("reject", "出现了未经来源标注的数字，事实性存疑")
def critic_lenient(text): return ("accept", "数据虽有风险但整体可读，标注来源即可")
def critic_market(text):  return ("reject", "营销口吻过重，与'研究报告'定位不符")

def jury(text, critics):
    votes = []
    for c in critics:
        decision, reason = c(text)
        votes.append((decision, reason))
        print(f"  {c.__name__:<16} → {decision:<6} {reason}")
    accepts = sum(1 for d, _ in votes if d == "accept")
    rejects = len(votes) - accepts
    print(f"  计票：通过 {accepts} 票 / 反对 {rejects} 票")
    if accepts == rejects:                      # 平票交给裁判加投一票
        print("  平票 → 交给裁判 Agent 加投一票：以'事实优先'为由判决 reject")
        return "reject"
    return "accept" if accepts > rejects else "reject"

print("评审一段草稿：")
print("最终裁决:", jury("咱们这个赛道，三家巨头吃掉了六成蛋糕。",
                    [critic_strict, critic_lenient, critic_market]))
```

**运行结果**：

```
评审一段草稿：
  critic_strict    → reject 出现了未经来源标注的数字，事实性存疑
  critic_lenient   → accept 数据虽有风险但整体可读，标注来源即可
  critic_market    → reject 营销口吻过重，与'研究报告'定位不符
  计票：通过 1 票 / 反对 2 票
最终裁决: reject
```

请把注意力放在**这三位评审的身份设定**上，这才是本模式的精髓：**他们看的不是同一件事**。事实委员只盯是否有来源，市场委员只盯调性是否符合定位，宽松委员负责兜底防止过度否决。**如果三个评审用同一个 prompt，那就不是投票，而是三次复读机**——花三倍的钱买一个幻觉 comfort。设计多评审时务必遵守一条原则：**每个 Agent 必须有且只有一个明确的评价维度**，维度重叠就合并，维度缺失就补齐。

另外注意三个评审是**互不依赖的**，所以这里天然适合套用 4.4 的线程池：三个评审并行跑完的时间同样约等于最慢那个，比串行遍历快得多。这也是为什么"哪些能并行"要在一开始设计时就标出来：并行不是优化手段，而是架构选择。

三种模式放在一张表里对比，方便你选型时直接查：

| 模式 | 结构 | 谁决定下一步 | 能否并行 | 适合 | 典型代价 |
|---|---|---|---|---|---|
| 主管-下属 | 星型（1 主 + N 从） | 主管 | ✅ 下属之间可并行 | 异构专长、需汇总 | 主管可能成为瓶颈 |
| 流水线 | 链式（首尾相接） | 流程本身 | ❌ 强有序 | 步骤固定、要质量稳定 | 一步返工全线重跑 |
| 辩论 / 投票 | 扇入（N 评审 → 1 裁决） | 投票规则 | ✅ 评审之间可并行 | 主观质量判定 | 成本 × N，需处理平票 |

## 四、手写一个主管调度器（离线版，看清逻辑）

下面用一个**不调 API** 的示例，演示主管如何按任务类型派活。每个"专职 Agent"这里用函数模拟，换成真 LLM 只改函数体（里面改成调用一个 8-2 学的 `AgentExecutor` 即可）。重点是看清"调度"这件事本身有多简单——难的从来不是调度，而是"怎么拆、怎么汇总"。

```python
# 三个专职 Agent：各自只干一件事，输入输出清晰
def researcher(topic):
    return f"[调研] 关于《{topic}》的公开资料：市场规模约 120 亿，头部三家占 60%。"

def writer(draft):
    return f"[文案] 基于「{draft}」改写为通俗稿：咱们这个赛道，三家巨头吃掉了六成蛋糕。"

def reviewer(text):
    suspicious = ["120 亿", "60%"]
    bad = [s for s in suspicious if s in text]
    return ("[校验] 通过" if not bad else
            f"[校验] 退回：以下数字需标注来源 {bad}")

# 主管：根据任务类型，决定派给谁、按什么顺序
WORKERS = {"调研": researcher, "撰写": writer, "校验": reviewer}

def supervisor(task_type, payload):
    if task_type not in WORKERS:
        return f"错误：没有「{task_type}」这个专职岗"
    return WORKERS[task_type](payload)

# 模拟一次完整协作：调研 → 撰写 → 校验（其实是流水线 + 主管调度）
steps = [("调研", "智能音箱"), ("撰写", None), ("校验", None)]
result = None
for typ, payload in steps:
    payload = payload or result          # 上一步输出喂给下一步
    result = supervisor(typ, payload)
    print(result, "\n")

# 单独派一个调研任务
print(supervisor("调研", "无人机"))
print(supervisor("财务", "报销"))        # 没有的岗 → 明确报错
```

**运行结果**（真实输出）：

```
[调研] 关于《智能音箱》的公开资料：市场规模约 120 亿，头部三家占 60%。

[文案] 基于「[调研] 关于《智能音箱》的公开资料：市场规模约 120 亿，头部三家占 60%。」改写为通俗稿：咱们这个赛道，三家巨头吃掉了六成蛋糕。

[校验] 退回：以下数字需标注来源 ['120 亿', '60%']

[调研] 关于《无人机》的公开资料：市场规模约 120 亿，头部三家占 60%。
错误：没有「财务」这个专职岗
```

注意最后一行：主管对"不存在的岗"**明确报错**，而不是硬着头皮让某个 Agent 瞎干——这是多 Agent 系统健壮性的关键：**职责边界要清晰，不能含糊**。真实系统里，这个"报错"还可以升级为"让主管重新规划"（比如"财务岗没有，要不要改成外包调用"），而不是直接抛给用户。

为了让你看到"主管-下属"和"流水线"的统一性，我们再加一个**真正的主管-下属 fan-out** 示例：主管并行派三个研究员，再汇总。

```python
# 主管-下属：并行派活再汇总（演示思想，真实用 asyncio 并发）
def supervisor_fanout(topics):
    reports = []
    for t in topics:
        reports.append(researcher(t))     # 真实场景可并发执行
    summary = "[汇总] " + " | ".join(r.replace("[调研] ", "") for r in reports)
    return summary

print(supervisor_fanout(["智能音箱", "无人机", "扫地机"]))
# 输出: [汇总] 关于《智能音箱》的公开资料：... | 关于《无人机》的... | 关于《扫地机》的...
```

这个 `supervisor_fanout` 就是"分头干活再汇总"的骨架——把串行 for 换成并发，就是生产里的并行调研，时间从"三者之和"变成"最慢一个"。这一行改造，就是多 Agent 相比单 Agent 最直观的提速证据。

### 4.3 给协作加上"契约"：用 schema 干掉互相甩锅

第四节里三个 Agent 之间传的是**自然语言字符串**——调研结果的整句话直接塞给写手，写手的输出整句塞给校验员。demo 里看着挺顺，但它埋了一颗定时炸弹：**当下游拿到的东西不符合预期时，没有任何机制能自动发现**。比如研究员这次少写了一个字段，写手拿到的文本里没有 URL，于是它编了一个——而没有任何环节报错，错误一路传到最后才发现"引用全是假的"。

这正是第七节要讲的"互相甩锅"的根治办法：**给每对上下游之间订一份"数据契约"（schema），交付时先验再收，不合规就打回重做**。看代码：

```python
RESEARCH_CONTRACT = {"topic": str, "market_size": str, "top3": list, "sources": int}
WRITE_CONTRACT    = {"title": str, "body": str, "word_count": int}

def validate(contract, data):
    """校验下属交付物是否符合契约：缺字段、类型错都算不合规"""
    missing = [k for k in contract if k not in data]
    badtype = [f"{k} 应为 {t.__name__} 但拿到 {type(data[k]).__name__}"
               for k, t in contract.items() if k in data and not isinstance(data[k], t)]
    return (not missing and not badtype), missing + badtype

def researcher(topic, broken=False):
    report = {"topic": topic, "market_size": "120 亿", "top3": ["甲", "乙", "丙"], "sources": 3}
    if broken:
        report.pop("sources")          # 模拟某个 worker 产出不完整
    return report

def writer(report):
    return {"title": f"{report['topic']}赛道速览",
            "body": f"市场规模约 {report['market_size']}，头部三家：{'、'.join(report['top3'])}。",
            "word_count": 32}

def supervisor_once(topic, max_retry=2):
    for attempt in range(1, max_retry + 1):
        raw = researcher(topic, broken=(attempt == 1))        # 第一次故意产出残缺数据
        ok, problems = validate(RESEARCH_CONTRACT, raw)
        print(f"第 {attempt} 次交付：合规={ok}，问题={problems or '无'}")
        if ok:
            return writer(raw)
        print("  → 主管把问题回喂给研究员，要求补齐字段后重试")
    return {"error": "研究员连续两次交付不合规，任务失败"}

print("产出：", supervisor_once("智能音箱"))
```

**运行结果**：

```
第 1 次交付：合规=False，问题=['sources']
  → 主管把问题回喂给研究员，要求补齐字段后重试
第 2 次交付：合规=True，问题=无
产出： {'title': '智能音箱赛道速览', 'body': '市场规模约 120 亿，头部三家：甲、乙、丙。', 'word_count': 32}
```

这段代码的价值在于把"甩锅"变成了"可判定的错"。请注意几个设计细节：

- **`validate` 返回具体问题列表**，而不是简单 True/False。因为这份 `problems` 就是回喂给上游的"修改意见"——它既是报错，也是提示词的一部分。**好的错误信息本身就应该是一条可执行的纠错指令**，这和 8-1 坑 2 里"把错误 Observation 回喂"是同一个思想。
- **重试要有上限**（这里 `max_retry=2`）。智能体世界里的重试和微服务一样，无上限重试等于把一个小问题放大成一张大账单。
- **校验失败时也可以不重试，而是降级**：比如 `sources` 缺失时，写手可以跳过引用段落照常交稿。什么时候重试、什么时候降级，取决于业务容忍度，这是你在设计期就要拍板的事，不要留到运行时随机决定。

顺带一提，`validate` 这层其实也可以用 pydantic 的 `BaseModel` 来做（类型即文档），生产项目里更推荐——但**先用原生 dict 写一遍，你才真的明白它在校验什么**。这又是本专栏"先手写，后框架"的老规矩。

### 4.4 并行到底能省多少：把时间账算给你看

"多 Agent 可以并行"这句话在上一节被一笔带过，这里补上硬数据。LLM 调用本质上是**IO 密集型**任务（发出请求后大部分时间在等网络），所以用 Python 的线程池就足够榨干并发价值，不需要上多进程。实测：

```python
import time
from concurrent.futures import ThreadPoolExecutor

def fake_worker(name, seconds):
    time.sleep(seconds)              # 模拟一次 LLM 调用的网络等待
    return f"{name}完成"

TOPICS = [("查竞品 A", 0.4), ("查竞品 B", 0.6), ("查竞品 C", 0.3)]

t0 = time.time()
results = [fake_worker(n, s) for n, s in TOPICS]              # 串行
serial = time.time() - t0

t0 = time.time()
with ThreadPoolExecutor(max_workers=3) as pool:               # 并行
    futures = [pool.submit(fake_worker, n, s) for n, s in TOPICS]
    results_p = [f.result() for f in futures]
parallel = time.time() - t0

print(f"串行：{[r for r in results]}  耗时 {serial:.2f}s")
print(f"并行：{[r for r in results_p]}  耗时 {parallel:.2f}s  （约等于最慢的那个：0.6s）")
print(f"提速 {serial / parallel:.1f} 倍；LLM 调用是 IO 密集型，所以线程并发就够用")
```

**运行结果**（耗时数值随机器略有浮动，规律不变）：

```
串行：['查竞品 A完成', '查竞品 B完成', '查竞品 C完成']  耗时 1.32s
并行：['查竞品 A完成', '查竞品 B完成', '查竞品 C完成']  耗时 0.61s  （约等于最慢的那个：0.6s）
提速 2.2 倍；LLM 调用是 IO 密集型，所以线程并发就够用
```

结论非常清晰：**并行后的总耗时 ≈ 最慢的那个子任务**，而串行是三者之和。子任务越多、越独立，收益越大——调研 10 个竞品时，这就是"1 小时 vs 6 分钟"的差别。但请同时记住它的代价：**并行的钱并没有省，一次要发出 N 个请求，token 一分不少**。省的是时间，不是成本。很多新手误以为"并行 = 省钱"，上线后账单翻倍就是这个误会造成的。

## 五、工程框架：LangGraph 与 AutoGen

手写调度适合理解原理，生产里常用两个框架，它们把"调度、状态、重试、回退"都封装好了：

| 框架 | 风格 | 适合 | 对应本文模式 |
|---|---|---|---|
| **LangGraph**（LangChain 出品） | 把多 Agent 画成**有状态图**（节点=Agent，边=流转） | 流程复杂、要可控、要回退 | 流水线 / 主管-下属皆可 |
| **AutoGen**（微软出品） | Agent 之间**自由对话**互相委派 | 开放协作、自动协商 | 弱化版主管-下属（无显式主管） |

- **LangGraph**：你用代码定义一张"图"，每个节点是一个 Agent 或一个处理步骤，边决定"下一步去哪"。好处是**完全可控**——你可以设条件分支（校验失败就回到撰写节点重来）、可回退、可持久化状态。它本质是把"流水线"和"主管-下属"都建模成图，灵活性最高，也最贴合生产对"可观测、可干预"的要求。
- **AutoGen**：你创建几个 Agent，它们自己开群聊、互相委派任务，没有硬编码的主管。适合"我也不知道该谁干，让它们商量"的开放场景，但可控性弱、容易跑偏、成本高。它更像一个"放养"的团队。

它们的本质，**依然是我们上面对应的两种模式**：图的节点是有向的（流水线），自由对话是主管-下属的弱化版（没有显式主管，大家自己商量）。学完 8-1 手写版和本节调度器，再看这些框架你只会觉得"换皮不换骨"——它们解决的还是"谁派活、怎么传、错了怎么办"这三个老问题。

### 5.1 从头设计一个多 Agent 系统：以"周报机器人"为例

概念都讲完了，我们完整走一遍设计流程。需求：**每周一早上，从三个数据源（Git 提交、销售数据库、客服工单）汇总出一份给 CEO 看的周报，并要求:数据必须可溯源、语气正式、不超过一页。**

**第一步：先问"单 Agent 能不能干？"**（第六节的原则，务必第一步就问）。单 Agent 要同时读三份数据、做三种分析、写正式稿、还得控制篇幅——上下文里很快会混进大量原始记录，"一页纸"这种约束会被长上下文稀释掉。而且查 Git 和查 SQL 是两种完全不同的技能（两套工具、两套术语）。**判定：角色异构明确，值得拆。**

**第二步：选模式。** 三个数据源互不依赖 → 用**主管-下属 fan-out 并行采集**；采集完到成稿是强有序的"分析 → 撰写 → 校对"→ 用**流水线**。于是得到混合型结构：

```
                        ┌──────────────┐
                        │   主管 Agent  │  ← 规则型：排班 + 汇总 + 失败重试
                        └──────┬───────┘
                  fan-out 三条并行
        ┌─────────────────┼─────────────────┐
        ▼                 ▼                 ▼
   Git 采集 Agent    销售采集 Agent    工单采集 Agent
   (工具: git log)   (工具: SQL)      (工具: 工单 API)
        └─────────────────┼─────────────────┘
                          ▼  (结构化 JSON，带 source 字段)
                    分析 Agent（算环比、找异常）
                          ▼
                    撰写 Agent（正式商务语体，≤1 页）
                          ▼
                    校对 Agent（校验每个数字都有 source）
                          ▼
                        CEO 周报
```

**第三步：定契约。** 三个采集 Agent 必须输出同构的 JSON：`{"metric": str, "value": float, "delta": float, "source": str}`，字段缺失即打回（4.3 的 `validate`）。有了 `source` 字段，最后的校对 Agent 才能逐条核对出处——**"可溯源"这个需求，是在契约设计这一步就被满足的，而不是靠最后祈祷**。

**第四步：定容错。** 销售数据库偶尔超时，主管重试一次；仍失败则该板块标注"数据暂缺"，周报照常发出。**永远允许用户拿到一份残缺但准时的报告，也不要给一份更晚的全量报告**——这是周报场景的业务权衡，换成合规报表则可能相反。

走完这四步，你会发现真正的难点从来不是"写个 for 循环调三次 LLM"，而是**第一步的必要性判断、第二步的结构选择、第三步的契约设计**。代码只是最后的翻译工作。这也解释了为什么有些人"用 AutoGen 搭了半天却效果很差"——他们跳过了一到三步，直接跳到了调 API。

## 六、最重要的提醒：别过度设计

这一节是全篇最想让你记住的。多 Agent 听起来很酷，但**大部分业务用单 Agent + 好 Prompt + 几个工具就够**。我见过太多项目，任务明明一句 Prompt 能搞定，非要拆五个 Agent，结果延迟翻倍、成本翻三倍、bug 翻倍，最后还跑不赢单 Agent。只有在下面情况才值得上多 Agent，请你逐条对照：

1. 任务明显能拆成**不同角色/不同专长**（研究员 vs 写手），且单 Agent 角色冲突明显；
2. 单 Agent 上下文被多类任务**严重污染**，质量下降（对应第一节坑 ①）；
3. 需要**并行**干几件独立的事，省时间（如同时调研三个竞品）。

否则——多 Agent 只会增加延迟、成本和调试难度。先单后多，是基本原则。一个实用的决策流程，建议你照着走：

```
任务复杂吗？
  ├─ 不复杂 → 单 Agent + 好 Prompt（别上多 Agent）
  └─ 复杂 → 单 Agent 试过质量不行？
              ├─ 否 → 继续用单 Agent
              └─ 是 → 看是"角色冲突"还是"要并行"
                          ├─ 角色冲突 → 主管-下属
                          └─ 强有序   → 流水线
```

我个人的经验法则：**能用一句清晰 Prompt 解决的，绝不拆 Agent。** 拆分的成本（协调、调试、成本）往往被初学者低估，而收益（隔离、并行）只在任务真复杂时才显现。

## 七、多 Agent 的常见坑（专属坑，单 Agent 没有）

除了过度设计，多 Agent 还有几个专属坑，它们来自"多个智能体之间的协作"本身：

- **通信开销爆炸**：Agent 之间互发长消息，token 累加，成本指数级上升（n 个 Agent 互相聊一轮，消息量是 n² 级别）。对策：限制每条消息长度，必要时让主管做摘要中转，而非全员广播。
- **责任不清导致互相甩锅**：A 说"B 给的数据错了"，B 说"是 A 的要求含糊"。对策：明确每个节点的输入输出契约（schema），谁产出谁负责，最好用结构化数据而非自然语言传参。
- **死循环协商**：AutoGen 风格下，两个 Agent 可能无限来回"你说得不对""明明是你错了"。对策：设最大轮数，超时强制主管裁决。
- **状态不一致**：并行 Agent 改了同一份共享状态（比如都往一个文档写）。对策：尽量让每个 Agent 无状态、只通过主管传参，共享状态集中由主管管理。

## 八、多 Agent 设计的进阶思路（问答与实战经验）

基础模式讲完，但真要做生产级多 Agent，还有一些"经验型"知识值得提前知道，它们能帮你避开大量返工。

**问一：主管一定要是大模型吗？能不能用规则？**
答：不一定，而且**很多场景规则主管更好**。我们的代码示例里 `supervisor` 就是纯规则（按 task_type 派活），它快、可控、零成本。只有当"怎么拆任务、派给谁"本身需要智能判断（比如拿到一个模糊需求要自己规划子任务）时，才值得让主管也是个 LLM Agent。一个常见且稳健的架构是：外层用规则/轻量模型做路由，内层每个专职 worker 才是重模型。这样兼顾成本与智能。

**问二：多个 Agent 之间传数据，用自然语言还是结构化？**
答：尽量**结构化**（JSON / 约定字段），少用自然语言自由传。自然语言传参是多 Agent 互相甩锅（第七节坑二）的根源——"你说得含糊""是你理解错"。给每个节点定义清晰的输入输出 schema（比如研究员必须输出 `{topic, market_size, top3}`），下游严格按 schema 取用，出问题立刻能定位是哪个节点产出不对。这是把"不可控的智能体协作"变成"可控的流水线"的关键一招。

**问三：Agent 数量是不是越多越好？**
答：绝对不是，甚至应该"越少越好"。每多一个 Agent，就多一份协调成本、延迟和出错面。经验法则：能两个 Agent 解决的，绝不用三个。Google 等团队的研究也表明，过多的 Agent 反而因通信噪声导致整体质量下降。如果你发现需要七个八个 Agent，大概率是任务没拆好，或者某些 Agent 其实可以合并成一个带多工具的单体。回到第六节的"先单后多"原则，Agent 数量是最后才考虑的调节旋钮，不是越多越先进。

**问四：怎么判断我的多 Agent 系统"对了"？**
答：看三个信号——（1）单 Agent 解决时质量明显不行（证明拆分有必要）；（2）每个 Agent 的上下文干净、角色不串（证明隔离有效）；（3）一个环节失败能局部重试而非全链崩溃（证明容错到位）。如果这三条不满足，你多半是在用多 Agent 的复杂度，换取单 Agent 就能给的效果，趁早合并回去。

补一张"多 Agent 设计自检清单"收尾：

| 检查项 | 通过标准 |
|---|---|
| 是否真需要多 Agent | 单 Agent 试过质量不行才上 |
| 职责是否清晰 | 每个 Agent 一句话说清只干啥 |
| 传参是否结构化 | 有 schema，非自然语言自由传 |
| 是否可控 | 出错能局部重试，不整体崩 |
| 数量是否克制 | 能少则少，无冗余岗 |

## 九、本篇小结

1. **单 Agent 三天花板**：上下文污染、角色冲突、容错差——复杂任务需要分工。
2. **两种模式**：主管-下属（分头干活再汇总，适合异构专长）、流水线（一环扣一环，适合强有序步骤）；二者常混合。
3. 手写的主管调度器已跑通：调研→撰写→校验，**职责边界清晰，遇到没定义的岗就明确报错**而非硬凑；并演示了 fan-out 并行汇总骨架。
4. 生产框架：LangGraph（有状态图）对应流水线/主管-下属，AutoGen（自由对话）对应弱化版主管-下属。
5. **别过度设计**：先单 Agent + 好 Prompt + 工具；只有角色异构、上下文污染、需并行时才上多 Agent。
6. **协作必须有契约**：每对上下游之间定义 JSON schema，交付时先验后收，不合规就回喂重试（上限 2 次）或降级——这是"互相甩锅"的唯一根治办法。
7. **第三种模式是辩论/投票**：给主观质量的判定用多个不同维度的评审 Agent 并行投票，注意每个评审必须只有一个评价维度，否则就是三份复读机。
8. **并行省的是时间不是钱**：并行后总耗时≈最慢的子任务，但 token 一分不少；设计时要在图上先把"哪些节点能并行"标出来。

最后留一句全阶段的总结心法：**8-1 给了 Agent 一颗会循环的大脑，8-2 给它标准化的手脚，8-3 给它长短期的记忆，8-4 给它一个团队。到今天为止，你已经具备了从零搭建一个完整智能体应用的全部零件。** 剩下的问题不再是"能不能做"，而是"值不值得这么做"——而判断值不值，靠的正是本篇反复强调的那句话：多 Agent 是止痛药，不是维生素。

## 十、实战练习（可验证小任务）

1. **加岗练习**：在 `WORKERS` 里新增一个 `"翻译"` 岗（函数把输入翻译成中文式口语），跑一次"调研→翻译"流水线，确认输出含 `[翻译]`。验证点：调度器可扩展。
2. **报错验证**：调用 `supervisor("不存在的岗", "x")`，确认返回"错误：没有「...」这个专职岗"而非崩溃。验证点：职责边界防护有效。
3. **并行改造**：把 `supervisor_fanout` 的 for 循环改成"模拟并发"（比如打印开始/结束时间差），理解并行的价值。验证点：理解为何能省时间。
4. **模式识别**：给你一个任务"收集 10 条新闻 → 按情感分类 → 生成日报"，判断该用主管-下属还是流水线，并画出 ASCII 结构图。验证点：模式选择能力。
5. **过度设计反思**：找一个你手头的真实小需求，先尝试用单 Agent 一句话 Prompt 解决，记录是否真需要多 Agent。验证点：建立"先单后多"的直觉。
6. **契约生效验证**：在 4.3 的 `supervisor_once` 里把 `max_retry` 改成 1（即研究员第一次残缺就放弃），确认返回的是 `{"error": "研究员连续两次交付不合规，任务失败"}`。验证点：理解重试上限的必要性。
7. **并行实测**：把 4.4 里 `TOPICS` 扩到 5 个子任务，重跑并对比 `serial / parallel` 的倍数变化，同时算一下 token 有没有因为并行而减少。验证点：亲手戳破"并行省钱"的误解。
8. **设计练习**：给一个你熟悉的公司流程（如"客户投诉处理""每周选题会"），按 5.1 的四步法画出它的多 Agent 架构图，并给每个节点写出输入/输出的 JSON schema。验证点：把本篇的方法论迁移到自己的业务。
