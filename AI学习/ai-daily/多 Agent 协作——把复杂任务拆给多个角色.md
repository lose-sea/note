# 多 Agent 协作——把复杂任务拆给多个角色

**承上**：8-1~8-3 我们给单个 Agent 装上了"循环（脑）、工具（手）、记忆（脑存储）"三件套。但真实复杂任务——比如"调研三个竞品、各写一段分析、汇成一份报告、再生成 PPT 大纲"——让**一个** Agent 又搜又写又汇总又排版，它容易顾此失彼、上下文被多种任务污染、还容易中途跑偏。

**本篇**：讲清"为什么一个大 Agent 不够"以及多 Agent 协作的两种主流模式——**主管-下属（Supervisor-Worker）** 与 **流水线（Pipeline）**。我用手写代码演示一个简单的"主管调度三个专职 Agent"的例子，并聊清楚"什么时候该拆、什么时候别拆"。

**启下**：阶段 8（Agent）到此讲完——单 Agent 循环、框架、记忆、协作都齐了。但你可能会问：这些 Agent 用的"基础模型"能不能变得更懂我的业务？比如让客服 Agent 真正熟读我家产品手册？这就进入 **阶段 9：微调与训练**——下一篇 **9-1《指令微调 SFT——数据与训练流程》** 讲怎么用自有数据"教"模型，而不是只会靠 Prompt 临时告诉它。

**学完这一节，你能动手做**：

1. 说清单 Agent 的瓶颈，以及多 Agent 在哪类任务上明显更优
2. 区分"主管-下属"与"流水线"两种协作模式的适用场景
3. 手写一个主管 Agent，按任务类型把活派给不同的专职 Agent
4. 判断"我的任务到底要不要上多 Agent"（避免过度设计）

## 一、为什么一个大 Agent 不够用？

把任务全压给一个 Agent，会撞上三个天花板：

```
① 上下文污染：搜来的资料、写的草稿、排版的指令全挤在一个上下文里，
   模型分不清"这是要给客户的"和"这是中间草稿"。
② 角色冲突：让它同时当"研究员"和"文案"，风格会拧巴——
   研究报告要严谨，营销文案要煽情，同一张嘴说不出两种调性。
③ 容错差：一步跑偏，整条链子全废，没法"这个环节换人重来"。
```

解决思路很朴素——**像公司一样分工**：一个主管负责拆解和汇总，几个专职员工各管一摊。这就是多 Agent 系统。

## 二、模式一：主管-下属（Supervisor-Worker）

结构像一个小团队：**主管** 听老板（用户）的需求，把任务拆成子任务，派给对应的**专职 Agent**，最后汇总各自产出。

```
            ┌─────────────┐
   用户 ───▶ │   主管 Agent │ ◀── 汇总
            └──────┬──────┘
       ┌──────────┼──────────┐
       ▼          ▼          ▼
  研究员 Agent  写手 Agent  校验 Agent
  (搜资料)     (写文案)     (查事实)
```

**适合**：任务能拆成几个相对独立的子任务、且需要不同"专长/角色"的场景。比如"竞品分析"——研究员搜数据、写手写稿、校验员核对数字。

## 三、模式二：流水线（Pipeline）

结构像工厂流水线：**上一个 Agent 的输出，是下一个 Agent 的输入**，顺序固定、首尾相接。

```
采集 Agent ──▶ 清洗 Agent ──▶ 分析 Agent ──▶ 撰写 Agent ──▶ 排版 Agent
   输出          输出           输出            输出           最终报告
```

**适合**：步骤强有序、前一步必为后一步铺垫的场景。比如"抓网页 → 抽正文 → 摘要 → 翻译 → 排版"，环环相扣。

**口诀**：要"分头干活再汇总"用主管-下属；要"一环扣一环"用流水线。

## 四、手写一个主管调度器（离线版，看清逻辑）

下面用一个**不调 API** 的示例，演示主管如何按任务类型派活。每个"专职 Agent"这里用函数模拟，换成真 LLM 只改函数体。

```python
# 三个专职 Agent：各自只干一件事，输入输出清晰
def researcher(topic):
    return f"[调研] 关于《{topic}》的公开资料：市场规模约 120 亿，头部三家占 60%。"

def writer(draft):
    return f"[文案] 基于「{draft}」改写为通俗稿：咱们这个赛道，三家巨头吃掉了六成蛋糕。"

def reviewer(text):
    suspicious = ["120 亿", "60%"]
    bad = [s for s in suspicious if s in text]
    return ("[校验] 通过" if not bad else
            f"[校验] 退回：以下数字需标注来源 {bad}")

# 主管：根据任务类型，决定派给谁、按什么顺序
WORKERS = {"调研": researcher, "撰写": writer, "校验": reviewer}

def supervisor(task_type, payload):
    if task_type not in WORKERS:
        return f"错误：没有「{task_type}」这个专职岗"
    return WORKERS[task_type](payload)

# 模拟一次完整协作：调研 → 撰写 → 校验（其实是流水线 + 主管调度）
steps = [("调研", "智能音箱"), ("撰写", None), ("校验", None)]
result = None
for typ, payload in steps:
    payload = payload or result          # 上一步输出喂给下一步
    result = supervisor(typ, payload)
    print(result, "\n")

# 单独派一个调研任务
print(supervisor("调研", "无人机"))
print(supervisor("财务", "报销"))        # 没有的岗 → 明确报错
```

**运行结果**（真实输出）：

```
[调研] 关于《智能音箱》的公开资料：市场规模约 120 亿，头部三家占 60%。

[文案] 基于「[调研] 关于《智能音箱》的公开资料：市场规模约 120 亿，头部三家占 60%。」改写为通俗稿：咱们这个赛道，三家巨头吃掉了六成蛋糕。

[校验] 退回：以下数字需标注来源 ['120 亿', '60%']

[调研] 关于《无人机》的公开资料：市场规模约 120 亿，头部三家占 60%。
错误：没有「财务」这个专职岗
```

注意最后一行：主管对"不存在的岗"**明确报错**，而不是硬着头皮让某个 Agent 瞎干——这是多 Agent 系统健壮性的关键：**职责边界要清晰，不能含糊**。

## 五、工程框架：LangGraph 与 AutoGen

手写调度适合理解原理，生产里常用两个框架：

| 框架 | 风格 | 适合 |
|---|---|---|
| **LangGraph**（LangChain 出品） | 把多 Agent 画成**有状态图**（节点=Agent，边=流转） | 流程复杂、要可控、要回退 |
| **AutoGen**（微软出品） | Agent 之间**自由对话**互相委派 | 开放协作、自动协商 |

它们的本质，**依然是我们上面对应的两种模式**：图的节点是有向的（流水线），自由对话是主管-下属的弱化版（没有显式主管，大家自己商量）。

## 六、最重要的提醒：别过度设计

多 Agent 听起来很酷，但**大部分业务用单 Agent + 好 Prompt + 几个工具就够**。只有在下面情况才值得上多 Agent：

1. 任务明显能拆成**不同角色/不同专长**（研究员 vs 写手）；
2. 单 Agent 上下文被多类任务**严重污染**，质量下降；
3. 需要**并行**干几件独立的事，省时间。

否则——多 Agent 只会增加延迟、成本和调试难度。先单后多，是基本原则。

## 七、本篇小结

1. **单 Agent 三天花板**：上下文污染、角色冲突、容错差——复杂任务需要分工。
2. **两种模式**：主管-下属（分头干活再汇总，适合异构专长）、流水线（一环扣一环，适合强有序步骤）。
3. 手写的主管调度器已跑通：调研→撰写→校验，**职责边界清晰，遇到没定义的岗就明确报错**而非硬凑。
4. 生产框架：LangGraph（有状态图）对应流水线，AutoGen（自由对话）对应弱化版主管-下属。
5. **别过度设计**：先单 Agent + 好 Prompt + 工具；只有角色异构、上下文污染、需并行时才上多 Agent。
